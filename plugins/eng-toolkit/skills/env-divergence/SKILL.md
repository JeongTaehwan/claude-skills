# 환경별 동작 차이 진단

**대개 코드 버그가 아니라 값이 갈라진 자리다.** 그래서 로직을 읽으면 아무것도 안 나온다.

## 출력 계약 — 먼저 읽는다

**내보내는 것은 원인 한 문장 + 근거 한 줄(파일:라인 또는 실행한 명령) + 최소 수정이다.**

절 번호, 훑은 순서, 배제한 가설, 스크립트 전체 출력은 내보내지 않는다. 이 절차는 입력이지 출력이 아니다. 남은 우회 지점이 있으면 맨 끝에 목록으로 한 번만 언급한다.

## 어디서 시작하나 — 사용자가 이미 좁혔으면 거기로 직행

| 사용자가 이미 말한 것 | 바로 갈 곳 |
|---|---|
| 토글·localStorage·"모드 바꾸니까" | 4절 |
| 배포했는데 값이 안 바뀜 | 3절 ① |
| 특정 변수 이름을 짚음 | `env-diff.py --var <이름>` 만 |
| 어느 화면인지만 앎 | 1절부터 |

**0~1절은 축이 안 잡혔을 때만 쓴다.** 사용자가 원인을 지목했는데 처음부터 되묻는 게 이 스킬이 지워지는 가장 빠른 길이다.

## 0. 게이트

**맞는 경우**: 에러 없이 조용히, 같은 코드가 A에서는 되고 B에서는 안 된다. A/B는 환경(로컬·STAGE·운영), 빌드, 사용자(로그인·권한·테넌트), 시점(배포 직후·캐시 만료 후).

**아닌 경우**:
- **에러 메시지·스택트레이스·빌드 로그가 있다** → 그 로그부터 읽는다. 빌드 실패는 "로컬은 되고 배포만 깨짐" 형태를 완벽히 만족하지만 원인은 로그 한 줄에 있다
- **브라우저·OS·기기 차이만 있다** → JS 엔진·CSS 지원·웹뷰 차이다. 여기 답이 없다
- **어디서나 똑같이 틀린다** → 그냥 로직 버그다

## 1. 두 가지를 먼저 가른다

코드를 읽기 전에 이 둘이면 절차의 절반이 잘린다.

**(a) 항상 그런가, 가끔 그런가.** 새로고침마다 바뀌면 설정 분기가 아니다 — 롤링 배포가 절반만 돌았거나, 공유 캐시이거나, 인스턴스가 여러 대다. 같은 요청을 10번 던져 응답이 갈리는지 본다.

**(b) 응답이 다른가, 화면만 다른가.** 커머스에서 "STAGE에서 안 보임"의 실제 1순위는 **STAGE DB에 그 레코드가 없거나 노출 플래그가 꺼진 것**이다. 설정을 다섯 층 훑고 나서 발견하면 늦다.

```bash
curl -s "$STAGE_BASE/products?..." | jq '.data|length'
curl -s "$PROD_BASE/products?..."  | jq '.data|length'
```

- 응답이 다르다 → **데이터·권한 문제다.** 2~4절 건너뛴다. 토큰 스코프, 테넌트, 노출 상태를 본다. 200인데 빈 배열이면 권한일 확률이 높다
- 응답이 같은데 화면만 다르다 → 그때 설정·라우팅으로 내려간다

사용자가 브라우저를 열어 둔 상태라면 네트워크 탭에서 요청 호스트를 보는 게 더 빠르다. 다만 그건 사람이 하는 일이라, 요청하기 전에 위 두 가지를 코드·curl로 먼저 시도한다.

## 2. 스크립트 — 지도이지 증거가 아니다

스크립트는 스킬 디렉터리에 있고 대상은 프로젝트다. 경로를 둘 다 명시해야 한다.

```bash
E=~/.claude/skills/env-divergence/scripts/env-diff.py
python3 $E --var NEXT_PUBLIC_API_URL .    # 변수를 알면 이것만
python3 $E .                              # 변수도 모를 때
```

네 가지를 본다 — 같은 변수의 서로 다른 fallback, 참조하는데 미정의, 정의 위치가 갈린 것, 정의됐는데 미참조.

**여기서 나온 fallback 목록은 "이 값들이 존재한다"이지 "이 값이 쓰였다"가 아니다.** 환경변수가 실제로 주입돼 있으면 fallback은 하나도 발동하지 않는다. 진짜 잠재 위험이지만 지금 증상의 원인이 아닐 수 있다. 확인은 배포 산출물에서 한다.

```bash
grep -ro 'https://[a-z.]*api[a-z.]*' .next/static | sort -u
```

**스크립트 결과는 그대로 옮기지 않는다.** 이번 증상과 관련된 줄만 인용하고, 무관한 건 맨 끝에 "별건 N건"으로만 남긴다.

**`.env*`·CI·Dockerfile은 변수 이름과 정의 위치만 인용한다. 값은 옮기지 않는다** — 필요하면 "설정됨/비어 있음/미정의"로만 말한다. CI 파일에 토큰이 평문으로 들어 있는 경우가 흔하다.

## 3. 값이 결정되는 순서대로

위쪽이 아래쪽을 덮어쓴다.

**① 빌드타임 고정** — `NEXT_PUBLIC_*`, `VITE_*`, `REACT_APP_*`는 번들에 문자열로 박힌다. 런타임에 컨테이너 env를 바꿔도 안 바뀐다. "배포했는데 값이 그대로"면 여기다.

**② 서버 런타임** — SSR·API 라우트가 읽는 env. 인스턴스마다 다를 수 있다.

**③ 미들웨어·프록시** — 호스트·경로로 rewrite. 코드는 같은데 도달하는 곳이 다르다. 여기서 갈리면 앱 코드를 아무리 읽어도 안 보인다.

**④ CDN·공유 캐시** — 서버와 브라우저 사이. 환경마다 캐시 정책이 다르거나 한쪽만 CDN 뒤에 있으면 갈린다. 하드 리로드·시크릿창에서 재현되지 않으면 여기다.

**⑤ 클라이언트 런타임** — 브라우저에서 읽는 값. ①과 어긋나기 시작한다.

**⑥ 저장소 토글** (localStorage·쿠키·쿼리) → 4절.

**⑦ 데이터·권한** — 1절 (b)에서 이미 갈랐어야 한다.

### 일곱 층이 전부 같으면

멈추고 셋만 확인한다. 여기서 추측으로 넘어가지 않는다.

| 확인 | 방법 |
|---|---|
| 두 환경의 **코드가 실제로 같은가** | 의존 패키지 버전 대조. 사내 패키지를 로컬에선 심볼릭 링크로, 배포에선 배포판으로 쓰면 다른 코드다 |
| **요청자가 다른가** | 토큰 스코프, 테넌트, 로그인 상태 |
| **시각·로케일이 다른가** | 서버 컨테이너 TZ(대개 UTC)와 브라우저 TZ. 날짜 경계 기능이면 여기다 |

셋 다 같으면 사용자에게 확인할 것 **하나**를 요청하고 멈춘다.

## 4. 토글이 있을 때 — 가설은 둘이다

환경 전환 스위치가 있으면 원인이 둘 중 하나다. 섣불리 한쪽으로 단정하지 않는다.

**(a) 서버 렌더링 경로가 토글을 못 본다.** `localStorage`는 브라우저에만 있다. SSR·`generateMetadata`·`sitemap`·`robots`·Route Handler는 그 값을 볼 수 없다.

**(b) 클라이언트 코드에 환경 강제 규칙이 박혀 있다.** 빌드 URL을 보고 다른 서버로 되돌리는 분기가 있는 경우다. 이건 버그가 아니라 의도된 동작인 경우가 많고, 주석까지 달려 있는 경우도 있다.

```js
const isStageBuild = envUrl.includes('dev.');
const baseURL = storedApiUrl || (isStageBuild && !isCypress ? PROD_URL : envUrl);
```

**두 가설을 가르는 1분짜리 확인**: 문제 화면의 초기 HTML에 데이터가 들어 있는지 본다.

```bash
curl -s "$URL" | grep -c '찾는 데이터 조각'
```

HTML에 없으면 클라이언트가 가져오는 것이므로 **(a)는 그 자리에서 탈락한다.** 그러면 클라이언트 코드에서 base URL이 어떻게 결정되는지 import를 따라간다.

토글 헬퍼가 이미 있다면 **누가 import 하는지 세어 본다.** 몇 개만 쓰고 나머지가 `process.env`를 직접 읽으면 그게 우회 지점이다.

## 5. 고칠 때 — 이번 것과 별건을 나눈다

**이번 수정**: 진범 지점 하나만 고친다. 헬퍼가 있으면 거기를 거치게 하고, 없으면 만들지 말고 그 자리에서 맞는 값을 쓰게 한다. 다른 스킬 필요 없다.

**별건으로 제안만**: 진입점 통합, `requireEnv` 도입, lint 규칙, CI 게이트. 이건 요청 범위 밖이다. 목록으로 알려주고 사용자가 하자고 할 때 `implementation-design`을 탄다.

한 줄 질문에 마흔 줄 diff가 돌아오면 리뷰가 불가능하다. 스크립트가 준 목록 전체를 고치고 싶은 충동이 여기서 생긴다.

CI 게이트를 붙인다면 **베이스라인 방식**이어야 한다 — 현재 검출 건수를 고정하고 그보다 늘 때만 실패시킨다. 기존 저장소에 `problems > 0 → 실패`를 붙이면 첫 파이프라인부터 빨간불이고 하루 만에 무력화된다.

## 6. 하지 말 것

**추측으로 고치지 마라.** "아마 env 때문"이라며 fallback을 바꾸면 원인은 그대로인 채 증상만 옮겨 간다. 어느 값이 실제로 쓰였는지 확인한 근거가 있어야 고친다.

**전제를 검증 없이 쓰지 마라.** "앱은 웹뷰라 클라이언트 렌더링 위주"같은 전제는 확인해야 한다. 앱이 네이티브거나 별도 코드베이스면 진단 전체가 틀어진다.
