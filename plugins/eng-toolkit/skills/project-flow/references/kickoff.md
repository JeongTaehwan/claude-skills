# 3단계 — 기획서 + 프로토타입 (킥오프 묶음)

질문 라운드가 끝나면 **기다리지 않고** 둘을 함께 만들어 한 번에 낸다. 사람의 "정리해줘"나 "프로토타입도 만들어줘"를 기다리지 않는다.

이유는 하나다. 사람은 글로 된 기획서를 읽고 "맞다"고 하지만, 화면을 눌러 보면 그제서야 빠진 화면, 틀린 흐름, 말과 다른 숫자가 보인다. 기획서만 내고 승인을 받으면 그 발견이 구현 도중으로 밀리고, 거기서 고치는 값이 가장 비싸다.

## 누가 무엇을 — 병렬로

| 에이전트 | 하는 일 | 쓰는 곳 |
|---|---|---|
| `planner` | 질문 답을 `requirements.md` 에 반영. 남은 `[미정]` 마다 `[제안]` 답 한 줄 | `docs/requirements.md`, `docs/open-questions.md` |
| `prototyper` | 반영본 기준 프로토타입. `[미정]` 은 `[제안]` 답으로 그리고 **화면에 표시** | `prototype/` |

둘은 같은 파일을 쓰지 않으므로 동시에 돌린다. 프로토타이퍼는 planner 의 반영이 끝나기 전에 시작해도 되지만, **끝내기 전에 반영본을 다시 읽고 어긋난 곳을 맞춘다.**

## 프로토타입이 갖춰야 할 것

1. **핵심 흐름 하나를 끝까지** — 기획서의 "답하는 질문 하나"에 도달하는 경로. 메뉴만 있고 눌러도 아무 일이 없는 화면은 프로토타입이 아니라 와이어프레임이다
2. **상태 화면** — 질문 모드 6번 축의 빈 값 / 로딩 / 실패 / 표본 부족 / 미확정 중 기획서에 문구가 있는 것. 정상 화면만 있으면 사람은 정상 화면만 승인한다
3. **화면마다 요구사항 ID** — 모서리에 작게 `R-CT-01·02`. 사람의 피드백("이 화면 이상해")이 기획서의 어느 줄인지 바로 이어진다
4. **`[미정]` 표시** — 제안 답으로 그리되 눈에 띄게 (`BLOCKER` 빨강, `LATER` 회색 배지 + 마우스를 올리면 질문). 사람이 "이건 내가 정한 게 아닌데"를 화면에서 알아보게 한다
5. **그럴듯한 고정 데이터** — 실제 같은 이름·금액·날짜, 그리고 경계값(0건, 아주 긴 이름, 큰 금액) 한두 개. `test1`, `foo` 는 판단을 흐린다
6. **범위 밖은 만들지 않는다** — `structure.md` 의 범위 밖 기능은 버튼도 두지 않는다

하지 않는 것: 인증·결제·배포(가짜로 둔다), 외부 API 호출, 정식 구현용 구조 설계, 디자인 시스템.

## 형태 — 여는 데 명령이 필요 없게

| 상황 | 형태 |
|---|---|
| 스택이 안 정해졌거나 화면 몇 개 | `prototype/index.html` 한 파일. 빌드 없이 더블클릭으로 열린다. 라이브러리가 필요하면 CDN 고정 버전 |
| 스택이 정해졌고 상호작용이 많다 (드래그, 실시간) | 그 스택의 최소 앱. 실행 명령 한 줄 |
| 기존 프로젝트에 기능 추가 | 기존 앱 안에 숨은 라우트 `/__prototype/<기능>` 또는 Storybook 스토리 — 실제 화면 옆에서 비교되게 |

```text
prototype/
  index.html          # 머리 주석: 프로토타입 — requirements.md 미승인 초안 기준, 정식 구현 아님
  fixtures.js         # 고정 데이터 (경계값 포함)
  README.md           # 여는 법 한 줄 + 아래 화면 표
```

```markdown
<!-- prototype/README.md -->
열기: `open prototype/index.html`

| # | 화면 | 요구사항 | 상태 화면 | [미정] |
|---|---|---|---|---|
| 1 | 상품 목록 → 장바구니 담기 | R-CT-01~03 | 빈 목록, 로딩 | — |
| 2 | 장바구니 | R-CT-04·05 | 비었음, 재고 부족 | BLOCKER R-CT-06 품절 상품을 담은 채로 둘지 |
| 3 | 주문 확인 | R-OD-01 | 결제 실패(가짜) | LATER R-OD-04 배송 메모 길이 |
```

이 표의 마지막 열이 사람이 결정해야 할 목록이다. 화면에서 본 것과 표가 같아야 한다.

프로토타이퍼는 끝내기 전에 **직접 열어 본다** — 콘솔 에러 0, 표의 화면이 전부 도달 가능, 상태 화면을 보는 방법(버튼, `?state=empty` 같은 쿼리)이 README 에 있다.

## 사람에게 내는 것 — 한 메시지

```text
기획서     docs/requirements.md — 미승인 초안 · BLOCKER 2 / LATER 7
프로토타입 open prototype/index.html

눌러 볼 것
  1. 상품 목록 → 장바구니 담기        R-CT-01~03
  2. 장바구니가 비었을 때            R-CT-05      (?state=empty)
  3. 주문 확인 → 결제 실패          R-OD-01·03

화면에 [미정]으로 표시한 곳 3개 — 그중 BLOCKER 2개는 승인 전에 정해야 한다
고칠 곳을 말하거나, 맞으면 requirements.md 상태를 "승인 완료"로
```

파일 내용을 붙이지 않는다. 경로, 숫자, 눌러 볼 순서만.

## 피드백 루프

사람이 프로토타입을 보고 말하면 → `planner` 가 기획서를 고치고 → `prototyper` 가 같은 화면을 고친다. 항상 **기획서 먼저**다. 프로토타입만 고치면 다음 구현은 고치기 전 기획서를 따른다.

두 바퀴를 돌고도 남는 것이 LATER 뿐이면 "LATER 는 구현 중에 정해도 된다"고 말하고 승인을 요청한다. BLOCKER 가 남아 있으면 승인 요청 대신 그 BLOCKER 만 다시 묻는다.

## 승인 뒤

`requirements.md` 가 `승인 완료` 가 되면 프로토타입은 할 일을 마쳤다. 지우지 않고 남기되, **정식 구현에 코드를 옮겨 쓰지 않는다** — 고정 데이터와 가짜 결제 위에서 자란 코드는 상태·에러 처리가 없는 채로 굳는다. 구현의 구조는 `project-structure` 스킬로 새로 정한다.
