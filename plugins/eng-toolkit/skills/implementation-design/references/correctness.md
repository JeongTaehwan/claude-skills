## 1. 멱등성

"멱등키를 쓴다"까지만 구현하면 재시도가 클라이언트에게 보이는 에러로 바뀌는 절반짜리가 된다. 네 가지를 같이 정해야 한다.

- **키의 범위** — 요청 단위인가 주문 단위인가. 결제 승인은 대개 주문(또는 결제 시도) 단위이고, 큐 소비는 메시지 단위다. 범위를 잘못 잡으면 정당한 두 번째 시도까지 막힌다
- **저장 대상** — "봤음" 표시만 저장하면 두 번째 호출에 돌려줄 게 없다. **첫 응답을 함께 저장**해야 재시도가 원래 응답을 그대로 받는다
- **보관 기간** — 상대의 재시도 정책보다 길게. PG가 24시간 동안 재시도하는데 키를 1시간 보관하면 없는 것과 같다
- **두 번째 호출의 응답** — 이전 응답 그대로인가 409인가. 웹훅 발신자는 대개 2xx만 보면 되므로 이전 응답 반환이 안전하다. 사용자 대면 API라면 409가 더 정직할 수 있다

경합 자체는 **유니크 제약**으로 막는 게 애플리케이션 락보다 확실하다. 삽입이 유니크 위반으로 실패하면 그게 "이미 처리됨"의 신호다.

## 2. 금액 — 배분과 잔차

정수 최소 단위로 계산하는 것은 부동소수점 드리프트를 막을 뿐, **가장 흔한 실제 버그를 막지 못한다.**

장바구니 단위 할인 3,000원을 라인 3개에 비율 배분하면 1,000/1,000/1,000이 아니라 999/1,000/1,000이 나오는 경우가 생긴다. 합계가 원금과 안 맞으면 주문 총액 대사가 깨지고, 부분 환불 금액이 몇 원씩 어긋난다. 정수 연산은 이 버그를 **없애는 게 아니라 결정론적으로 만든다.**

정해야 할 것:

- **반올림 방향** — 내림이 기본으로 안전하다(고객에게 유리, 합계 초과 없음). 하지만 결정이지 자동이 아니다
- **잔차의 주인** — 가장 비싼 라인, 첫 라인, 마지막 라인 중 하나로 고정한다. 어느 쪽이든 코드에 드러나야 하고, **이건 비즈니스가 소유한 결정이므로 사용자에게 밝힌다**
- **검산** — `sum(line_discounts) === cart_discount`를 코드가 보장하게 만든다. 주석으로 적어두면 다음 리팩터링에서 사라진다

**통화가 하나가 아니게 될 가능성**이 있으면 금액에 통화와 소수 자릿수를 함께 들고 다닌다. 최소 단위 자릿수가 통화마다 다르다(KRW 0, USD 2, JPY 0, KWD 3). 암묵적 스케일을 가진 정수 필드 하나는 두 번째 통화가 들어오는 순간 잠재 버그다.

## 3. 동시 증감과 조건부 UPDATE

읽고-검사하고-쓰는 형태는 트래픽이 낮을 때 정상 동작하므로 테스트를 통과한다.

```sql
-- 안 되는 것: 두 요청이 모두 99를 읽고 모두 통과한다
SELECT issued_count FROM coupons WHERE id = ?;   -- 99
-- 애플리케이션에서 99 < 100 검사
UPDATE coupons SET issued_count = 100 WHERE id = ?;

-- 되는 것: 조건을 DB가 판정하고, 결과를 영향 행 수로 읽는다
UPDATE coupons SET issued_count = issued_count + 1
WHERE id = ? AND issued_count < max_issue;
-- affected rows === 0 이면 소진. 예외가 아니라 정상적인 결과다
```

핵심은 **영향 행 수를 판정에 쓰는 것**이다. UPDATE를 날리고 성공했다고 가정하면 조건부로 만든 의미가 없다.

상태 전이도 같다. `WHERE status = 'PENDING'`을 걸면 두 번 실행돼도 두 번째는 0행이고, 그 0행이 "이미 처리됨"을 알려준다.

## 4. 스키마·계약 변경과 배포 창

**배포 중에는 옛 코드와 새 스키마가 동시에 돈다.** 이 한 문장이 이 절의 전부다. 인플라이트 요청, 큐에 쌓인 메시지, 이미 스토어에 배포된 모바일 클라이언트가 옛 코드에 해당한다.

한 번에 하면 깨지는 것들: NOT NULL 컬럼 추가, 컬럼 이름 변경, enum 값 추가(소비자의 exhaustive switch), 검증 강화, 응답 필드 제거.

**expand → backfill → switch reads → contract**를 각각 별도 배포로 나눈다.

1. **expand** — 새 컬럼을 nullable로 추가. 옛 코드는 모른 채로 계속 돈다
2. **backfill** — 기존 행을 채운다. 배치라면 청크로
3. **switch reads** — 새 코드가 새 컬럼을 읽기 시작. 쓰기는 양쪽에
4. **contract** — 옛 컬럼 제거. 옛 코드가 전부 사라진 것이 확인된 뒤에

응답 필드 제거도 같다. 추가는 대체로 안전하지만 제거와 의미 변경은 소비자가 다 옮겨간 뒤다.

## 5. 파생·캐시 값

비정규화 컬럼이나 사전 계산 테이블을 고르기 전에 **원본을 쓰는 곳을 전부 셀 수 있어야 한다.** 못 세면 이 방식을 고를 자격이 없다. 쿠폰 적용가를 컬럼에 저장했는데 어드민 쿠폰 편집기, 캠페인 스케줄러, 자정에 도는 만료 배치가 각각 원본을 바꾸고 아무도 무효화하지 않으면, 목록은 존재하지 않는 할인을 보여주고 결제는 다른 금액을 청구한다.

셀 수 있으면 **무효화가 일어나는 지점을 코드로 가리킨다.** 그리고 어긋났을 때 **무엇이 진실인지** 정한다 — 대개 결제 직전 재계산이 진실이고 목록의 값은 표시용이다. 이 구분을 안 정하면 나중에 둘 중 어느 쪽을 고칠지 아무도 모른다.

## 6. 여러 단계의 부분 실패

주문 생성 → 결제 승인 → 재고 차감 → 쿠폰 소진 → 메일 발송에서 3번째가 실패하면 지금 어떤 상태인가.

- **되돌릴 수 없는 단계를 되돌릴 수 있는 단계보다 뒤에 놓는다.** 외부 결제 승인은 되돌리기 비싸다. 앞에서 실패할 것들을 먼저 실패시킨다
- **트랜잭션 경계 안에 외부 HTTP를 넣지 않는다.** 상대가 느려지면 우리 락이 그만큼 오래 잡힌다
- **커밋 후 이벤트 발행이면 유실 가능성을 인정하고 처리한다.** 인정하지 않는 선택지는 없다 — outbox 패턴으로 막든지, 유실 시 복구 경로를 두든지

패턴 이름이 필요하면 `software-reference-library`의 `references/development.md` §2에 microservices.io 패턴 카탈로그(Saga, Outbox)가 있다. 단 코드가 나간 뒤에 본다.

## 7. 트랜잭션 범위와 락

여는 지점과 닫는 지점 사이에 **몇 개의 행이 잠기는가**, 그리고 그동안 무엇을 기다리는가.

**두 트랜잭션이 같은 행들을 다른 순서로 잠그면 데드락이다.** 커머스의 고전은 주문 + 재고 + 쿠폰 3중 조합이다. 여러 행을 잠글 때는 **항상 같은 순서**(예: id 오름차순)로 잠근다.

선택이 애매하면 SKILL.md의 비대칭 규칙을 적용한다 — 긴 트랜잭션이 조용히 죽는 쪽이다.

## 8. 페이지네이션

**offset 페이지네이션은 동시 삽입이 있는 테이블에서 행을 건너뛰고 중복시킨다.** 사용자가 2페이지를 보는 사이 1페이지에 새 행이 들어오면 밀려난 행은 영영 안 보인다. 주문 내역과 이벤트 피드에서 실제로 나는 버그다.

정렬 키가 안정적이면 **cursor 방식**을 쓴다. offset은 관리자 화면처럼 정확도가 덜 중요한 곳에.

목록 응답은 처음부터 페이지네이션 계약을 갖고 나간다. 나중에 붙이는 건 파괴적 변경이다.

## 9. 가정이 깨진 순간을 남기기

문서에 적은 가정은 아무도 안 읽지만 **코드에 박힌 가정은 스스로 알린다.** 다만 SKILL.md의 경고대로, 부탁받지 않은 방어 코드를 기본값으로 넣는 것과는 다르다. 남기는 건 **정상 흐름이 아니라 가정이 깨진 순간**이고, 한 곳에 하나면 충분하다.

- 조건부 UPDATE의 영향 행 수가 0이었을 때
- 멱등키 충돌이 실제로 일어났을 때
- 외부 호출이 타임아웃났을 때
- LIMIT에 걸려 잘렸을 때 (그리고 잘린 걸 조용히 넘기지 않을 때)

임계값 로그는 루프 안이 아니라 루프가 끝난 뒤 한 번 남긴다. 여기저기 뿌리면 그 자체가 새로운 종류의 쓰레기다.

**언제 걷어내는지도 같이 정한다.** 실측이 쌓여 n을 알게 되면 tripwire는 목적을 다한 것이다. 남겨두면 그게 다음 사람에게는 의미를 알 수 없는 노이즈가 된다.
