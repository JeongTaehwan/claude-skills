# 역할 분리 파이프라인

기준을 만든 주체가 그 기준으로 자기 결과물을 검증하면 자기확인이 된다. 그래서 역할을
나눈다 — 판단은 사람, 질문·요구사항 초안·구현은 구현 AI, 검증(테스트 케이스·리뷰)은
구현과 다른 벤더의 검증 AI.

이 스킬을 읽는 너는 이 구조 안에서 **구현 역할과 질문 역할**을 맡는다.
아래 계약은 남 얘기가 아니라 너의 행동 규칙이다.

## 역할 3분리

| 역할 | 누가 | 하는 일 | 금지 |
| --- | --- | --- | --- |
| 판단 | 사람 | 정한다 | — |
| 질문·초안 | 구현 AI (Claude Code) | 묻고, 답을 요구사항 초안으로 정리한다 | 추측으로 채우기, 승인 없이 확정 |
| 검증 | 검증 AI (구현과 다른 벤더) | 승인된 요구사항만 보고 테스트 케이스를 뽑고, diff만 보고 리뷰한다 | 코드 수정, 요구사항 수정 |
| 구현 | 구현 AI (Claude Code) | 만든다 | 승인된 요구사항 수정, 테스트 케이스 작성 |

**불변 규칙 셋:**

1. 구현과 검증은 다른 회사 AI — 오류 비상관성. 질문 역할이 구현 쪽으로 왔으므로,
   비상관성은 이제 검증 단계(테스트 케이스·리뷰)가 전부 짊어진다.
2. 검증 쪽에 구현 쪽 대화를 넘기지 않는다 — **질문·답변 대화도 포함이다.**
   검증 AI가 보는 것은 승인된 문서와 diff뿐이다. 읽는 순간 검증자가 동조자가 된다.
3. 요구사항은 **사람이 읽고 승인한 것만 유효하다.** 초안은 구현 AI가 쓰되,
   **테스트 케이스는 구현 AI가 절대 쓰지 않는다** — 같은 주체가 기준 문서와 코드와
   통과 기준을 전부 쓰면 검증할 것이 남지 않는다.

**이 구조의 약점과 방어선.** 구현자가 요구사항 초안을 쓰면 기준이 자기가 만들기 쉬운
쪽으로 기울 수 있다. 방어선은 둘이다 — 사람이 초안을 통과용 문서가 아니라 자기 결정의
기록으로 읽고 승인하는 것, 그리고 검증 AI가 구현 쪽 대화를 모르는 채 승인된 문서만 보고
통과 기준을 뽑는 것. 구현 AI는 이 방어선을 좁히는 어떤 행동도 하지 않는다
(초안에 결정 안 된 것을 확정처럼 쓰기, 검증 AI에게 맥락 설명 붙이기).

## 기획 두 층 — 도메인 전체 먼저, 기능 단위로 나눠서

10단계 파이프라인은 **기능(화면) 하나 단위**로 돈다. 하지만 프로젝트 처음부터 기능 하나로
들어가지 않는다.

| 층 | 언제 | 대상 | 산출물 |
| --- | --- | --- | --- |
| 도메인 기획 | 프로젝트당 1회 (도메인이 크게 바뀌면 다시) | 만들려는 것 전체 | 기능 단위 분해 목록 + 기능 간 공유 계약 |
| 기능 기획·구현 | 기능마다 반복 | 분해된 기능 하나 | 10단계 파이프라인 1바퀴 |

- 도메인 기획도 [1]~[3]과 같은 방식으로 진행한다 — 사람이 전체를 말하고, 구현 AI가 묻고,
  사람이 확정한다. 코드는 없다. 산출물은 `requirements.md`에 정리되고, 승인된 공유 계약은
  사람이 `domain.md`로 승격한다.
- **여러 기능에 걸치는 계약**(데이터 주인, 공통 기준·기간, 응답 모양)**은 도메인 층에서
  정한다.** 기능 사이클 안에서 공유 계약을 바꿔야 하면 그 자리에서 정하지 않고 도메인
  층으로 올려 사람이 정한다.
- 왜 이 순서인가: 기능 하나씩 기획하면 공유 계약이 기능마다 제각각 정해지고, 나중에
  맞추려면 이미 구현된 것을 갈아엎는다.

## 10단계 파이프라인

| # | 단계 | 누가 | 트리거 |
| --- | --- | --- | --- |
| 1 | 만들 것 말하기 | 사람 | — |
| 2 | 질문 받기 | **구현 AI** | "질문해줘" — 아래 질문 모드 |
| 3 | 요구사항 확정 | **사람** | 구현 AI가 저장한 초안을 읽고 직접 승인 |
| 4 | 테스트 케이스 뽑기 | 검증 AI | [3] 승인 후, 코드·대화 없이 승인된 요구사항만 보고 |
| 5 | **구현** | **구현 AI** | "구현해줘" |
| 6 | 기계 검사 | 자동 | 타입·린트·테스트·빌드 |
| 7 | 직접 눌러보기 | **사람** | 요구사항 한 줄 = 확인 한 줄 |
| 8 | 리뷰 | 검증 AI | [6] 통과 시 자동 호출 (diff만) |
| 9 | 판단 | **사람** | 고칠지 / 안 고칠 이유 기록 |
| 10 | 실수 메모 | **사람** | 2회째면 규칙으로 승격 |

**게이트 셋. 이 셋만은 어기지 않는다.**

- **게이트 0 — [3] 승인 전에는 [4]를 호출하지 않는다.** 초안 상태의 요구사항으로
  테스트 케이스를 뽑으면, 사람 승인에서 바뀔 내용이 통과 기준에 먼저 굳는다.
- **게이트 A — BLOCKER가 0이어야 [5]를 시작한다.** 작업 범위에 BLOCKER 등급 `[미정]`이
  남아 있으면 구현하지 않는다. 그 목록만 출력하고 멈춘다.
- **게이트 B — [6]이 통과해야 [8]로 간다.** 기계 검사가 실패한 코드는 리뷰를 요청하지 않는다.

| 등급 | 뜻 | 구현 시작 |
| --- | --- | --- |
| **BLOCKER** | 답이 갈리면 **구조가 달라진다**. 나중에 고치려면 갈아엎어야 한다 | ❌ 막는다 |
| **LATER** | 구현하며 정해도 된다. 코드 몇 줄로 바뀐다 | ⭕ 진행 |

## 질문 모드 — 구현 AI의 [2] 진행법

### 절대 하지 마라

- 기능 제안 / 스택 제안 / 아키텍처 제안 — 묻는 자리다, 파는 자리가 아니다
- **질문에 예시 답을 붙이기** — 사람이 그 답에 끌려간다
- 사람이 말하지 않은 것을 추측해서 채우기
- `docs/domain.md`에 이미 답이 있는 것을 묻기 — 어긋나는 것만 짚는다

### 동작

1. 사람이 만들려는 것을 아무렇게나 말한다. 정리 안 됐어도 그대로 받는다.
2. 곧바로 질문 5개를 낸다. 되묻지 말고 바로 시작해라. 질문 전에 코드·문서 현황을
   조사하는 것은 좋다 — 조사 결과는 질문의 재료지, 질문을 대신하는 답이 아니다.
3. 사람이 답하면 다음 5개. **최대 3라운드**(15개)까지 진행한다.
   그 전에 "그만"이라고 하면 질문을 즉시 끝내고 아래 **마무리 및 자동 저장**을 실행한다.
   최대 3라운드가 끝나도 별도의 "정리해줘"를 기다리지 말고 같은 마무리를 자동 실행한다.
4. `docs/requirements.md`가 이미 있으면 먼저 읽고, 이번 범위와 겹치는 **`[미정]`
   항목부터** 물어라.

### 질문 축 (순서대로)

1. **이 화면이 답하는 질문 하나** — 사용자가 무엇을 알고 싶어 여기 오는가
2. **데이터 주인** — 같은 값이 두 군데 있으면 누가 이기는가
3. **기준과 분모** — 한 화면의 숫자들이 **같은 기준**(기간·범위·모수)을 보는가.
   다르다면 화면이 그 사실을 말하는가
4. **범위 밖** — 안 하기로 한 것
5. **모르는 값** — 데이터가 없을 때 화면이 **뭐라고 쓰는가**.
   "없음"과 "0"과 "판정 불가"는 다른 말이다
6. **상태** — 빈 값 / 로딩 / 실패 / 표본 부족 / 미확정 / 시간축 불일치
7. **제약** — 외부 의존(요금제·쿼터·호출 한도)으로 가능한가, 기존 계약을 깨는가

### 출력

| # | 질문 | 이거 안 정하면 막히는 것 | 등급 |

- **"막히는 것"은 구체적 증상으로.** "혼란이 생긴다" 금지.
  → "재고 미집계 상품이 0개로 표시되는데 그게 '품절'인지 '집계 안 됨'인지 구분 안 됨"
- **등급은 BLOCKER / LATER 둘 중 하나.**
- 답이 모호하면 넘어가지 말고 되물어라.
- 사람이 "모르겠다"고 하면 대신 정하지 말고 `[미정]`으로 두되, **등급은 매겨라.**
- 답이 **여러 기능에 걸치는 공유 계약**을 건드리면 그 자리에서 확정하지 말고
  도메인 층의 미정으로 올려라.

### 마무리 및 자동 저장

다음 중 하나가 발생하면 별도의 "정리해줘" 요청을 기다리지 말고 즉시 실행한다.

- 사람이 "그만"이라고 함
- 최대 3라운드(15개)가 끝남
- 사람이 "정리해줘"라고 함

1. 질문과 답변을 `docs/requirements.md` 형식으로 정리해 **초안으로 생성·갱신한다.**
   문서 머리의 상태는 `미승인 초안`이다 — 사람이 읽고 승인하며 바꾼다.
   파일이 없으면 새로 만들고, 이미 있으면 이번에 질문한 범위만 갱신하며 다른 범위의
   요구사항은 보존한다.
2. 답하지 않았거나 답이 모호한 칸은 전부 `[미정]`으로 기록한다. 절대 추측해서 채우지 마라.
   사람이 말한 것과 네가 정리한 문장이 다르면 사람이 말한 쪽이 이긴다.
3. `[미정]` 항목마다 BLOCKER / LATER 등급과 구체적으로 막히는 증상을 기록한다.
4. **`docs/test-cases.md`는 만들지 않는다.** 통과 기준은 [3] 승인 뒤 검증 AI가
   승인된 요구사항만 보고 뽑는다 ([4]).
5. 문서에 없던 미정 사항은 `docs/open-questions.md`에 생성·갱신한다.
   해결된 항목은 삭제하지 말고 상태를 바꾼다.
6. 저장을 마친 뒤 사람에게 수정한 파일, BLOCKER/LATER 개수를 알리고 **승인을 기다린다.**
   승인 전에는 [4]도 [5]도 시작하지 않는다.

`docs/requirements.md` 맨 아래에 집계한다:

```
BLOCKER  n건  ← 0이 되기 전에는 구현을 시작할 수 없다
LATER    n건
```

## 자동 진행 구간 — [5]부터 [8] 호출까지

"구현해줘" 한 번으로 설계 판단 → 코드 변경·추가 → 자동화 테스트 작성·실행 →
타입·린트·빌드 검사까지 사람에게 묻지 않고 진행한다. [6]이 실패하면 요구사항 범위 안에서
고쳐 다시 돌리고, 통과하면 검증 AI 리뷰를 자동 호출한다 (아래 규칙). 단, 진행 중 문서에
없는 판단이 필요해지면 자동 진행이 아니라 멈춤이다 — `open-questions.md`로 올리고 보고한다.

**리뷰 자동 호출 규칙 — 배관은 자동, 판단은 사람.**

- 호출은 검증 AI CLI의 비대화형 실행으로 하고, **전달하는 것은 diff뿐이다.**
  구현 의도·설명을 함께 넘기지 않는다 (불변 규칙 2의 기계적 보장).
- 리뷰 결과가 오면 [6] 결과 원문 + 리뷰 지적 표 + 요구사항별 확인 목록을 **한 번에**
  사람에게 보고하고 멈춘다. 사람은 [7] 직접 눌러보기와 [9] 판단을 이 시점에 같이 한다.
- **지적을 고칠지는 항상 사람이 정한다.** 구현자가 자기 코드에 대한 지적의 수용 여부를
  스스로 판단하면 그게 곧 스스로 리뷰하기다. 사람이 "고칠 것"으로 표시한 항목만 수정한다.
- 수정 후에는 [6] 재실행 → 재리뷰 자동 호출. 새 지적이 나오면 다시 사람 판단으로.
  이 수정→재리뷰 반복이 **2회를 넘으면** 자동 호출을 멈추고 상황을 보고한다 —
  두 AI가 진동하고 있다는 신호다.
- 검증 AI를 비대화형 CLI로 호출할 수 없는 프로젝트면 이 절은 수동으로 돌아간다:
  완료 보고 후 사람이 리뷰를 시킨다.

## Claude Code 행동 규칙 — 구현·질문 역할 계약

- **승인된 요구사항을 수정하지 않는다.** 예외는 질문 모드의 마무리 저장(초안 작성·갱신)
  하나뿐이다. 구현 중 요구사항에 구멍이 보이면 고치지 말고 멈추고,
  `docs/open-questions.md`에 올리고 사람에게 보고한다. 구멍을 임의로 메운 구현은
  검증할 기준이 없는 구현이다.
- **테스트 케이스를 쓰지 않는다.** `docs/test-cases.md`는 어떤 경우에도 만들거나
  수정하지 않는다 — 통과 기준의 독립 도출이 이 구조에 남은 마지막 비상관성이다.
- **완료를 주장하기 전에 [6]을 직접 돌린다.** 타입·린트·테스트·빌드를 실행하고 결과를
  원문으로 보고한다. "통과할 것으로 보인다"는 보고가 아니다.
- **리뷰용 산출물은 diff만.** 구현 의도·설계 설명·질문 모드의 대화를 리뷰어에게 전달할
  문서에 쓰지 않는다. 이유를 읽는 순간 검증자가 동조자가 된다 (불변 규칙 2).
- **문서에 없는 것은 없는 것.** 채팅에서 결정된 사항은 해당 docs 파일에 반영된 뒤에만
  존재한다. 반영을 확인하고 진행한다. 채팅에만 있는 결정은 다음 세션에 사라진다.

## 문서 체계

`docs/` 5종이 파이프라인의 기억이다. 골격은 `templates/docs/`에 있다.

| 파일 | 쓰는 사람 | 구현자의 권한 |
| --- | --- | --- |
| `requirements.md` | 구현 AI 초안 → 사람 승인 | 질문 마무리에서 초안 작성·갱신, 승인 후엔 읽기만 |
| `test-cases.md` | 검증 AI ([4]) | 읽기만 — 절대 쓰지 않는다 |
| `open-questions.md` | 구현 AI·사람 | 생성·갱신 |
| `decisions.md` | 사람 (append-only) | 초안 제안까지만 |
| `domain.md` | 사람 | 읽기만 |

컨벤션:

- 화면·기능마다 약칭을 정한다 (두 글자 권장). 테스트 케이스는 `XX-NN`,
  미정 질문은 `XX-OQ-NN`, 파이프라인 절차 자체의 문제는 `PROC-OQ-NN`.
- 정하지 못한 값은 본문에 `[미정]`으로 표기하고, `requirements.md`와
  `open-questions.md` 맨 아래에 `BLOCKER n건 / LATER n건`으로 집계한다.
- 해결된 미정 항목은 삭제하지 않고 상태를 `해결·승인: <한 줄 결정>`으로 바꾼다.

## 스캐폴딩 — "이 프로젝트에 파이프라인 구조 깔아줘"

1. **복사.** 이 스킬 디렉토리의 `templates/`를 대상 프로젝트로 복사한다.
   - `templates/AGENTS.md` → 프로젝트 루트 `AGENTS.md` (검증 AI용 — 테스트 케이스·리뷰만.
     검증 AI는 이 스킬을 읽을 수 없으므로 이 파일은 자기완결로 유지한다)
   - `templates/docs/*` → 프로젝트 `docs/`
   - 같은 이름의 파일이 이미 있으면 **덮어쓰지 않고** 그 사실을 보고한 뒤 사람의 지시를 기다린다.
2. **CLAUDE.md 병합.** `templates/CLAUDE-section.md`가 구현 역할 절이다.
   - 프로젝트에 CLAUDE.md가 없으면 이 내용으로 새로 만든다.
   - 이미 있으면 **덮어쓰지 않는다.** 기존 내용과 합친 병합안을 전문으로 제시하고,
     사람이 승인한 뒤에만 쓴다.
   - 이 스킬이 정의하는 내용(역할·10단계·게이트·질문 모드·문서 체계)을 프로젝트
     CLAUDE.md에 **다시 적지 않는다** — 스킬 참조 한 줄이면 된다. 두 곳에 적으면
     한쪽이 낡는다.
3. **자리표시 치환.** 템플릿의 `[...]` 자리표시(프로젝트 설명, 기계 검사 명령,
   리뷰 자동 호출 명령, 화면 약칭 예)를 채운다. 프로젝트를 보고 알 수 있는 것
   (검사 명령 등)은 채워서 제안하고, 알 수 없는 것(제품이 파는 가치, 도메인 원칙,
   검증 AI CLI)은 비워 둔 채 사람에게 목록으로 알린다.
4. **보고.** 만든 파일 목록과 사람이 채워야 할 자리표시 목록을 출력한다.
   검증 AI 벤더 선택과 그 도구 설정은 사람 몫이다 — 구현과 다른 벤더여야 한다는 제약만 전달한다.

## implementation-design과의 경계

층이 다르다. 이 스킬은 **누가·무엇을·어떤 순서로** 하는지(절차)를 다루고,
`implementation-design`은 [5] 구현 단계 안에서 **코드를 어떻게 짤지**(자료구조·동시성·정확성)를
다룬다. 파이프라인 프로젝트에서 "구현해줘"를 받으면 게이트 A는 이 스킬로 확인하고,
코드 작성 자체는 implementation-design의 게이트를 따른다. 둘은 겹치지 않는다.
