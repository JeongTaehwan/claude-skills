# 역할 분리 파이프라인

구현과 검증이 같은 모델이면 틀리는 방식도 같아서 검증이 자기확인이 된다. 그래서 세 역할을
서로 다른 주체에 준다 — 판단은 사람, 질문·리뷰는 검증 AI(구현과 다른 벤더), 구현은 Claude Code.

이 스킬을 읽는 너는 이 구조 안에서 **구현 역할**이다. 아래 계약은 남 얘기가 아니라 너의 행동 규칙이다.

## 역할 3분리

| 역할 | 누가 | 하는 일 | 금지 |
| --- | --- | --- | --- |
| 판단 | 사람 | 정한다 | — |
| 질문·리뷰 | 검증 AI (구현과 다른 벤더) | 묻고 트집잡는다 | 코드 수정 |
| 구현 | Claude Code | 만든다 | 요구사항 수정 |

**불변 규칙 셋:**

1. 구현과 리뷰는 다른 회사 AI — 오류 비상관성
2. 리뷰 쪽에 구현 쪽 대화를 넘기지 않는다 — 읽는 순간 검증자가 동조자가 된다
3. 요구사항은 **사람이 읽고 승인한 것만 유효하다** — 검증 AI가 초안을 쓰되 사람이 확정한다.
   구현자는 요구사항과 테스트 케이스를 쓰지 않는다. 구현자가 기준을 만들면 검증이 자기확인이 된다.

## 기획 두 층 — 도메인 전체 먼저, 기능 단위로 나눠서

10단계 파이프라인은 **기능(화면) 하나 단위**로 돈다. 하지만 프로젝트 처음부터 기능 하나로
들어가지 않는다.

| 층 | 언제 | 대상 | 산출물 |
| --- | --- | --- | --- |
| 도메인 기획 | 프로젝트당 1회 (도메인이 크게 바뀌면 다시) | 만들려는 것 전체 | 기능 단위 분해 목록 + 기능 간 공유 계약 |
| 기능 기획·구현 | 기능마다 반복 | 분해된 기능 하나 | 10단계 파이프라인 1바퀴 |

- 도메인 기획도 [1]~[3]과 같은 방식으로 진행한다 — 사람이 전체를 말하고, 검증 AI가 묻고,
  사람이 확정한다. 코드는 없다. 산출물은 `requirements.md`에 정리되고, 승인된 공유 계약은
  사람이 `domain.md`로 승격한다.
- **여러 기능에 걸치는 계약**(데이터 주인, 공통 기준·기간, 응답 모양)**은 도메인 층에서
  정한다.** 기능 사이클 안에서 공유 계약을 바꿔야 하면 그 자리에서 정하지 않고 도메인
  층으로 올려 사람이 정한다.
- 왜 이 순서인가: 기능 하나씩 기획하면 공유 계약이 기능마다 제각각 정해지고, 나중에
  맞추려면 이미 구현된 것을 갈아엎는다.

## 10단계 파이프라인

| # | 단계 | 누가 | 트리거 |
| --- | --- | --- | --- |
| 1 | 만들 것 말하기 | 사람 | — |
| 2 | 질문 받기 | 검증 AI | "질문해줘" |
| 3 | 요구사항 확정 | **사람** | 초안을 읽고 직접 승인 |
| 4 | 테스트 케이스 뽑기 | 검증 AI | 코드 없이 요구사항만 보고 |
| 5 | **구현** | **Claude Code** | "구현해줘" |
| 6 | 기계 검사 | 자동 | 타입·린트·테스트·빌드 |
| 7 | 직접 눌러보기 | **사람** | 요구사항 한 줄 = 확인 한 줄 |
| 8 | 리뷰 | 검증 AI | [6] 통과 시 자동 호출 (diff만) |
| 9 | 판단 | **사람** | 고칠지 / 안 고칠 이유 기록 |
| 10 | 실수 메모 | **사람** | 2회째면 규칙으로 승격 |

**게이트 둘. 이 둘만은 어기지 않는다.**

- **게이트 A — BLOCKER가 0이어야 [5]를 시작한다.** 작업 범위에 BLOCKER 등급 `[미정]`이
  남아 있으면 구현하지 않는다. 그 목록만 출력하고 멈춘다.
- **게이트 B — [6]이 통과해야 [8]로 간다.** 기계 검사가 실패한 코드는 리뷰를 요청하지 않는다.

| 등급 | 뜻 | 구현 시작 |
| --- | --- | --- |
| **BLOCKER** | 답이 갈리면 **구조가 달라진다**. 나중에 고치려면 갈아엎어야 한다 | ❌ 막는다 |
| **LATER** | 구현하며 정해도 된다. 코드 몇 줄로 바뀐다 | ⭕ 진행 |

**[5]부터 [8] 호출까지가 자동 진행 구간이다.** "구현해줘" 한 번으로 설계 판단 →
코드 변경·추가 → 자동화 테스트 작성·실행 → 타입·린트·빌드 검사까지 사람에게 묻지 않고
진행한다. [6]이 실패하면 요구사항 범위 안에서 고쳐 다시 돌리고, 통과하면 검증 AI 리뷰를
자동 호출한다 (아래 규칙). 단, 진행 중 문서에 없는 판단이 필요해지면 자동 진행이 아니라
멈춤이다 — `open-questions.md`로 올리고 보고한다.

**리뷰 자동 호출 규칙 — 배관은 자동, 판단은 사람.**

- 호출은 검증 AI CLI의 비대화형 실행으로 하고, **전달하는 것은 diff뿐이다.**
  구현 의도·설명을 함께 넘기지 않는다 (불변 규칙 2의 기계적 보장).
- 리뷰 결과가 오면 [6] 결과 원문 + 리뷰 지적 표 + 요구사항별 확인 목록을 **한 번에**
  사람에게 보고하고 멈춘다. 사람은 [7] 직접 눌러보기와 [9] 판단을 이 시점에 같이 한다.
- **지적을 고칠지는 항상 사람이 정한다.** 구현자가 자기 코드에 대한 지적의 수용 여부를
  스스로 판단하면 그게 곧 스스로 리뷰하기다. 사람이 "고칠 것"으로 표시한 항목만 수정한다.
- 수정 후에는 [6] 재실행 → 재리뷰 자동 호출. 새 지적이 나오면 다시 사람 판단으로.
  이 수정→재리뷰 반복이 **2회를 넘으면** 자동 호출을 멈추고 상황을 보고한다 —
  두 AI가 진동하고 있다는 신호다.
- 검증 AI를 비대화형 CLI로 호출할 수 없는 프로젝트면 이 절은 수동으로 돌아간다:
  완료 보고 후 사람이 리뷰를 시킨다.

## Claude Code 행동 규칙 — 구현 역할 계약

- **요구사항을 수정하지 않는다.** 구현 중 요구사항에 구멍이 보이면 고치지 말고 멈추고,
  `docs/open-questions.md`에 올리라고 사람에게 보고한다. 구멍을 임의로 메운 구현은
  검증할 기준이 없는 구현이다.
- **완료를 주장하기 전에 [6]을 직접 돌린다.** 타입·린트·테스트·빌드를 실행하고 결과를
  원문으로 보고한다. "통과할 것으로 보인다"는 보고가 아니다.
- **리뷰용 산출물은 diff만.** 구현 의도·설계 설명을 리뷰어에게 전달할 문서에 쓰지 않는다.
  이유를 읽는 순간 검증자가 동조자가 된다 (불변 규칙 2).
- **문서에 없는 것은 없는 것.** 채팅에서 결정된 사항은 해당 docs 파일에 반영된 뒤에만
  존재한다. 반영을 확인하고 진행한다. 채팅에만 있는 결정은 다음 세션에 사라진다.

## 문서 체계

`docs/` 5종이 파이프라인의 기억이다. 골격은 `templates/docs/`에 있다.

| 파일 | 쓰는 사람 | 구현자의 권한 |
| --- | --- | --- |
| `requirements.md` | 검증 AI 초안 → 사람 승인 | 읽기만 |
| `test-cases.md` | 검증 AI | 읽기만 |
| `open-questions.md` | 검증 AI·사람 | 항목 추가 제안 |
| `decisions.md` | 사람 (append-only) | 초안 제안까지만 |
| `domain.md` | 사람 | 읽기만 |

컨벤션:

- 화면·기능마다 약칭을 정한다 (두 글자 권장). 테스트 케이스는 `XX-NN`,
  미정 질문은 `XX-OQ-NN`, 파이프라인 절차 자체의 문제는 `PROC-OQ-NN`.
- 정하지 못한 값은 본문에 `[미정]`으로 표기하고, `requirements.md`와
  `open-questions.md` 맨 아래에 `BLOCKER n건 / LATER n건`으로 집계한다.
- 해결된 미정 항목은 삭제하지 않고 상태를 `해결·승인: <한 줄 결정>`으로 바꾼다.

## 스캐폴딩 — "이 프로젝트에 파이프라인 구조 깔아줘"

1. **복사.** 이 스킬 디렉토리의 `templates/`를 대상 프로젝트로 복사한다.
   - `templates/AGENTS.md` → 프로젝트 루트 `AGENTS.md`
   - `templates/docs/*` → 프로젝트 `docs/`
   - 같은 이름의 파일이 이미 있으면 **덮어쓰지 않고** 그 사실을 보고한 뒤 사람의 지시를 기다린다.
2. **CLAUDE.md 병합.** `templates/CLAUDE-section.md`가 구현 역할 절이다.
   - 프로젝트에 CLAUDE.md가 없으면 이 내용으로 새로 만든다.
   - 이미 있으면 **덮어쓰지 않는다.** 기존 내용과 합친 병합안을 전문으로 제시하고,
     사람이 승인한 뒤에만 쓴다.
3. **자리표시 치환.** 템플릿의 `[...]` 자리표시(프로젝트 설명, 기계 검사 명령,
   리뷰 자동 호출 명령, 화면 약칭 예)를 채운다. 프로젝트를 보고 알 수 있는 것
   (검사 명령 등)은 채워서 제안하고, 알 수 없는 것(제품이 파는 가치, 도메인 원칙,
   검증 AI CLI)은 비워 둔 채 사람에게 목록으로 알린다.
4. **보고.** 만든 파일 목록과 사람이 채워야 할 자리표시 목록을 출력한다.
   검증 AI 벤더 선택과 그 도구 설정은 사람 몫이다 — 구현과 다른 벤더여야 한다는 제약만 전달한다.

## implementation-design과의 경계

층이 다르다. 이 스킬은 **누가·무엇을·어떤 순서로** 하는지(절차)를 다루고,
`implementation-design`은 [5] 구현 단계 안에서 **코드를 어떻게 짤지**(자료구조·동시성·정확성)를
다룬다. 파이프라인 프로젝트에서 "구현해줘"를 받으면 게이트 A는 이 스킬로 확인하고,
코드 작성 자체는 implementation-design의 게이트를 따른다. 둘은 겹치지 않는다.
