# 구조 냄새 — 증상에서 처방까지

사용자는 대개 원인이 아니라 증상을 말한다 ("이거 고치려면 파일 열 개를 열어야 해"). 증상으로 찾고, **확인 방법**으로 진짜인지 본 뒤에 처방한다. 확인 없이 처방하면 멀쩡한 구조를 옮기게 된다.

`scan` 은 `structure_scan.py` 다.

| 증상 (사용자가 하는 말) | 확인 | 원인 | 처방 |
|---|---|---|---|
| "기능 하나 고치는데 폴더 다섯 개를 연다" | scan 의 커밋당 모듈 수 중앙값 ≥ 3 | 최상위가 레이어(controller/service/repo)다. 변경은 기능 단위로 오는데 구조는 기술 단위로 갈려 있다 | 기능 우선으로 뒤집는다. 한 번에 말고, 다음에 손댈 기능부터 하나씩 `features/<이름>/` 으로 (SKILL.md 5절) |
| "이 함수 어디 둬야 할지 모르겠다" | 후보 디렉터리 두 곳의 역할을 한 문장씩 써 본다. 못 쓰면 확인 끝 | 디렉터리 역할이 이름으로 정의돼 있다(`services/`, `helpers/`). 이름이 하는 일을 말하지 않는다 | 이 코드가 **어떤 이유로 바뀌는가**로 고른다. 그 이유의 주인이 없으면 새 모듈이 아니라 가장 가까운 사용처에 둔다 |
| "utils 가 2천 줄이다" · "common 을 고치면 다 깨진다" | scan 의 공통 모듈 파일 수, 한 곳 전용 공통 파일, 공통의 불안정도 I | 공통이 쓰레기통이 됐다. 두 번째 사용처에서 승격했고, 도메인 규칙이 섞였다 | ① 한 곳 전용 파일은 그 모듈로 내린다 ② 도메인 규칙(할인, 권한)은 그 도메인으로 ③ 남은 것을 하는 일로 이름 짓는다(`money.ts`) ④ 공통 → 기능 import 를 규칙으로 막는다 |
| "A 를 고쳤더니 B 테스트가 깨졌다" (관계없어 보이는데) | scan 의 순환, A↔B 간선 | 순환 의존. 둘은 사실상 한 모듈이다 | 가장 약한 간선을 끊는다 — 그 의존을 이벤트로 바꾸거나, 공유하는 타입을 아래로 내리거나, 의존 방향을 뒤집는 인터페이스(포트)를 둔다 |
| "같이 바뀌는데 코드상으로는 연결이 없다" | scan 의 변경 결합 "import 없음" | 숨은 결합 — 같은 DB 테이블, 같은 API 응답 형태, 복붙한 검증 규칙 | 결합을 코드에 드러낸다. 공유 테이블이면 소유 모듈을 정하고 다른 쪽은 그 모듈 API 로, 계약이면 스키마 하나에서 생성 (OpenAPI, zod), 복붙이면 3-4 조건을 따져 합친다 |
| "모듈 내부 파일을 여기저기서 import 한다" | scan 의 공개 표면 우회 | 진입점이 없거나 있어도 강제가 없다 | 진입점을 만들고 밖에서 오는 내부 import 를 전부 진입점으로 돌린 뒤 lint 로 막는다 |
| "index.ts 를 import 하면 앱 전체가 딸려온다" · "테스트 하나가 느리다" | 번들 분석, 테스트 하나의 모듈 로드 수 | 모든 폴더에 배럴. 배럴이 배럴을 re-export 한다 | 배럴은 모듈 경계에만. 모듈 내부는 직접 경로로. `export *` 대신 이름을 나열한다 |
| "서비스 레이어가 리포지토리를 그대로 부르기만 한다" | 서비스 메서드 중 한 줄짜리 위임 비율 | 지금 필요 없는 레이어를 의식으로 만들었다 | CRUD 뿐인 기능은 레이어를 접는다(컨트롤러 → 리포지토리). 규칙이 생기면 그때 펼친다. 레이어 수는 기능마다 달라도 된다 (`vertical-slice-architecture`) |
| "도메인 테스트에 DB 가 필요하다" | `domain/` 의 import 목록에 ORM·HTTP·프레임워크 | 도메인이 인프라를 안다 | 인프라 타입을 도메인 밖으로. 도메인이 필요한 것을 인터페이스로 선언하고 인프라가 구현한다 (`hexagonal-architecture`) |
| "주문 목록 화면 고쳤더니 정산이 틀렸다" | 두 곳이 같은 모델/엔티티 클래스를 쓰는가 | 이름이 같은 다른 개념을 한 모델로 공유한다 | 모델을 가른다. 주문 시점 값은 스냅샷으로, 현재 값은 카탈로그 모델로. 경계 사이는 변환 함수 하나 |
| "마이크로서비스로 쪼갰는데 배포를 같이 해야 한다" | 서비스 배포 기록이 같은 날 묶이는가, 동기 호출 체인 길이 | 분산 모놀리스. 코드 경계를 확인하기 전에 네트워크 경계를 그었다 | 합치거나, 최소한 같이 바뀌는 쌍을 한 서비스로. 다시 나누려면 모듈러 모놀리스에서 경계를 먼저 검증한다 (`monolith-first`) |
| "모노레포인데 패키지가 서른 개고 다 같이 버전이 오른다" | 패키지별 변경 빈도, 패키지 사이 의존 그래프 | 이유 없이 패키지로 올렸다 (SKILL.md 3-6) | 늘 같이 바뀌는 패키지는 합친다. 독립 배포·소유·런타임 이유가 있는 것만 패키지로 남긴다 |
| "환경마다 동작이 다르다" · "설정이 어디서 오는지 모르겠다" | `process.env`/`os.environ` 참조 파일 수 | 설정 읽기가 흩어졌다 | 설정 모듈 하나가 읽고 검증하고, 나머지는 그것을 import 한다 (`env-divergence` 스킬, `the-twelve-factor-app`) |
| "팀 둘이 같은 폴더에서 계속 충돌한다" | CODEOWNERS, 같은 파일을 고친 작성자 분포 | 조직 경계와 코드 경계가 어긋난다 | 코드 경계를 팀 경계에 맞추거나 소유를 한 팀으로. 콘웨이의 법칙은 거스르면 진다 (`conways-law`) |
| "생성 코드를 고쳤는데 다시 사라졌다" | 생성 코드가 손 코드 사이에 섞여 있는가 | 생성물의 자리가 정해지지 않았다 | 생성 코드는 한 디렉터리, 손대지 말라는 표시, lint·스캔 제외. 확장은 래퍼로 |

## 냄새가 아닌 것

- **중복 코드가 두 군데 있다** — 바뀌는 이유가 다르면 중복이 아니다. 합치는 쪽이 결합을 만든다
- **디렉터리가 깊다** — 깊이 자체는 문제가 아니다. 문제는 경로가 하는 일을 말하지 않을 때다
- **한 모듈이 크다** — 크기가 아니라 응집이 기준이다. 같은 이유로 바뀌는 큰 모듈이, 늘 같이 바뀌는 작은 모듈 다섯 개보다 낫다
- **레이어 우선 구조** — 기능이 적거나 본체가 파이프라인이면 맞는 구조다. 커밋당 모듈 수가 낮으면 고칠 이유가 없다
- **프레임워크 관례가 이 표의 처방과 다르다** — 프레임워크를 따른다. 관례를 거스르는 비용은 처음 온 사람 모두가 낸다
