# 프로젝트 구조 설계

구조의 목적은 **변경 하나가 닿는 범위를 작게 유지하는 것**이다. 디렉터리 트리는 그 경계를 눈에 보이게 한 것일 뿐이고, 트리가 예쁜 것은 목적이 아니다.

그리고 경계는 **강제되지 않으면 사라진다.** README 에 적은 규칙은 첫 마감 주에 깨지고, 깨진 걸 아무도 모른 채 반년이 지나면 폴더 이름만 남은 진흙 덩어리가 된다. 그래서 이 절차의 산출물은 항상 *트리 + 규칙 + 그 규칙을 CI 에서 깨지게 하는 설정* 세 가지다.

## 1. 게이트

이 중 하나면 발동한다.

1. **새 골격** — 새 프로젝트·앱·패키지를 만든다
2. **새 경계** — 새 최상위 모듈(기능·도메인·패키지)을 만들거나, 두 모듈 사이에 **처음으로** 의존을 놓는다 (A 가 B 를 처음 import)
3. **구조 수리** — 순환, 비대한 공통 폴더, "어디 둬야 할지 모르겠다", 변경 하나가 디렉터리 다섯 개를 건드린다
4. **분할·병합** — 모노레포 도입, 패키지 분리, 서비스 분리, 또는 그 반대

발동하지 않는다: 기존 모듈 안에 파일 추가, 이름 변경, 한 모듈 내부 리팩터링, 일회성 스크립트. **사용자가 구조를 지정했으면** 그대로 하고, 이견은 한 줄로 말한다.

**저장소에 이미 규칙이 있으면 그게 정답이다.** 먼저 찾는다 — `.dependency-cruiser.*`, eslint 의 `boundaries/*`·`import/no-restricted-paths`·`@nx/enforce-module-boundaries`, `.importlinter`, ArchUnit·Spring Modulith 테스트, `package.yml`(packwerk), `docs/adr/`, `docs/decisions.md`. 있으면 이 절차는 그 규칙 안에서 위치를 고르는 일로 줄어든다.

## 2. 기존 코드가 있으면 먼저 잰다

구조가 나쁘다는 말은 대개 감으로 나오고, 감으로는 재구조화 비용을 설득하지 못한다. 고치기 전에, 그리고 새 경계를 기존 코드 옆에 놓기 전에 한 번 돌린다.

```bash
python3 ~/.claude/skills/project-structure/scripts/structure_scan.py <저장소>
python3 ~/.claude/skills/project-structure/scripts/structure_scan.py <저장소> --root src --depth 2
```

위 경로에 없으면(플러그인 설치·저장소 직접 사용) 이 SKILL.md 옆의 `scripts/` 를 같은 방식으로 부른다. JS/TS(경로 별칭·워크스페이스 패키지 포함)·Python·Go·Java/Kotlin 의 import 를 읽어서, **판단을 바꾸는 신호만** 낸다.

| 신호 | 뜻 | 바뀌는 결정 |
|---|---|---|
| 순환 | 순환 안의 모듈은 따로 테스트·배포·이해할 수 없다. 사실상 한 모듈이다 | 이동보다 먼저 끊는다. 스크립트가 짚는 **가장 약한 간선**부터 |
| 공통이 기능을 import | 공통이 잎이 아니다. 공통을 쓰는 모든 곳이 그 기능에 묶인다 | 그 코드는 공통이 아니라 그 기능의 것이다 |
| 공개 표면 우회 | index 가 있는데 내부 파일을 직접 import | 경계가 이름뿐이다. 강제 도구를 켤 때 첫 위반 목록이 된다 |
| 한 곳 전용 공통 파일 | 공통에 있는데 한 모듈만 쓴다 | 그 모듈로 내린다 — 공통이 커지는 주된 경로다 |
| 커밋당 모듈 수 중앙값 ≥ 3 | 기능 하나를 바꾸려면 디렉터리 여러 개를 연다 | 최상위 축이 틀렸다 (3-1) |
| import 없는 변경 결합 | 같이 바뀌는데 코드 의존이 없다 | 스키마·API 계약·복붙으로 묶여 있다. 경계가 데이터를 가로지른다 |

**숫자는 대화를 시작하는 근거이지 판결이 아니다.** 정규식 근사라서 동적 import 나 문자열로 부르는 코드는 못 본다. 모듈이 하나로 뭉쳐 나오면 `--root`·`--depth` 로 한 단계 안을 본다.

## 3. 결정 순서

새로 짤 때든 고칠 때든 이 순서로 정한다. 뒤의 것은 앞의 것에 기대므로 순서를 바꾸지 않는다.

### 3-1. 최상위 축 — 무엇이 함께 바뀌는가

**기본값은 기능(도메인) 우선, 레이어는 그 안에.** 최상위 디렉터리를 열었을 때 `controllers/ services/ repositories/` 가 아니라 `orders/ payments/ catalog/` 가 보여야 한다. 기능 하나를 바꾸는 커밋이 디렉터리 하나 안에 머물기 때문이다. 레이어 우선 구조에서는 "쿠폰 조건 추가" 하나가 컨트롤러·서비스·리포지토리·DTO·테스트 다섯 폴더에 흩어진다.

레이어 우선이 맞는 경우도 있다 — 판정은 "흩어지는 변경이 실제로 일어나는가"다.

- 기능이 몇 개 안 되고 더 늘 계획이 없다 (사내 도구, 1인 프로젝트)
- 본체가 기능이 아니라 **기술 파이프라인**이다 — CLI 도구, 컴파일러, SDK, 데이터 변환기
- 프레임워크가 최상위를 정한다 — Next.js `app/` 은 URL 구조이고, 그 안에서 `_components`·라우트 그룹으로 기능을 묶는다 (→ `references/layouts.md`)

**경계는 명사가 아니라 "다른 이유로 바뀌는 것"으로 자른다** (Parnas). 주문의 "상품"(주문 시점 가격·이름 스냅샷)과 카탈로그의 "상품"(현재 재고·노출 상태)은 이름이 같아도 다른 모델이다. 하나로 공유하면 카탈로그 변경이 지난 주문을 깨뜨린다.

**확신이 없으면 크게 자른다.** 큰 모듈을 나중에 쪼개는 건 그 안의 리팩터링이지만, 잘못 쪼갠 경계를 합치는 건 경계 양쪽의 계약·데이터·소유권을 전부 되돌리는 일이다.

### 3-2. 의존 방향 — 규칙 세 개

1. **모듈 그래프는 비순환(DAG)이다.** 예외 없음. 순환이 필요해 보이면 경계가 틀렸거나 한쪽이 이벤트로 바뀌어야 한다
2. **안정적인 쪽을 향한다.** 도메인 규칙은 아무것도 모르고, DB·HTTP·프레임워크·UI 가 도메인을 안다 (의존성 규칙). 남이 많이 쓰는 모듈일수록 남을 적게 알아야 한다 — 스캔의 불안정도 `I` 가 공통 모듈에서 높으면 이게 깨진 것이다
3. **기능끼리는 공개 표면으로만, 또는 아예 금지.** 금지하면 기능을 엮는 일은 위쪽 조립 계층(`app/`, 페이지, 컴포지션 루트, 유스케이스)이 한다

기능 A 가 B 의 것이 필요할 때의 선택지:

| 필요한 것 | 방법 | 대가 |
|---|---|---|
| B 에게 동기적으로 물어야 한다 (결제 승인 여부) | B 의 공개 API 호출. A → B 간선이 생기므로 B → A 는 영구히 막힌다 | 방향이 굳는다 — 어느 쪽이 위인지 지금 정한다 |
| B 에서 일어난 일에 반응한다 (주문 완료 → 재고 차감) | B 가 이벤트를 내고 A 가 구독. 코드 의존은 B 의 이벤트 타입으로만 | 흐름이 코드에서 안 보인다. 실패·재처리를 따로 설계한다 |
| 화면에 둘을 같이 보여준다 | 상위(페이지·위젯)가 둘을 각각 불러 조립 | 조립 계층이 두꺼워진다. 그게 맞는 자리다 |
| 둘 다 같은 개념을 쓴다 (금액, 사용자 ID) | 공통으로 내린다 — 단 3-4 의 조건을 통과할 때만 | 공통이 모든 곳에 묶인다 |

### 3-3. 공개 표면

**모듈마다 진입점은 하나다.** 밖에서는 그것만 import 한다. 내부 경로를 직접 가져다 쓰면 모듈 내부 리팩터링이 남의 코드를 깨뜨리고, 그때부터 내부는 내부가 아니다.

언어가 강제해 주면 그걸 쓴다 — Go `internal/`, Rust `pub(crate)`, Kotlin `internal`, Java 패키지 전용(public 을 안 붙인다)·JPMS `exports`, Gradle `implementation`(api 로 새지 않게). TS/JS·Python 은 언어가 못 막으므로 lint 로 막는다 (4절).

**배럴(`index.ts`)은 모듈 경계에만 둔다.** 모든 폴더에 index 를 두면 번들러 트리 셰이킹이 약해지고, 테스트 하나가 모듈 전체를 로드하고, 모듈 안에서 자기 배럴을 import 하는 순간 순환이 생긴다.

### 3-4. 공통 모듈 (shared · common · utils · lib · core)

공통은 **잎**이다 — 아무 기능도 import 하지 않는다. 그리고 **도메인 지식이 없다.** "VIP 할인율 계산"은 공통이 아니라 가격 도메인의 것이다. 이 둘을 어기는 순간 공통을 쓰는 모든 곳이 그 기능에 묶인다.

공통으로 내리는 조건은 둘 다다.

- **세 번째 사용처가 생겼다.** 두 번째에서 내리면 두 곳의 우연한 공통점을 일반화하게 된다
- **같은 이유로 바뀐다.** 지금 코드가 같아도 바뀌는 이유가 다르면(주문 금액 포맷 vs 정산 리포트 금액 포맷) 중복이 아니라 우연이다. 합치면 한쪽 요구가 다른 쪽을 깨뜨린다

`utils.ts`·`helpers/` 라는 이름은 쓰지 않는다. 무엇을 하는지로 이름 짓는다 — `money.ts`, `date-range.ts`, `http-client/`. 이름을 못 짓겠으면 공통이 아니라는 신호다.

### 3-5. 테스트·생성 코드·설정의 자리

- **테스트** — 저장소 관례를 따른다. 정한다면 단위 테스트는 대상 옆(`cart.test.ts`), 통합·e2e 는 최상위 `tests/`·`e2e/`. 언어 관례가 있으면 그게 이긴다 (Go `_test.go` 옆, JVM `src/test/` 미러)
- **생성 코드**(OpenAPI 클라이언트, ORM 클라이언트, protobuf) — 한 디렉터리에 모으고, 손대지 말라는 표시를 하고, lint·스캔에서 뺀다. 생성 코드를 손으로 고치면 다음 생성이 지운다
- **설정** — 환경 변수를 읽는 곳은 설정 모듈 하나다. 나머지는 그 모듈을 import 한다. `process.env` 가 스무 파일에 흩어져 있으면 "환경마다 다르게 돈다"는 버그의 온상이 된다 (→ `env-divergence` 스킬)

### 3-6. 경계를 단단하게 만드는 단계

경계는 네 단계로 단단해지고, 단계가 오를수록 비용이 늘고 되돌리기 비싸진다.

| 단계 | 경계 | 깨지면 | 드는 것 |
|---|---|---|---|
| 1. 디렉터리 | 관례 | 아무도 모른다 | 없음 |
| 2. 모듈 + lint | import 규칙 | CI 가 빨개진다 | 설정 파일 하나 |
| 3. 패키지 (워크스페이스) | 빌드 그래프·package.json | 빌드가 안 된다 | 패키지별 빌드·버전·배포 설정 |
| 4. 서비스 | 네트워크 | 런타임 장애 | 배포 파이프라인, 부분 실패, 분산 트랜잭션, 관측성 |

**한 단계 아래에서 경계가 한동안 깨지지 않았을 때만 올린다.** 2단계에서 계속 예외를 추가하고 있는 경계를 4단계로 올리면, 그 예외들이 전부 네트워크 호출이 된다.

- **패키지로 뺄 이유**: 독립 배포·버전이 필요하다, 다른 팀이 소유한다, 빌드 캐시 단위가 필요하다, 런타임이 다르다(서버/브라우저/모바일). 이유가 없으면 2단계로 충분하다
- **서비스로 뺄 이유**는 조직·배포 주기·확장 특성이다. **코드 정리는 서비스 분리의 이유가 아니다** — 모듈러 모놀리스에서 정리할 수 없는 코드는 네트워크 너머에서도 정리되지 않는다

## 4. 강제한다

규칙은 문서가 아니라 **CI 에서 깨지는 검사**로 남긴다. 스택별 도구와 설정 골격은 `references/enforcement.md` 에 있다.

| 스택 | 도구 |
|---|---|
| TS/JS | dependency-cruiser, eslint-plugin-boundaries, (Nx 모노레포) `@nx/enforce-module-boundaries` |
| Python | import-linter |
| Java/Kotlin | ArchUnit, Spring Modulith, Gradle 모듈 |
| Go | `internal/` + depguard(golangci-lint) |
| Ruby | packwerk |

**기존 위반이 많으면 얼린다.** 현재 위반을 기준선으로 기록하고 **새 위반만** 막는다 (dependency-cruiser `--baseline`, packwerk `update-todo`, ArchUnit `freeze`, import-linter `ignore_imports`). 전부 고칠 때까지 규칙을 미루면 그동안 위반이 계속 늘어난다. 단, 기준선은 줄어들기만 해야 한다 — 늘어나는 기준선은 규칙이 없는 것과 같다.

규칙이 없을 때의 임시 수단으로 스캐너도 CI 에 걸 수 있다.

```bash
python3 structure_scan.py . --rules .structure-rules --fail-on cycle,rule
```

```
# .structure-rules — deny|allow  <from>  ->  <to>   # 이유
deny   features/*  ->  features/*      # 기능끼리는 직접 import 하지 않는다. 상위에서 조립
deny   shared      ->  *               # 공통은 잎이다
allow  features/checkout -> features/cart   # 결제는 장바구니 공개 API 를 쓴다 (ADR-0007)
```

## 5. 고칠 때 — 재구조화

1. **순서**: 순환 끊기 → 공개 표면 만들기(밖에서 오는 내부 import 를 진입점으로) → 규칙 켜기(기준선으로 얼림) → 이동. 이동부터 하면 규칙 없이 옮긴 자리에서 다시 엉킨다
2. **한 PR 은 이동만, 또는 동작 변경만.** 이동 PR 은 `git mv` 와 import 경로 수정 외에 아무것도 없어야 리뷰가 가능하고, 문제가 생기면 통째로 되돌릴 수 있다
3. **빅뱅 금지.** 기능 하나씩 새 구조로 옮긴다. 두 구조가 몇 주 공존한다는 걸 전제로 "새 코드는 `features/` 에, 옛 `services/` 는 옮기는 중"을 README 한 줄에 적는다
4. **이동 PR 은 짧게 열고 빨리 머지한다.** 열려 있는 동안 다른 브랜치가 전부 충돌한다. 큰 이동은 팀에 미리 알린다
5. **끝나면 다시 잰다.** 순환·커밋당 모듈 수가 실제로 줄었는지 스캔으로 확인한다. 안 줄었으면 폴더만 옮긴 것이다

## 6. 출력 계약

| 요청 | 내보내는 것 |
|---|---|
| 새 골격 | ① 2~3단계 깊이의 트리, 최상위 디렉터리마다 한 줄 역할 ② 의존 규칙 3~5줄 ③ 그 규칙을 강제하는 설정 파일 ④ 되돌리기 비싼 결정이면 ADR 한 장 |
| "어디에 둬야 해" | 경로 한 줄 + 이유 한 문장. 그 이유가 3절의 어느 규칙인지 |
| 진단 | 스캔 결과 중 결정을 바꾸는 것만 — 순환과 끊을 간선, 위반, 같이 바뀌는 쌍. 처방은 순서대로 |
| 재구조화 | PR 단위 계획 — 각 PR 이 무엇만 하는지 |

**빈 폴더를 미리 만들지 않는다.** 첫 기능에 필요한 디렉터리만 만들고, 나머지는 규칙으로 남긴다. 아무것도 없는 `domain/ application/ infrastructure/` 는 구조가 아니라 의식이다.

쓰지 않는 것: 아키텍처 스타일 비교표, 각 레이어에 대한 일반론, 묻지 않은 마이크로서비스 이야기. 사용자는 트리를 원했지 강의를 원하지 않았다.

**정책을 대신 정했으면 밝힌다.** "기능 간 직접 import 금지", "공통 모듈 승격 기준", "어느 쪽이 위인가"는 팀이 지켜야 하는 약속이다. 조용히 설정 파일에 들어가면 다음 사람에게는 이유 모를 빨간 CI 다. 한 줄로 말하고, 근거가 필요하면 아래 레퍼런스를 단다.

## 멈추는 규칙

- 지금 있는 기능 수로 정당화되지 않는 레이어·폴더는 만들지 않는다
- 구조 논의가 첫 기능 구현보다 길어졌다 → 크게 자르고 규칙만 켜고 시작한다. 경계는 코드가 생겨야 보인다
- 두 안이 비슷하다 → 프레임워크 관례, 그다음 팀이 이미 아는 쪽. 구조의 가치 절반은 모두가 같은 곳을 찾는다는 데 있다
- 측정 없이 "결합이 높다"고 말하지 않는다 — 스캔이나 git log 의 숫자를 댄다
- 재구조화의 이득을 한 문장으로 못 대면(어떤 변경이 몇 디렉터리에서 몇 디렉터리로 줄어드는가) 하지 않는다

멈춤은 결정이 끝났다는 뜻이지 구조가 검증됐다는 뜻이 아니다. 구조는 다음 기능 세 개가 디렉터리 하나 안에서 끝나는지로 검증된다.
