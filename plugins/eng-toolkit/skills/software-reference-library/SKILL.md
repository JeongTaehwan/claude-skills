# Software Reference Library

소프트웨어를 만들고 알리고 굴리는 10개 도메인의 1차 자료 512개. 모든 URL은 등록 시점에 HTTP 검증했다.

목적은 답을 **인용 가능하게** 만드는 것이다 — 사용자가 원문을 읽고 반박할 수 있게.

## 구조 — 항목마다 파일 하나

```
references/<도메인>/<slug>.md      ← 항목 하나
scripts/find.py                    ← 찾는 도구. 이걸 쓴다
references/<도메인>/_index.md      ← 사람이 GitHub 에서 훑는 표
INDEX.md                           ← 사람이 훑는 512개 목록
```

**`_index.md` 와 `INDEX.md` 는 읽지 마라.** 도메인 색인 하나가 6천~2만7천 토큰이고 `INDEX.md` 는 11만 토큰이다. 한 번 읽으면 세션이 끝날 때까지 매 턴 다시 읽히고, 항목이 늘면 그 비용도 같이 는다. 그 훑기를 `find.py` 로 내려서 **맞는 후보만** 받는다 — 조회 한 번이 약 1,900 토큰으로 끝나고 라이브러리가 커져도 그대로다.

## 도메인

`planning` 기획 · `architecture` 설계 · `development` 개발 · `design` 디자인 · `qa` QA · `testing` 테스트 · `performance` 성능 · `security` 보안 · `infrastructure` 인프라 · `marketing` 마케팅

각 도메인의 항목 수는 `find.py --domains` 로 본다.

**QA와 테스트의 경계**: QA는 *무엇을 어떻게 보증할지 정하는 것*, 테스트는 *실제로 검증하는 것*이다. "테스트 전략을 어떻게 세우나"는 QA, "Playwright에서 이 요소를 어떻게 잡나"는 테스트다.

**성능 도메인과 `slow-network-ux` 스킬의 경계**: 어떤 기법을 어떤 순서로 적용할지는 그 스킬의 플레이북이 정하고, 이 도메인은 근거 자료를 든다. 자료만 필요하면 여기로 바로 온다.

## 찾는 순서

**1. 처한 상황을 그대로 넣는다.** 자료 이름이 아니라 증상을 쓴다. 사용자는 대개 이름을 모르고 상황만 알고, **페르소나가 그 상황으로 걸리라고 있는 검색 키다.**

```bash
python3 ~/.claude/skills/software-reference-library/scripts/find.py "리뷰가 취향 싸움이 된다"
python3 ~/.claude/skills/software-reference-library/scripts/find.py "간헐적으로 깨지는 테스트 때문에 CI를 아무도 안 믿는다"
```

세션의 작업 디렉터리는 사용자 프로젝트이므로 **상대경로로 부르면 깨진다.** 위 경로에 없으면(플러그인으로 설치했거나 저장소에서 직접 쓰는 중이면) 이 SKILL.md 가 있는 디렉터리의 `scripts/find.py` 를 같은 방식으로 부른다.

**2. 도메인이 분명하면 좁힌다.** 어휘가 도메인을 넘나들어서(“리뷰”, “취향”, “지표”) 무필터 상위권에 엉뚱한 도메인이 섞인다.

```bash
python3 ~/.claude/skills/software-reference-library/scripts/find.py "리뷰가 취향 싸움이 된다" --domain development
```

**3. 후보군이지 정답이 아니다.** 8건은 걸러 쓰라고 주는 것이다. 한 줄 요약을 보고 2~3개로 좁힌 뒤 그것만 연다. 아무것도 안 맞으면 단어를 바꿔 한 번 더 하고, 그래도 없으면 없다고 한다.

**4. 항목은 필요한 절만 연다.** 항목 전체는 약 2,300 토큰이고, 인용에 필요한 건 대개 두 절이다.

```bash
python3 ~/.claude/skills/software-reference-library/scripts/find.py --show <slug> --only 인용,아니다
```

절 이름: `한줄` `페르소나` `연다` `아니다` `내용` `인용` `코드`. **`아니다`는 되도록 함께 본다** — 인접한 다른 자료를 지목하고 있으면 그쪽이 맞는 경우가 많다. 전체가 필요하면 `--only` 없이 부르거나 파일을 직접 연다.

**5. 인용 전에 원문을 가져온다.** 항목 파일은 요약이지 원문이 아니다. 자료가 *무엇을 말하는지* — 숫자, 절차, 정의 — 를 진술할 거면 WebFetch로 URL을 먼저 열어라. 요약은 **추천**엔 충분하지만 **인용**엔 부족하다.

## 답할 때

**추천을 먼저, 근거는 그 다음.** 사용자는 질문을 했지 참고문헌 목록을 요청한 게 아니다. 잘 고른 두세 개가 열두 개보다 낫다.

**1차 자료를 우선한다.** Shape Up 웹북 > Shape Up 소개 블로그. Raft 논문 > Raft 설명 글. 2차 자료는 그쪽이 정말 더 잘 설명할 때만 쓴다.

**연도를 함께 본다.** 원리를 다루는 고전(Parnas 1972, Lamport 1978)은 만료되지 않는다. 도구 문서는 만료된다. 도구를 인용할 땐 API가 바뀌었을 수 있다고 밝힌다.

**의견이 갈리는 지점을 숨기지 않는다.** 이 라이브러리에는 서로 반대하는 자료가 일부러 들어 있다 — Test Pyramid vs Testing Trophy, Scrum vs Shape Up, 마이크로서비스 vs 모듈러 모놀리스. 업계가 실제로 갈리는 질문이면 한쪽을 정답처럼 말하지 말고 양쪽을 준다.

**여기 없으면 없다고 한다.** 이 라이브러리는 의도적으로 유한하다. 맞는 게 없으면 웹을 검색하고 라이브러리 밖 출처라고 밝혀라. 느슨하게 관련된 항목을 억지로 끌어다 쓰거나, 그럴듯한 URL을 지어내지 마라.

## 유지보수

```bash
python3 scripts/find_test.py                     # 검색 품질 회귀
python3 scripts/check_links.py references/       # 링크 썩음만 빠르게
python3 ../../../../scripts/audit.py --out reports  # 링크 + 저장소 건강 + 스킬 사용률
```

`audit.py`는 지난 실행을 `reports/state.json`에 기억하므로 **달라진 것만** 보고한다. `doi.org`, `dl.acm.org`, `w3.org`, `iso.org`, `medium.com` 등은 스크립트 요청에 403을 주지만 브라우저에서는 정상이라 `BLOCKED`로 분류된다. 반복 재현되는 `404`/`410`만 실제 썩음이다.

`find.py` 는 색인 파일을 따로 만들지 않고 항목 512개를 매번 직접 읽는다. **그래서 색인이 본문과 어긋날 수 없고, 항목을 추가해도 다시 만들 것이 없다.** 대신 검색 점수를 건드렸으면 `find_test.py` 를 돌린다 — 한 질의를 고치려다 나머지를 망가뜨리는 게 이 종류에서 가장 흔한 실패다.

항목을 추가할 때는 기존 파일의 형식을 그대로 따르고, 커밋 전에 URL을 확인한다. 절 이름(`## 한 줄`, `## 페르소나` …)은 `find.py` 가 파싱하므로 그대로 써야 한다.

**코드 예시는 그 자료의 주장을 실행으로 옮긴 최소 코드**이고, 마지막 줄에 *이 코드가 감추는 것*을 적는다. 선언문·전략서처럼 코드로 옮기면 껍데기만 남는 자료에는 이 절이 없다 — 없는 것이 억지로 붙인 것보다 낫다.

```bash
curl -sSL -o /dev/null -w "%{http_code}" <url>
```

검증 안 된 링크는 없는 링크보다 나쁘다. 파일 전체를 못 믿게 만든다.
