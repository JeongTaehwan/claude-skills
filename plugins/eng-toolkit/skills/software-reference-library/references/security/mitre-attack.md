# MITRE ATT&CK

https://attack.mitre.org/

## 한 줄
실제 침해 사고에서 관찰된 공격자의 **행동**을 전술(왜)과 기법(어떻게)의 격자로 정리한 공개 지식 베이스 — 취약점 목록이 아니라 "침입한 다음 무엇을 하는가"의 목록이고, 그래서 탐지와 로깅을 설계할 때 쓰인다.

## 페르소나
**서비스가 커져서 보안 로그를 쌓기 시작했는데, 무엇을 알림으로 올려야 하는지 기준이 없어 로그인 실패 횟수 하나만 세고 있는 백엔드·플랫폼 엔지니어.** 취약점 스캐너는 돌리고 있고 Top 10 대조도 했지만, 그것들은 전부 "들어오기 전"을 막는 이야기다. 실제로 계정 하나가 털렸을 때 그다음 행동을 무엇으로 알아채는지에 대해서는 팀에 언어가 없다. 남들이 실제로 관찰한 행동 목록을 빌려 와야 한다.

## 이럴 때 연다
- 보안 로그·감사 로그에 무엇을 남길지, 어떤 조건을 알림으로 올릴지 정할 때
- 침해 사고 대응 시나리오나 훈련(테이블톱)을 설계하며 단계별 행동을 나열해야 할 때
- 현재 탐지 커버리지에 어떤 구멍이 있는지 지도로 그려야 할 때
- 사고 후 회고에서 공격자가 무엇을 했는지 팀·외부와 같은 용어로 기술해야 할 때
- 보안 제품·서비스가 "ATT&CK 커버리지"를 주장할 때 그게 무엇을 뜻하는지 검증할 때
- 위협 모델링에서 STRIDE 로 도출한 위협을 실제 관찰된 행동으로 구체화하고 싶을 때

## 이럴 땐 아니다
- 우리 코드의 취약점을 무엇부터 고칠지 정하는 일에는 맞지 않는다 — `security/owasp-top-10.md`, `security/owasp-asvs.md`
- 개별 취약점의 심각도 산정은 `security/cvss-specification.md`
- 설계 단계에서 우리 시스템 고유의 위협을 발굴하는 활동은 `security/owasp-threat-modeling.md`
- 결함 유형의 분류 체계가 필요하면 `development/cwe-top-25-most-dangerous-software-weaknesses.md`
- 조직의 보안 프로그램 전반을 어떤 축으로 세울지는 `security/nist-cybersecurity-framework-2-0.md`
- **공격 실행 절차를 얻는 용도로는 이 항목을 열지 않는다.** 여기서의 쓸모는 탐지·로깅·대응 설계 한 방향이다.

## 무엇이 들어있나
행렬(matrix) 형태가 이 자료의 얼굴이다. 열이 **전술(tactic)** — 초기 접근, 실행, 지속성, 권한 상승, 방어 회피, 자격증명 접근, 탐색, 측면 이동, 수집, 명령·제어, 유출, 영향 — 즉 공격자가 달성하려는 목적이고, 각 열 아래 칸이 그 목적을 이루는 **기법(technique)** 이다. 기법마다 `T1110` 같은 고유 ID 가 있고 하위 기법은 `T1110.003` 처럼 소수점으로 붙는다. 이 ID 체계가 실무적으로 가장 큰 가치다 — 탐지 규칙, 사고 보고서, 벤더 문서가 같은 문자열로 서로를 가리킬 수 있다.

행렬은 대상 환경별로 나뉜다 — Enterprise(윈도우·리눅스·macOS·클라우드·컨테이너·SaaS), Mobile, ICS. 웹 서비스를 굴리는 팀이 주로 보는 것은 Enterprise 안의 클라우드·컨테이너·SaaS 플랫폼 열이다.

각 기법 페이지의 구조가 이 자료의 실제 사용법을 규정한다. 설명 다음에 **Procedure Examples**(어떤 실제 사고에서 관찰됐는가), **Mitigations**(구조적으로 막는 방법), **Detection**(무엇을 어디서 보면 알아챌 수 있는가)이 붙는다. 방어 쪽에서 이 자료를 쓴다는 것은 사실상 뒤의 두 절을 읽는다는 뜻이다.

Top 10 이나 CWE 와의 결정적 차이는 **관점의 시제**다. Top 10 과 CWE 는 코드에 이미 존재하는 결함을 말하고, ATT&CK 는 침입이 성립한 이후의 행동을 말한다. 그래서 둘은 대체 관계가 아니라 순서 관계에 가깝다 — 결함을 줄여도 계정 탈취는 일어나고, 그 이후를 다루는 언어가 따로 필요하다.

자주 오해되는 지점 하나: 행렬을 커버리지 체크리스트로 삼아 "몇 퍼센트 덮었다"를 목표로 삼는 사용법은 이 자료가 의도한 바가 아니다. 기법들은 우리 환경에서의 적용 가능성이 제각각이라, 우리 스택에 해당하지 않는 칸까지 세는 순간 숫자가 무의미해진다.

## 인용 포인트
- "로그인 실패만 세면 되지 않나"라는 질문에, 자격증명 접근은 전술 12개 중 하나일 뿐이라는 구조를 그대로 보여 줄 수 있다.
- 사고 회고 문서에서 공격자 행동을 기법 ID 로 적으면, 서술이 사람마다 달라지는 문제와 외부와 대화가 안 되는 문제를 동시에 없앤다.
- 보안 제품이 "ATT&CK 전 영역 커버"를 주장할 때, 기법 페이지의 Detection 절이 요구하는 데이터 소스를 우리가 실제로 수집하고 있는지 되물을 근거가 된다.
- 탐지 규칙 저장소에 기법 ID 태그를 의무화하자고 제안할 때, 커버리지 공백이 목록이 아니라 지도로 보인다는 점을 든다.

## 코드 예시

탐지 규칙에 기법 ID 를 태그로 박아 두면, 규칙 목록이 곧 커버리지 지도가 된다 — 어느 전술 아래에 규칙이 하나도 없는지가 바로 보인다.

```yaml
# detections/password-spraying.yml — Sigma 포맷, 태그 규칙은 Sigma 의 ATT&CK 표기 관례를 따른다
title: 단일 출발지에서 다수 계정 로그인 실패
status: experimental
description: 한 IP 가 짧은 시간에 서로 다른 계정으로 반복 로그인을 시도한다
references:
  - https://attack.mitre.org/techniques/T1110/003/
logsource:
  product: checkout-api
  service: authentication
detection:
  failed_logins:
    event_name: login_failed
  timeframe: 10m
  condition: failed_logins | count(distinct user_id) by source_ip > 20
falsepositives:
  - 사내 NAT 출구 IP (허용 목록으로 제외)
  - 모바일 캐리어 공용 IP
level: high
tags:
  - attack.credential_access
  - attack.t1110.003
```

이 코드가 감추는 것: 이 규칙이 성립하려면 로그에 `source_ip` 와 `user_id` 가 **실패한 시도에도** 남아 있어야 한다. 기법 페이지의 Detection 절이 늘 데이터 소스부터 말하는 이유가 이것이고, 대개 진짜 작업은 규칙을 쓰는 쪽이 아니라 없는 필드를 애플리케이션 로그에 새로 심는 쪽이다.
