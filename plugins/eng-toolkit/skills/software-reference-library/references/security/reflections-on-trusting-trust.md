# Reflections on Trusting Trust (Ken Thompson, 1984)

https://www.cs.cmu.edu/~rdriley/487/papers/Thompson_1984_ReflectionsonTrustingTrust.pdf

## 한 줄
세 쪽짜리 튜링상 수상 강연 — **소스 코드를 아무리 읽어도 발견할 수 없는 백도어**를 컴파일러 안에 심는 방법을 보여 주고, 거기서 "직접 만들지 않은 코드는 신뢰할 수 없다"는 결론을 끌어낸다. 공급망 보안이라는 분야 전체가 서 있는 원점 문서다.

## 페르소나
**"소스가 공개되어 있으니 검증 가능하다"는 문장을 별 저항 없이 써 왔는데, 빌드 파이프라인 보안을 설계하면서 그 문장이 정확히 무엇을 보장하는지 되짚어야 하는 개발자·아키텍트.** SLSA 나 재현 가능한 빌드가 왜 "코드 리뷰만으로는 부족하다"를 전제로 시작하는지, 서명과 출처 증명이 왜 필요한지를 팀에 설명해야 한다. 결론만 인용하기보다 논증 자체를 보여 주는 편이 훨씬 빠른 상황이다.

## 이럴 때 연다
- 공급망 보안(빌드 무결성, 재현 가능한 빌드, 출처 증명) 도입의 배경을 설명할 때
- "오픈소스니까 안전하다"는 명제의 한계를 팀에 설명해야 할 때
- 빌드 도구·베이스 이미지·CI 러너를 신뢰의 범위에 포함시켜야 하는 이유를 정리할 때
- 보안 교육이나 온보딩에서 신뢰의 경계라는 개념을 처음 소개할 때
- 코드 리뷰와 정적 분석만으로 구성된 보안 계획의 공백을 지적할 때

## 무엇이 들어있나
논증이 3단계로 쌓인다.

**1단계**는 자기 자신의 소스를 출력하는 프로그램(quine)이다. 재미있는 퍼즐처럼 제시되지만, 뒤에서 쓰일 "코드가 자기를 재생산한다"는 도구를 미리 깔아 두는 부분이다.

**2단계**는 컴파일러가 자기 자신을 컴파일하며 지식을 대물림하는 현상이다. C 컴파일러가 `\n` 같은 이스케이프의 의미를 배우고 나면, 다음 세대 컴파일러는 그 지식을 소스에 명시하지 않고도 갖게 된다. **컴파일러 바이너리 안에는 그 소스에 적혀 있지 않은 것이 이미 들어 있다**는 사실이 여기서 드러난다.

**3단계**가 핵심이다. 컴파일러에 두 개의 트로이 목마를 심는다. 하나는 로그인 프로그램을 컴파일할 때 백도어를 삽입하는 코드. 다른 하나는 **컴파일러 자신의 소스를 컴파일하고 있음을 알아채고 위 두 코드를 결과 바이너리에 다시 삽입하는 코드**. 두 번째가 완성되면 컴파일러 소스에서 트로이 목마를 전부 지워도 된다. 깨끗한 소스로 컴파일해도 감염된 바이너리가 감염을 재생산하기 때문이다. 이제 어떤 소스 코드에도 백도어의 흔적이 없고, 컴파일러 소스를 아무리 읽어도 찾을 수 없다.

여기서 나오는 문장이 이 강연의 결론이다 — **"당신이 완전히 직접 만들지 않은 코드는 신뢰할 수 없다."** 그리고 그 신뢰의 정도는 코드를 쓴 사람에 대한 신뢰에 비례한다는 말이 이어진다. 소스 수준의 검증에는 원리적 한계가 있고, 신뢰는 결국 코드 밖의 것(사람, 프로세스, 절차)에 근거를 둘 수밖에 없다는 뜻이다.

강연은 여기서 한 걸음 더 나간다. 컴파일러만의 이야기가 아니라 어셈블러, 로더, 마이크로코드, 하드웨어까지 같은 논리가 적용되며, 신뢰의 바닥은 어디에도 없다.

**오늘의 실무로 옮기면 이렇게 읽힌다.** 우리가 신뢰해야 하는 것은 우리 소스만이 아니라 컴파일러, 빌드 도구, 베이스 이미지, CI 러너, 그것을 만든 조직 전부다. 코드 리뷰와 정적 분석은 그 목록의 첫 항목만 다룬다. 재현 가능한 빌드(같은 소스에서 같은 바이너리가 나오는가), 서명과 출처 증명, 그리고 서로 다른 컴파일러로 교차 검증하는 기법들이 이 강연이 제기한 공백을 실무적으로 좁히려는 시도들이다.

## 인용 포인트
- "소스가 공개되어 있으니 검증 가능하다"는 주장의 한계를 지적할 때, 소스에 흔적이 남지 않는 공격이 1984년에 이미 제시되었다는 사실을 든다.
- 재현 가능한 빌드나 빌드 출처 증명에 투자하자는 제안의 서문으로 쓴다 — 코드 리뷰로 닫히지 않는 구멍이 있다는 근거.
- CI 러너·베이스 이미지·빌드 도구를 신뢰 경계 안에 명시하자고 할 때, 신뢰가 코드가 아니라 사람과 프로세스에 근거한다는 결론을 인용한다.
- 보안 온보딩에서 "무엇을 신뢰하고 있는가"를 물어보는 첫 자료로 쓰기 좋다 — 짧아서 회의 전에 읽힐 수 있다.

## 코드 예시

이 강연의 공백을 실무에서 좁히는 방향 하나 — 같은 소스에서 항상 같은 바이너리가 나오는지 확인해, 산출물이 소스로부터 검증 가능한 상태를 유지한다.

```yaml
# .github/workflows/reproducible-build.yml
name: reproducible-build
on: pull_request
jobs:
  double-build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: 1차 빌드
        run: |
          export SOURCE_DATE_EPOCH=$(git log -1 --pretty=%ct)  # 타임스탬프 고정
          make build
          sha256sum dist/app | cut -d' ' -f1 > first.txt
      - name: 산출물 제거 후 2차 빌드
        run: |
          git clean -xdf dist
          export SOURCE_DATE_EPOCH=$(git log -1 --pretty=%ct)
          make build
          sha256sum dist/app | cut -d' ' -f1 > second.txt
      - name: 두 다이제스트 비교
        run: |
          diff first.txt second.txt \
            || { echo "같은 소스에서 다른 바이너리가 나왔습니다"; exit 1; }
```

이 코드가 감추는 것: 같은 러너에서 두 번 빌드하는 것은 비결정성(타임스탬프, 경로, 파일 순서)을 잡아낼 뿐, 강연이 말한 문제는 건드리지 못한다. 감염된 툴체인은 두 번 다 똑같이 감염된 결과를 내놓기 때문이다. 그쪽을 좁히려면 **서로 다른 환경·다른 툴체인으로 빌드한 결과를 대조**해야 하고, 그마저도 신뢰의 바닥을 만들어 주지는 않는다.
