# gitleaks

https://github.com/gitleaks/gitleaks

## 한 줄
현재 코드뿐 아니라 **git 히스토리 전체**를 훑어 API 키·토큰·개인키가 커밋된 적이 있는지 찾아내는 스캐너 — "지웠으니 괜찮다"가 왜 틀린 말인지를 실제 결과로 보여 주는 도구다.

## 페르소나
**누군가 `.env` 를 커밋했다가 다음 커밋에서 지운 것을 발견한 개발 리드.** 파일은 사라졌지만 히스토리에는 남아 있고, 그 키가 아직 유효한지, 비슷한 일이 과거에 몇 번이나 있었는지 아무도 모른다. 앞으로는 커밋 자체를 막고 싶은데 사내 토큰 형식은 공개 도구의 기본 규칙에 없다. 과거를 한 번 전수 조사하고, 미래를 훅과 CI 로 막는 두 가지가 동시에 필요하다.

## 이럴 때 연다
- 저장소 히스토리에 유출된 자격증명이 있는지 한 번 전수 조사할 때
- 커밋 전(pre-commit) 또는 PR 단계에서 비밀값 유입을 차단하는 장치를 붙일 때
- 사내 고유 토큰·키 형식을 규칙으로 추가해 기본 규칙의 사각지대를 메울 때
- 테스트 픽스처·문서의 더미 값이 계속 잡혀 스캔이 무시되기 시작할 때 (허용 규칙 정비)
- 오픈소스로 공개하기 전 저장소를 정리할 때
- 보안 실사에서 "소스에 비밀값이 없음을 어떻게 확인하는가"를 답해야 할 때

## 이럴 땐 아니다
- 우리 코드의 로직 결함(주입, 인가 누락)을 찾는 일은 `security/semgrep.md`
- 의존 라이브러리·이미지의 알려진 취약점은 `security/trivy.md`, `security/owasp-dependency-check.md`
- 비밀값을 **어떻게 보관할 것인가**(시크릿 매니저, 암호화 저장)는 이 도구의 범위 밖이다 — `security/owasp-cheat-sheet-series.md`
- 유출된 키를 사후에 어떻게 폐기·회전할지의 절차는 도구가 아니라 `security/nist-secure-software-development-framework.md` (RV 그룹)
- 산출물 서명·출처 증명은 `security/sigstore.md`
- 무엇을 비밀로 취급해야 하는지의 분류 기준은 `security/nist-sp-800-53.md`

## 무엇이 들어있나
Go 로 작성된 단일 바이너리이며, git 저장소·디렉터리·표준 입력을 대상으로 규칙 집합을 돌려 탐지 결과를 보고한다. 핵심 구별점은 **커밋 히스토리를 대상으로 삼는다**는 것이다 — 워킹 트리만 보는 도구는 "커밋했다가 지운" 사례를 원리적으로 찾지 못한다.

기본 규칙 집합에 주요 클라우드·SaaS 의 키 형식(AWS, GitHub, Slack, Stripe 계열 등)과 개인키 블록이 들어 있고, 대부분 정규식 + 엔트로피 판정의 조합이다. 여기에 `.gitleaks.toml` 로 **사내 형식을 추가**할 수 있는데, 실제로 이 도구가 유용해지는 지점은 거의 항상 이쪽이다. 우리 게이트웨이 키, 내부 서비스 토큰처럼 공개 규칙이 알 리 없는 형식이 정작 우리에게 가장 위험하다.

**허용 규칙(allowlist)이 이 도구의 성패를 가른다.** 테스트 픽스처의 더미 키, 문서의 예시 토큰, lock 파일의 해시가 계속 잡히면 결과를 아무도 안 보게 되고 그 순간 도구는 없는 것과 같아진다. 설정은 전역 허용과 규칙별 허용 두 층으로 나뉘며, 경로 패턴과 값 패턴 양쪽으로 좁힐 수 있다.

운용은 대개 세 지점에 건다 — 커밋 전 훅(로컬에서 즉시 차단), PR/CI(변경분 검사), 그리고 정기적인 히스토리 전수 스캔. 결과는 SARIF 등으로 내보내 코드 호스팅의 보안 탭에 올릴 수 있다.

**도구가 해 주지 않는 일을 분명히 해 둘 필요가 있다.** 탐지는 시작일 뿐이고, 진짜 대응은 (1) 해당 자격증명을 즉시 폐기·회전하고 (2) 그 키로 무슨 일이 있었는지 로그를 확인하는 것이다. 히스토리에서 커밋을 지우는 작업은 이미 클론된 사본에는 소급되지 않으므로, **유출된 키는 "지웠다"가 아니라 "폐기했다"로만 종결된다.** 순서를 뒤집는 것 — 히스토리 재작성부터 하고 키 회전을 미루는 것 — 이 이 상황에서 가장 흔한 실수다.

## 인용 포인트
- "커밋했다가 바로 지웠다"는 보고에 대해, 히스토리 스캔 결과를 근거로 키 폐기를 요구할 수 있다.
- 비밀값 스캔 도입 제안에서, 로컬 훅만으로는 우회 가능하고 CI 게이트가 함께 필요하다는 논거로 쓴다.
- 스캔 결과가 무시되기 시작할 때, 허용 규칙 정비가 도구 유지의 필수 작업이라는 점을 근거로 시간을 확보한다.
- 사고 대응 절차 문서에서 "탐지 → 폐기 → 로그 확인 → 히스토리 정리" 순서를 못 박을 때.

## 코드 예시

기본 규칙에 사내 키 형식을 더하고, 픽스처·lock 파일의 오탐을 좁혀 결과가 계속 읽히게 만든다.

```toml
# .gitleaks.toml
[extend]
useDefault = true            # 공개 기본 규칙 위에 우리 규칙을 얹는다

[[rules]]
id = "acme-gateway-key"
description = "사내 게이트웨이 API 키"
regex = '''acme_(live|test)_[A-Za-z0-9]{32}'''
tags = ["key", "acme"]
entropy = 3.5

  # 규칙별 예외: 문서·테스트에 쓰는 0 으로 채운 더미 값만 제외
  [rules.allowlist]
  regexes = ['''acme_test_0{32}''']
  paths = ['''(^|/)fixtures/''']

# 전역 예외: 값이 아니라 해시가 들어 있는 파일들
[allowlist]
description = "저장소 전역 예외"
paths = [
  '''(^|/)package-lock\.json$''',
  '''(^|/)go\.sum$''',
]
```

이 코드가 감추는 것: 정규식과 엔트로피로 잡는 방식은 형식이 정해진 키에만 잘 듣는다. 무작위 문자열로 발급되는 내부 비밀번호나 base64 로 감싼 설정값은 이 규칙들을 조용히 빠져나가므로, 스캔이 초록불이라는 사실은 "우리가 아는 형식의 키가 없다"까지만 의미한다.
