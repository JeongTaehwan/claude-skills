# Threat Modeling — Designing for Security (Adam Shostack)

https://shostack.org/books/threat-modeling-book

## 한 줄
위협 모델링을 "보안 전문가의 감각"이 아니라 **아무나 따라 할 수 있는 절차와 도구 세트**로 분해한 책 — 네 가지 질문, 요소 종류별로 물어야 할 STRIDE 범주, 카드 게임까지, 빈 화면 앞에서 막히는 문제를 없애는 데 지면 대부분을 쓴다.

## 페르소나
**위협 모델링 회의를 몇 번 열어 봤지만 매번 각자 아는 취약점을 떠올리다 끝났고, 결과물이 다음 스프린트에 아무 영향을 주지 못한 팀의 리드.** OWASP 개요 문서로 "네 가지 질문"과 STRIDE 는 알게 됐는데, 정작 회의에서 "그래서 이 데이터 저장소에 대해 무엇을 물어야 하죠"에 답할 수 있는 사람이 없다. 절차를 워크숍 진행 대본 수준까지 내려서 가진 자료가 필요하다.

## 이럴 때 연다
- 위협 모델링을 팀의 정기 활동으로 정착시키는 방법을 설계할 때 (한 번의 워크숍이 아니라 반복 가능한 절차로)
- 회의 진행자가 되어 무엇을 어떤 순서로 물을지 대본을 만들어야 할 때
- STRIDE 를 실제로 적용하다 "이 요소에 여섯 범주를 다 대야 하나"에서 막혔을 때
- 도출된 위협을 완화·제거·이전·수용 중 무엇으로 처리할지 판단 기준이 필요할 때
- 도출된 위협을 요구사항·테스트 케이스로 옮기는 다리를 놓아야 할 때
- 보안 인력 없이 개발팀만으로 위협 모델링을 굴려야 할 때
- 위협 모델링을 처음 배우는 사람에게 교육 자료를 만들어야 할 때

## 이럴 땐 아니다
- 활동의 정의와 네 가지 질문만 빠르게 훑는 것이 목적이면 `security/owasp-threat-modeling.md` 가 훨씬 짧다
- 모델을 그리고 저장·버전 관리할 도구가 필요하면 `security/owasp-threat-dragon.md`
- 도출된 위협을 통과/실패 판정 가능한 요구사항으로 옮기는 표준은 `security/owasp-asvs.md`
- 개별 위협의 구체적 방어 구현은 `security/owasp-cheat-sheet-series.md`
- 이미 알려진 위험 목록을 빠르게 대조하는 것이 목적이면 `security/owasp-top-10.md`
- 침입 이후 공격자 행동의 분류가 필요하면 `security/mitre-attack.md`
- 조직 차원의 보안 개발 프로세스 설계는 `security/nist-secure-software-development-framework.md`, `security/owasp-samm.md`

## 무엇이 들어있나
책 전체가 **네 가지 질문** — 무엇을 만들고 있는가 / 무엇이 잘못될 수 있는가 / 그에 대해 무엇을 할 것인가 / 잘했는가 — 을 축으로 배열되고, 각 질문마다 쓸 수 있는 기법이 병렬로 제시된다. 저자의 표현대로 이 책의 구성은 "하나의 방법론"이 아니라 **조합 가능한 블록의 모음**이다. 그래서 우리 팀 상황에 맞는 최소 조합을 고르는 식으로 읽는 것이 의도된 사용법이다.

첫 질문에 대한 답은 **데이터 흐름도(DFD)** 다. 프로세스, 데이터 저장소, 외부 엔티티, 데이터 흐름, 그리고 신뢰 경계. 책은 이 그림을 예쁘게 그리는 것보다 **신뢰 경계를 어디에 긋느냐**가 결과를 좌우한다고 반복한다 — 경계를 넘는 지점이 곧 위협이 몰리는 지점이기 때문이다.

두 번째 질문에서 이 책의 가장 실용적인 기여가 나온다. STRIDE 여섯 범주를 아무 데나 대는 대신, **요소 종류마다 물어야 할 범주가 다르다**는 정리(STRIDE-per-element)를 제시한다. 외부 엔티티에는 Spoofing 과 Repudiation 을, 데이터 흐름과 데이터 저장소에는 Tampering·Information Disclosure·Denial of Service 를, 프로세스에는 여섯 범주 전부를 댄다. 이 표 하나가 "무엇을 물어야 할지 모르겠다"를 "이 칸을 채우면 된다"로 바꾼다. 요소 하나가 아니라 요소 사이의 상호작용에 STRIDE 를 대는 변형(STRIDE-per-interaction)과 공격 트리도 함께 다룬다.

**Elevation of Privilege 카드 게임**은 이 책에서 나온 유명한 도구다. STRIDE 범주가 카드 슈트로 되어 있고 각 카드에 구체적 위협 문장이 적혀 있어, 참가자가 자기 카드에 해당하는 위협을 우리 시스템에서 찾아 말한다. 보안 지식이 없는 팀원도 참여할 수 있게 만드는 장치이자, 위협 모델링의 진짜 난점이 지식이 아니라 **참여**라는 저자의 관점이 드러나는 부분이다.

세 번째 질문에는 네 가지 처리 방식이 제시된다 — 완화(mitigate), 제거(eliminate), 이전(transfer), 수용(accept). 여기서 중요한 태도가 나온다: **모든 위협을 막아야 하는 것이 아니라 각 위협에 대해 결정을 내리고 그 결정을 기록해야 한다.** "수용"도 정당한 결과이며, 기록되지 않은 수용만이 문제다.

네 번째 질문(잘했는가)에 별도의 지면이 배정되어 있다는 점이 이 책이 다른 자료와 갈리는 지점이다. 모델의 완결성 점검, 각 위협이 실제로 처리됐는지 추적, 그리고 도출된 위협을 요구사항과 테스트로 옮기는 방법까지 다룬다. 위협 모델링이 "회의로 끝나는" 실패 유형을 정면으로 겨냥한 부분이다.

프라이버시 위협(LINDDUN 등), 요구사항 도출, 조직에 정착시키는 방법이 뒤쪽 장에 이어진다. 2014년 책이라 클라우드·컨테이너 사례는 얇지만, 절차와 사고 틀은 그대로 유효하다.

## 인용 포인트
- 위협 모델링 회의가 산으로 갈 때, STRIDE-per-element 표를 그대로 진행 도구로 쓰면 논의가 요소 단위로 닫힌다.
- "위협을 다 막을 수는 없다"는 반론에, 책이 수용을 정당한 처리 방식으로 규정하되 **기록을 요구한다**는 점을 든다.
- 보안 담당자 없이 개발팀이 위협 모델링을 하겠다고 할 때, 카드 게임을 포함한 참여 도구들이 그 목적으로 설계되었다는 점이 근거가 된다.
- 위협 모델이 회의록으로 끝나는 문제를 지적할 때, 네 번째 질문(검증·추적)이 책에서 별도 지면을 차지한다는 사실을 인용한다.
- 신뢰 경계를 그리지 않은 아키텍처 다이어그램을 위협 모델로 제출하려는 시도를 교정할 때.

## 코드 예시

책의 STRIDE-per-element 표를 데이터로 고정하면, 회의 준비물이 "빈 화면"에서 "채울 칸 목록"으로 바뀐다.

```yaml
# threat-models/stride-per-element.yml — 요소 종류마다 물어야 할 범주가 다르다
question_matrix:
  external_entity: [S, R]              # Spoofing, Repudiation
  process:         [S, T, R, I, D, E]  # 프로세스에는 여섯 범주 전부
  data_flow:       [T, I, D]           # Tampering, Info Disclosure, DoS
  data_store:      [T, I, D]           # 로그 저장소라면 R 도 함께 본다

# 다이어그램의 각 요소를 종류만 적어 두면 물어야 할 칸이 정해진다
elements:
  - { name: PG 사업자,          type: external_entity, boundary: 외부 }
  - { name: 결제 웹훅 수신기,    type: process,         boundary: 내부 }
  - { name: 주문 DB,            type: data_store,      boundary: 내부 }
  - { name: 앱 → 주문 API,      type: data_flow,       boundary: 인터넷 → 게이트웨이 }

# 세 번째 질문의 답은 네 가지 중 하나여야 하고, 무엇이든 기록된다
allowed_decisions: [mitigate, eliminate, transfer, accept]
require_rationale_for: [accept, transfer]
```

이 코드가 감추는 것: 이 표는 **다이어그램에 그려진 요소**에 대해서만 질문을 만들어 준다. 그리지 않은 관리자 백오피스나 배치 잡은 칸이 생기지 않아 조용히 빠지고, 그래서 첫 번째 질문("무엇을 만들고 있는가")에 쓰는 시간이 결국 결과의 상한을 정한다.
