# Heuristic Test Strategy Model (James Bach)

https://www.satisfice.com/download/heuristic-test-strategy-model

## 한 줄
"무엇을 테스트할지"를 빠짐없이 떠올리기 위한 가이드워드 목록 — 프로젝트 환경·제품 요소·품질 기준·테스트 기법 네 축의 단어들을 훑으며 자기 상황에 맞는 전략을 스스로 만들게 하는 사고 도구 (James Bach, 현재 v6.3, 무료 PDF).

## 페르소나
**테스트 계획서를 백지에서 시작해야 하는데 무엇부터 적을지 모르는 사람.** 기능 목록을 그대로 옮겨 적은 테스트 케이스는 만들 수 있지만, 성능·보안·데이터 마이그레이션·운영 시나리오처럼 기능 목록에 없는 축을 통째로 빠뜨린다는 자각이 있다. 표준 문서(29119, ISTQB)는 형식은 알려주지만 "이번 프로젝트에서 실제로 무엇이 위험한가"는 알려주지 않는다. 필요한 건 채울 양식이 아니라, 누락을 잡아내는 질문 목록이다.

## 이럴 때 연다
- 테스트 계획·전략 문서를 처음부터 써야 하는데 항목 목록이 없을 때
- 릴리스 직전 "우리가 뭘 안 봤지"를 체계적으로 훑고 싶을 때
- 기능 케이스 위주 테스트에서 벗어나 품질 기준(성능·보안·호환성·운용성)을 축으로 커버리지를 점검할 때
- 탐색적 테스트 세션의 차터(charter)를 뽑을 소재가 필요할 때
- 결제 게이트웨이 교체, 정산 로직 변경처럼 영향 범위가 기능 목록으로 안 잡히는 변경을 앞뒀을 때

## 이럴 땐 아니다
- 문서 형식·산출물 명칭 등 표준 준수가 요구되는 상황이면 `qa/iso-iec-ieee-29119.md`
- 용어와 기법을 체계적으로 학습하려는 목적이면 `qa/istqb-foundation-level.md`
- 이 모델을 실제 테스트 수행 방법론으로 확장한 본편은 `qa/rapid-software-testing.md`
- 왜 표준화된 절차보다 맥락이 우선인지의 사상적 배경은 `qa/context-driven-testing.md`

## 무엇이 들어있나
문서 자체가 "따라 하면 되는 절차"가 아니라 **가이드워드(guideword) 모음**이라는 점이 핵심이다. 저자의 표현대로 이것은 더 잘 생각하도록 돕는 장치이지 채워 넣을 템플릿이 아니며, 각 팀이 자기 버전으로 잘라 쓰는 것을 전제로 한다.

네 축은 프로젝트 환경(사람·일정·장비·정보 등 제약), 제품 요소(구조·기능·데이터·인터페이스·플랫폼·운영·시간 — SFDIPOT), 품질 기준(기능성·신뢰성·사용성·보안·성능·확장성 등), 테스트 기법(기능 테스트, 흐름 테스트, 도메인 테스트, 스트레스 테스트, 시나리오 테스트 등)이다. 전략은 이 축들을 교차시켜 도출한다 — 제품 요소 × 품질 기준으로 위험을 뽑고, 거기에 기법을 붙이는 식.

분량은 몇 쪽짜리 PDF다. 읽는 데 걸리는 시간보다 회의 테이블에 올려놓고 훑는 데 쓰는 시간이 훨씬 길어지는 종류의 자료다.

## 인용 포인트
- "테스트 전략은 문서가 아니라 사고의 결과물이며, 이 모델은 템플릿이 아니라 가이드워드다" — 테스트 계획서를 양식 채우기로 만들려는 압력에 대한 반론.
- 제품 요소를 구조·기능·데이터·인터페이스·플랫폼·운영·시간으로 나누는 SFDIPOT은, 기능 목록만 훑던 테스트 범위 논의에 데이터·플랫폼·시간 축을 추가하는 근거로 바로 쓸 수 있다.
