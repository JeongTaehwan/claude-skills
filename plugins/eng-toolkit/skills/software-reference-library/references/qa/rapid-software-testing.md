# Rapid Software Testing (James Bach)

https://www.satisfice.com/rapid-testing-methodology

## 한 줄
테스트 케이스 문서가 아니라 **테스터의 사고 과정**을 방법론의 중심에 두는 접근으로, 탐색적 테스트를 "즉흥적 클릭"이 아니라 관리·보고 가능한 활동으로 만든 세션 기반 테스트 관리(SBTM)의 출처.

## 페르소나
**탐색적 테스트를 하고는 있는데 팀장에게 진척을 설명할 수 없어 곤란한 QA.** "몇 개 케이스 중 몇 개 통과"라는 숫자가 없으니 관리 쪽에서는 놀고 있는 것처럼 보이고, 그렇다고 사전 작성 케이스로 돌아가면 정작 중요한 버그는 케이스 밖에서 나온다. 탐색적 테스트에 시간을 배분하고, 무엇을 얼마나 봤는지 남기고, 커버리지를 말로 설명할 수 있는 틀이 필요하다.

## 이럴 때 연다
- 탐색적 테스트를 타임박스와 차터(charter)로 쪼개 관리 가능한 형태로 만들 때
- "테스트 케이스 몇 건" 대신 무엇을 근거로 릴리스 판단을 했는지 설명해야 할 때
- 회귀 케이스만 반복 실행하는데 프로덕션에서 계속 버그가 나오는 상황을 뒤집으려 할 때
- 결제·쿠폰처럼 조합이 폭발해서 케이스를 다 적는 것이 애초에 불가능한 영역의 테스트 전략을 짤 때

## 이럴 땐 아니다
- 사고법이 아니라 **테스트 대상의 어떤 측면을 볼지**에 대한 체크리스트가 필요하면 같은 저자의 `qa/heuristic-test-strategy-model.md` 가 직접적이다.
- 문서화된 프로세스와 산출물 양식이 요구되는 규제 대응 상황이라면 이 방법론은 정반대 방향이다 — `qa/iso-iec-ieee-29119.md`.
- 테스트 자동화 스위트의 구조를 정하는 문제라면 `qa/testpyramid.md` / `qa/the-practical-test-pyramid.md`.

## 무엇이 들어있나
RST는 "테스팅은 제품에 대해 배우기 위한 탐구이며, 그 질은 테스터의 기량에 달려 있다"는 전제에서 출발한다. 그래서 방법론의 산출물은 상세 테스트 케이스가 아니라 **차터(무엇을 어떤 목적으로 탐색할지 한두 줄), 세션(보통 90분 안팎의 타임박스), 세션 리포트(무엇을 봤고 무엇을 발견했으며 무엇이 막았는가)** 다. 이것이 SBTM이고, 여기서 "테스트 커버리지"는 케이스 소진율이 아니라 탐색한 영역의 서술로 표현된다.

통념과 어긋나는 지점이 분명하다. 사전 작성된 스크립트 테스트는 대체로 낭비이며, 테스터가 실행 중에 판단을 바꿀 수 없게 만들어 오히려 결함 발견을 방해한다고 본다. 또한 "테스팅(testing)"과 "체킹(checking)"을 구분해 — 자동화가 잘하는 것은 이미 아는 기대값을 반복 확인하는 체킹이고, 사람이 하는 것은 새로운 문제를 찾는 테스팅이라고 정의한다(이 구분은 Michael Bolton과 공동으로 정교화했다).

사이트에는 RST 방법론 개요와 함께 무료 자료(가이드, 슬라이드, 차터 템플릿류)와 유료 교육 과정 안내가 함께 있다.

## 인용 포인트
- "testing vs checking" 구분은, 자동화 커버리지를 올렸는데 왜 여전히 사람이 봐야 하냐는 질문에 대한 가장 깔끔한 답이다.
- 세션 리포트 형식(차터 / 소요 시간 / 테스트 설계·조사·셋업 비율 / 발견 / 이슈)은 그대로 사내 템플릿으로 옮겨 쓸 수 있다.
