# Context-Driven Testing 원칙

https://context-driven-testing.com/

## 한 줄
"베스트 프랙티스는 없다, 맥락 속의 좋은 프랙티스가 있을 뿐이다"라는 일곱 개 원칙을 선언한 한 페이지짜리 문서로, 표준화된 테스트 프로세스에 반대하는 학파의 강령이다.

## 페르소나
**"업계 표준이니까 이렇게 해야 한다"는 논리로 테스트 프로세스가 위에서 내려오는 상황에 놓인 QA 리드나 테크리드.** 팀 규모도 릴리스 주기도 다른데 옆 조직과 똑같은 테스트 계획서 양식, 똑같은 커버리지 목표, 똑같은 단계 게이트를 요구받는다. 거부감은 명확한데 반박의 언어가 없어서 매번 "저희는 좀 다릅니다" 수준에서 대화가 끝난다. 이 문서는 그 반박에 이름과 출처를 붙여 준다.

## 이럴 때 연다
- 조직 차원의 획일적 테스트 프로세스·문서 양식 도입에 반대 의견을 낼 때
- 테스트 전략 문서 서두에 "왜 우리 맥락에 맞춰 설계했는가"의 근거를 붙일 때
- 탐색적 테스트나 RST 계열 방법론이 어떤 전제 위에 서 있는지 확인할 때
- 커버리지 목표·테스트 케이스 수 같은 숫자 목표가 지표로 굳어지려 할 때

## 이럴 땐 아니다
- 반대로 공통 용어와 프로세스 정의가 실제로 필요한 상황(감사 대응, 계약 요건)이라면 이 문서는 도움이 안 된다 → `qa/iso-iec-ieee-29119.md`, `qa/istqb-foundation-level.md`
- 원칙이 아니라 실제로 테스트를 어떻게 수행할지 절차가 필요하면 → `qa/rapid-software-testing.md`
- 무엇을 테스트할지 훑는 체크리스트가 필요하면 → `qa/heuristic-test-strategy-model.md`
- 학파의 논지를 저자 개인의 글로 더 깊게 읽고 싶으면 → `qa/satisfice-james-bach.md`, `qa/developsense-michael-bolton.md`

## 무엇이 들어있나
분량은 매우 짧다. 핵심은 일곱 개 원칙이고, 그중 세 개가 이 학파의 성격을 결정한다. "어떤 프랙티스의 가치는 그 맥락에 달려 있다", "맥락 속의 좋은 프랙티스는 있어도 베스트 프랙티스는 없다", "함께 일하는 사람들이 프로젝트 맥락에서 가장 중요한 부분이다".
나머지 원칙은 프로젝트가 예측 불가능하게 전개된다는 점, 제품은 문제의 해결책이며 문제가 안 풀리면 동작하는 게 아니라는 점, 좋은 테스트는 도전적인 지적 활동이라는 점, 그리고 프로젝트 전 기간에 걸친 판단과 기량을 통해서만 옳은 일을 옳은 때에 할 수 있다는 점을 말한다.
배경에는 Cem Kaner, James Bach, Bret Pettichord의 *Lessons Learned in Software Testing*이 있고, 사이트는 이 학파가 소프트웨어 개발을 창의적이고 복잡한 인간 활동으로 보며 심리학·경제학·사회과학에서 지식을 끌어온다고 밝힌다.

## 인용 포인트
- "There are good practices in context, but there are no best practices." — 획일적 프로세스 요구에 대한 표준 반론으로 그대로 인용 가능하다.
- 원칙 3(사람이 맥락의 가장 중요한 부분)은 테스트 자동화만으로 품질을 보장하겠다는 계획에 대한 반론 근거가 된다.
