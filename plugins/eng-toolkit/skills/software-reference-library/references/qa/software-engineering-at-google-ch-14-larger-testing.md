# Software Engineering at Google — Ch.14 Larger Testing

https://abseil.io/resources/swe-book/html/ch14.html

## 한 줄
단위 테스트가 구조적으로 못 잡는 것(설정 오류, 낡은 목, 부하 특성, 예상 못 한 입력, 창발적 동작)을 먼저 규정한 다음, 큰 범위 테스트를 충실도(fidelity)와 유지비의 트레이드오프로 설계하는 방법과 그 종류를 정리한 장.

## 페르소나
**E2E 스위트가 30분씩 걸리고 아무 이유 없이 빨개져서, 실패해도 아무도 놀라지 않게 된 상태를 맡은 사람.** 재실행하면 통과하는 테스트가 쌓이면서 CI 신호 자체가 무의미해졌고, 그렇다고 지우자니 이 계층이 잡아 주던 문제(배포 설정, 서비스 간 계약)를 대신할 것이 없다. 필요한 건 E2E를 늘릴지 줄일지의 이분법이 아니라, 각 큰 테스트가 **어떤 위험을 대가로 얼마의 비용을 쓰는지** 따지는 틀이다.

## 이럴 때 연다
- E2E/통합 스위트가 느리고 불안정해져 신뢰를 잃었을 때
- 큰 테스트를 어디까지 유지하고 어디부터 걷어낼지 근거가 필요할 때
- 스테이징 공유 환경 대 격리 환경(테스트 전용 인스턴스) 중 무엇을 쓸지 정할 때
- 테스트 데이터(시드 데이터, 프로덕션 복사본)를 어떻게 조달할지 설계할 때
- 프로덕션 모니터링(prober)·카나리 분석을 테스트 전략의 일부로 편입하려 할 때
- 배포 설정 변경 때문에 장애가 반복되는데 단위 테스트로는 안 잡힐 때

## 이럴 땐 아니다
- 테스트 계층 비중 자체를 어떻게 잡을지의 논쟁은 `qa/testpyramid.md`, `qa/the-practical-test-pyramid.md`
- 마이크로서비스 환경에서 계층을 나누는 구체적 설계는 `qa/testing-strategies-in-a-microservice-architecture.md`
- 불안정한 테스트를 실제로 제거하는 기법이 급하면 `testing/eradicating-non-determinism-in-tests.md`, 실증 데이터는 `testing/an-empirical-analysis-of-flaky-tests.md`
- 서비스 간 계약 검증을 E2E 대신 값싸게 하려면 `testing/pact.md`
- 장애 주입을 실제로 돌리는 도구·원칙은 `testing/principles-of-chaos-engineering.md`, `testing/chaos-monkey.md`
- 부하 테스트 도구가 필요하면 `testing/k6-io-docs.md`, `testing/gatling.md`

## 무엇이 들어있나
출발점은 "왜 큰 테스트가 필요한가"에 대한 구체적 목록이다 — 목이 실제 구현과 어긋나 낡아버린 경우, **설정(configuration) 변경**(구글에서 대형 장애의 가장 잦은 원인으로 지목된다), 고부하에서만 드러나는 동작, 명세에 없지만 사용자가 의존하게 된 동작(Hyrum's Law), 그리고 실제 의존성과 네트워크가 만들어 내는 창발적 성질. 이것들은 단위 테스트를 아무리 늘려도 안 잡힌다.

핵심 설계 축은 **충실도와 밀폐성(hermeticity)의 상충**이다. SUT(테스트 대상 시스템)를 단일 프로세스에 다 넣으면 안정적이지만 실제 토폴로지를 반영하지 못하고, 여러 머신에 펼치면 현실에 가까워지지만 불안정해진다. 공유 스테이징은 싸지만 위험이 크다. 어느 지점을 고를지는 무슨 위험을 사려는지에 달려 있다는 것.

테스트 종류도 넓게 잡는다. 구 버전과 신 버전의 응답을 비교하는 A/B diff 테스트(구글에서 2001년부터 가장 흔히 쓰인 방식), 프로덕션에서 도는 prober와 카나리 분석, 장애 주입(Catzilla, 연례 DiRT 훈련), 그리고 자동화로 대체할 수 없는 **탐색적 테스트**까지 테스트 전략의 일부로 포함시킨다.

운영 지침도 실용적이다. 큰 테스트는 **소유자가 명시돼야 하고**(주인 없는 테스트는 썩는다), 불안정성은 범위 축소·sleep 대신 이벤트 기반 대기·조정 가능한 타임아웃·요청 ID로 로그 상관관계 추적으로 줄인다.

## 인용 포인트
- "설정 변경이 대형 장애의 가장 잦은 원인인데, 단위 테스트는 배포 설정과 바이너리의 호환성을 검증할 수 없다" — E2E/통합 계층을 유지해야 하는 이유를 비용 논의에서 위험 논의로 옮길 때.
- "소유자가 지정되지 않은 큰 테스트는 썩는다" — 불안정한 스위트를 정리할 때 삭제·인수인계 결정을 강제하는 근거.
- prober와 카나리 분석을 테스트의 한 종류로 명시한 점은, 모니터링 예산을 테스트 전략 안에서 정당화할 때 쓸 수 있다.
