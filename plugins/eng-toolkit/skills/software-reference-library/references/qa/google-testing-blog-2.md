# Google Testing Blog

https://testing.googleblog.com/

## 한 줄
같은 블로그를 **테스트 정책의 근거 창고**로 쓰는 항목 — 테스트 크기 분류(Small/Medium/Large), 플레이키 테스트 대응, 코드 커버리지를 어떻게 다룰지에 대한 구글의 글들이 여기 모여 있다.

## 페르소나
**"커버리지 80% 넘기자" 같은 목표를 위에서 받았거나 반대로 제안해야 하는데, 그 숫자가 무엇을 보장하는지 설명 못 하는 리드.** 목표를 걸면 의미 없는 테스트가 늘어난다는 감은 있지만 반대 근거가 개인 경험뿐이다. 플레이키 테스트를 재실행으로 넘기는 관행도 마찬가지 — 다들 문제라고 하면서 아무도 정책으로 정리하지 않았다. 필요한 건 팀 규칙 문서에 각주로 달 수 있는 **큰 조직의 실제 운영 기록**이다.

## 이럴 때 연다
- 테스트 정책(커버리지 기준, 플레이키 테스트 처리, 테스트 분류)을 문서로 정할 때
- 커버리지 목표치 강제에 찬성하거나 반대할 근거가 필요할 때
- 재실행으로 덮고 있는 불안정 테스트를 정책적으로 다루기 시작할 때
- CI 파이프라인을 테스트 크기별로 나누는 기준을 세울 때
- QA 조직의 역할을 "검증 수행"에서 "정책 수립"으로 옮기는 논의에 사례가 필요할 때

## 이럴 땐 아니다
- 개발자 개인의 테스트 설계 조언을 찾는 맥락이면 `qa/google-testing-blog.md`
- 커버리지와 테스트 효과의 상관관계를 실증 연구로 따지려면 `testing/coverage-is-not-strongly-correlated-with-test-suite-effectiv.md`, 대안 지표는 `testing/state-of-mutation-testing-at-google.md`
- 플레이키 테스트를 실제로 제거하는 기법은 `testing/eradicating-non-determinism-in-tests.md`, 규모 있는 실측 데이터는 `testing/an-empirical-analysis-of-flaky-tests.md`
- 테스트 크기 분류의 정리된 서술은 블로그보다 `qa/software-engineering-at-google-ch-11-testing-overview.md`

## 무엇이 들어있나
정책을 세울 때 실제로 쓰이는 글은 대체로 세 묶음이다. **테스트 크기 분류** — 단위/통합/E2E 같은 해석이 갈리는 용어 대신 그 테스트가 쓸 수 있는 자원(프로세스, 머신, 네트워크)으로 나누는 방식. **플레이키 테스트** — 대규모 CI에서 불안정 테스트가 신호를 어떻게 오염시키는지, 재실행·격리(quarantine)·모니터링을 어떻게 조합하는지. **코드 커버리지** — 커버리지를 어디까지 신뢰할지, 숫자 자체를 목표로 삼을 때 생기는 부작용.

주의할 점은 이 블로그가 커버리지를 무용하다고 말하지 않는다는 것이다. 구글은 커버리지를 측정하고 활용하며, 경계하는 대상은 **측정값을 목표로 전환하는 것**과 낮은 수준의 커버리지 지표(라인 커버리지)를 품질의 대리 지표로 착각하는 것이다. "커버리지 목표를 정하지 말라"는 식의 단정으로 인용하면 과장이 된다.

## 인용 포인트
- 테스트를 자원 기준(크기)으로 분류하는 방식은, 팀 CI를 "빠른 스위트 / 느린 스위트"로 나누는 규칙의 근거로 그대로 옮길 수 있다.
- 플레이키 테스트를 개인의 부주의가 아니라 CI 신호 품질의 문제로 다루는 프레임 — 격리·추적 정책을 제안할 때의 출발점.
