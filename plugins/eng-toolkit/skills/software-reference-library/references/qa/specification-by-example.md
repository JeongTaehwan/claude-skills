# Specification by Example (Gojko Adzic)

https://gojko.net/books/specification-by-example/

## 한 줄
50개 넘는 프로젝트 팀을 인터뷰해서, 구체적 예시로 요구사항을 합의하고 그 예시를 자동화해 "살아있는 문서(living documentation)"로 유지하는 과정이 실제로 어떻게 굴러갔는지 정리한 책 (Gojko Adzic).

## 페르소나
**명세 문서, 테스트 케이스, 실제 코드가 각각 다른 진실을 말하고 있는 팀의 리드.** Confluence의 기획서는 6개월 전에 멈춰 있고, QA의 테스트 케이스 시트는 따로 관리되며, 진짜 동작은 코드를 읽어야만 알 수 있다. BDD를 도입해 봤지만 Gherkin 파일이 늘어나기만 하고 아무도 안 읽는 상태가 됐거나, 도입 전에 그렇게 될까 봐 망설이는 중이다. 필요한 건 문법이 아니라 이 방식이 실패하는 지점과 성공한 팀이 무엇을 다르게 했는지에 대한 사례다.

## 이럴 때 연다
- BDD/ATDD 도입을 제안하거나, 도입했다가 정체된 이유를 진단할 때
- 기획서·테스트·코드가 따로 노는 문제를 프로세스 차원에서 손보려 할 때
- 인수 조건을 자동화된 테스트로 옮기는 팀 규칙을 설계할 때
- "문서는 어차피 낡는다"는 체념에 반박할 실증 사례가 필요할 때
- 정산·수수료 규칙처럼 표로 표현되는 도메인 규칙을 명세이자 테스트로 만들고 싶을 때

## 이럴 땐 아니다
- 회의 한 번을 어떻게 진행할지가 문제라면 `qa/example-mapping.md`
- Gherkin 문법과 실행 도구가 필요하면 `qa/cucumber-bdd.md`
- 코드 레벨에서 테스트를 어떤 단위로 쓸지의 문제라면 `qa/software-engineering-at-google-ch-12-unit-testing.md`

## 무엇이 들어있나
저자는 방법론을 발명해서 제시하지 않고, 이미 이렇게 일하고 있던 팀들을 찾아가 공통 패턴을 뽑아냈다. 그래서 책의 무게중심은 "이렇게 하라"보다 **"이렇게 하다가 이런 데서 넘어졌다"** 쪽에 있다.

주요 프로세스 패턴은 범위를 기능이 아니라 비즈니스 목표에서 도출하기, 협업으로 명세하기, 예시를 정제해 핵심만 남기기, 예시를 자동화하되 스크립트가 아니라 명세로 유지하기, 그리고 그것을 살아있는 문서로 진화시키기다.

중요한 반직관은 **도구가 아니라 대화가 산출물**이라는 주장이다. 자동화된 예시는 대화의 부산물이며, 대화 없이 도구부터 도입한 팀에서 테스트 자동화 부채만 쌓였다는 사례가 반복해서 등장한다. 또 하나는 예시를 많이 만드는 게 아니라 **줄이는(refining)** 단계가 성패를 갈랐다는 점이다.

## 인용 포인트
- 50개 이상의 실제 프로젝트 사례에 기반했다는 점 자체가, BDD 도입 제안에서 "이론일 뿐"이라는 반론을 막는 근거가 된다.
- "자동화된 예시는 목적이 아니라 대화의 부산물" — Gherkin 파일 수를 성과 지표로 삼으려는 시도를 되돌릴 때.
- "살아있는 문서" 개념은, 기획 문서를 따로 갱신하는 비용 대신 테스트가 문서 역할을 하게 만드는 제안의 표준 용어로 쓸 수 있다.
