# Google Testing Blog

https://testing.googleblog.com/

## 한 줄
구글 엔지니어들이 테스트에 대해 쓴 글이 2007년부터 쌓여 있는 공식 블로그 — QA 채널이지만 실제로는 개발자가 테스트 설계 논쟁에서 근거로 가장 자주 인용하는 출처다.

## 페르소나
**"이건 단위 테스트로 해야 하나 통합으로 해야 하나" 같은 논쟁이 팀 안에서 취향 싸움으로 끝나는 상황에 있는 개발자.** 각자 경험담은 있는데 공통의 기준점이 없어서, 리뷰마다 같은 논쟁이 반복된다. 책 한 권을 읽자고 하기엔 무겁고, 블로그 글 한두 개면 팀 논의를 정리할 수 있는 상황이다. 필요한 건 방법론 전체가 아니라 **인용 가능한 짧은 글**이다.

## 이럴 때 연다
- 테스트 계층·범위 논쟁에 팀 공통의 참조점이 필요할 때
- 특정 주제(플레이키 테스트, 테스트 크기, 커버리지, 목 사용)에 대한 짧고 인용 가능한 글을 찾을 때
- 사내 테스트 가이드나 코드 리뷰 기준 문서를 쓰면서 근거 링크를 붙일 때
- 큰 조직이 실제로 어떻게 굴리는지 사례가 필요할 때

## 이럴 땐 아니다
- 같은 블로그를 QA 정책·커버리지 논쟁의 출처로 쓰려는 맥락이면 `qa/google-testing-blog-2.md`
- 정리된 체계로 한 번에 읽고 싶으면 블로그보다 책 쪽 — `qa/software-engineering-at-google-ch-11-testing-overview.md` 이하 장들
- 도구 사용법이 필요한 것이라면 `testing/` 도메인의 해당 도구 문서

## 무엇이 들어있나
글의 성격이 두 갈래다. 하나는 구글 내부 실천의 공개 — Testing on the Toilet 시리즈, 테스트 크기 분류, 대규모 CI 운영 경험처럼 조직 차원에서만 나올 수 있는 이야기. 다른 하나는 개별 엔지니어의 설계 의견 — 무엇을 목으로 대체할지, 테스트 이름을 어떻게 지을지 같은 코드 레벨 조언.

블로그이므로 시점이 섞여 있다는 점은 감안해야 한다. 같은 주제(예: 모킹)에 대해 연도별로 논조가 달라지며, 오래된 글이 현재 구글의 입장이라는 보장은 없다. 책(Software Engineering at Google)이 나온 이후로는 정리된 결론은 책에, 개별 사례와 후속 논의는 블로그에 남는 구도에 가깝다.

## 인용 포인트
- 사내 테스트 가이드를 쓸 때, 특정 규칙에 대한 외부 근거 링크로 붙이기 좋은 형태(짧고 주제 단위)다.
- 조직 규모에서 검증됐다는 사실 자체가 "우리 팀엔 과하다/부족하다" 논쟁의 기준선이 된다.
