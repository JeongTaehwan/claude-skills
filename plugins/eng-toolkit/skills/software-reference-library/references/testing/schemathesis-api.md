# Schemathesis — API 속성 기반 테스트

https://schemathesis.readthedocs.io/

## 한 줄
OpenAPI(2.0~3.2)나 GraphQL 스키마를 읽어서 **테스트 케이스 자체를 생성**하는 도구. 엔드포인트별로 테스트를 쓰는 대신 스키마 URL 하나를 주면 경계값·잘못된 타입·누락 필드를 만들어 실제 서버에 던지고, 실패를 재현 가능한 curl 명령으로 돌려준다.

## 페르소나
**API 테스트가 "행복 경로 + 생각난 몇 가지"에 머물러 있는 백엔드 엔지니어.** 엔드포인트가 수십 개인데 각각에 이상 입력 테스트를 손으로 쓸 시간은 없고, 정작 장애는 스펙에 없는 입력이 들어와 500을 뱉는 데서 난다. 스펙 문서는 있는데 그 스펙이 실제로 지켜지는지 검증할 수단이 없는 상태다.

## 이럴 때 연다
- OpenAPI 스펙은 있는데 구현이 그 스펙을 실제로 따르는지 확인해 본 적이 없을 때
- 주문/쿠폰 API에서 예상 못 한 입력에 500이 나는지 CI에서 자동으로 훑고 싶을 때
- 엔드포인트마다 이상 케이스 테스트를 쓰는 비용이 감당 안 될 때
- 속성 기반 테스트를 도입하고 싶은데 도메인 생성기를 처음부터 쓸 여력이 없을 때(스키마가 곧 생성기가 된다)

## 이럴 땐 아니다
- 케이스를 사람이 정확히 지정해서 응답을 단언해야 하는 회귀 테스트라면 `testing/rest-assured-api.md`(Java) 또는 `testing/postman.md`
- 소비자와 제공자 사이 계약의 합의 자체가 문제라면 `testing/pact.md`
- 속성 기반 테스트를 도메인 로직(금액 계산 등)에 적용하려는 것이면 `testing/hypothesis.md` / `testing/fast-check.md`, 배경은 `testing/quickcheck-a-lightweight-tool-for-random-testing-of-haskell.md`
- 보안 취약점 스캔이 목적이라면 `testing/owasp-zap.md`

## 무엇이 들어있나
핵심 주장은 "스키마가 이미 테스트 명세다"라는 것이다. 타입·필수 여부·형식·범위가 스키마에 적혀 있으므로 유효 입력과 무효 입력을 모두 기계가 만들 수 있고, 사람이 쓸 몫은 케이스가 아니라 예외적으로 필요한 후크뿐이라는 입장이다. 내부적으로 Hypothesis 계열의 속성 기반 생성과 축소를 쓴다.

문서는 CLI(`uvx schemathesis run <schema-url>`), pytest 통합, GitHub Actions 통합의 세 갈래로 사용법을 나누고, 실패 보고를 curl 재현 명령·JUnit XML·HAR 등으로 뽑는 방법을 다룬다. 응답에서 얻은 실제 값을 이후 요청에 이어 붙이고, 신호가 나오지 않는 오퍼레이션에는 힘을 덜 쓰는 적응적 탐색도 문서가 내세우는 지점이다. 첫 실행에서 5~15개 정도의 문제를 찾는다는 것이 사이트의 표현인데, 이는 벤더 주장이므로 그대로 인용하지 말고 우리 API에 한 번 돌려 본 결과로 말하는 편이 낫다.

## 인용 포인트
- 도입 논거는 "테스트 개수를 늘리자"가 아니라 "이미 있는 스키마를 검증에 재사용하자"로 세우는 것이 통과율이 높다. 스펙 문서 유지 비용을 회수하는 명분이 되기 때문이다.
