# axe-core

https://github.com/dequelabs/axe-core

## 한 줄
Lighthouse·Playwright·Cypress·Storybook 등 대부분의 접근성 검사 기능이 내부에서 공통으로 쓰고 있는 검사 엔진 그 자체 — 규칙(rule) 목록과 각 규칙이 무엇을 어떻게 판정하는지가 코드와 문서로 공개되어 있다.

## 페르소나
**접근성 지적을 받았고 CI에서 자동으로 막고 싶은데, 어디까지 자동으로 잡히는지 몰라 범위를 못 정하는 사람.** 도구를 붙이면 위반 목록이 쏟아지는데 그중 무엇이 진짜 차단 사유이고 무엇이 오탐인지 판단이 안 서거나, 반대로 "자동 검사 통과했으니 접근성 OK"라고 보고했다가 스크린리더 사용자 리포트로 뒤집힌 경험을 한 상태다. 필요한 건 규칙의 근거와 이 엔진이 원리적으로 못 잡는 영역의 경계다.

## 이럴 때 연다
- 접근성 회귀를 CI에서 자동 검출하도록 파이프라인에 붙일 때
- 검출된 위반의 규칙 ID를 근거(WCAG 조항)까지 추적해 설명해야 할 때
- 실패 기준을 조정해야 할 때 — 어떤 규칙 태그를 차단으로 볼지 정하는 단계
- 여러 도구가 서로 다른 결과를 낼 때, 같은 엔진을 쓰는지 버전 차이인지 확인할 때

## 이럴 땐 아니다
- 검사 결과를 사람이 읽고 개선 방향을 잡는 단계라면 도구 리포지토리보다 `testing/deque-axe.md` 쪽 자료가 맞다
- 컴포넌트 단위 시각·상호작용 회귀가 목적이면 `testing/chromatic.md` 또는 `testing/storybook.md`
- 자동으로 안 잡히는 영역(대체 텍스트의 적절성, 포커스 순서의 의미, 스크린리더 흐름)은 결국 사람이 하는 탐색적 테스트의 영역이다

## 무엇이 들어있나
axe-core는 DOM을 순회하며 규칙 집합을 평가하고, 결과를 violations / passes / incomplete / inapplicable로 나눠 돌려준다. 여기서 실무적으로 중요한 것이 **incomplete** 범주다 — 자동으로 판단할 수 없어 사람이 확인해야 하는 항목을 위반과 분리해 내놓는다는 설계 자체가, 이 도구가 자기 한계를 명시적으로 다룬다는 뜻이다.

각 규칙은 WCAG 성공 기준이나 모범 사례에 태그로 연결되어 있어, 위반 하나를 두고 "왜 이게 문제인가"를 조항까지 거슬러 설명할 수 있다. 오탐을 최소화하는 것을 설계 원칙으로 내세우는 점도 특징이라, 검출된 violations는 대체로 그대로 고칠 대상으로 취급해도 된다.

가장 중요한 한계는 저장소가 스스로 밝히는 것이다 — **자동 검사는 접근성 문제의 일부만 잡는다.** 색 대비, 누락된 라벨, 잘못된 ARIA 같은 기계적으로 판정 가능한 것들이 대상이고, 콘텐츠의 의미나 조작 흐름의 실제 사용 가능성은 범위 밖이다. 이 경계를 같이 알리지 않고 "axe 통과"를 품질 근거로 쓰면 그게 곧 사고 지점이 된다.

## 인용 포인트
- incomplete 범주의 존재 자체 — "자동 검사 통과 = 접근성 확보"라는 보고를 되돌릴 때 쓸 수 있는 도구 자신의 근거.
- 여러 상용/오픈소스 도구가 같은 엔진을 공유한다는 점 — 도구 선정 논의를 "무엇을 쓸까"에서 "어떤 규칙 집합을 차단 기준으로 삼을까"로 옮기는 프레임.
