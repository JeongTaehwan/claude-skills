# Chromatic — 시각 회귀 테스트

https://www.chromatic.com/docs/

## 한 줄
Storybook 팀이 만든 UI 테스트 플랫폼의 공식 문서 — 이미 써 둔 story를 그대로 스냅샷 테스트로 바꿔, 브라우저별 픽셀 변경을 PR마다 검토·승인하게 만드는 워크플로우가 핵심이다.

## 페르소나
**공용 컴포넌트를 하나 고쳤는데 어느 화면이 깨졌는지 알 방법이 없는 사람.** 버튼 패딩이나 디자인 토큰을 건드리면 장바구니·주문서·쿠폰 모달까지 영향이 가는데, 확인은 QA가 눈으로 훑는 것뿐이라 릴리스 때마다 불안하다. 스냅샷 테스트를 직접 만들어 봤지만 이미지 diff가 폰트 렌더링 차이로 계속 깨져서 아무도 안 보게 된 경험도 있다. 필요한 건 diff를 내는 기능이 아니라 **변경을 승인·기각하는 절차**다.

## 이럴 때 연다
- 디자인 시스템·공용 컴포넌트 변경의 영향 범위를 PR 단계에서 눈으로 확인하고 싶을 때
- 시각 회귀를 CI 게이트로 만들되, 의도된 변경은 승인으로 통과시키는 흐름이 필요할 때
- 스냅샷 수가 늘어 비용·시간이 문제가 될 때 변경분만 찍는 방법을 찾을 때
- 디자이너·기획자에게 구현된 UI를 링크로 리뷰받는 경로를 만들 때

## 이럴 땐 아니다
- story를 작성하고 컴포넌트를 격리 개발하는 단계 자체가 먼저면 `testing/storybook.md`
- 접근성 위반의 자동 검출만 필요하면 `testing/axe-core.md`
- 사용자 흐름(로그인 → 장바구니 → 결제)을 끝까지 검증하는 것이 목적이면 `testing/playwright.md`

## 무엇이 들어있나
문서는 Visual Tests / Accessibility Tests / Interaction Tests 세 갈래를 축으로 하고, 운영 쪽으로 CI, Configuration, Snapshot 장이 따로 있다. 전제는 **story가 곧 테스트 케이스**라는 것 — 컴포넌트를 격리해서 상태별로 렌더링해 둔 story가 이미 있으면, 별도 테스트 코드 없이 그 상태들이 스냅샷 대상이 된다. 새 테스트를 쓰는 비용이 아니라 이미 있는 자산을 재사용하는 구조라서 도입 장벽이 낮다.

핵심 워크플로우는 베이스라인과 승인이다. 커밋을 푸시하면 브라우저별로 스냅샷을 찍고 이전 베이스라인과 비교해 변경을 목록으로 보여준다. 사람이 각 변경을 승인하면 그것이 새 베이스라인이 되고, 기각하면 회귀로 처리된다. 즉 이 도구가 판정하는 것은 "옳다/틀리다"가 아니라 **"바뀌었다"**이고, 옳고 그름의 판단은 리뷰 절차로 넘긴다. 직접 만든 이미지 diff가 실패하는 지점이 대개 여기다.

TurboSnap은 Git 히스토리와 번들러 의존성 그래프를 분석해 변경의 영향을 받는 컴포넌트만 스냅샷하는 기능으로, 스냅샷 수와 비용을 크게 줄이는 용도다. Vitest·Playwright·Cypress 연동 문서도 별도로 있어, 기존 테스트 러너에 얹는 경로도 다룬다.

## 인용 포인트
- "story가 곧 테스트"라는 전제 — Storybook 유지 비용을 정당화하거나, 반대로 story 작성 규약을 강제할 때 쓰는 논거.
- 승인 기반 베이스라인 갱신 — 자체 구현 이미지 diff가 왜 팀에서 사장되는지(판정 주체가 없어서)를 설명하는 대비점.
