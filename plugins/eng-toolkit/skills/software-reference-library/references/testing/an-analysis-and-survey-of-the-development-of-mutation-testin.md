# An Analysis and Survey of the Development of Mutation Testing

http://crest.cs.ucl.ac.uk/fileadmin/crest/sebasepaper/JiaH10.pdf

## 한 줄
1970년대부터 2010년경까지 뮤테이션 테스트 연구 전체를 한 편으로 정리한 표준 서베이 (Yue Jia & Mark Harman, IEEE TSE 2011) — 기법 자체보다 **왜 이 좋은 기법이 현업에 안 퍼졌는가**(비용과 등가 뮤턴트)를 지형도로 보여준다.

## 페르소나
**"우리 커버리지 80%인데 왜 계속 버그가 나가지?"에서 출발해 뮤테이션 테스트를 검토 중인데, 도입 비용을 설명하지 못해 멈춰 선 사람.** 테스트가 실제로 결함을 잡는지 측정할 다른 지표가 필요하다는 것까지는 왔지만, 전체 테스트를 뮤턴트 수만큼 돌린다는 얘기를 듣고 "그건 CI에서 못 돌린다"는 반대에 부딪힌 상태다. 필요한 건 도구 사용법이 아니라, 이 기법의 비용 구조와 그걸 깎는 방법들이 어디까지 연구되어 있는지를 아는 것이다.

## 이럴 때 연다
- 커버리지 지표를 대체·보완할 측정 방법을 팀에 제안하기 전에 배경을 잡을 때
- 뮤테이션 테스트 도입의 비용(실행 시간, 등가 뮤턴트 판별)을 미리 설명해야 할 때
- 뮤턴트 축소·선택적 뮤테이션 같은 최적화 전략의 이름과 계보를 알아야 할 때
- 테스트 효과성 관련 논문을 읽다가 뮤테이션 점수가 기준으로 쓰이는 이유를 알고 싶을 때

## 이럴 땐 아니다
- 실제로 돌려볼 도구가 필요하면 `testing/stryker-mutator.md` (JS/TS) 또는 `testing/pit.md` (Java)
- 대규모 조직에서 실제로 어떻게 운용했는지가 궁금하면 `testing/state-of-mutation-testing-at-google.md`
- 커버리지가 왜 효과성의 대리 지표로 약한지 자체가 논점이면 `testing/coverage-is-not-strongly-correlated-with-test-suite-effectiv.md`

## 무엇이 들어있나
서베이는 뮤테이션 테스트를 "테스트가 잡아야 할 인공 결함을 코드에 심고, 테스트가 그걸 죽이는지 본다"는 원리에서 시작해, 그 원리를 실용화하려는 30여 년의 시도를 분류한다. 핵심 축은 두 가지 난제다. 하나는 **비용** — 뮤턴트 하나마다 테스트 스위트를 돌려야 하므로 순진하게 구현하면 감당이 안 된다. 다른 하나는 **등가 뮤턴트(equivalent mutant)** — 의미가 원본과 같아서 어떤 테스트로도 죽일 수 없는 뮤턴트를, 자동으로 판별하는 것이 일반적으로 결정 불가능하다는 점이다.

연구 흐름은 이 두 문제를 깎아 내려는 방향으로 정리된다. 뮤턴트 수를 줄이는 쪽(연산자 선별, 무작위 표본, 뮤턴트 결합), 실행을 빠르게 하는 쪽(약한 뮤테이션, 컴파일 대신 바이트코드 조작, 병렬 실행), 그리고 등가 뮤턴트를 근사적으로 걸러내는 쪽이다. 서베이 후반부는 언어·도구별 구현체와 뮤테이션 테스트가 결함 검출력의 기준선으로 쓰이는 연구들을 훑는다.

읽고 나면 태도가 바뀌는 지점은 여기다 — 뮤테이션 테스트는 "이상적이지만 비현실적"이 아니라, **비용을 어디까지 깎을지 결정하는 문제**로 재정의된다. 전체 코드베이스가 아니라 결제 금액 계산이나 쿠폰 차감처럼 조용히 틀리면 치명적인 모듈에만 걸어 두는 선택도 이 프레임 안에 들어온다.

## 인용 포인트
- 등가 뮤턴트 판별이 일반적으로 결정 불가능하다는 점 — 뮤테이션 점수를 100%로 몰아붙이는 목표 설정이 왜 잘못된 KPI인지 설명하는 근거.
- 비용 절감 연구가 "do fewer / do faster" 방향으로 축적되어 왔다는 지형 — 전면 도입 대신 고위험 모듈 한정 적용을 제안할 때의 논거.

## 코드 예시

"뮤테이션 점수 100%"가 왜 잘못된 KPI인지를, 죽일 수 있는 뮤턴트와 죽일 수 없는 등가 뮤턴트를 나란히 놓아 보인 것.

```js
// 원본
function shippingFee(total) {
  if (total >= 50000) return 0;
  return 3000;
}

// 뮤턴트 A: >= 를 > 로 바꿈 — 경계값 테스트가 있으면 죽는다
//   shippingFee(50000) 이 0 대신 3000 을 반환하므로 잡힌다
function shippingFeeMutantA(total) {
  if (total > 50000) return 0;
  return 3000;
}

// 뮤턴트 B: >= 를 > 로 바꾸고 경계를 49999 로 옮김 — 의미가 원본과 같다
//   어떤 입력으로도 원본과 다른 값을 낼 수 없으므로 "등가 뮤턴트"
function shippingFeeMutantB(total) {
  if (total > 49999) return 0; // total 이 정수라면 원본과 동치
  return 3000;
}
```

뮤턴트 B가 등가라는 판정은 "total 은 정수"라는 도메인 지식이 있어야 가능하고, 일반적으로는 자동 판별이 결정 불가능하다 — 남은 뮤턴트가 버그인지 등가인지는 결국 사람이 봐야 한다.
