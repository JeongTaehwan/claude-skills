# WireMock — HTTP 목 서버

https://wiremock.org/docs/

## 한 줄
코드에 목 객체를 심는 대신 **실제 HTTP 서버를 띄워** 스텁 응답을 돌려주는 도구 — 클라이언트 라이브러리·직렬화·타임아웃·재시도까지 실제 네트워크 경로를 그대로 태운 채 외부 API만 갈아 끼운다.

## 페르소나
**외부 API에 의존하는 코드를 테스트하려다 목킹 지점을 잘못 잡은 백엔드 엔지니어.** PG사·배송사·쿠폰 정산 같은 외부 연동이 있는데, HTTP 클라이언트를 모킹해 버리니 정작 자주 터지는 부분 — 헤더 누락, 타임아웃 설정, 5xx 재시도, 응답 JSON 파싱 — 은 하나도 검증되지 않는다. 반대로 샌드박스 서버를 그대로 쓰자니 느리고, 불안정하고, "결제 실패", "타임아웃", "429 스로틀링" 같은 시나리오는 재현할 방법이 없다.

## 이럴 때 연다
- 외부 API 연동 코드를 실제 HTTP 왕복 포함해 테스트하고 싶을 때
- 타임아웃·연결 끊김·5xx·지연 응답 같은 장애 시나리오를 재현해 재시도/서킷 브레이커 로직을 검증할 때
- 아직 완성되지 않은 API를 대상으로 클라이언트를 먼저 개발할 때(프로토타이핑)
- 실 서비스 트래픽을 녹화해 스텁으로 바꿔 두고(record & playback) 안정적인 테스트 픽스처로 삼을 때
- 요청이 기대한 형태(경로·헤더·바디)로 나갔는지 서버 쪽에서 검증하고 싶을 때
- CI에서 외부 의존성 없이 통합 테스트를 돌려야 할 때

## 이럴 땐 아니다
- 브라우저에서 프론트엔드가 부르는 API를 가로채는 게 목적이라면 `testing/mock-service-worker.md`
- 소비자와 제공자의 계약이 실제로 일치하는지 양쪽에서 검증해야 한다면 `testing/pact.md`, `testing/pact-js.md`, `testing/contracttest.md`
- 우리 서비스의 DB·큐 같은 인프라 의존성이 문제라면 `testing/testcontainers.md`
- API 요청을 직접 보내 응답을 검증하는 쪽이라면 `testing/rest-assured-api.md`, `testing/postman.md`
- 목/스텁/페이크의 선택 기준 자체가 논쟁이라면 `qa/mocks-aren-t-stubs.md`

## 무엇이 들어있나
핵심 발상은 목킹 경계를 코드 안이 아니라 **네트워크 밖**에 두는 것이다. 애플리케이션은 평소처럼 HTTP 요청을 보내고, 목적지 주소만 WireMock 인스턴스로 바뀐다. 그래서 클라이언트 설정·직렬화·커넥션 풀·타임아웃처럼 목 객체로는 검증할 수 없는 층이 테스트 범위 안으로 들어온다.

문서가 다루는 기능은 크게 네 갈래다. **요청 매칭** — URL, 메서드, 헤더, 쿠키, 쿼리, 바디(JSON/XML/정규식)로 어떤 요청에 어떤 스텁을 매길지 정밀 지정. **응답 구성** — 정적 응답부터 요청 값을 끌어와 응답을 만드는 템플릿, 상태를 갖는 시나리오(같은 엔드포인트가 호출 순서에 따라 다르게 응답)까지. **검증** — 특정 요청이 몇 번, 어떤 내용으로 왔는지 사후 단언. **결함·지연 주입** — 응답 지연, 연결 리셋, 잘못된 응답 등 정상 서버로는 만들 수 없는 상황 재현.

운영 형태도 여러 가지다. JUnit 4/5 확장으로 테스트에 붙이거나, 독립 JAR·도커 컨테이너로 띄워 팀 공용 목 서버로 쓰거나, 프록시 모드로 실제 API 앞에 세워 트래픽을 녹화한 뒤 스텁으로 전환할 수 있다. Java에서 출발했지만 Python·Node.js·.NET 등 다른 언어 클라이언트와 WebSocket·gRPC·GraphQL 지원도 문서에 포함되어 있다.

## 인용 포인트
- "목킹 경계를 코드가 아니라 네트워크에 둔다" — HTTP 클라이언트를 모킹하는 기존 테스트를 바꾸자고 설득할 때의 핵심 논지. 타임아웃·재시도 버그가 왜 안 잡혔는지가 이 한 문장으로 설명된다.
- 결함·지연 주입 기능은 재시도·서킷 브레이커·폴백 로직에 대해 "테스트 불가"라는 변명을 없앤다. 주문·결제 연동의 장애 대응 코드에 테스트를 요구할 근거.
