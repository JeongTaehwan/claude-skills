# fast-check (JS 속성 기반 테스트)

https://github.com/dubzzz/fast-check

## 한 줄
JS/TS 진영의 속성 기반 테스트 라이브러리 — 예제를 손으로 나열하는 대신 **"어떤 입력이든 성립해야 하는 성질"을 선언하면 입력을 자동 생성해 깨뜨리려 들고, 깨지면 반례를 사람이 읽을 수 있는 최소 형태로 줄여(shrinking) 준다.**

## 페르소나
**엣지 케이스 버그가 프로덕션에서만 발견되는 코드를 맡고 있는 JS/TS 엔지니어.** 쿠폰 할인 계산, 가격 반올림, 장바구니 병합, 날짜 구간 처리처럼 입력 조합이 사실상 무한한 로직인데, 테스트는 사람이 떠올린 대여섯 개의 예제뿐이다. 매번 "이 조합은 생각 못 했네"로 끝나는 장애 회고를 반복하고 있고, 예제를 더 많이 쓰는 것 말고 다른 접근이 필요하다는 감은 있지만 무엇을 단언해야 할지 모르는 상태.

## 이럴 때 연다
- 입력 공간이 넓은 순수 로직 — 파서, 직렬화/역직렬화, 금액 계산, 정렬·병합 — 을 검증할 때
- 왕복 성질(encode → decode = 원본), 불변식(합계는 음수가 될 수 없다) 같은 것을 테스트로 표현하고 싶을 때
- 사람이 만든 예제 테스트가 놓치는 경계값을 기계적으로 찾고 싶을 때
- 리팩터링 전후 구현이 동등한지 확인해야 할 때 (구 구현을 오라클로 두고 비교)
- 상태 머신(주문 상태 전이 등)의 임의 명령 시퀀스를 돌려 불변식이 깨지는지 보고 싶을 때

## 이럴 땐 아니다
- 파이썬 코드라면 `testing/hypothesis.md`
- OpenAPI 스펙을 기준으로 API 를 속성 기반으로 두드리는 거라면 `testing/schemathesis-api.md`
- 크래시·메모리 안전성을 노리는 바이너리 수준 퍼징이라면 `testing/afl.md`, `testing/libfuzzer.md`
- 속성 기반 테스트의 원래 아이디어와 이론적 배경이 궁금하면 `testing/quickcheck-a-lightweight-tool-for-random-testing-of-haskell.md`
- 값의 형태를 런타임에 검증하는 스키마 라이브러리를 찾는 거라면 `testing/joi.md`

## 무엇이 들어있나
핵심 구성은 arbitrary(입력 생성기)와 property(성질), 그리고 runner 다. 기본 제공되는 arbitrary 를 조합·변형해 도메인 값(예: 유효한 주문 객체)을 만들고, 그 위에 "이 성질은 항상 참이어야 한다"를 쓴다. Jest, Vitest, Mocha 등 기존 러너 안에서 그대로 돌아가므로 테스트 인프라를 갈아엎을 필요는 없다.

실무에서 이 도구의 값어치를 결정하는 건 생성기보다 **shrinking** 이다. 무작위 입력으로 실패를 찾아내도 그 입력이 거대하면 디버깅이 불가능한데, fast-check 은 실패를 유지하는 범위에서 입력을 계속 줄여 최소 반례를 제시한다. 실패는 시드로 재현 가능하므로 CI 에서 잡힌 케이스를 로컬에서 그대로 되돌릴 수 있다.

TypeScript 지원과 타입 추론이 강한 편이고, 모델 기반/상태 머신 테스트, 비동기 속성, 레이스 조건 탐지용 스케줄러 같은 확장 기능도 포함되어 있다.

가장 어려운 부분은 도구가 아니라 사고 전환이다. "입력 X 에 대해 출력이 Y" 대신 "어떤 입력에 대해서도 성립하는 무엇"을 찾아야 하고, 그 성질을 못 찾으면 이 도구는 쓸모가 없다.

## 인용 포인트
- shrinking 으로 최소 반례를 얻는다는 점은, 무작위 테스트가 "재현 불가능한 실패만 늘린다"는 흔한 우려에 대한 직접적인 반박이다.
- 기존 러너(Jest/Vitest) 위에서 동작한다는 점은 도입 비용이 낮다는 근거로 제안서에 쓸 수 있다.

## 코드 예시

"예제 대여섯 개" 대신 할인 계산이 어떤 입력에서도 지켜야 할 불변식을 선언한 것 — 기존 Jest 러너 안에서 그대로 돈다.

```js
import fc from 'fast-check';

test('할인가는 항상 [0, 원금] 안에 있다', () => {
  fc.assert(
    fc.property(
      fc.integer({ min: 0, max: 10_000_000 }), // 원금
      fc.integer({ min: 0, max: 100 }),        // 할인율(%)
      fc.integer({ min: 0, max: 50_000 }),     // 정액 할인
      (total, rate, flat) => {
        const paid = applyDiscount(total, { rate, flat });
        expect(paid).toBeGreaterThanOrEqual(0);
        expect(paid).toBeLessThanOrEqual(total);
      }
    ),
    { numRuns: 1000 }
  );
});

// 실패하면 최소 반례와 함께 시드가 출력된다.
// { seed: -1234, path: "3:1" } 를 옵션에 그대로 넣으면 로컬에서 재현된다.
```

이 테스트는 내가 적은 성질만 지킨다 — 범위만 단언했으므로 할인 금액이 완전히 틀린 구현도 통과한다. 왕복 성질이나 기존 구현과의 동등성처럼 더 강한 성질을 찾는 것이 진짜 작업이다.
