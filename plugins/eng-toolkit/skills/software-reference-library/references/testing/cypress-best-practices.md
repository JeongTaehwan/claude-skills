# Cypress — Best Practices

https://docs.cypress.io/app/core-concepts/best-practices

## 한 줄
Cypress 팀이 실제 지원 과정에서 반복해서 본 안티패턴을 "이렇게 쓰지 말고 이렇게 써라" 형태로 정리한 문서 — 튜토리얼이 아니라 **이미 짜 놓은 스펙을 리뷰할 때 쓰는 체크리스트**에 가깝다.

## 페르소나
**E2E 스펙이 쌓이면서 CI 가 간헐적으로 빨개지기 시작했고, 실패가 진짜 버그인지 테스트 탓인지 판별하는 데 시간을 쓰고 있는 프론트/풀스택 엔지니어.** 원인을 찾다 보면 `cy.wait(3000)` 로 타이밍을 때우거나, 앞 테스트가 만든 주문 데이터에 뒤 테스트가 의존하거나, 클래스명 셀렉터가 스타일 리팩터링에 같이 깨지는 패턴이 반복해서 나온다. 개별 스펙을 땜질하는 대신 어떤 패턴이 구조적으로 잘못됐는지 이름을 붙이고 팀 컨벤션으로 못 박고 싶은 상태다.

## 이럴 때 연다
- Cypress 스펙 PR 리뷰 기준을 문서로 만들 때
- 플레이키한 E2E 실패의 원인을 유형별로 좁혀 들어갈 때
- `cy.wait(숫자)`, 임의 sleep, 재시도 래핑이 코드베이스에 번지기 시작했을 때
- 셀렉터 전략(`data-cy` 도입 등)을 팀 규칙으로 정할 때
- 로그인 같은 선행 조건을 매 테스트마다 UI 로 통과시키느라 스위트가 느려졌을 때

## 이럴 땐 아니다
- Playwright 를 쓰고 있다면 같은 성격의 문서로 `testing/playwright-best-practices.md`
- 플레이키의 원인을 도구와 무관하게 유형론으로 정리하고 싶다면 `testing/eradicating-non-determinism-in-tests.md`
- E2E 를 얼마나 둘지, 어느 층에 테스트를 배치할지가 문제라면 `qa/the-practical-test-pyramid.md`
- 백엔드 응답을 가짜로 만들 방법을 찾는 거라면 `testing/mock-service-worker.md` 또는 `testing/wiremock-http.md`

## 무엇이 들어있나
문서의 형식 자체가 특징이다. 각 항목이 "Anti-pattern / Best practice" 쌍으로 제시되어, 리뷰에서 "이건 문서에 안티패턴으로 명시돼 있다"고 지목하기 쉽다.

반복해서 강조되는 축은 셋이다. 첫째, **테스트를 서로 독립적으로 유지하라** — 테스트가 앞 테스트의 상태에 의존하기 시작하면 순서·병렬화·단독 실행이 전부 깨진다. 둘째, **DOM 구조나 스타일에 결합된 셀렉터를 쓰지 말라** — 테스트 전용 속성을 붙여 마크업 변경과 테스트 실패를 분리하라는 것. 셋째, **임의 대기를 걸지 말라** — Cypress 는 이미 재시도 기반으로 대기하므로 고정 시간 `cy.wait()` 은 느리면서 동시에 불안정하다.

여기에 더해, 로그인 같은 반복 선행 조건을 매번 UI 로 수행하지 말고 프로그래밍적으로 처리하라는 조언과, 테스트 밖에서 통제할 수 없는 외부 사이트를 방문하지 말라는 조언이 있다. 통념과 어긋나는 지점은 "테스트 하나에 단언 하나" 규칙을 명시적으로 거부한다는 점 — Cypress 의 실행 모델에서는 하나의 방문 안에서 여러 단언을 하는 편이 오히려 낫다고 본다.

## 인용 포인트
- 임의 `cy.wait(ms)` 를 공식 문서가 안티패턴으로 규정한다는 사실은, "일단 대기 시간 늘려서 넘기자"는 임시방편을 막는 근거가 된다.
- 테스트 전용 셀렉터 속성 권고는 마크업 리팩터링 때마다 E2E 가 깨지는 비용을 팀에 설명할 때 인용하기 좋다.
- 테스트 간 상태 공유 금지 원칙은 CI 병렬화를 도입하기 전 정리해야 할 부채 목록의 근거가 된다.
