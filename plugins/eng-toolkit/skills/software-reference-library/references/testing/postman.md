# Postman 문서

https://learning.postman.com/docs/

## 한 줄
API 요청을 손으로 쏴 보는 도구로 알려진 Postman 을, 컬렉션·스크립트·환경 변수로 **반복 실행 가능한 API 테스트 자산**으로 쓰는 방법을 다루는 공식 학습 문서.

## 페르소나
**API 검증이 각자 개인 Postman 워크스페이스에 흩어져 있어, 다른 사람이 그 요청을 재현하지 못하는 팀의 개발자/QA.** 배포 전 확인은 매번 수동이고, 누가 어떤 케이스를 봤는지 기록이 남지 않는다. 코드로 된 API 테스트를 짜기엔 아직 스펙이 흔들리고, 그렇다고 손으로 계속 쏘기엔 회귀 확인 비용이 감당이 안 되는 중간 지점에 있다.

## 이럴 때 연다
- 주문·결제 API 검증 요청들을 컬렉션으로 묶어 팀이 공유·버전 관리하게 만들 때
- 로컬/스테이징/운영 환경을 변수로 분리하고 토큰 같은 민감값을 안전하게 다루는 방법이 필요할 때
- 요청 간 데이터 전달(로그인 응답의 토큰을 다음 요청에 사용)이나 응답 단언 스크립트를 붙일 때
- 스펙이 자주 바뀌는 초기 API 를 코드 테스트로 굳히기 전에 임시 회귀 세트를 만들 때
- 비개발 직군(기획·QA)이 API 동작을 직접 확인할 수 있게 문서화된 컬렉션을 넘길 때

## 이럴 땐 아니다
- CI 에 붙는 코드 기반 API 테스트가 목적이면 `testing/rest-assured-api.md`(Java) 또는 언어별 러너 — `testing/pytest.md`, `testing/jest.md`
- 스키마로부터 케이스를 자동 생성해 빈틈을 찾으려면 `testing/schemathesis-api.md`
- 서비스 간 호환을 계약으로 고정하려는 것이면 `testing/pact.md`
- API 스펙 자체를 어떻게 쓸지가 문제면 `development/openapi-specification.md`

## 무엇이 들어있나
문서는 크게 요청 보내기·컬렉션으로 조직화하기·테스트 스크립트 작성하기·API 설계와 협업·관리 순으로 구성돼 있고, 테스트 절은 요청과 컬렉션에 동적 동작을 부여하는 관점 — 파라미터를 넘기고, 요청 사이에 데이터를 전달하고, 응답에 단언을 붙이는 — 으로 서술된다. 즉 Postman 을 "요청 클라이언트"가 아니라 스크립트가 붙은 실행 자산으로 보게 만드는 것이 문서의 방향이다.

실무에서 이 도구의 가치가 갈리는 지점은 공유다. 개인 워크스페이스에 남은 요청은 자산이 아니고, 컬렉션·환경·변수로 정리되어 팀 워크스페이스에 올라가야 회귀 세트가 된다. 반대로 한계도 분명하다 — 컬렉션이 커지면 코드 리뷰·리팩터링·버전 관리 측면에서 코드 기반 테스트보다 불리해지므로, 안정된 계약은 결국 코드 테스트로 옮겨 가는 편이 낫다.

## 인용 포인트
- 컬렉션을 팀 워크스페이스로 옮기는 것만으로 "개인 검증"이 "공유 회귀 세트"가 된다 — API 검증 자산화를 제안할 때의 최소 첫걸음.
