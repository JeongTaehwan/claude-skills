# The Oracle Problem in Software Testing: A Survey

https://discovery.ucl.ac.uk/1471263/1/06963470.pdf

## 한 줄
Barr·Harman·McMinn·Shahbaz·Yoo (IEEE TSE 2015) — 테스트 자동화 논의가 늘 "입력을 어떻게 만드나"에만 쏠려 있는 사이 방치돼 온 반대쪽 절반, 즉 **"그래서 정답이 뭔지 어떻게 아는가"**를 네 종류의 테스트 오라클로 분류해 정리한 서베이.

## 페르소나
**테스트를 짜야 하는데 기대값을 적을 수가 없어서 멈춘 엔지니어.** 입력을 만드는 건 어렵지 않다 — 문제는 추천 결과, 검색 랭킹, 렌더링된 화면, 복잡한 정산 금액, ML 모델 출력처럼 "이 출력이 맞는지"를 사람이 손으로 적어 둘 수 없는 대상이라는 것이다. 결국 크래시가 안 나면 통과로 처리하는 테스트만 쌓이고, 조용히 틀린 값이 흘러가도 스위트는 계속 초록이다.

## 이럴 때 연다
- 기대값을 명시하기 어려운 대상(추천·정산·이미지/렌더링·ML 추론)의 테스트 전략을 세울 때
- 메타모픽 테스트(입력을 규칙대로 바꿨을 때 출력이 만족해야 할 관계)를 도입할 근거와 어휘가 필요할 때
- 레거시 리팩터링에서 기존 구현을 기준(pseudo-oracle)으로 삼는 회귀 테스트를 설계할 때
- "테스트 자동화 도입" 계획이 입력 생성만 다루고 판정 문제를 비워 두고 있음을 지적해야 할 때
- 사람이 결과를 눈으로 확인해야 하는 비용(human oracle cost)을 줄일 방법을 찾을 때

## 이럴 땐 아니다
- 판정 기준은 이미 있고 입력을 자동 생성하는 게 문제라면 `testing/hypothesis.md`, `testing/fast-check.md`, `testing/evosuite.md`
- 크래시·행 같은 명백한 이상만 잡으면 되는 상황이면 퍼징 쪽 — `testing/the-art-science-and-engineering-of-fuzzing-a-survey.md`
- 단언(assertion)을 얼마나·어떻게 써야 스위트가 강해지는지의 실증이 필요하면 `testing/assertions-are-strongly-correlated-with-test-suite-effective.md`
- 테스트가 결함을 실제로 잡는지 측정하는 문제라면 `testing/pit.md`, `testing/stryker-mutator.md`
- 사람이 판단하는 탐색적 테스트를 어떻게 조직할지의 문제라면 `qa/rapid-software-testing.md`, `qa/heuristic-test-strategy-model.md`

## 무엇이 들어있나
서베이는 테스트 오라클을 네 부류로 나눈다. **명세 기반(specified)** — 형식 명세·계약·상태 기계에서 판정을 끌어내는 것. **파생(derived)** — 명세가 없을 때 다른 산출물에서 판정을 만들어 내는 것으로, 메타모픽 테스트, 이전 버전이나 참조 구현을 쓰는 pseudo-oracle, 실행에서 불변식을 추론하는 방식(Daikon 계열), 명세 마이닝이 여기 들어간다. **암묵(implicit)** — 크래시, 데드락, 메모리 오류처럼 별도 정보 없이도 실패임이 자명한 이상 징후. 그리고 **자동 오라클이 없는 경우** — 사람이 판정해야 하는 상황을 어떻게 줄이고 배분할지.

가장 실무적으로 쓸모 있는 통찰은 암묵 오라클이 보편적이지 않다는 지적이다. 어떤 시스템·맥락에서 비정상인 동작이 다른 맥락에서는 정상이거나 심지어 의도된 것일 수 있다(크래시를 찾는 것이 목적인 시스템처럼). "죽지 않으면 통과"라는 기본 설정이 왜 위험한지의 근거가 된다.

네 번째 부류는 특히 현실적이다. 사람이 오라클 역할을 하는 비용을 두 축 — 오라클을 **작성**하는 비용과 결과를 **평가**하는 비용 — 으로 나누고, 테스터를 봐야 할 코드로 유도해 작성 비용을 줄이는 접근, 오라클 후보를 제안하고 사람이 채택 여부만 결정하게 하는 도구, 나아가 판정 자체를 크라우드소싱하는 시도까지 다룬다.

문헌 조사 범위는 1978년 이후 축적된 출판물이며, 네 부류 각각의 연구량이 모두 꾸준히 증가하는 추세를 보인다고 보고한다.

## 인용 포인트
- 테스트 자동화의 절반은 입력 생성이고 나머지 절반은 판정이며, 후자가 오래 방치돼 왔다는 문제 제기 — 자동화 계획서에 "판정 전략" 절을 신설할 근거.
- "암묵 오라클은 보편적이지 않다" — 크래시 없음을 통과 조건으로 쓰는 테스트에 반대할 때 인용할 수 있다.
- 메타모픽 테스트를 파생 오라클의 한 갈래로 위치시킨 분류는, 정답을 모르는 대상에도 테스트를 쓸 수 있다는 설득의 출발점이 된다.
