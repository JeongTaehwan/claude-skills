# Deque axe

https://www.deque.com/axe/

## 한 줄
접근성 검사 엔진 axe-core를 감싼 상용 제품군(브라우저 확장, DevTools, CI 리포팅, 모니터링)의 소개 페이지로, "무엇을 무료로 쓰고 무엇에 돈을 내는가"를 가르는 지점이다.

## 페르소나
**접근성 이슈 제보를 받았는데 팀에 접근성 전문가가 없어, 우선 도구부터 붙여 현황을 숫자로 만들어야 하는 프론트엔드 리드.** 검사 도구가 axe, Lighthouse, WAVE 등 여러 개 이름으로 돌아다니는데 서로 어떤 관계인지 모르겠고, 개발자 로컬 점검용과 CI 게이트용과 경영진 보고용이 각각 다른 물건이라는 걸 아직 구분하지 못한 상태다. 브라우저 확장으로 한 번 돌려보고 "위반 0건"이 나왔을 때 그게 무슨 뜻인지도 아직 모른다.

## 이럴 때 연다
- 접근성 점검을 처음 시작하며 손으로 돌려볼 도구를 고를 때
- 개발자가 PR 전에 로컬에서 스스로 점검할 브라우저 확장이 필요할 때
- 자동 검사 결과를 팀·조직 단위로 집계해 추이 리포트를 만들어야 할 때
- axe 계열 제품 중 어디까지가 오픈소스(axe-core)이고 어디부터 유료인지 정리할 때

## 이럴 땐 아니다
- 테스트 코드에 접근성 검사를 코드로 넣고 싶다면 엔진 자체인 `testing/axe-core.md`
- 위반으로 잡힌 항목의 근거 기준·성공 조건을 읽어야 한다면 `design/wcag-2-2.md`
- 성능·SEO까지 묶어 한 번에 점수를 내고 싶다면 `development/lighthouse.md`
- 자동 검사가 잡지 못하는 영역(키보드 순서, 스크린리더 낭독 흐름, 대체 텍스트의 적절성)을 사람 손으로 점검하려면 `design/mdn-accessibility.md`, `design/the-a11y-project.md`

## 무엇이 들어있나
axe의 핵심 주장은 "자동 검사로 잡을 수 있는 접근성 문제는 전체의 일부일 뿐"이라는 것이다. Deque는 이 한계를 감추지 않고, 자동 도구는 오탐 없는(false-positive를 최소화한) 규칙만 돌리고 나머지는 안내형 수동 점검으로 넘기는 구조를 택했다. 그래서 axe 결과의 "위반 0건"은 접근성 통과가 아니라 "자동으로 판별 가능한 규칙 위반이 없음"으로 읽어야 한다.
제품군은 결과적으로 세 층위로 나뉜다 — 개발자가 브라우저에서 즉시 돌리는 확장/DevTools, 테스트 코드와 CI에 붙이는 엔진 연동, 조직 단위 집계·모니터링. 규칙은 WCAG 성공 기준에 매핑돼 있어 위반 항목마다 근거 조항을 따라갈 수 있다.

## 인용 포인트
- "자동 접근성 검사는 통과 증명이 아니라 스크리닝"이라는 선을 그을 때 벤더 자신의 문서를 근거로 쓸 수 있다 — 접근성 대응 범위를 과대 약속하지 않도록 막는 데 유용하다.
- 자동/수동 점검 예산 분리를 제안할 때, 도구 벤더조차 수동 점검 트랙을 별도 제품으로 두고 있다는 사실이 설득력을 준다.
