# Pact — 계약 테스트 문서

https://docs.pact.io/

## 한 줄
소비자(consumer)가 자기 테스트를 돌리는 과정에서 "나는 이 요청을 보내고 이런 응답을 기대한다"는 계약 파일을 만들어 내고, 공급자(provider)가 그 계약을 자기 CI 에서 재생해 검증하는 **소비자 주도 계약 테스트**의 표준 구현.

## 페르소나
**서비스가 늘어나면서 E2E 스위트가 폭발했고, 그마저도 배포 순서를 맞춰야만 초록불이 되는 상태의 백엔드 엔지니어.** 주문 서비스가 쿠폰 서비스의 응답 필드 하나를 바꾸면 어디가 깨지는지 배포해 봐야 알고, 통합 환경은 항상 누군가가 쓰고 있어 대기가 걸린다. 필요한 건 더 많은 E2E 가 아니라, 두 서비스를 동시에 띄우지 않고도 호환성을 확인하고 "지금 배포해도 되는가"에 답하는 방법이다.

## 이럴 때 연다
- 서비스가 여러 개라 E2E 조합이 폭발하고 실행 시간·불안정성이 감당이 안 될 때
- 배포 순서 의존성을 끊고 각 서비스가 독립적으로 배포되게 만들고 싶을 때
- 목으로 짠 통합 테스트가 실제 상대 서비스와 어긋나 있는지 확인할 방법이 필요할 때
- API 변경이 어떤 소비자를 깨뜨리는지 배포 전에 알고 싶을 때

## 이럴 땐 아니다
- 계약 테스트의 개념·유형 구분(소비자 주도인지 아닌지)을 먼저 잡고 싶다면 `testing/contracttest.md`
- 마이크로서비스 테스트 전략 전체에서 계약 테스트의 위치가 궁금하면 `qa/testing-strategies-in-a-microservice-architecture.md`
- JS/TS 구현체의 구체적 API 가 필요하면 `testing/pact-js.md`
- 단순히 외부 의존성을 가짜로 세우는 것이 목적이라면 `testing/wiremock-http.md` 또는 `testing/mock-service-worker.md`
- 스펙에서 자동으로 케이스를 생성해 API 를 두들기는 쪽이라면 `testing/schemathesis-api.md`

## 무엇이 들어있나
핵심 주장은 방향성이다. 계약을 공급자가 문서로 던지는 것이 아니라 **소비자가 실제로 필요로 하는 것만** 기술한다. 그래서 계약은 API 전체 명세가 아니라 "이 소비자가 실제로 쓰는 부분"의 집합이고, 공급자는 아무도 쓰지 않는 필드를 자유롭게 바꿀 수 있다.

절차는 두 단계다. 소비자 쪽 테스트가 Pact 목 서버를 상대로 돌면서 pact 파일(요청/응답 예시 + 상태 전제)을 생성하고, 공급자 쪽 검증 단계에서 그 파일을 재생해 실제 구현이 응답하는지 확인한다. 이때 공급자가 특정 상태(예: "쿠폰 ABC 가 존재함")를 만들어 주는 **provider state** 훅이 계약의 실행 가능성을 담보한다.

운영을 성립시키는 조각이 Pact Broker 와 **can-i-deploy** 다. 계약과 검증 결과를 중앙에 모아 두고, 배포 직전에 "지금 이 버전을 이 환경에 올려도 상대편들과 호환되는가"를 질의해 답을 받는다. 계약 테스트의 진짜 산출물은 테스트 통과가 아니라 이 배포 가능 판정이라는 점이 문서 전체를 관통한다.

문서는 한계도 명시한다. Pact 는 요청/응답 호환성을 보증할 뿐 기능이 옳은지는 검증하지 않으며, 소비자가 여럿인 공개 API 나 계약 관계가 불분명한 경우에는 적합하지 않다.

## 인용 포인트
- "계약은 소비자가 실제로 쓰는 것만 기술한다" — 공급자 주도 스펙 문서와 계약 테스트를 혼동하는 논의를 정리하는 문장.
- can-i-deploy 로 배포 가부를 판정한다는 구조는, E2E 통합 환경을 배포 게이트로 쓰는 관행을 대체하자는 제안의 핵심 근거.
- Pact 가 호환성만 보증하고 기능 정확성은 다루지 않는다는 문서의 명시는, 계약 테스트가 E2E 를 전부 대체한다는 과잉 주장을 막는 데 쓸 수 있다.
