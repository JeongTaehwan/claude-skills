# Joi

https://github.com/hapijs/joi

## 한 줄
"가장 강력한 JS 스키마 기술 언어이자 데이터 검증기"를 표방하는 hapi 생태계의 검증 라이브러리로, 입력 규칙을 코드가 아니라 **선언적 스키마**로 적어 두고 그 스키마를 런타임 검증과 테스트 픽스처 검증에 동시에 재사용하게 해 준다.

## 페르소나
**요청 바디 검증이 컨트롤러마다 흩어져 있어, 어떤 필드가 필수인지 코드를 다 읽어야만 알 수 있는 상태의 백엔드 개발자.** 주문 생성 API 에 필드가 하나 늘 때마다 검증 if 문과 테스트가 같이 늘어나고, 정작 "쿠폰 코드가 null 로 들어오면 어떻게 되나" 같은 경계는 아무도 명세하지 않은 채 남아 있다. 필요한 건 검증 코드를 더 잘 쓰는 요령이 아니라, 규칙을 한 곳에 모아 놓고 그 자체를 계약으로 취급하는 형태다.

## 이럴 때 연다
- 입력 검증 규칙을 코드 곳곳의 조건문이 아니라 한 개의 스키마로 명세화하고 싶을 때
- 테스트에서 만들어 낸 픽스처·목 응답이 실제 계약과 어긋나지 않는지 스키마로 확인하고 싶을 때
- 이미 hapi 기반이거나 Joi 를 쓰는 코드베이스를 유지보수해야 할 때
- 속성 기반 테스트나 퍼징의 입력 생성/검증 단에 쓸 스키마 표현이 필요할 때

## 이럴 땐 아니다
- 새 TypeScript 프로젝트에서 타입 추론까지 함께 얻고 싶다면 `development/zod.md` 쪽이 더 자연스럽다
- 언어 중립적인 스키마 표준 자체가 필요하면 `development/json-schema.md`
- API 스펙에서 자동으로 테스트 케이스를 뽑아내고 싶은 것이라면 `testing/schemathesis-api.md`

## 무엇이 들어있나
API 레퍼런스가 본체다. 타입별 체이닝(`Joi.string().email().required()`), 조건부 규칙(`when`), 객체 간 상호 의존(`and`, `or`, `xor`), 커스텀 에러 메시지, 값 변환(convert) 규칙이 문서화되어 있다.

테스트 관점에서 의미 있는 지점은 "검증기"라기보다 "명세"라는 성격이다. 스키마 하나를 런타임 방어와 테스트 어서션 양쪽에서 쓰면, 목 서버가 돌려주는 응답이나 테스트 픽스처가 실제 계약에서 조용히 벗어나는 문제를 잡을 수 있다. 반대로 검증 로직이 스키마로 옮겨 가면 "이 필드는 왜 필수인가"를 코드 리뷰에서 논의할 수 있는 형태가 된다.

문서·튜토리얼은 저장소가 아니라 joi.dev 개발자 포털로 안내한다.

## 인용 포인트
- 검증 규칙을 스키마로 외부화하면 "입력 계약"이 리뷰 가능한 산출물이 된다 — 검증 코드 분산을 정리하자는 제안의 근거.
