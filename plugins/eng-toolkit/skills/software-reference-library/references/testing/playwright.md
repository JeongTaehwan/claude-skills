# Playwright 저장소

https://github.com/microsoft/playwright

## 한 줄
Playwright 의 소스·이슈·릴리스가 있는 곳 — 가이드 문서로는 설명되지 않는 브라우저별 동작 차이나 "이건 버그인가 원래 이런가"를 판정해야 할 때 들어가는 원본.

## 페르소나
**E2E 가 Chromium 에서는 통과하는데 WebKit 에서만 간헐적으로 깨지고, 공식 가이드 문서를 아무리 읽어도 이유가 안 나오는 상황의 엔지니어.** 자기 테스트 코드가 잘못됐는지, Playwright 의 알려진 제약인지, 브라우저 엔진 차이인지를 구분하지 못해 디버깅이 헛돌고 있다. 필요한 건 사용법이 아니라 "이 동작이 의도된 것인지"에 대한 판정 근거와, 이미 같은 문제를 겪은 사람의 이슈 스레드다.

## 이럴 때 연다
- 특정 브라우저 엔진에서만 재현되는 실패를 만나 알려진 이슈인지 검색할 때
- 원하는 기능(특정 API, 특정 프로토콜 지원)이 이미 있는지, 논의 중인지, 거절됐는지 확인할 때
- 버전 업그레이드 후 동작이 바뀌어 릴리스 노트와 변경 커밋을 추적할 때
- 자동 대기(auto-waiting)나 액션ability 판정이 왜 그렇게 동작하는지 구현을 직접 확인해야 할 때
- 버그를 재현 코드와 함께 신고하거나, 워크어라운드를 찾을 때

## 이럴 땐 아니다
- 테스트를 어떻게 써야 안 깨지는지 규칙을 세우는 게 목적이면 `testing/playwright-best-practices.md`
- 페이지 전체가 아니라 컴포넌트 단위로 테스트하려는 것이면 `testing/playwright-2.md`
- 이미 Cypress 로 쓰고 있고 규칙만 정비하려는 상황이면 `testing/cypress-best-practices.md`
- 간헐적 실패의 원인 분류와 대응 원칙 자체가 필요하면 `testing/eradicating-non-determinism-in-tests.md`

## 무엇이 들어있나
Playwright 는 브라우저 자동화 라이브러리와 테스트 러너를 한 저장소에서 함께 관리한다. 그래서 여기에는 세 층이 섞여 있다 — 브라우저를 제어하는 프로토콜 계층, 로케이터/자동 대기 같은 상위 API, 그리고 `@playwright/test` 러너(격리된 브라우저 컨텍스트, 병렬 실행, 트레이스·재시도).

이 저장소가 가이드 문서보다 유용해지는 지점은 브라우저별 차이다. Chromium·Firefox·WebKit 을 각각 패치된 빌드로 구동하기 때문에, 어떤 실패는 사용법이 아니라 특정 엔진 빌드의 제약에서 나온다. 이슈 트래커는 사실상 그 차이를 정리한 비공식 지식 베이스다.

릴리스가 잦다는 점도 실무 정보다. 브라우저 빌드가 버전에 묶여 있어 업그레이드가 동작 변화를 동반할 수 있고, 그래서 "어제까지 되던 테스트"의 원인 추적이 릴리스 노트에서 끝나는 경우가 잦다.

## 인용 포인트
- 브라우저 빌드가 패키지 버전에 고정되어 있다는 구조는, E2E 실패를 조사할 때 "우리 코드 / 우리 앱 / 도구 버전" 세 축을 분리해야 하는 이유가 된다.
