# pytest 공식 문서

https://docs.pytest.org/

## 한 줄
`self.assertEqual` 계열 API 를 외울 필요 없이 평범한 `assert` 만으로 상세한 실패 진단을 내주고, 상속 대신 픽스처 조합으로 테스트 준비를 조립하는 Python 테스트 프레임워크의 공식 문서.

## 페르소나
**unittest 기반 테스트가 setUp 상속 계층으로 얽혀, 새 테스트 하나 추가하려면 어느 베이스 클래스를 물려받아야 하는지부터 고민하게 된 Python 개발자.** DB 연결·샘플 데이터·외부 API 목이 클래스 계층 여기저기 흩어져 있고, 케이스 하나마다 조합이 조금씩 달라 중복이 계속 늘어난다. 픽스처와 파라미터화가 답이라는 말은 들었는데 스코프·자동 사용·의존 관계를 어디까지 써야 하는지 기준이 없다.

## 이럴 때 연다
- 테스트 준비 코드를 상속에서 픽스처 조합으로 옮기며 스코프(function/module/session) 를 정할 때
- 할인율·수량 경계처럼 같은 로직에 입력만 다른 케이스를 `parametrize` 로 정리할 때
- 마커로 느린 테스트·통합 테스트를 분리해 CI 단계별로 나눠 돌릴 때
- `conftest.py` 배치, 임포트 모드, 테스트 발견 규칙 때문에 실행이 꼬였을 때
- 기존 unittest 스위트를 유지한 채 점진적으로 옮겨 갈 때
- 필요한 기능이 플러그인으로 이미 있는지 찾을 때(문서는 1300개 이상의 외부 플러그인을 언급한다)

## 이럴 땐 아니다
- JS/TS 스택이면 `testing/jest.md`, `testing/vitest.md`, `testing/mocha.md`
- 예제 기반이 아니라 속성 기반으로 입력을 생성하려면 `testing/hypothesis.md`
- 실제 DB·브로커를 컨테이너로 띄워 통합 테스트하려면 `testing/testcontainers.md`
- 목·스텁을 어디까지 쓸지 판단 자체가 문제면 `qa/mocks-aren-t-stubs.md`
- 간헐적으로 깨지는 테스트의 원인 분류와 대응은 `testing/eradicating-non-determinism-in-tests.md`

## 무엇이 들어있나
문서가 앞세우는 것은 두 가지다. 첫째, **단언 재작성(assertion introspection)** — 평범한 `assert` 문이 실패했을 때 좌우 값과 차이를 자동으로 풀어 보여 주므로 프레임워크 전용 단언 이름을 외울 이유가 없다. 둘째, **픽스처** — 준비 코드를 상속 계층이 아니라 이름으로 요청해 받는 의존성 주입 형태로 만들고, 픽스처끼리도 서로를 요청할 수 있으며 파라미터화도 가능하다. 이 구조가 unittest 의 setUp 상속과 갈리는 지점이다.

구성은 Getting Started / How-to 가이드 / 레퍼런스 / Explanation 네 축이며, 마지막 Explanation 절에는 임포트 메커니즘이나 플레이키 테스트처럼 "왜 이렇게 되는가"를 다루는 글이 있다. 실행이 이상하게 꼬였을 때 how-to 가 아니라 여기를 봐야 하는 경우가 많다.

기존 unittest 스위트를 그대로 실행할 수 있다는 호환성도 명시돼 있어, 전면 전환 없이 러너만 바꾸는 점진적 이행이 가능하다. 플러그인 생태계는 이 프레임워크의 실질적 표면적이다 — 커버리지, 비동기, DB, 스냅샷 같은 기능은 대부분 코어가 아니라 플러그인에서 온다.

## 인용 포인트
- "실패한 assert 문에 대한 상세 정보 — `self.assert*` 이름을 외울 필요 없이" — unittest 에서 옮기자는 제안의 가장 짧은 근거.
- 픽스처는 상속이 아니라 요청으로 준비 코드를 조립한다 — 테스트 베이스 클래스가 비대해진 코드베이스를 정리할 때의 방향 제시.
- 기존 unittest 스위트를 그대로 돌릴 수 있다는 점은 "한 번에 다 바꿔야 한다"는 전환 저항을 제거한다.
