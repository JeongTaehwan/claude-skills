# JavaScript Testing Best Practices

https://github.com/goldbergyoni/javascript-testing-best-practices

## 한 줄
JS/TS 테스트 실무 원칙 50여 개를 "이렇게 쓰면 이렇게 읽힌다"는 코드 예제와 함께 나열한 저장소 — 특정 프레임워크 매뉴얼이 아니라 **팀 테스트 컨벤션 문서를 만들 때 초안으로 쓰는 목록**이다.

## 페르소나
**테스트는 있는데 아무도 읽지 않는 코드베이스를 물려받은 프론트/Node 엔지니어.** 테스트 이름이 `test('works')` 수준이라 실패해도 무엇이 깨졌는지 알 수 없고, 모킹이 과해서 프로덕션 버그를 못 잡으며, 리뷰에서 지적하려 해도 "취향 아니냐"는 말로 끝난다. 개인 의견이 아니라 **인용 가능한 공통 기준**이 필요한 상태다.

## 이럴 때 연다
- 팀의 프론트/Node 테스트 컨벤션 문서를 새로 쓰거나 개정할 때
- 테스트 코드 리뷰에서 지적할 항목의 근거가 필요할 때
- 테스트 이름 규칙, 단언 스타일, 데이터 준비 방식을 통일하려 할 때
- 모킹을 어디까지 할지, 무엇을 실제로 띄울지 기준을 정할 때
- 신규 입사자에게 "우리 테스트는 이렇게 쓴다"를 한 번에 전달할 자료가 필요할 때

## 이럴 땐 아니다
- Jest/Vitest 의 API·설정 자체가 궁금하면 `testing/jest.md`, `testing/vitest.md`
- 리액트 컴포넌트를 어떤 관점으로 쿼리하고 단언할지가 문제라면 `testing/testing-library.md`
- 단위/통합/E2E 비율 같은 전략 층위의 결정이라면 `qa/the-practical-test-pyramid.md`, `qa/write-tests-not-too-many-mostly-integration.md`
- 테스트 더블 용어를 정확히 구분해야 하면 `qa/mocks-aren-t-stubs.md`
- E2E 도구별 안티패턴은 `testing/cypress-best-practices.md`, `testing/playwright-best-practices.md`

## 무엇이 들어있나
구성은 테스트 해부(이름·구조·단언), 백엔드 테스트, 프론트엔드 테스트, 품질 측정, CI 로 나뉜다. 각 항목이 짧은 원칙 한 줄 + "이렇게 하지 말라 / 이렇게 하라" 코드 쌍으로 되어 있어, 리뷰 코멘트에 링크를 그대로 붙이기 좋다.

반복해서 나오는 축 몇 가지. 테스트 이름은 **무엇을 하는가 / 어떤 상황에서 / 기대 결과는 무엇인가**의 세 부분을 담아야 한다는 것 — 실패 메시지만 보고도 원인을 좁힐 수 있게 하는 장치다. 본문은 준비/실행/검증(AAA)으로 시각적으로 분리하라는 것. 그리고 테스트에는 로직(if, 반복, 계산)을 넣지 말라는 것 — 테스트를 검증할 테스트는 없기 때문이다.

통념과 어긋나는 지점은 모킹과 내부 구현에 대한 태도다. 내부 구현이 아니라 **밖에서 보이는 결과**를 검증하라, 그래서 리팩터링에 테스트가 따라 깨지지 않게 하라는 방향이고, 백엔드 쪽에서는 모든 것을 모킹한 단위 테스트보다 실제에 가까운 컴포넌트/통합 테스트에 무게를 싣는다.

## 인용 포인트
- 테스트 이름 3부 구조(대상 / 상황 / 기대)는 컨벤션 문서에 그대로 옮겨 쓸 수 있는 규칙이다.
- "테스트 안에 로직을 넣지 말라"는 원칙은 조건 분기로 비대해진 헬퍼 테스트를 리뷰에서 반려할 때 인용하기 좋다.
- 구현 세부가 아니라 외부 결과를 검증하라는 원칙은, 리팩터링마다 테스트가 무더기로 깨지는 비용을 팀에 설명하는 근거가 된다.
