# Stryker Mutator (JS/TS/C#/Scala)

https://stryker-mutator.io/

## 한 줄
JS/TS·C#·Scala용 뮤테이션 테스트 도구. 소스에 의도적인 변형(비교 연산 뒤집기, 조건 상수화, 반환값 제거 등)을 심고 기존 테스트가 그 변형을 잡아내는지 세어, **커버리지가 아니라 테스트의 검출력**을 점수로 내놓는다.

## 페르소나
**커버리지 90%를 달성해 놓고도 배포 때마다 불안한 프론트/Node 개발자.** 지표는 초록인데 실제로는 렌더링만 시키고 아무것도 단언하지 않는 테스트가 섞여 있다는 의심이 있다. 리뷰에서 "이 테스트 의미 없다"고 말하려 해도 근거가 감이라서 매번 논쟁이 된다. 필요한 건 **테스트 스위트를 테스트하는 수단**이다.

## 이럴 때 연다
- 커버리지가 높은데도 버그가 새는 모듈에서 테스트가 실제로 무엇을 잡는지 계량할 때
- 금액·할인·쿠폰 조건 분기처럼 부등호 하나가 뒤집혀도 조용히 통과할 수 있는 코드를 점검할 때
- 리뷰 기준에 "커버리지" 대신 다른 품질 게이트를 넣을지 검토할 때
- 대규모 리팩터링 전에 기존 테스트가 안전망 구실을 하는지 확인할 때

## 이럴 땐 아니다
- Java 프로젝트라면 `testing/pit.md`
- 이걸 조직 규모로 굴릴 때의 운영 설계(범위 한정, 노이즈 제거, 결과 노출 위치)는 `testing/state-of-mutation-testing-at-google.md`
- 기법 자체의 배경·연구사는 `testing/an-analysis-and-survey-of-the-development-of-mutation-testin.md`
- 단순히 단언이 부족하다는 진단만 필요하면 먼저 `testing/assertions-are-strongly-correlated-with-test-suite-effective.md`

## 무엇이 들어있나
문서는 뮤테이션 점수의 해석부터 잡아 준다 — 죽은 뮤턴트(테스트가 잡음), 살아남은 뮤턴트(놓침), 커버되지 않은 뮤턴트, 그리고 어떤 테스트로도 잡을 수 없는 동치 뮤턴트. 목표는 100%가 아니라 살아남은 뮤턴트를 하나씩 읽으며 "이건 진짜 구멍인가, 무의미한 변형인가"를 판정하는 것이라는 태도가 일관된다.

실무에서 관건은 실행 시간이다. Stryker는 커버리지 정보로 각 뮤턴트에 관련된 테스트만 돌리는 최적화, 증분 실행, 변경 파일 한정 실행, 동시 실행 설정 등을 제공한다. 전체 스위트에 매번 돌리는 대신 핵심 도메인 디렉터리부터 좁혀 시작하라는 것이 사실상의 권고다. HTML 리포트로 살아남은 뮤턴트를 소스 위에 표시해 주는 것이 실제 개선 작업의 출발점이 된다.

## 인용 포인트
- "커버리지는 테스트가 코드를 지나갔다는 뜻이고, 뮤테이션 점수는 테스트가 변화를 알아챈다는 뜻"이라는 구분. 커버리지 목표치 논쟁을 끝내는 데 가장 짧은 문장이다.
