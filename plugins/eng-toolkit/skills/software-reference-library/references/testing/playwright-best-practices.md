# Playwright — Best Practices

https://playwright.dev/docs/best-practices

## 한 줄
플레이키한 E2E 를 만드는 대표적 습관(구현 결합 셀렉터, 수동 sleep, 테스트 간 상태 공유)을 지목하고 그 대안을 규칙 형태로 제시하는 Playwright 공식 지침.

## 페르소나
**E2E 가 하루걸러 빨간불이라 팀이 CI 실패를 보고도 일단 재실행부터 누르게 된 상태의 엔지니어.** 실패가 진짜 회귀인지 테스트 문제인지 구분이 안 되니 파이프라인 자체가 신뢰를 잃었고, 개별 테스트를 하나씩 고쳐도 다음 주에 다른 데가 깨진다. 필요한 건 개별 수정이 아니라 팀이 합의할 수 있는 작성 규칙 — 그리고 리뷰에서 "이렇게 쓰지 말자"고 말할 때 기댈 공식 근거다.

## 이럴 때 연다
- E2E 작성 규칙(코딩 컨벤션)을 문서로 정해 팀에 배포할 때
- CSS/XPath 셀렉터가 UI 변경마다 무더기로 깨져 로케이터 전략을 갈아엎을 때
- `waitForTimeout` 같은 임의 대기가 코드베이스에 퍼져 있어 걷어낼 근거가 필요할 때
- 테스트 간 순서 의존·데이터 공유 때문에 병렬 실행이 불가능할 때
- 무엇을 E2E 로 두고 무엇을 아래 층으로 내릴지 경계를 다시 그을 때

## 이럴 땐 아니다
- Cypress 를 쓰고 있으면 `testing/cypress-best-practices.md`
- 도구 사용법이 아니라 플레이키 테스트의 원인 분류와 조직적 대응이 필요하면 `testing/eradicating-non-determinism-in-tests.md`, 실증 근거는 `testing/an-empirical-analysis-of-flaky-tests.md`
- 컴포넌트 단위로 내려서 해결할 문제라면 `testing/playwright-2.md`
- 특정 브라우저에서만 깨지는 원인을 추적하려면 `testing/playwright.md`

## 무엇이 들어있나
지침의 축은 하나다 — **테스트는 사용자가 보는 것에 결합해야 하고, 구현 세부에 결합하면 안 된다.** 그래서 로케이터는 역할(role)·레이블·텍스트 같은 사용자 지향 기준을 우선하고, 그것으로 안 되면 테스트 전용 속성(`data-testid`)을 명시적으로 붙이라고 한다. CSS 클래스나 DOM 경로에 매달리는 셀렉터는 리팩터링 한 번에 무더기로 깨진다.

두 번째 축은 대기다. Playwright 의 로케이터와 웹 우선 단언은 조건이 충족될 때까지 자동으로 재시도하므로, 고정 시간 sleep 은 느려지기만 하고 안정성을 주지 않는다. 임의 대기가 필요하다고 느끼는 지점은 대개 잘못된 단언 대상의 신호다.

세 번째는 격리다. 각 테스트는 자기 데이터를 만들고 독립 브라우저 컨텍스트에서 돌아야 하며, 그래야 병렬 실행과 재시도가 의미를 가진다. 여기에 더해 문서는 E2E 를 전부 다 쓰지 말고 사용자 흐름 중심으로 최소한만 유지하라는 방향, 그리고 실패 조사를 위해 트레이스·CI 통합을 켜 두라는 실무 조언을 붙인다.

## 인용 포인트
- "구현 세부가 아니라 사용자에게 보이는 것을 테스트하라" — 리뷰에서 클래스 셀렉터를 반려할 때 그대로 인용 가능한 원칙.
- 자동 대기가 있으므로 고정 sleep 은 불필요하다는 공식 입장은, 코드베이스에서 임의 대기를 일괄 제거하자는 제안의 근거가 된다.
- 테스트 격리와 독립적 데이터 생성이 병렬화의 전제라는 서술은, "테스트가 느리다"는 문제를 인프라가 아니라 설계 문제로 되돌린다.
