# Atlassian Agile Coach

https://www.atlassian.com/agile

## 한 줄
스크럼·칸반·백로그·에픽/스토리·스프린트 같은 실무 용어를 "그래서 지라에서 이걸 어떻게 굴리는가" 수준까지 내려서 설명하는, Jira 제작사의 무료 애자일 실무 가이드 모음.

## 페르소나
**팀 프로세스와 이슈 트래커 운영 규칙을 떠맡게 됐는데, 정작 에픽과 스토리의 경계·백로그 정리 주기 같은 걸 아무도 정의해 주지 않은 개발자.** 원문(Agile Manifesto, Scrum Guide)은 추상적이라 "그래서 이 티켓을 스토리로 쪼갤지 말지"에 답을 주지 않는다. 신규 입사자가 들어올 때마다 같은 설명을 반복하고 있고, 팀마다 용어 쓰임이 달라 스프린트 리뷰에서 이야기가 어긋난다. 온보딩 문서에 링크로 붙일 공통 설명이 필요한 상태다.

## 이럴 때 연다
- 신규 입사자 온보딩 문서에서 애자일 용어 설명을 외부 링크로 대체할 때
- 지라 운영 규칙(에픽 단위, 스토리 포인트, 백로그 그루밍 주기)을 처음 설계할 때
- 스크럼과 칸반 중 무엇을 쓸지 팀 안에서 비교 논의할 때
- 스탠드업·회고·백로그 리파인먼트 각 이벤트를 "왜 하는지"부터 다시 정리할 때
- 스프린트 계획에서 스토리 분해 기준이 사람마다 달라 견적이 흔들릴 때

## 이럴 땐 아니다
- 스크럼의 공식 정의·역할·산출물을 규범적으로 확정해야 한다면 — `planning/the-scrum-guide.md` (Atlassian은 해석과 변형을 섞는다)
- "애자일"의 원문 취지를 두고 다투는 중이라면 — `planning/agile-manifesto.md`
- 사용자 스토리 작성법 자체를 깊게 배우려면 — `planning/mountain-goat-software-user-stories.md`, `planning/user-story-mapping.md`
- 스프린트 대신 다른 작업 단위 체계를 검토 중이라면 — `planning/shape-up.md`
- 프로세스 개선의 효과를 지표로 증명해야 한다면 — `development/dora.md`

## 무엇이 들어있나
Agile Coach는 단일 문서가 아니라 여러 갈래의 실무 가이드 묶음이다. 스크럼/칸반 같은 프레임워크 비교, 프로젝트 관리(백로그, 스프린트, 견적, 스토리 포인트), 팀 이벤트(스탠드업, 회고, 리뷰), 그리고 애자일 조직 문화·DevOps 연계까지를 한 사이트 안에서 층층이 다룬다.
성격은 규범이 아니라 해설이다. Scrum Guide처럼 "무엇이 스크럼인가"를 정의하는 문서가 아니라, 현장에서 어떻게 변형되어 쓰이는지를 소개하고 각각의 장단을 붙인다. 그래서 "우리 팀은 왜 이렇게 하는가"를 정할 때는 유용하고, "이게 정통 스크럼이냐"를 판정할 때는 근거로 삼기 약하다.
Jira 마케팅 자산이라는 편향은 감안해야 한다. 도구가 해결해 주는 지점을 상대적으로 크게 그리며, 프로세스의 실패 원인을 조직 구조나 인센티브에서 찾는 논의는 거의 없다. 용어 합의와 온보딩용으로 쓰고, 판단 근거는 원문 쪽에 두는 조합이 안전하다.

## 인용 포인트
- 에픽·스토리·태스크의 계층 정의는 팀 이슈 트래커 규칙 문서에 그대로 옮겨 쓸 수 있고, "이건 에픽인가 스토리인가" 논쟁의 기준선이 된다.
- 스토리 포인트를 시간이 아니라 상대적 크기로 다룬다는 설명은, 포인트를 인시(man-hour)로 환산해 압박하는 관행에 반대할 때 인용한다.

## 코드 예시

에픽·스토리·태스크의 경계와 "포인트는 상대 크기"라는 규칙을, 매번 설명하는 대신 이슈 템플릿에 박아 둔 형태.

```markdown
## 스토리: <사용자 관점 한 줄>

- 에픽: EPIC-12          <!-- 여러 스프린트에 걸치는 목표 단위 -->
- 유형: story            <!-- 한 스프린트에 안 들어가면 스토리가 아니라 에픽이다 -->
- 포인트: 3              <!-- 상대 크기. 3점 ≠ 3일, 인시 환산 금지 -->

### 사용자 스토리
<역할>로서 <목적>을 위해 <기능>을 원한다.

### 완료 조건
- [ ] ...
- [ ] ...

### 범위 밖
- 이번 스토리에서 하지 않는 것 (다음 스토리로 뺀 것은 티켓 번호를 적는다)

### 태스크
- [ ] ...
```

템플릿은 칸을 만들 뿐 판정을 대신해 주지 않는다 — "한 스프린트에 들어가는가"는 결국 팀이 매번 합의해야 한다. 그리고 포인트 칸이 존재하는 이상 속도를 인시로 환산하려는 압력은 사라지지 않으므로, 주석이 아니라 팀 규칙 쪽에서 막아야 한다.
