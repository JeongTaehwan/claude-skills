# Kano 모델 실무 가이드

https://foldingburritos.com/blog/kano-model/

## 한 줄
Daniel Zacarias 가 쓴 Kano 모델 실무 가이드 — 이론 설명에 그치지 않고 기능별 설문 문항(기능형/역기능형 한 쌍), 5단계 응답 척도, 이산/연속 두 가지 분석 방법과 계산용 스프레드시트까지 제공해 실제로 돌릴 수 있게 만든 글.

## 페르소나
**기능 후보 목록을 앞에 두고 "이건 있으면 좋고 저건 필수"라는 감각적 분류만 반복하다 합의에 실패한 기획자·PO.** RICE 같은 점수제는 Impact 값을 결국 감으로 넣게 되고, 사용자에게 물어보면 다들 "다 있으면 좋다"고 답한다. 필요한 건 **없을 때의 반응까지 함께 묻는 설문 설계** — 그래야 필수 기능과 있으면 좋은 기능이 갈린다.

## 이럴 때 연다
- 기능 후보를 사용자 만족 관점에서 필수/성능/매력/무관심으로 분류해야 할 때
- "다 중요하다"는 이해관계자 의견을 데이터로 반박해야 할 때
- 리소스가 부족해 무엇을 빼도 되는지(무관심 기능 = 낭비) 근거를 찾을 때
- 경쟁사 대비 차별화 포인트를 고를 때, 이미 기대치가 된 기능과 아직 놀라움을 주는 기능을 구분해야 할 때
- 실제 설문 문항과 집계 방식이 필요할 때 — 이 글은 스프레드시트를 제공한다

## 이럴 땐 아니다
- 도달 범위·공수 기준으로 정량 순위를 매기려면 `planning/rice.md`
- 목표와 기능의 인과 연결이 목적이면 `planning/impact-mapping.md`
- 요구의 배경 상황과 동기를 정성적으로 캐내려면 `planning/jobs-to-be-done-know-your-customers-jobs-to-be-done.md`
- 개발 사이클 안에서 범위를 잘라내는 문제면 `planning/shape-up.md`

## 무엇이 들어있나
분류는 네 가지다. Must-be(없으면 강한 불만, 있어도 만족도는 안 오름), Performance(많을수록 만족도 상승, 선형), Attractive(없어도 불만 없지만 있으면 큰 만족), Indifferent(있든 없든 무반응 — 만들면 돈 낭비).
설문의 핵심 장치는 **질문 쌍**이다. 같은 기능에 대해 "있다면 어떻게 느끼십니까"(기능형)와 "없다면 어떻게 느끼십니까"(역기능형)를 따로 묻고, 응답은 좋다/당연하다/무관심/감수한다/싫다 5단계로 받는다. 두 답의 조합을 평가표에 넣어야 비로소 카테고리가 나온다 — 한쪽만 물으면 전부 "필요하다"로 수렴한다.
분석은 두 층위다. 이산 분석은 응답을 표에 대입해 최빈 카테고리를 취하는 빠른 방식이고, 연속 분석은 응답을 수치화(중요도까지 함께 수집)해 평균·표준편차로 산점도를 그린다. 이산은 빠르지만 정보 손실이 있다는 것을 글이 명시한다.
우선순위 규칙은 Must-be > Performance > Attractive > Indifferent.
가장 실무적으로 중요한 통찰: **매력 요소는 시간이 지나면 필수 요소로 내려앉는다.** 2007년 아이폰의 터치스크린이 그랬듯, 오늘의 차별화는 내년의 기본 기대치다 — 그래서 Kano 분류는 한 번 하고 끝내는 것이 아니라 주기적으로 다시 재야 한다.
실행 가이드도 구체적이다 — 한 번에 다루는 기능 수를 적게 유지하고, 인구통계 세그먼트별로 충분한 응답자를 확보하며, 텍스트만으로 애매하면 목업을 함께 보여주라고 권한다.

## 인용 포인트
- "다 중요하다"는 회의에서: 없을 때의 반응을 함께 묻지 않으면 필수와 선호를 구분할 수 없다는 논리.
- 과거에 차별화 기능이었던 것을 계속 자랑하는 로드맵에 대해, "매력 → 필수" 이동을 근거로 재분류를 요구할 수 있다.

## 코드 예시

"한쪽만 물으면 전부 필요하다로 수렴한다"는 지적을, 두 답의 조합에서만 카테고리가 나오는 평가표로 옮긴 것.

```python
# 응답 척도: 좋다 / 당연하다 / 무관심 / 감수한다 / 싫다
LIKE, MUST_BE, NEUTRAL, LIVE_WITH, DISLIKE = range(5)

# 행 = 기능형("있다면?") 답, 열 = 역기능형("없다면?") 답
# A 매력 · O 성능 · M 필수 · I 무관심 · R 역효과 · Q 모순응답
TABLE = [
    ["Q", "A", "A", "A", "O"],   # 있으면 좋다
    ["R", "I", "I", "I", "M"],   # 있는 게 당연하다
    ["R", "I", "I", "I", "M"],   # 있든 없든 무관
    ["R", "I", "I", "I", "M"],   # 있어도 감수한다
    ["R", "R", "R", "R", "Q"],   # 있으면 싫다
]

def classify(functional, dysfunctional):
    return TABLE[functional][dysfunctional]

classify(LIKE, DISLIKE)     # "O" — 있으면 좋고 없으면 싫다 → 성능 요소
classify(MUST_BE, DISLIKE)  # "M" — 당연하고 없으면 싫다 → 필수 요소
classify(LIKE, NEUTRAL)     # "A" — 없어도 그만이지만 있으면 좋다 → 매력 요소
```

이 표는 응답 한 쌍을 라벨로 바꿀 뿐이고, 응답자 전체를 최빈값으로 뭉개는 이산 분석에서 분포 정보가 사라진다 — 40%가 M, 35%가 I 인 기능과 90%가 M 인 기능이 같은 글자로 보인다. `Q`(모순) 비율이 높게 나오면 응답자가 아니라 문항 서술이 애매한 것이고, 결과는 그 시점의 스냅샷이라 매력 요소가 필수로 내려앉으면 다시 재야 한다.
