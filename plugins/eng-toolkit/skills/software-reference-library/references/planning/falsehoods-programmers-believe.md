# Falsehoods Programmers Believe (awesome-falsehood)

https://github.com/kdeldycke/awesome-falsehood

## 한 줄
"이름은 하나다", "주소에는 우편번호가 있다", "시간은 뒤로 가지 않는다" 같은 — 개발자가 무심코 참이라고 가정했다가 데이터가 들어오는 순간 깨지는 전제들을 주제별로 모아둔 큐레이션 저장소.

## 페르소나
**주문·회원 스키마를 새로 설계하면서 필드 하나하나에 제약을 걸고 있는 백엔드 엔지니어.** 이름 컬럼 길이를 얼마로 할지, 전화번호를 정규식으로 막을지, 성별을 enum 두 개로 둘지 지금 정하면 나중에 마이그레이션 비용이 크다. 리뷰어들도 "그 정도면 되겠지"라고 넘어가는데, 실제로 어디서 깨지는지 사례가 있어야 방어할 수 있다.

## 이럴 때 연다
- 회원가입·배송지·결제자 정보처럼 사람이 입력하는 필드의 스키마와 검증 규칙을 확정하기 직전
- 해외 배송·다국가 결제로 도메인을 확장하면서 기존 주소·통화·시간 처리가 버틸지 점검할 때
- 배치·정산·쿠폰 만료처럼 시간 계산이 걸린 로직에서 타임존·서머타임·윤초 가정을 재검토할 때
- 요구사항 문서에 숨어 있는 암묵적 전제를 리뷰에서 끄집어내야 할 때
- 정규식 하나로 이메일·전화번호를 막자는 제안이 올라왔을 때 반대 근거가 필요할 때

## 이럴 땐 아니다
- 스키마 변경 자체의 안전한 절차(무중단 마이그레이션 등)를 찾는 거라면 이 저장소가 아니라 아키텍처 쪽 자료를 봐야 한다 — `architecture/designing-data-intensive-applications.md`
- 입력 검증을 코드로 구현할 스키마 검증 라이브러리를 찾는 거면 `development/zod.md`
- 보안 관점의 입력 처리 규칙이면 `development/owasp-cheat-sheet-series.md`

## 무엇이 들어있나
"Falsehoods programmers believe about X" 형식의 글들을 X 별로 묶은 링크 모음이다. 이름, 주소, 시간과 타임존, 전화번호, 이메일, 성별, 통화와 금액, 국가·지리, 네트워크 등이 대표 카테고리다.
각 글의 형식은 대체로 동일하다 — 참이라고 믿기 쉬운 명제를 번호 매겨 나열하고, 각각이 왜 거짓인지 실제 사례로 반박한다.
이 저장소의 실질적 용도는 읽고 감탄하는 것이 아니라 **설계 리뷰의 체크리스트**다. 내가 지금 넣으려는 제약이 이 목록에 반례로 등장하는지 검색하는 방식으로 쓴다.
통념과 어긋나는 지점: 개발자가 "예외 케이스"라고 부르는 것들 상당수가 실제로는 예외가 아니라 특정 문화권·제도에서는 기본값이다. 예외 처리로 미루면 그 시장에 못 들어간다.

## 인용 포인트
- 리뷰에서 "그런 경우가 있나요?"라는 반문이 나올 때, 해당 카테고리 글의 반례 목록을 그대로 붙이면 논쟁이 짧아진다.
- 금액·통화 필드를 부동소수점으로 두자는 제안에 대한 반박 근거를 여기서 찾을 수 있다.
