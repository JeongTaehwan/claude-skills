# Product Fail (Marty Cagan)

https://www.svpg.com/product-fail/

## 한 줄
"아이디어 → 사업성 검토 → 로드맵 → 요구사항 문서 → 디자인 → 개발 → QA → 배포"라는 익숙한 프로세스를 단계별로 해부하면서, 각 단계가 왜 실패를 구조적으로 생산하는지를 10개 항목으로 짚은 글이다.

## 페르소나
**분기 로드맵이 위에서 내려오고, 자기 역할은 그걸 요구사항 문서로 번역하는 것뿐인 사람.** 프로세스가 잘못됐다는 감은 있는데, 회의에서 문제를 제기하면 "그럼 어떻게 하자는 거냐"로 되돌아온다. 필요한 건 대안 제시 이전에 **문제의 구조를 조목조목 이름 붙여 놓은 문서**다. 이 글은 각 단계의 결함을 분리해서 제시하기 때문에, 전부를 뒤집자는 주장 대신 한 지점만 골라 논의를 시작할 수 있게 해 준다.

## 이럴 때 연다
- 로드맵 중심·요구사항 전달 중심 기획의 문제를 조직에 설득해야 할 때
- 개발팀이 항상 마지막에 불려 와서 "이거 왜 이렇게 만들기로 했나"를 되묻는 상황이 반복될 때
- 기획 프로세스 개선 논의의 출발 문서가 필요할 때
- "우리는 애자일을 한다"는데 애자일이 개발 단계에만 적용되고 있는 게 이상할 때
- 산출물(기능 배포) 기준으로 성과를 보는 관행을 성과(outcome) 기준으로 바꾸자고 제안할 때

## 이럴 땐 아니다
- 문제 진단이 아니라 **대안 절차**가 필요하면 `planning/teresa-torres-opportunity-solution-tree.md`, `planning/product-trio.md`
- Cagan의 다른 글 전반과 그가 제시하는 대안(empowered team 등)은 `planning/svpg-marty-cagan.md`
- 로드맵을 없애는 대신 **6주 고정 사이클**이라는 구체적 대안을 검토 중이면 `planning/shape-up.md`
- 로드맵 자체를 잘 만드는 실무 가이드를 원하면 `planning/aha.md`, `planning/roman-pichler.md`
- 우선순위 결정 방법 자체가 문제라면 `planning/rice.md`, `planning/kano.md`

## 무엇이 들어있나
글의 형식이 특이하다. 먼저 대부분의 회사가 실제로 쓰는 프로세스를 8단계로 그대로 서술한 뒤 — 임원·이해관계자에게서 아이디어가 나오고, 사업성 검토와 연간·분기 계획을 거쳐 우선순위가 매겨진 로드맵이 만들어지고, PM이 요구사항을 정리하고, 디자인이 붙고, 엔지니어가 스펙을 받아 스프린트로 쪼개고, QA를 거쳐 배포된다 — 그 다음에 문제를 10개로 나눠 지목한다.
지목되는 결함들: 아이디어의 출처가 세일즈·이해관계자에 편중되어 팀이 권한을 못 갖는다는 점, 계획 단계의 사업성 검토가 근거 없는 숫자 위에 세워진다는 점, PM 역할이 프로젝트 관리로 축소된다는 점, 디자인이 뒤늦게 화장하는 일로 밀린다는 점, 엔지니어가 너무 늦게 합류해 혁신 여지가 사라진다는 점, 애자일이 프로세스 끝단에서만 적용된다는 점, 산출물 중심이라 성과를 안 본다는 점, 고객 검증이 완성 이후로 미뤄진다는 점, 그리고 기회비용.
Cagan이 가장 뼈아프게 짚는 건 세 번째 — 두 가지 불편한 진실이다. 아이디어의 **절반 이상은 어차피 작동하지 않고**, 작동하는 아이디어조차 실제로 사업 가치를 낼 수준이 되려면 여러 번의 반복이 필요하다는 것. 이 두 가지를 인정하면 위 프로세스는 성립할 수 없다. 검증이 맨 끝에 있기 때문이다.

## 인용 포인트
- "적어도 우리 아이디어의 절반은 작동하지 않는다" + "작동하는 것도 여러 번의 반복을 거쳐야 필요한 사업 가치에 도달한다" — 이 두 문장이 로드맵 확정형 기획을 무너뜨리는 핵심 논거다. 실험 데이터로 뒷받침하려면 `planning/online-controlled-experiments-at-large-scale.md` 를 같이 걸면 강해진다.
- "엔지니어를 너무 늦게 부른다"는 항목은, 개발자가 기획 초기 논의에 들어가야 하는 이유를 조직에 설명할 때 그대로 인용 가능하다.
- 산출물(output) 대 성과(outcome) 구분은, 분기 목표를 "기능 N개 배포"로 잡는 관행을 재고할 때의 표준 인용구다.

## 코드 예시

글이 지목한 10개 결함을 그대로 프로세스 감사 항목으로 내린 것 — "그럼 어떻게 하자는 거냐"로 되돌아오는 회의에서, 전부를 뒤집는 대신 아니오가 나온 한 줄만 골라 논의를 시작하기 위한 형식.

```markdown
# 기획 프로세스 감사 — 2026 Q3 / 결제 도메인

각 항목은 "지난 분기에 실제로 그랬는가"로 답한다. 인상이 아니라 사례를 적는다.

| # | 점검 | 답 | 근거가 된 사례 |
|---|---|---|---|
| 1 | 아이디어가 팀 밖(임원·세일즈)에서만 왔는가 | 예 | 분기 항목 7개 중 6개 |
| 2 | 사업성 검토 숫자에 출처가 있었는가 | 아니오 | ROI 추정 근거 없음 |
| 3 | PM이 발견이 아니라 일정 조율만 했는가 | 예 | |
| 4 | 디자인이 결정 이후에 투입됐는가 | 예 | |
| 5 | 엔지니어가 스펙 확정 후에 처음 봤는가 | 예 | 착수 후 재설계 2건 |
| 6 | 애자일이 개발 단계에만 적용됐는가 | 예 | |
| 7 | 분기 목표가 "기능 N개 배포"였는가 | 예 | ← 산출물 목표 |
| 8 | 고객 검증이 완성 이후로 미뤄졌는가 | 예 | |
| 9 | 실패한 아이디어를 배포 전에 걸러냈는가 | 아니오 | 걸러진 것 0건 |
| 10 | 위 항목에 쓴 시간의 기회비용을 계산했는가 | 아니오 | |

## 이번 분기에 고칠 것 (하나만)
#5 — 스펙 확정 전 엔지니어 참여. 나머지 9개는 다음 분기 이후로 미룬다.
```

이 표는 진단까지만 한다 — 아니오를 예로 바꾸는 절차는 이 글에 없고, 대안 쪽 자료에서 가져와야 한다.
