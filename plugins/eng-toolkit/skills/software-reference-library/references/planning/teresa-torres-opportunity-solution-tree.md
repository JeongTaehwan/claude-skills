# Teresa Torres — Opportunity Solution Tree

https://www.producttalk.org/opportunity-solution-tree/

## 한 줄
목표 → 기회(사용자가 겪는 문제) → 솔루션 → 실험을 하나의 트리로 그려, "이 기능이 어떤 문제를 푸는지"와 "이 문제가 어떤 목표에 닿는지"를 강제로 연결하게 만드는 도구. 『Continuous Discovery Habits』의 중심 도구다.

## 페르소나
**아이디어는 넘치는데 무엇을 먼저 할지 정할 근거가 없는 팀의 PM.** 인터뷰도 하고 VOC도 모으는데, 회의에서는 결국 개별 기능 아이디어들이 평평하게 나열되고 목소리로 순위가 정해진다. "이 기능 왜 하죠?"에 "고객이 요청했어요"밖에 답할 게 없다.

## 이럴 때 연다
- 우선순위 회의 직전, 후보들을 같은 축에 올려놓아야 할 때 (솔루션끼리가 아니라 기회끼리 비교하게 만드는 게 핵심)
- 사용자 인터뷰 결과가 쌓였는데 구조화가 안 되어 인사이트로 안 바뀔 때
- 하나의 기회에 대해 대안 솔루션을 억지로 3개 이상 만들어 비교하고 싶을 때
- 실험 설계 전에 "이 실험이 검증하려는 가정"이 트리 어디에 붙는지 명시해야 할 때

## 이럴 땐 아니다
- 이미 무엇을 만들지 정해졌고 릴리스 범위를 자르는 문제라면 `planning/user-story-mapping.md`
- 후보에 숫자를 매겨 순서를 설명해야 하면 `planning/rice.md`
- 목표 자체(어떤 지표를 트리 꼭대기에 놓을지)가 안 정해졌으면 `planning/north-star-metric.md`, `planning/heart.md`
- 조직 구조 차원의 문제라면 `planning/svpg-marty-cagan.md`
- 발견 활동을 누가 함께 하는지(3인조 구성)는 `planning/product-trio.md`

## 무엇이 들어있나
트리의 규칙이 곧 주장이다. 꼭대기에는 하나의 결과 지표(outcome)만 둔다 — 목표가 여럿이면 트리가 성립하지 않고 우선순위도 못 정한다.
기회는 "사용자가 겪는 문제·니즈·불만"이지 해결책이 아니다. 여기에 기능 이름을 적는 순간 트리는 기능 목록으로 퇴화한다. Torres가 반복해서 경고하는 실패 모드가 이것이다.
비교는 솔루션끼리가 아니라 형제 기회끼리 한다. 이 순서를 지키면 "A 기능 vs B 기능" 같은 취향 논쟁이 "어떤 사용자 문제가 더 목표에 가까운가"로 바뀐다.
한 기회에 솔루션을 여러 개 붙이도록 강제하는 것도 의도적이다. 첫 번째 아이디어에 고정되는 것을 막기 위한 장치다.
실험은 솔루션이 아니라 솔루션 밑에 깔린 가정에 붙인다.

## 인용 포인트
- "기회는 해결책이 아니다" — 기회 트리가 기능 목록으로 무너질 때 되돌리는 규칙.
- 트리 꼭대기는 하나의 outcome — 목표가 5개인 로드맵을 문제 삼을 때 쓸 수 있다.
