# Open Product Management

https://github.com/ProductHired/open-product-management

## 한 줄
PM 자료를 주제별로 늘어놓은 링크 목록이 아니라, "무엇을 먼저 읽고 다음에 무엇을 읽을지"의 학습 경로 형태로 묶은 큐레이션 저장소다.

## 페르소나
**신규 합류자에게 "기획 좀 배워두라"고 말해야 하는데, 넘겨줄 목록이 자기 북마크뿐인 리드.** 자료 자체는 널려 있지만 순서가 없어서, 신입은 Marty Cagan 아티클과 OKR 문서와 스크럼 가이드를 무작위로 읽다가 서로 충돌하는 주장들에 헷갈리고 만다. 필요한 건 자료 더미가 아니라 진입 순서다. 개발자가 기획 쪽으로 역할을 넓히는 경우에도 같은 문제를 겪는다.

## 이럴 때 연다
- 신규 PM 또는 기획 역할을 겸하게 된 개발자의 온보딩 커리큘럼을 짤 때
- PM 직무 전환을 준비하며 학습 순서를 잡을 때
- 팀 스터디의 4~8주짜리 커리큘럼 뼈대를 만들 때
- 특정 주제(가격 정책, 로드맵, 인터뷰 등)의 정평 있는 자료를 한 번에 훑고 싶을 때

## 이럴 땐 아니다
- 링크를 최대한 넓게 모은 쪽을 원하면 `planning/awesome-product-management.md`
- 최신 흐름·현업 담론을 따라가려면 큐레이션 저장소가 아니라 `planning/lenny-s-newsletter.md`, `planning/mind-the-product.md`
- 개별 프레임워크의 정본은 각 원전으로 — `planning/rice.md`, `planning/svpg-marty-cagan.md`, `planning/heart.md`
- 엔지니어에게 기획 관점을 설명할 자료면 `planning/posthog-newsletter.md`

## 무엇이 들어있나
GitHub 저장소 형태의 큐레이션이며, 콘텐츠를 직접 생산하지 않고 외부 자료를 골라 배치한다. 그래서 이 저장소의 가치는 개별 링크가 아니라 **배치 순서와 선별 기준**에 있다.
큐레이션 저장소의 공통 한계는 그대로 적용된다 — 링크 부패(죽은 링크)와 갱신 시차. 최근 몇 년의 자료가 얇을 수 있으니, 최신성을 요구하는 주제(AI 제품, 최근 조직론)는 여기서 찾지 말 것.
반대로 시간이 지나도 안 바뀌는 기초(발견, 우선순위, 지표, 인터뷰)는 여전히 유효하다. 온보딩 커리큘럼용으로 쓰기 좋은 이유가 이것이다.
