# Getting Real (Basecamp, 무료)

https://basecamp.com/gettingreal

## 한 줄
37signals(현 Basecamp)가 2006년에 쓴, "기능을 더하는 것이 아니라 빼는 것이 제품 결정"이라고 주장하는 짧은 무료 웹북 — 스펙 문서와 기능도표 대신 실제 화면(인터페이스)부터 만들라는 방법론.

## 페르소나
**요구사항 목록이 계속 늘어나기만 하고 아무도 자르지 못해서, 출시 일정이 두 번째로 밀린 기획자·개발 리드.** 이해관계자마다 "이것도 있어야 하지 않나"를 하나씩 얹고 그 각각은 다 나름 타당해 보인다. 필요한 건 새 우선순위 프레임워크가 아니라, **덜 만드는 것 자체가 정당한 결정**이라고 말해줄 수 있는 근거와 언어다.

## 이럴 때 연다
- 스코프가 계속 불어나는 프로젝트에서 "지금 버전에서는 안 만든다"를 문서로 정당화해야 할 때
- 긴 PRD 를 쓰기 전에, 화면 스케치부터 만들고 논의하자고 제안할 때
- 초기 제품·내부 도구처럼 빠르게 형태를 잡아야 하는 일에서 과잉 설계를 줄이는 원칙이 필요할 때
- 팀에 "작게 시작한다"는 공유된 태도를 심고 싶을 때 짧게 읽힐 읽을거리를 찾을 때

## 이럴 땐 아니다
- 같은 회사의 더 최신·더 구조화된 개발 사이클 운영법(6주 사이클, appetite, betting)이 필요하면 `planning/shape-up.md`
- 무엇을 자를지 데이터로 고르고 싶다면 이 책이 아니라 `planning/kano.md` 나 `planning/rice.md`
- 제대로 된 PRD 를 써야 하는 상황이면 `planning/atlassian-prd.md`
- 큰 조직에서 문서로 정렬을 만들어야 하는 상황이면 `planning/design-docs-at-google.md` 나 `planning/working-backwards.md` 쪽이 맞다

## 무엇이 들어있나
핵심 주장은 "Build Less" — 경쟁사보다 기능을 적게, 옵션을 적게, 추상화를 적게, 인력을 적게 두라는 것이다. 기능 대결에서 이기려 하지 말고 다른 게임을 하라고 본다.
문서보다 실물 우선. 기능 명세서·간트차트·와이어프레임 단계를 최소화하고 실제 인터페이스를 먼저 만들어 그것을 논의의 기준으로 삼으라고 주장한다("epicenter design" — 화면의 핵심부터 그린다).
스코프 관리에 대한 이 책의 유명한 태도는 **일정이 밀릴 때 늘리지 말고 기능을 자르라**는 것이다.
읽을 때 유의할 점: 2006년 소규모 자기자본 SaaS 팀의 맥락에서 쓰였다. 규제·정산·결제처럼 요구사항을 임의로 자를 수 없는 도메인에는 그대로 적용되지 않는다. 태도를 빌려오되 규칙으로 옮기면 위험하다.

## 인용 포인트
- "일정이 밀리면 범위를 줄인다"는 원칙을 팀 합의로 만들 때 출처로 쓰기 좋다.
- 기능 추가 요청을 반려하는 문서에서 "만들지 않는 것도 결정"이라는 프레임을 세울 때.
