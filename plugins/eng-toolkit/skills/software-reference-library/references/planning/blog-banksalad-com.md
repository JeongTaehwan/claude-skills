# 뱅크샐러드 기술블로그

https://blog.banksalad.com/

## 한 줄
국내 기술블로그 중 드물게 **제품 조직 구조·의사결정 프로세스·직군 간 협업 방식**을 코드 이야기만큼 자주 다루는 곳 — 기획과 개발 사이의 운영 규칙을 국내 맥락에서 참고할 때 쓰는 사례집.

## 페르소나
**"이건 기획이 정할 일인가, 개발이 정할 일인가"의 경계가 매번 흐려서 같은 갈등이 반복되는 팀의 리드.** 해외 자료(Shape Up, SVPG, GitLab Handbook)를 읽어 봤지만 조직 규모·의사결정 문화·직군 구성이 달라 그대로 옮기면 부작용이 난다. 한국 회사가 실제로 어떤 규칙을 세웠고 무엇이 안 됐는지, 같은 언어로 쓰인 사례가 필요한 상황이다.

## 이럴 때 연다
- 제품팀 구성(스쿼드·챕터·트라이브 등)이나 직군 간 역할 분담을 바꾸려 할 때 국내 선례를 찾을 때
- 기획–디자인–개발 사이의 문서·리뷰·핸드오프 규칙을 정하면서 참고 사례가 필요할 때
- 금융/핀테크 도메인의 데이터·정합성·규제 제약이 제품 결정에 어떻게 반영되는지 보고 싶을 때
- 사내 발표나 제안서에 "국내에서도 이렇게 한다"는 사례를 붙여야 할 때

## 이럴 땐 아니다
- 조직 운영 규칙의 완전한 참조 매뉴얼이 필요하다면 — `planning/gitlab-handbook.md`, `planning/posthog-handbook.md`
- 제품 조직 이론의 원문(권한 있는 주장)을 찾는다면 — `planning/svpg-marty-cagan.md`, `planning/product-trio.md`
- 국내 기술블로그를 아키텍처·구현 사례 목적으로 본다면 — `development/techblog-woowahan-com.md`, `development/toss-tech.md`, `development/tech-kakaopay-com.md`, `development/medium-com-daangn.md`
- 커머스(주문·결제·쿠폰) 도메인의 구현 사례가 필요하다면 — `development/helloworld-kurly-com.md`, `development/techblog-woowahan-com.md`

## 무엇이 들어있나
개별 글 단위의 자료가 아니라 지속적으로 갱신되는 블로그이므로, 특정 주장을 인용하려면 그때그때 해당 글을 직접 확인해야 한다. 이 항목이 가리키는 것은 **이 블로그가 축적한 주제의 성향**이다.
성향은 뚜렷하다. 프레임워크 사용기나 성능 튜닝기보다, 팀을 어떻게 나눴고 결정을 누가 어떻게 내리며 그 방식이 어떤 문제를 낳았는지에 대한 회고성 글의 비중이 높다. 개발 문화·채용·온보딩·직군 협업이 반복 주제로 나타난다.
한국어라는 점, 그리고 조직 규모와 채용 시장이 유사하다는 점 때문에 해외 사례보다 이식 가능성이 높다. 다만 회사 브랜딩 목적의 글이라 실패와 비용은 축소되어 서술되는 경향이 있으므로, "이렇게 하면 된다"가 아니라 "이런 선택지를 이 회사는 이렇게 골랐다"로 읽는 편이 안전하다.
