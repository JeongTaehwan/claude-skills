# Checklist Design

https://www.checklist.design/

## 한 줄
버튼·폼·모달 같은 UI 요소와 회원가입·결제 같은 페이지 유형별로 "빠뜨리기 쉬운 것"을 체크리스트 형태로 모아둔 사이트 — 이론이 아니라 리뷰 직전에 훑는 용도의 목록이다.

## 페르소나
**혼자 화면을 처음부터 끝까지 만들어야 해서, 디자이너가 잡아줬을 법한 누락을 스스로 잡아야 하는 개발자.** 결제 폼을 다 만들고 나니 에러 상태를 안 만들었고, 회원가입 화면에는 비밀번호 표시 토글이 없고, 모달은 Esc로 안 닫힌다. 매번 배포 후에 하나씩 발견되는데, 만들기 전에 훑을 수 있는 목록이 필요하다.

## 이럴 때 연다
- 화면 하나를 만들기 직전, 그 유형에서 흔히 빠뜨리는 항목을 먼저 훑고 싶을 때
- PR 올리기 전 UI 자가 점검 목록이 필요할 때
- 디자이너 없이 만든 화면을 QA에 넘기기 전 1차 필터로 쓸 때
- 팀 내 UI 리뷰 체크리스트의 초안을 만들 때

## 이럴 땐 아니다
- 왜 그래야 하는지 원리와 근거가 필요하면 `design/nn-g-10-usability-heuristics.md` 또는 `design/laws-of-ux.md`
- 접근성 준수를 공식 기준으로 판정해야 하면 `design/wcag-2-2.md`
- 컴포넌트 구현의 role·키보드 동작 명세가 필요하면 `design/aria-authoring-practices-guide.md`
- 시각적 완성도를 끌어올리는 감각 훈련은 `design/refactoring-ui.md`

## 무엇이 들어있나
컴포넌트(버튼, 입력, 체크박스, 모달, 카드 등)와 페이지(회원가입, 로그인, 결제, 404, 가격표 등) 단위로 나뉜 항목마다, 지켜야 할 사항이 짧은 문장의 목록으로 나열된다. 각 항목은 한 줄짜리 판정 가능한 문장이라 "됐다/안 됐다"로 바로 체크된다.
이 자료의 성격은 교과서가 아니라 **점검표**다. 왜 그런지를 설명하지 않는 대신, 배포 직전 5분 안에 훑을 수 있는 밀도를 택했다. 그래서 학습 자료로는 얕고, 누락 방지 도구로는 효율이 높다.
정본 표준이 아니라 큐레이션이므로, 접근성이나 법적 요건 판정의 근거로는 부적절하다 — 그 용도로는 WCAG를 봐야 한다.

## 인용 포인트
- UI 리뷰가 매번 리뷰어 취향으로 흐를 때, 해당 컴포넌트 체크리스트를 팀의 최소 기준선으로 고정하면 논쟁이 줄어든다.
