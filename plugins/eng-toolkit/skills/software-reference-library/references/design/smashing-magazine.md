# Smashing Magazine

https://www.smashingmagazine.com/

## 한 줄
2006년부터 이어져 온 웹 디자인·프론트엔드 매거진 — 디자인 시스템, 접근성, CSS 신기능, 성능, 폼·테이블 UX 같은 주제를 실무자가 길게 쓰고 편집을 거쳐 싣는, 개인 블로그와 공식 문서 사이의 층을 메우는 곳.

## 페르소나
**공식 문서에는 "이 속성은 이렇게 동작한다"까지만 있고, 실제로 우리 상황에 어떻게 조합해야 하는지가 빠져 있어 막힌 프론트엔드 개발자.** 예를 들어 복잡한 필터 폼이나 반응형 데이터 테이블을 접근성까지 지키면서 만들어야 하는데, 스펙 문서도 디자인 시스템 문서도 그 조합까지는 다루지 않는다. 같은 문제를 이미 풀어 본 사람의 긴 글이 필요하다.

## 이럴 때 연다
- 특정 UI 문제(반응형 테이블, 복잡한 폼, 날짜 선택기 등)의 실무 사례와 트레이드오프를 훑을 때
- CSS 신기능(컨테이너 쿼리, 서브그리드, `:has()` 등)의 실제 활용 패턴을 볼 때
- 디자인 시스템 운영·거버넌스처럼 문서화가 드문 주제의 경험담이 필요할 때
- 접근성 개선을 실제 코드 수준에서 어떻게 적용했는지 사례가 필요할 때
- 팀에 공유할 읽을거리를 고를 때

## 이럴 땐 아니다
- 사양·API의 정확한 정의가 필요하면 `development/mdn-web-docs.md`, `design/mdn-accessibility.md`
- 사용자 연구에 기반한 판정이 필요하면 `design/nn-g-design-patterns.md`
- CSS 기법을 주제별로 정리된 형태로 찾으려면 `design/css-tricks-guides.md`
- 로딩 성능·저속 네트워크 대응은 `development/web-vitals.md` 쪽이 더 직접적이다

## 무엇이 들어있나
아티클, 뉴스레터, 온라인 워크숍, 인쇄·전자책을 함께 운영하는 매체다. 글의 성격은 튜토리얼보다 사례 서술에 가까워, 배경 → 시도한 방법 → 실패 지점 → 최종 결론 순으로 길게 이어지는 경우가 많다. 개인 블로그와 다른 점은 편집을 거친다는 것이고, 벤더 공식 문서와 다른 점은 특정 제품을 팔 이유가 없어 대안 비교와 한계 언급이 남아 있다는 것이다. 다만 매체 특성상 글마다 필자와 발행 시점이 제각각이므로, 오래된 CSS·브라우저 관련 글은 현재 사양과 어긋날 수 있어 발행일 확인이 필요하다.

## 인용 포인트
- 특정 기법의 실무 도입 사례가 필요할 때, "누군가 이미 이렇게 했다"는 근거로 기획·설계 문서에 붙이기 좋다. 다만 규범이 아니라 사례이므로 사양 문서와 함께 인용하는 편이 안전하다.
