# WCAG 2.2

https://www.w3.org/TR/WCAG22/

## 한 줄
웹 접근성의 규범 원문 — "보기 좋게 만들라"가 아니라 각 항목이 통과/실패로 판정 가능한 성공 기준(Success Criteria)으로 쓰여 있어서, 요구사항 문서와 QA 체크리스트에 그대로 옮겨 담을 수 있는 유일한 형태의 접근성 문서다.

## 페르소나
**"접근성 대응해야 한다"는 말은 위에서 내려왔는데 무엇을 어디까지 해야 끝인지 아무도 정의해주지 않은 상태의 프론트/백엔드 엔지니어.** 블로그 글은 "alt 넣으세요" 수준에서 끝나고, 디자이너는 대비값을 물어보면 감으로 답하고, QA는 테스트 케이스를 뭘로 잡아야 할지 모른다. 필요한 건 조언이 아니라 **합격선의 정의**다. 국내 웹 접근성 인증 심사도 결국 이 문서의 기준을 따르므로, 여기서 시작하지 않으면 나중에 두 번 일한다.

## 이럴 때 연다
- 접근성 요구사항을 스펙 문서에 적어야 하는데 "어느 레벨(A/AA/AAA)까지"를 정해야 할 때
- QA 접근성 테스트 항목을 도출할 때 — 성공 기준 하나가 테스트 케이스 하나가 된다
- 색 대비, 포커스 표시, 터치 타깃 크기 같은 구체적 수치를 놓고 디자이너와 합의해야 할 때
- 자동화 도구가 낸 위반 리포트의 규칙 ID가 실제로 어떤 기준을 가리키는지 원문 확인이 필요할 때
- 국내 웹 접근성 인증 심사·공공기관 납품 요건을 대비할 때
- WCAG 2.1 기준으로 만들어둔 체크리스트를 2.2로 갱신할 때 (2.2에서 신설된 기준만 따로 보면 된다)

## 이럴 땐 아니다
- 규범 원문은 읽기 힘들고 "지금 당장 무엇을 고칠지" 순서가 필요하면 `design/the-a11y-project.md` 의 체크리스트로 먼저 간다
- 각 기준을 코드로 어떻게 구현하는지 예제가 필요하면 `design/mdn-accessibility.md`
- 커스텀 위젯(탭, 콤보박스, 모달)의 ARIA 역할·키보드 조작 규약은 `design/aria-authoring-practices-guide.md`
- 대비 계산기·WCAG 체크리스트의 실무형 요약본은 `design/webaim.md`
- 위반을 자동으로 검출하는 도구는 `testing/axe-core.md`

## 무엇이 들어있나
4개 원칙(Perceivable / Operable / Understandable / Robust) 아래 가이드라인이 있고, 그 아래 각각 A·AA·AAA 등급이 붙은 성공 기준이 나열되는 3단 구조다. 실무에서 목표로 잡는 선은 거의 항상 **AA**다.
이 문서의 핵심 성질은 성공 기준이 **기술 중립적이고 테스트 가능하게** 쓰였다는 점이다. "충분히 크게"가 아니라 판정 가능한 문장으로 서술되어 있어서, 스펙-구현-QA 사이에서 해석 다툼이 생기지 않는다. 접근성 논의가 취향 싸움으로 번질 때 이 문서를 펴는 것이 가장 빠른 종결 수단이다.
2.2는 2.1의 상위 호환이다 — 2.1의 기준은 그대로 유지되고 위에 새 기준이 추가되는 구조라, 이미 2.1로 맞춰둔 팀은 델타만 보면 된다. 2.2에서 추가된 항목은 포커스 가시성, 드래그 대체 수단, 타깃 크기, 인증 과정에서의 인지 부담(비밀번호를 외워 다시 입력하게 만들지 말 것) 쪽에 몰려 있다. 커머스 기준으로는 결제·로그인·주소 입력 흐름이 가장 크게 걸리는 영역이다.
각 기준마다 Understanding 문서와 Techniques 문서로 링크가 걸려 있어, 원문이 짧을수록 그 링크를 따라가야 실제 구현 방법이 나온다.

## 인용 포인트
- "접근성 어디까지 할까요"라는 질문에 "WCAG 2.2 AA"라고 답하면 범위 논쟁이 한 문장에 끝난다. 등급이 곧 스코프 정의다.
- 성공 기준은 통과/실패로 판정되므로, 그대로 QA 테스트 케이스 ID로 승격시킬 수 있다 — 별도의 체크리스트를 창작할 필요가 없다.
- 접근성 요구를 "선의"가 아니라 "국내 인증 심사 기준의 원본"으로 프레이밍하면 우선순위 협상이 쉬워진다.
