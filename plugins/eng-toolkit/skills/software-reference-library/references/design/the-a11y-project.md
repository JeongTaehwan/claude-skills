# The A11Y Project

https://www.a11yproject.com/

## 한 줄
접근성을 "표준 문서 읽기"가 아니라 "지금 무엇부터 고칠지"로 바꿔주는 커뮤니티 사이트 — 핵심은 WCAG A/AA 상당 항목을 실행 가능한 문장으로 재작성한 체크리스트다.

## 페르소나
**접근성 작업을 처음 떠맡았고, 이번 스프린트 안에 눈에 보이는 개선을 만들어야 하는 엔지니어.** WCAG 원문을 열었다가 용어와 계층 구조에 막혀 덮은 상태다. 필요한 건 완전한 이해가 아니라, 오늘 오후에 코드에 반영할 수 있는 항목 목록과 그것들의 우선순위다. 동시에 "자동화 도구 돌렸으니 끝난 거 아닌가"라는 팀 내 오해도 정리해야 한다.

## 이럴 때 연다
- 접근성 개선을 착수하면서 첫 작업 목록을 뽑아야 할 때 — 체크리스트를 그대로 티켓으로 쪼갠다
- 기존 화면(주문서, 결제, 쿠폰 적용 폼 등)을 접근성 관점으로 1차 감사할 때
- 시맨틱 HTML로 해결될 문제를 ARIA로 덮으려는 코드를 리뷰에서 되돌려야 할 때
- 접근성 관련 도구·책·뉴스레터·전문가를 찾을 때 (Resources 섹션)
- "자동 검사 통과 = 접근성 준수"라는 오해를 팀에 설명해야 할 때

## 이럴 땐 아니다
- 계약·인증 심사의 근거로 인용해야 하면 규범 원문인 `design/wcag-2-2.md` 를 걸어야 한다. 이 체크리스트는 A/AA를 전부 덮지 않는다고 스스로 밝히고 있다
- 대비 계산, WAVE 같은 실측 도구와 업계 통계는 `design/webaim.md`
- 탭·모달·콤보박스 등 위젯별 ARIA 역할과 키보드 규약은 `design/aria-authoring-practices-guide.md`
- API·속성 단위의 레퍼런스가 필요하면 `design/mdn-accessibility.md`
- 접근 가능한 컴포넌트를 처음부터 설계하는 사고법은 `design/inclusive-components.md`

## 무엇이 들어있나
Checklist, Posts, Resources, Spotlight 네 축으로 구성된다.
**Checklist**가 이 사이트의 존재 이유다. WCAG를 기반으로 하되 "많은, 그러나 전부는 아닌 A·AA 항목"을 다룬다고 스스로 범위를 한정해 놓았고, 각 항목이 "확인하라"는 지시문 형태라 감사 작업으로 바로 옮겨진다. 완전성을 포기하는 대신 실행 가능성을 얻은 문서라고 보면 정확하다.
**Posts**는 통념을 깨는 쪽에 힘이 실려 있다. 대표적으로 "자동화 도구로 접근성 준수를 완전히 보장할 수 있다"는 믿음을 정면으로 다루는 글이 있고, 시맨틱 HTML만으로 해결되는 문제에 ARIA를 덧붙이는 흔한 실수를 반복적으로 지적한다.
**Resources**는 도구·책·영상·팟캐스트·뉴스레터, 그리고 전문 인력까지 묶은 큐레이션이라, 팀에 접근성 역량을 들여올 때의 출발점으로 쓸 수 있다.
Spotlight는 접근성 실무자 인터뷰로, 급할 때 읽을 섹션은 아니다.

## 인용 포인트
- 접근성 착수 시점에 "무엇부터?"를 정할 때, 이 체크리스트를 그대로 백로그로 변환하면 논의 없이 첫 스프린트가 채워진다.
- 리뷰에서 불필요한 ARIA를 걷어낼 때, "시맨틱 HTML이 먼저"라는 이 사이트의 입장을 근거로 쓴다.
- 단, 인증·계약 문맥에서는 이 문서가 스스로 커버리지를 한정하고 있다는 점을 반드시 함께 밝혀야 한다.
