# Designing Data-Intensive Applications (책 사이트)

https://dataintensive.net/

## 한 줄
Martin Kleppmann이 복제·파티셔닝·트랜잭션·합의를 **논문 수준의 근거를 달아** 설명한 책의 공식 사이트 — 특정 DB 사용법 책이 아니라, 어떤 데이터 시스템을 고르든 반복되는 근본 트레이드오프를 다루는 책이고, 장별 참고문헌 목록 자체가 훌륭한 논문 색인이다.

## 페르소나
**"읽기 부하가 커졌으니 리드 레플리카를 붙이자"까지는 갔는데, 붙이고 나서 주문 직후 조회에서 방금 만든 주문이 안 보이는 문제를 만난 백엔드 엔지니어.** 검색하면 "복제 지연 때문"이라는 답은 나오지만, 그래서 어떤 보장이 필요한 건지(읽기 후 쓰기 일관성인지 단조 읽기인지), 그걸 애플리케이션에서 어떻게 만들지의 선택지를 체계적으로 아는 사람이 팀에 없다. 또는 반대 상황 — 설계 리뷰에서 "이건 최종 일관성으로 충분하다" 같은 말이 오갈 때 그 말의 실제 의미를 검증할 언어가 없는 테크리드.

## 이럴 때 연다
- 데이터 저장소를 새로 고르거나 바꾸는 결정의 트레이드오프를 문서로 정리해야 할 때
- 복제 지연, 읽기 일관성, 격리 수준(Read Committed / Snapshot Isolation / Serializable) 때문에 버그가 나고 원인을 언어로 정리해야 할 때
- 샤딩·파티셔닝 키를 정할 때, 그리고 그 선택이 나중에 무엇을 막는지 알고 싶을 때
- 이벤트 기반 아키텍처나 CDC, 스트림 처리를 도입하기 전에 로그 기반 시스템의 성질을 이해하고 싶을 때
- 분산 트랜잭션·2PC를 쓸지, 사가나 멱등성으로 우회할지 논쟁이 붙었을 때
- 원 논문(Dynamo, Spanner, Kafka, Raft 등)으로 들어가기 전에 지도를 그리고 싶을 때 — 각 장 말미 참고문헌이 이 라이브러리 논문 항목 상당수의 출처다

## 이럴 땐 아니다
- 사이트에는 요약·목차·참고문헌이 있고 **본문은 유료 서적**이다. 지금 당장 무료로 읽을 것이 필요하면 논문 항목으로 직행하는 편이 낫다
- 특정 DB의 인덱스 튜닝, 쿼리 플랜 문제면 `development/use-the-index-luke.md` 나 `development/postgresql.md`
- 서비스 분해·통신 패턴이 문제의 축이면 `architecture/microservices-io.md`
- 운영 신뢰성(SLO, 온콜, 장애 대응)이면 `development/google-sre-books.md`
- 한 가지 정리(CAP)만 정확히 확인하고 싶으면 `architecture/brewer-s-conjecture-and-the-feasibility-of-consistent-availa.md`

## 무엇이 들어있나
책은 세 부로 나뉜다. 1부는 단일 노드 관점의 데이터 시스템 — 신뢰성·확장성·유지보수성의 정의, 데이터 모델(관계형·문서·그래프)과 질의 언어, 저장 엔진(B-트리 vs LSM 트리), 인코딩과 스키마 진화. 2부가 분산 데이터 — 복제, 파티셔닝, 트랜잭션과 격리 수준, 분산 시스템의 문제들(부분 실패, 신뢰할 수 없는 시계, 네트워크 지연), 일관성과 합의. 3부는 파생 데이터 — 배치 처리, 스트림 처리, 그리고 데이터 시스템의 미래에 대한 저자의 견해.

통념과 어긋나는 지점이 이 책의 값어치다. 몇 가지만 꼽으면 — **CAP 정리는 실무 설계 지침으로 쓰기에는 정의가 좁고 오해를 많이 낳았다**는 비판(가용성의 정의가 통상적 이해와 다르고, 파티션이 없을 때의 지연 트레이드오프를 다루지 않는다). **"NoSQL은 스키마가 없다"가 아니라 스키마 검증 시점이 쓰기에서 읽기로 옮겨간 것**이라는 재정의(schema-on-read). **격리 수준의 이름은 표준화되어 있지만 실제 DB가 그 이름으로 제공하는 보장은 제각각**이라는 지적 — 특히 많은 DB의 "Repeatable Read"가 실제로는 스냅샷 격리이고, 쓰기 스큐(write skew)를 막지 못한다는 대목은 재고 차감이나 쿠폰 발급 한도처럼 동시 요청이 같은 상태를 건드리는 코드에서 그대로 사고로 이어진다. 그리고 **로그(추가 전용 순서 있는 기록)를 데이터 시스템의 공통 기반으로 보는 관점** — 복제, 스트림, CDC, 이벤트 소싱을 하나의 렌즈로 묶는다.

## 인용 포인트
- 쓰기 스큐와 스냅샷 격리의 한계는, "트랜잭션으로 감쌌으니 안전하다"는 리뷰 코멘트를 반박할 때 가장 자주 쓰이는 근거다. 재고·쿠폰 수량 차감 설계 문서에 그대로 인용 가능.
- CAP에 대한 저자의 비판은, 설계 문서에서 CAP을 근거로 든 주장을 되돌릴 때 쓸 수 있다.
- 각 장 말미의 참고문헌 목록이 공개되어 있어, 특정 주제의 1차 논문을 찾는 색인으로 책을 안 사도 활용 가치가 있다.
