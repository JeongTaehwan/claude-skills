# The Architecture of Open Source Applications

https://aosabook.org/en/

## 한 줄
nginx, Git, LLVM, SQLite, ZeroMQ 등 실제로 널리 쓰이는 오픈소스의 내부 구조를 **그 프로젝트를 만든 사람들이 직접** 해설한 무료 책 시리즈. 결과 구조뿐 아니라 시행착오와 폐기한 설계까지 적혀 있다.

## 페르소나
**아키텍처 이론은 읽었는데 "잘 만든 시스템"의 실물을 본 적이 없는 엔지니어.** 패턴 카탈로그와 원칙은 알겠는데, 그것들이 실제 코드베이스에서 어떤 모양으로 나타나는지, 어디서 원칙이 깨지고 왜 깨지는지 감이 없다. 우리 회사 코드밖에 본 적이 없어서 그게 좋은 건지 나쁜 건지 비교 기준이 없는 상태. 또는 큰 리팩터링을 앞두고 비슷한 규모의 시스템이 같은 문제를 어떻게 풀었는지 선례를 찾는 사람.

## 이럴 때 연다
- 잘 만든 시스템의 실제 구조와 그 결정의 이유를 읽고 싶을 때
- 우리 시스템의 구조를 평가할 비교 기준(선례)이 필요할 때
- 특정 도구(nginx, Git, SQLite 등)의 내부 동작을 이해해야 운영·튜닝이 가능할 때
- 성능 중심 설계의 실제 사례가 필요할 때 — 특히 4권 500 Lines or Less는 작은 규모로 핵심만 구현한 사례집이다
- 아키텍처 문서를 쓰면서 "이런 식으로 쓰면 되는구나"의 본보기가 필요할 때

## 이럴 땐 아니다
- 개념과 용어를 먼저 정리해야 하면 `architecture/system-design-primer.md` 나 `architecture/designing-data-intensive-applications.md` 가 순서상 앞이다.
- 대규모 트래픽 시스템의 최신 사례·발표 모음이 필요하면 `architecture/awesome-scalability.md`.
- 클라우드 환경에서 검증된 운영 실무 문서는 `architecture/amazon-builders-library.md`.
- 직접 구현하며 배우는 쪽이 목적이면 `development/build-your-own-x.md`.
- 이 시리즈의 장(章)들은 집필 시점의 스냅샷이다. 초기 권은 2011~2012년 자료라 해당 프로젝트의 **현재** 구조와 다를 수 있다 — 최신 동작이 필요하면 각 프로젝트 공식 문서로 가야 한다.

## 무엇이 들어있나
시리즈는 여러 권으로 구성돼 있다. 1·2권은 다양한 오픈소스 프로젝트의 아키텍처 장들을 모았고, 3권 The Performance of Open Source Applications는 성능 개선 사례에 집중하며, 4권 500 Lines or Less는 각 저자가 500줄 이내로 핵심 시스템(작은 웹 서버, 인터프리터, 버전 관리, 스프레드시트 등)을 구현하며 설계를 설명한다. 전권이 온라인 무료 공개다.
이 시리즈의 값은 "정답 구조 소개"가 아니라 **결정의 맥락**에 있다. 각 장은 대체로 문제 상황 → 고려한 대안 → 선택과 이유 → 돌이켜보니 잘못했던 것 순으로 쓰여 있고, 저자들이 자기 프로젝트의 실패한 설계를 솔직하게 적는다. 완성된 시스템만 보고 "원래 이렇게 설계된 것"이라 착각하기 쉬운데, 여기서는 그 구조가 어떤 압력을 받아 그 모양이 됐는지 드러난다.
그래서 통념 반박도 자연스럽게 나온다 — 잘 알려진 프로젝트들도 층 분리가 깔끔하지 않고, 성능이나 이식성 때문에 원칙을 의도적으로 깨며, 그 예외가 어디인지 아는 것이 설계의 일부라는 게 반복되는 메시지다.
저자들이 인세를 자선단체에 기부하는 형태로 만들어진 커뮤니티 프로젝트이기도 하다.

## 인용 포인트
- 설계 문서에 "돌이켜본 결정" 절을 두자고 제안할 때: 이 시리즈의 각 장이 실패한 설계를 기록하는 형식을 본보기로 들 수 있다.
- "원칙을 깨는 예외를 언제 허용하는가" 논쟁에서, 널리 쓰이는 시스템들도 명시적 이유와 함께 예외를 두고 있다는 실제 사례를 댈 수 있다.

## 코드 예시

각 장이 따르는 서술 순서(문제 → 대안 → 선택 → 돌이켜보니)를 사내 설계 문서 템플릿으로 옮긴 것 — 이 시리즈에서 가져올 수 있는 실물은 구조가 아니라 이 형식이다.

```markdown
# 주문 조회 읽기 모델 분리

## 1. 문제 상황
주문 목록 화면 1회 렌더링에 서비스 4개 호출, p95 1.8초.
피크에 주문 서비스 DB 커넥션이 조회 트래픽으로 포화된다.

## 2. 고려한 대안
- (A) API Composition — 게이트웨이에서 병렬 호출 후 병합
- (B) 읽기 전용 복제본 추가
- (C) 이벤트 기반 읽기 모델(CQRS)

## 3. 선택과 이유
(C). (A)는 최악 지연이 가장 느린 서비스에 묶이고, (B)는 커넥션 포화는
풀지만 서비스 간 호출 횟수를 줄이지 못한다.

## 4. 의도적으로 깬 원칙
읽기 모델은 주문/쿠폰 두 컨텍스트의 데이터를 한 테이블에 비정규화한다.
경계를 넘는 건 알고 있으며, 쓰기는 하지 않는다는 조건으로 허용한다.

## 5. 돌이켜보니 (2026-08 갱신)
이벤트 지연 상한(현재 최대 4초)을 화면에 노출하지 않은 것이 실수였다.
CS 문의의 대부분이 "결제했는데 목록에 없다"였다.
```

템플릿은 5번 절이 실제로 채워질 때만 값이 있다 — 승인 시점에 쓰고 닫아버리면 이 문서도 결과 구조만 남은 보통의 설계서가 된다.
