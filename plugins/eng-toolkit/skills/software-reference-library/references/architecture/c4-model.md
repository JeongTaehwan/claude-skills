# C4 Model

https://c4model.com/

## 한 줄
Simon Brown이 만든 아키텍처 다이어그램 표기법 — 그림을 예쁘게 그리는 법이 아니라 **한 장의 그림에 담을 추상화 수준을 하나로 고정하는 규율**이 핵심이고, System Context / Container / Component / Code 네 단계로 줌 레벨을 나눈다.

## 페르소나
**설계 리뷰에 그림을 들고 갔는데 논의가 시작되자마자 "이 박스는 서버야 클래스야?"에서 막혀버린 백엔드 엔지니어 또는 테크리드.** 그린 사람 머릿속에서는 자명했지만, 한 장 안에 배포 단위(주문 서비스)와 코드 단위(OrderValidator)와 외부 시스템(PG사)이 같은 크기 박스로 섞여 있어서, 보는 사람마다 다른 그림을 읽는다. 지적은 받는데 "그럼 어떻게 그리라는 건데"의 답은 아무도 주지 않는 상태.

## 이럴 때 연다
- 아키텍처 다이어그램을 처음부터 그려야 하는데 표기 규칙이 팀에 없을 때
- 그림 한 장에 여러 추상화 수준이 섞여 리뷰가 산으로 갈 때
- 청중이 다를 때 — 기획·PM에게는 Context 한 장, 개발팀에는 Container, 특정 서비스 내부 논의에는 Component로 갈아 끼워야 할 때
- ADR이나 설계 문서에 붙일 그림의 범위를 정할 때 ("이 문서는 Container 레벨까지만 다룬다"라고 못박기)
- 기존 다이어그램을 리뷰하면서 "이건 어느 레벨이냐"를 물어 문제를 드러내고 싶을 때

## 이럴 땐 아니다
- 설계 문서 전체의 목차·구성이 필요하면 `architecture/arc42.md` (C4는 그림 표기법이지 문서 템플릿이 아니다)
- 그림이 아니라 "왜 이 선택을 했는가"의 결정 기록이 필요하면 `architecture/architecture-decision-records.md`
- 도메인 경계 자체를 아직 못 정했다면 그리기 전에 `architecture/ddd-starter-modelling-process.md` 또는 `architecture/event-storming.md`
- 마이크로서비스 간 패턴 이름과 선택지 카탈로그가 필요하면 `architecture/microservices-io.md`

## 무엇이 들어있나
네 개의 레벨이 축이다. **Context** — 시스템 하나를 검은 상자로 두고 사용자와 외부 시스템과의 관계만. **Container** — 그 상자를 열어 독립 실행/배포되는 단위(웹앱, API 서버, DB, 메시지 브로커)로 쪼갠 것. 여기서 container는 Docker 컨테이너가 아니라 "따로 돌아가는 것"을 뜻하며, 이 용어 혼동이 실무에서 가장 잦은 오독이다. **Component** — 한 컨테이너 내부의 논리적 묶음. **Code** — 클래스 다이어그램 수준으로, 사이트 자체가 대부분의 경우 여기까지는 그리지 말라고 권한다.

통념과 어긋나는 지점: C4는 표준 기호 세트를 강제하지 않는다. 대신 **모든 박스와 선에 이름·타입·설명·기술 스택을 적고, 범례를 반드시 붙이라**고 요구한다. 즉 문제는 모양이 아니라 그림이 자기 설명적이지 않은 것이라고 본다. UML을 대체하려는 것도 아니고, 모델(시스템의 구조)과 뷰(그 모델을 보는 방식)를 분리해 하나의 모델에서 여러 그림을 뽑는 사고방식을 강조한다.

## 인용 포인트
- "그림 한 장은 추상화 수준 하나만 담는다" — 리뷰에서 다이어그램을 반려할 때 취향 싸움이 아닌 규칙으로 제시할 수 있는 문장.
- 레벨을 청중에 매핑하는 방식(Context=비개발 이해관계자, Container=개발팀 전체, Component=해당 서비스 담당자)은 문서 구조를 정할 때 그대로 인용 가능.
- 범례 없는 다이어그램을 금지하는 규칙 하나만 팀 컨벤션으로 도입해도 즉시 효과가 있다.
