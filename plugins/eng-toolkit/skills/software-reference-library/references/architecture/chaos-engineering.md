# Chaos Engineering

https://arxiv.org/abs/1702.05843

## 한 줄
Netflix 팀이 IEEE Software에 낸 논문으로, "장애를 주입해본다"는 관행을 **가설 → 실험 → 반증**의 과학적 절차로 정식화하고, 그 실험이 왜 스테이징이 아니라 프로덕션에서 이뤄져야 하는지를 논증한다.

## 페르소나
**"운영 환경에 일부러 장애를 낸다"는 제안을 팀장이나 인프라 조직에 올려야 하는데, 승인권자 눈에는 그냥 사고 치겠다는 소리로만 들리는 백엔드/SRE 엔지니어.** 실제로는 결제 대행사 지연이나 캐시 노드 하나 죽었을 때 시스템이 어떻게 되는지 아무도 모르고, 매번 진짜 장애가 나서야 알게 되는 상황이다. 필요한 건 도구가 아니라 **"이건 무모한 짓이 아니라 통제된 실험이다"를 문서로 설명할 언어와 출처**다.

## 이럴 때 연다
- 장애 주입 실험 도입 제안서·RFC를 쓸 때, 근거로 걸 1차 출처가 필요할 때
- "왜 스테이징에서 하면 안 되냐"는 반론에 답해야 할 때
- 실험 설계 자체를 잡을 때 — 무엇을 정상 상태로 볼지, 폭발 반경(blast radius)을 어떻게 제한할지
- 이미 Chaos Monkey류 도구는 돌리고 있는데 실험 결과를 해석할 기준이 없어 "그냥 죽여봤다"에 그치고 있을 때
- 주문·결제처럼 실패가 돈으로 직결되는 경로에 대해 실험 범위를 어디까지 허용할지 선을 그을 때

## 이럴 땐 아니다
- 원칙을 실무 체크리스트 형태로 짧게 훑고 싶으면 `infrastructure/principles-of-chaos-engineering.md`
- 실제 주입 도구를 고르는 단계면 `testing/chaos-monkey.md`, 도구·라이브러리 지형 전반은 `qa/awesome-chaos-engineering.md`
- 실험이 아니라 *이미 난 장애*에서 배우는 체계(포스트모템)를 만들려면 `development/postmortem-culture-learning-from-failure.md`
- 분산 시스템의 일관성 보장이 실제로 깨지는지를 외부에서 검증하는 쪽이면 `architecture/jepsen.md`

## 무엇이 들어있나
핵심 주장은 정의 자체에 있다. 카오스 엔지니어링은 "시스템을 망가뜨리는 것"이 아니라 **정상 상태(steady state)에 대한 가설을 세우고, 현실적인 장애 이벤트를 주입해 그 가설이 반증되는지 보는 실험**이라는 것. 정상 상태를 내부 지표(CPU, 에러 로그)가 아니라 사용자 관점의 출력 지표로 정의하라는 점이 실무적으로 가장 중요한 대목이다 — Netflix의 경우 초당 스트리밍 재생 시작 수 같은 것.

통념과 어긋나는 부분이 이 논문의 값어치다. (1) 실험은 **프로덕션에서** 해야 한다 — 스테이징은 트래픽 패턴, 데이터 규모, 의존성 조합이 다르므로 거기서 통과한 것이 프로덕션의 증거가 되지 않는다. (2) 목적은 장애를 찾는 것이 아니라 **시스템에 대한 우리의 믿음이 틀렸음을 드러내는 것**이다. 실패한 실험보다 아무 일도 안 일어난 실험이 오히려 정보가 적다. (3) 자동화되고 상시 실행되어야 한다 — 일회성 이벤트는 시스템이 변하는 속도를 따라가지 못한다. (4) 폭발 반경 최소화는 타협이 아니라 실험 설계의 필수 조건이다.

## 인용 포인트
- "카오스 엔지니어링은 장애를 일으키는 것이 아니라 이미 시스템에 존재하는 무질서를 드러내는 것" — 승인 논의에서 프레임을 바꾸는 데 쓰인다.
- 정상 상태를 비즈니스 출력 지표로 정의하라는 원칙은, 실험을 넘어 SLI 설계 논의에도 그대로 인용 가능.
- IEEE Software 게재 + Netflix 실무진 저자라는 출처 조합이라, "검증되지 않은 유행"이라는 반론을 무력화하는 데 효과적이다.

## 코드 예시

논문이 요구하는 네 가지 — 정상 상태를 사용자 출력 지표로, 가설을 먼저, 폭발 반경을 설계 조건으로, 상시 반복 — 을 실험 정의 파일 한 장으로 만든 것.

```yaml
experiment: pg-latency-2s
hypothesis: >
  PG 응답이 2초 지연돼도 분당 주문 완료 수는 기준선의 95% 이상을 유지한다.

steady_state:
  metric: orders_completed_per_minute   # CPU·에러 로그가 아니라 사용자 관점 출력
  baseline_window: 30m
  pass_if: ">= 0.95 * baseline"

method:
  fault: latency
  target: outbound-http:pg.example.com
  inject: 2000ms

blast_radius:
  environment: production   # 스테이징 통과는 프로덕션의 증거가 되지 않는다
  traffic_share: 1%
  duration: 10m

abort_when:                 # 하나라도 걸리면 즉시 주입 해제
  - orders_completed_per_minute < 0.90 * baseline
  - payment_error_rate > 2%

schedule: "0 14 * * TUE"    # 상시 반복 — 시스템은 실험보다 빨리 변한다
```

`traffic_share: 1%` 는 지표가 즉시 보일 때만 1% 다 — 집계 지연이 60초면 실제 폭발 반경은 "1% × 감지 지연"이고, 중단 버튼보다 사고가 먼저 끝난다. 그리고 가설이 반증되지 않았다는 것은 안전하다는 뜻이 아니라 이 실험이 정보를 별로 주지 못했다는 뜻에 가깝다.
