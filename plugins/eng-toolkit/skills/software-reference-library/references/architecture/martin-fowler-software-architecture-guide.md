# Martin Fowler — Software Architecture Guide

https://martinfowler.com/architecture/

## 한 줄
"아키텍처란 무엇인가"와 "왜 내부 품질에 돈을 써야 하는가"를 정면으로 다루는 큐레이션 허브. 개별 패턴이 아니라 **아키텍처라는 활동 자체**에 대한 글 모음이다.

## 페르소나
**"리팩터링/구조 개선에 왜 스프린트를 쓰느냐"는 질문에 답을 못 하고 있는 테크리드.** 기능은 계속 나가야 하고, 설계 정리는 매번 "다음 분기에"로 밀린다. 코드가 느려지고 있다는 건 체감하는데, 그걸 비용 언어로 번역해 본 적이 없어서 우선순위 회의에서 항상 진다. 또는 아키텍트 직함을 막 받았는데 그 역할이 실제로 무엇을 하는 자리인지 정의가 없는 사람.

## 이럴 때 연다
- 내부 품질 개선 작업의 예산·시간을 경영진이나 PO에게 설득해야 할 때
- "아키텍처"를 팀에서 어떻게 정의할지 합의가 필요할 때 (문서인가, 다이어그램인가, 결정 집합인가)
- 아키텍트 역할을 신설하거나 재정의할 때 — 상아탑형 아키텍트를 피하려면 무엇을 해야 하는지
- 레거시 주문/정산 시스템 교체 전략을 세우며 무엇부터 읽을지 지도가 필요할 때
- 마이크로서비스·서버리스·마이크로 프론트엔드 중 무엇을 검토할지 입구를 찾을 때

## 이럴 땐 아니다
- 특정 용어 하나의 정의만 필요하면 `architecture/martin-fowler-bliki.md` 로 바로 가는 게 빠르다. 이 가이드는 주제별 진입점이다.
- 구조를 그림으로 표현하는 표기법이 필요하면 `architecture/c4-model.md`, 문서 양식이 필요하면 `architecture/arc42.md`.
- 결정 자체를 기록하는 형식은 `architecture/architecture-decision-records.md`.

## 무엇이 들어있나
핵심은 아키텍처의 정의다. Ralph Johnson을 인용해 아키텍처를 객관적 실체가 아니라 **"숙련된 개발자들이 공유하는 시스템 설계에 대한 이해"** 로 규정하고, "나중에 바꾸기 어려운 것들", "중요한 것들 — 그게 뭐든"이라는 실용적 정의를 함께 둔다. 즉 아키텍처는 다이어그램이 아니라 합의와 변경 비용의 문제라는 입장이다.
두 번째 축은 경제 논증이다. "Is High Quality Software Worth the Cost?"는 품질과 비용이 트레이드오프라는 통념을 정면으로 부정한다 — 내부 품질은 신기능 추가 속도를 좌우하므로, 그 투자 회수 기간은 통념보다 훨씬 짧아 **수 주 단위**라는 주장이다. 결과적으로 "빨리 가려고 품질을 포기한다"는 선택이 대부분 잘못된 계산이라고 말한다.
나머지는 애플리케이션 아키텍처(마이크로서비스, 레거시 대체 패턴, 마이크로 프론트엔드, GUI 아키텍처, 서버리스, 피처 토글)와 엔터프라이즈 아키텍처(제품 중심 조직, Architect Elevator, REST 기반 통합)로 나뉜 링크 허브다.

## 인용 포인트
- 기술 부채 상환 예산을 요청할 때: 품질-비용 트레이드오프가 거짓이며 회수 기간이 수 주 수준이라는 주장을 근거로 쓸 수 있다.
- 아키텍처 문서화 요구가 과해질 때: 아키텍처를 "팀이 공유하는 이해"로 정의하는 대목은, 문서 산출물보다 합의 형성이 목적이라는 방향 전환에 쓸 만하다.
