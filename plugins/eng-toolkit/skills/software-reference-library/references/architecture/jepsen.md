# Jepsen — 분산 시스템 안전성 분석

https://jepsen.io/analyses

## 한 줄
Kyle Kingsbury가 실제 DB·큐·코디네이션 서비스에 장애를 주입해 그들이 문서에서 주장한 일관성 보장을 실제로 깨뜨려 보고, 그 결과를 벤더 반응까지 포함해 공개한 검증 보고서 모음이다.

## 페르소나
**"이 DB는 스냅샷 격리를 지원한다"는 문서 한 줄을 근거로 재고·잔액 로직을 설계하려는 백엔드 엔지니어.** 트랜잭션 격리 수준 이름은 표준어처럼 보이지만 제품마다 실제 의미가 다르고, 네트워크 파티션 중에는 문서와 다르게 동작하는 경우가 많다. 도입 결정 전에 "이 제품의 그 주장이 검증된 적 있나"를 확인해야 하는데, 벤더 문서만으로는 알 수 없다.

## 이럴 때 연다
- 새 DB·메시지 브로커 도입 검토에서 일관성/내구성 주장을 액면 그대로 믿기 전에
- MongoDB, Redis(Redlock), Elasticsearch, Kafka, PostgreSQL, etcd 등 특정 제품의 알려진 이상 현상을 확인할 때
- "Read Committed", "Serializable" 같은 격리 수준 용어의 실제 의미 차이를 팀에 설명해야 할 때
- 결제·정산처럼 실패가 조용한 경로에서 저장소를 고를 때 근거 자료가 필요할 때

## 이럴 땐 아니다
- 검증을 직접 돌려보고 싶다면 도구 저장소 `architecture/jepsen-2.md`
- 일관성 모델 자체의 이론적 구도가 주제라면 `architecture/brewer-s-conjecture-and-the-feasibility-of-consistent-availa.md`
- 프로덕션 시스템에 의도적으로 장애를 주입하는 조직 관행이 목적이면 `architecture/chaos-engineering.md`
- 인덱스·쿼리 성능 문제라면 `development/use-the-index-luke.md`

## 무엇이 들어있나
제품별 보고서가 연도순으로 쌓여 있고, 각 보고서는 (1) 문서가 주장하는 보장, (2) 주입한 장애 시나리오(파티션, 클럭 스큐, 프로세스 정지, 멤버십 변경), (3) 관찰된 이상 현상(lost update, stale read, split-brain 등)을 히스토리 다이어그램과 함께 제시한다. 이 자료의 통념 파괴 지점은 결론이 아니라 반복되는 패턴이다 — 상용 제품들이 표준 격리 수준 이름을 실제보다 강한 의미로 마케팅해 왔고, 다수 사례에서 기본 설정이 안전하지 않은 쪽이었다. 보고서 상당수는 벤더의 후속 수정과 재검증까지 이어지므로, 버전을 확인하지 않고 옛 결론을 인용하면 부당해진다.

## 인용 포인트
- "문서의 일관성 주장은 검증된 적 없으면 가설로 취급한다"는 원칙을 저장소 선정 기준에 넣을 때, 이 시리즈가 실증 근거가 된다.
- Redis 기반 분산 락(Redlock)의 안전성 논쟁은 재고 차감 락 설계 리뷰에서 자주 재현되는 사례다.
