# DDD Starter Modelling Process

https://github.com/ddd-crew/ddd-starter-modelling-process

## 한 줄
DDD를 "어디서부터 시작하느냐"에서 막히는 사람을 위해 DDD Crew가 만든 **9단계 순서도** — 이론 설명이 아니라, 각 단계에서 어떤 워크숍을 돌리고 어떤 산출물을 만드는지를 링크로 연결한 실행 절차다.

## 페르소나
**"우리 서비스 도메인이 복잡해졌으니 DDD로 정리하자"는 합의까지는 됐는데, 다음 주 월요일에 팀을 모아놓고 정확히 뭘 시켜야 할지 모르겠는 테크리드.** 책을 읽었더니 엔티티·값객체·애그리거트 이야기는 많은데 그건 이미 코드를 쓰기 시작한 다음 이야기고, 정작 지금 필요한 건 "주문 도메인과 정산 도메인의 경계를 어디에 그을 것인가"다. 전술 패턴부터 손대다가 결국 폴더 구조만 바꾸고 끝난 경험이 있다면 여기가 맞다.

## 이럴 때 연다
- 도메인이 커져 모듈·서비스 경계를 정해야 하는데 기준이 없을 때
- DDD 도입을 결정했지만 첫 워크숍 아젠다를 못 짜고 있을 때
- 기획·개발·QA가 같은 단어를 다르게 쓰고 있어(예: "주문 완료"가 결제 승인인지 배송 시작인지) 공통 언어가 필요할 때
- 모놀리스를 쪼갤 때 자르는 선을 기술이 아니라 도메인 기준으로 잡고 싶을 때
- 이미 Event Storming은 해봤는데 그 다음에 뭘 해야 할지 모를 때

## 이럴 땐 아니다
- 워크숍 기법 하나(포스트잇으로 이벤트 펼치기) 자체를 익히려면 `architecture/event-storming.md`, 용어만 빠르게 확인하려면 `architecture/event-storming-2.md`
- 경계는 이미 정해졌고 서비스 간 통신·데이터 일관성 패턴이 필요하면 `architecture/microservices-io.md`
- 한 서비스 내부의 계층 구조와 의존 방향이 문제면 `architecture/hexagonal-architecture.md`
- 모듈 분해의 원리적 근거(무엇을 기준으로 잘라야 하는가)를 인용하려면 `architecture/on-the-criteria-to-be-used-in-decomposing-systems-into-modul.md`
- 리포지토리·서비스·매퍼 같은 구현 레벨 패턴 이름이 필요하면 `architecture/patterns-of-enterprise-application-architecture.md`

## 무엇이 들어있나
저장소의 본체는 한 장의 프로세스 다이어그램과, 각 단계로 들어가는 링크다. 흐름은 대략 **비즈니스 이해 → 도메인 탐색 → 하위 도메인 분해 및 전략적 중요도 판단(core / supporting / generic) → 바운디드 컨텍스트 정의 → 컨텍스트 간 관계 설계 → 아키텍처와 팀 구성 결정 → 전술 설계 → 코드** 순이고, 마지막이 다시 앞으로 돌아오는 반복 루프로 그려진다.

여기서 통념과 어긋나는 지점이 둘 있다. 하나는 **순서**다. 많은 팀이 DDD를 애그리거트·엔티티 같은 전술 패턴에서 시작하는데, 이 프로세스는 그걸 거의 마지막에 둔다. 경계가 틀린 상태에서의 전술 설계는 잘못된 곳에 정교한 구조를 짓는 일이라는 입장이다. 다른 하나는 **아키텍처와 조직을 같은 단계에서 결정한다**는 점 — 바운디드 컨텍스트를 팀 경계와 어떻게 맞출지가 설계 결정의 일부로 명시되어 있다.

또한 "이 프로세스를 처음부터 끝까지 한 번에 다 돌리라"고 하지 않는다. 상황에 따라 진입점을 다르게 잡는 변형(이미 도메인을 아는 경우, 레거시를 쪼개는 경우 등)을 제시하고, 각 단계는 완료가 아니라 반복 대상으로 본다.

## 인용 포인트
- "전술 설계보다 전략적 설계가 먼저" — 폴더 구조 리팩터링부터 하자는 제안을 되돌릴 때 쓸 수 있는 프레임.
- core / supporting / generic 하위 도메인 구분은, 어디에 인력과 설계 노력을 몰아줄지 결정하는 논의(직접 만들 것 vs 사서 쓸 것)에 그대로 인용된다.
- DDD Crew는 커뮤니티 저장소라 라이선스가 열려 있어, 다이어그램을 팀 내부 문서에 가져다 쓰기 좋다.
