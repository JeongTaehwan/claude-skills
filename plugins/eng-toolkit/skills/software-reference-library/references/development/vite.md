# Vite 공식 문서

https://vite.dev/guide/

## 한 줄
프런트엔드 빌드 툴 Vite 의 공식 가이드 — 개발 중에는 번들링을 하지 않고 브라우저의 네이티브 ES 모듈로 소스를 그대로 주고, 프로덕션에서만 최적화 번들을 만드는 이중 구조를 설명한다. 다루는 범위는 개발 서버·HMR·플러그인·환경변수·라이브러리 모드·SSR 까지다.

## 페르소나
**Webpack 기반 프로젝트의 개발 서버 시작이 수십 초씩 걸리고 저장할 때마다 리빌드를 기다리는 프런트엔드/풀스택 엔지니어.** 설정 파일은 수년간 누적돼 아무도 전부 이해하지 못하고, 마이그레이션하려니 프록시·환경변수·에일리어스·빌드 산출물 형식을 어디까지 옮겨야 하는지 감이 없다.

## 이럴 때 연다
- 개발 서버 기동/HMR 이 느려 번들러 교체를 검토할 때
- 개발 서버에서 백엔드로 API 프록시를 붙이거나 CORS 를 우회할 때 (`server.proxy`)
- `import.meta.env` 기반 환경변수 규칙과 `.env` 파일 우선순위를 확인할 때
- 정적 자산 처리, public 디렉터리, 에일리어스, 청크 분할 등 빌드 설정을 조정할 때
- 사내 공용 컴포넌트를 패키지로 배포하려고 라이브러리 모드를 쓸 때
- SSR 이나 프레임워크(Vue/React/Svelte/Solid 등) 템플릿으로 프로젝트를 시작할 때

## 이럴 땐 아니다
- 린트 규칙·포매팅은 빌드 도구의 몫이 아니다 — `development/eslint.md`, `development/prettier.md`
- 타입 시스템 문제로 빌드가 깨지는 경우는 `development/typescript-handbook.md`
- 번들 크기가 실제 사용자 체감에 미치는 영향과 목표 수치는 `development/web-vitals.md`, 측정은 `development/lighthouse.md`
- 테스트 러너로서의 Vitest 는 별도 프로젝트다 — `testing/vitest.md`

## 무엇이 들어있나
가이드의 출발 주장은 "개발 시간에 전체 번들링을 하는 것은 프로젝트가 커질수록 원리적으로 감당이 안 된다"는 것이다. 그래서 Vite 는 개발 서버에서 모듈을 원본에 가까운 형태로 브라우저에 넘기고, 브라우저가 요청한 모듈만 변환한다 — 기동 시간이 프로젝트 크기에 거의 비례하지 않는 이유가 이것이다. HMR 도 변경된 모듈 경계만 교체한다.
의존성은 별도로 취급한다. 자주 바뀌지 않는 node_modules 는 사전 번들링(pre-bundling)해 두어 요청 수를 줄이고, CJS/UMD 모듈을 ESM 으로 변환해 준다. 소스 코드와 의존성을 다르게 다루는 이 분리가 설계의 핵심이다.
프로덕션 빌드는 개발과 다른 경로다 — 최신 Vite(v8 계열)는 Rolldown 을 사용해 최적화된 정적 자산을 만든다. 개발/빌드 파이프라인이 다르다는 점은 장점이자 함정이라, 개발에서만 동작하고 빌드에서 깨지는 문제를 이해하려면 이 구분을 알아야 한다.
지원 범위도 명시돼 있다. 개발은 최신 브라우저 기능을 전제하고, 프로덕션 산출물은 널리 쓰이는 브라우저를 대상으로 한다. Node.js 최소 버전 요구사항이 있으므로 CI 이미지 확인이 필요하다.
플러그인은 Rollup 플러그인 인터페이스를 확장한 형태이며, 프레임워크 지원 대부분이 플러그인으로 제공된다.

## 인용 포인트
- "개발 중 번들링을 하지 않는다"는 설계 선택은, 번들러 교체 제안서에서 "설정만 바꾸는 게 아니라 개발 모델이 다르다"를 설명하는 근거로 쓸 수 있다.
- 의존성 사전 번들링과 소스 변환을 분리한다는 설명은, 캐시 무효화 문제나 `optimizeDeps` 관련 이슈를 팀에 설명할 때의 기준이 된다.
