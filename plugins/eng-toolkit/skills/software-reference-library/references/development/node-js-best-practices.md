# Node.js Best Practices

https://github.com/goldbergyoni/nodebestpractices

## 한 줄
Node 백엔드의 관행을 프로젝트 구조·에러 처리·코드 스타일·테스트·프로덕션·보안·성능으로 나눠 **항목 하나당 "한 줄 규칙 + 왜 + 코드 예시 + 반대 사례 + 출처 링크"** 형식으로 못 박아 둔, Node 진영에서 가장 많이 인용되는 실무 가이드.

## 페르소나
**Node/TypeScript 로 커머스 백엔드를 굴리는데, 팀 컨벤션이 "이전 사람이 그렇게 짜서" 수준의 구전으로만 존재하는 상황의 리드 또는 시니어.** 리뷰에서 "에러를 어디서 잡을 것인가", "커스텀 에러 클래스를 쓸 것인가", "프로세스를 죽일 것인가 말 것인가" 같은 논쟁이 매번 취향 싸움이 되고, 결론이 문서로 남지 않아 다음 달에 같은 논쟁을 반복한다. 각 주장에 외부 근거 링크가 달린 항목 목록이 필요하다.

## 이럴 때 연다
- 신규 Node/TS 서비스의 코딩 컨벤션·폴더 구조 문서를 처음 쓸 때, 백지에서 시작하지 않기 위해
- 에러 처리 정책(운영 에러 vs 프로그래머 에러, 언제 프로세스를 죽이는가)을 팀 규칙으로 확정할 때
- 프로덕션 배포 전 점검표를 만들 때 — 로깅, 헬스체크, 프로세스 관리, 의존성 고정 등
- 리뷰에서 반복되는 지적을 "매번 말하기" 대신 링크 하나로 대체하고 싶을 때
- 주니어에게 "왜 이렇게 짜야 하는지"를 설명할 근거가 필요할 때

## 이럴 땐 아니다
- API 시그니처나 런타임 동작의 정확한 사실 확인은 이 저장소가 아니라 `development/node-js-api.md`
- 코드 포맷팅(따옴표, 세미콜론, 줄바꿈) 논쟁은 여기서 끝내지 말고 `development/prettier.md` 와 `development/eslint.md` 로 자동화해서 없애라
- JavaScript 스타일 규칙 자체의 정본은 `development/airbnb-javascript-style-guide.md`
- 웹 애플리케이션 보안 위험의 전체 지형은 여기 보안 절이 아니라 `development/owasp-top-10.md` 와 `development/owasp-cheat-sheet-series.md`
- 조직 차원의 리뷰 문화·기준은 `development/google-code-review-developer-guide.md`

## 무엇이 들어있나
README 자체가 목차이자 본문 요약이다. 각 항목은 "규칙 한 줄(굵게) → 그렇지 않으면(Otherwise) 무슨 일이 벌어지는가 → 코드 예시" 구조로, **반대 사례를 명시한다**는 점이 이 가이드의 특징이다. 규칙만 나열하는 스타일 가이드와 달리 "지키지 않으면 어떻게 망가지는가"가 항상 붙는다.
가장 실전적인 절은 에러 처리와 Going to Production 이다. 에러 처리 절은 운영상 예상 가능한 에러(operational)와 버그(programmer)를 구분하고, 후자는 잡아서 삼키지 말고 프로세스를 재시작하라는 입장을 취한다 — try/catch 로 전부 감싸는 흔한 관행과 정면으로 어긋나는 지점이다.
프로젝트 구조 절은 계층(controller/service/repository)이 아니라 **컴포넌트(도메인) 단위 분할**을 기본으로 삼는다. 주문·결제·쿠폰처럼 도메인이 뚜렷한 커머스 백엔드에서 바로 적용 가능한 주장이다.
보안 절은 OWASP 항목과 매핑돼 있고, 성능·Docker 절도 별도로 있다.
한국어를 포함한 다국어 번역본이 저장소 안에 있으나 최신성은 영어 원문이 앞선다.

## 인용 포인트
- "모든 에러를 try/catch 로 잡아야 하지 않나"는 반론에, 운영 에러와 프로그래머 에러를 구분하고 후자는 재시작이 정답이라는 근거를 이 저장소에서 링크로 제시할 수 있다.
- 폴더 구조를 계층형에서 도메인형으로 바꾸자고 설득할 때, 항목별 "Otherwise" 설명이 그대로 제안서의 리스크 절이 된다.
- 각 항목에 외부 출처(블로그·컨퍼런스 발표)가 달려 있어, 사내 컨벤션 문서에 인용을 붙이기 좋다.
