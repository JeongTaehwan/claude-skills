# Go To Statement Considered Harmful

https://homepages.cwi.nl/~storm/teaching/reader/Dijkstra68.pdf

## 한 줄
두 쪽짜리 편지 한 통 — "goto 를 쓰지 말자"가 아니라 **정적인 코드 텍스트와 동적인 실행 상태 사이의 거리를 좁혀야 한다**는 원리를 세운 글이고, 구조적 프로그래밍의 출발점이다.

## 페르소나
**중첩된 조건문과 예외 흐름 때문에 "이 시점에 상태가 뭔지" 아무도 답 못 하는 모듈을 리팩터링하려는 엔지니어.** 주문 상태 전이 코드가 early return, 예외, 플래그 변수, 콜백으로 흩어져 있어서 버그를 재현해도 어디를 통과해 왔는지 추적이 안 된다. "복잡하다"는 말로는 리뷰에서 설득이 안 되고, 왜 이 구조가 나쁜지 원리적 언어가 필요하다.

## 이럴 때 연다
- 제어 흐름 복잡도를 지적하는 리뷰 코멘트에 감상 이상의 근거를 붙이고 싶을 때
- 예외를 흐름 제어로 쓰는 코드, 깊은 중첩, 상태 플래그를 걷어내자고 제안할 때
- 코드를 읽고 "지금 어디까지 진행됐는지" 한 지점으로 말할 수 있게 만드는 것이 왜 중요한지 설명할 때
- 소프트웨어 공학 고전을 팀 스터디로 다룰 때 — 분량이 짧아 첫 편으로 적합하다

## 이럴 땐 아니다
- 실제로 무엇을 어떻게 고칠지, 리팩터링 수법의 카탈로그는 `development/refactoring-catalog.md`, `development/refactoring-guru.md`
- 모듈을 어떤 기준으로 쪼갤지의 원리는 `architecture/on-the-criteria-to-be-used-in-decomposing-systems-into-modul.md`
- 복잡도의 원천을 상태 자체로 보는 논의는 `architecture/out-of-the-tar-pit.md`
- 언어별 제어 흐름 관용구(Go 의 early return, 에러 값 처리 등)는 `development/effective-go.md` 같은 언어 문서

## 무엇이 들어있나
Dijkstra 의 논지는 인간의 능력에 대한 관찰에서 출발한다. 우리는 정적인 텍스트를 읽는 데는 능하지만 시간에 따라 펼쳐지는 과정을 머릿속에서 따라가는 데는 약하다. 그러므로 좋은 프로그램은 **텍스트 상의 위치와 실행 진행 상태가 최대한 가깝게 대응**하는 프로그램이다.
순차 실행, 조건 분기, 반복만으로 짜인 프로그램에서는 "지금 어디까지 왔는가"를 텍스트 상의 지점 + 반복 횟수 같은 소수의 좌표로 기술할 수 있다. goto 가 들어오면 이 좌표계가 무너져서, 프로그램의 진행 상태를 서술할 의미 있는 인덱스를 만들 수 없게 된다. 이것이 goto 를 반대하는 진짜 이유다 — 미학이 아니라 추론 가능성의 문제다.
그래서 이 글의 함의는 goto 를 넘어선다. 오늘날의 코드에서 좌표계를 무너뜨리는 것은 대개 goto 가 아니라 흐름 제어로 남용된 예외, 깊게 얽힌 콜백, 어디서든 바뀌는 전역 상태다. 원문의 기준을 적용하면 이들에 대한 반대 논거가 그대로 나온다.
덧붙일 사실: 지금의 도발적인 제목은 저자가 아니라 편집자(Niklaus Wirth)가 붙인 것이고, 원래 제목은 goto 문에 대한 반론이라는 훨씬 밋밋한 표현이었다. "X Considered Harmful" 이라는 관용 표현 자체가 여기서 나왔다.

## 인용 포인트
- "정적인 코드와 동적인 실행 사이의 개념적 거리를 줄여야 한다"는 문장은, 복잡한 제어 흐름을 반대하는 리뷰 코멘트의 원리적 근거로 그대로 쓸 수 있다.
- goto 가 아니라 "추론 가능성"이 논점이라는 재해석은, 예외 남용이나 콜백 지옥을 지적할 때 논쟁을 취향에서 원리로 옮긴다.
