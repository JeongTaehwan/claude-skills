# Trunk Based Development

https://trunkbaseddevelopment.com/

## 한 줄
장수 브랜치를 없애고 하루 이내 수명의 짧은 브랜치로 trunk 에 자주 합치자는 브랜칭 전략의 표준 문서 — Git Flow 를 비롯한 대안들과의 트레이드오프, 그리고 릴리스 브랜치·피처 플래그로 미완성 코드를 감추는 실행 방법까지 정리돼 있다.

## 페르소나
**브랜치가 2주씩 살아 있어 머지할 때마다 충돌 지옥을 겪고, 릴리스 직전에 대규모 통합 리스크가 몰리는 팀의 리드.** Git Flow 를 그대로 도입했는데 develop/release/hotfix 브랜치 관리 비용이 기능 개발보다 커졌다. 바꾸자고 말하려면 "미완성 기능은 어떻게 감추냐"는 반문에 답할 준비가 필요하다.

## 이럴 때 연다
- 브랜치 전략을 새로 정하거나 Git Flow 에서 이탈할지 결정할 때
- 머지 충돌·재충돌이 반복되어 통합 주기 자체를 손봐야 할 때
- "완성 안 된 기능을 어떻게 main 에 넣냐"는 반론에 답해야 할 때
- 릴리스 브랜치를 둘지, trunk 에서 바로 릴리스할지 정할 때
- 코드 리뷰를 게이트로 둘지, 커밋 후 리뷰로 갈지 논의할 때

## 이럴 땐 아니다
- 미완성 코드를 감추는 기법 자체를 깊게 파려면 `development/feature-toggles.md` 가 본문이다
- 배포 리스크를 점진 노출로 줄이는 방법은 `development/canary-release.md`
- 통합 주기 개선이 실제 성과로 이어지는지의 지표 체계는 `development/dora.md` / `development/dora-four-keys.md`
- 이미 충돌이 난 특정 MR 을 어떻게 푸느냐는 운영 절차 문제지 전략 문서가 답할 영역이 아니다

## 무엇이 들어있나
핵심 주장은 "머지 충돌은 도구 문제가 아니라 브랜치 수명 문제"라는 것이다. 브랜치가 오래 살수록 통합 비용은 선형이 아니라 급격히 커지므로, 전략은 충돌을 잘 푸는 게 아니라 충돌이 자랄 시간을 주지 않는 쪽이어야 한다.
그래서 이 문서는 흔한 직관을 뒤집는다 — 기능이 완성될 때까지 브랜치에 두는 대신, **미완성 코드를 trunk 에 넣되 실행 경로에서 감추라**고 한다. 수단은 피처 플래그, 브랜치 바이 애브스트랙션, 그리고 아직 호출되지 않는 코드다.
규모에 따라 두 갈래를 제시한다. 소규모 팀은 trunk 에 직접 커밋도 가능하고, 규모가 커지면 수명이 하루를 넘지 않는 짧은 브랜치와 PR 을 쓴다. 어느 쪽이든 "브랜치가 며칠 이상 산다"는 상태를 실패 신호로 본다.
릴리스는 trunk 에서 태그를 따거나 릴리스 브랜치를 잘라내되, 릴리스 브랜치에서는 개발하지 않고 수정은 trunk 에 먼저 넣은 뒤 체리픽하라고 한다 — 브랜치가 다시 갈라지는 것을 구조적으로 막는 규칙이다.
Git Flow, GitHub Flow, GitLab Flow 등과의 비교 절이 따로 있어, 팀 상황(릴리스 주기, 지원 버전 수)에 따라 무엇이 맞는지 판단할 재료를 준다.

## 인용 포인트
- "브랜치 수명이 길수록 통합 비용이 커진다"는 명제는 브랜치 전략 변경 제안서의 첫 문단으로 쓸 수 있다.
- "미완성 기능은 브랜치가 아니라 플래그로 감춘다"는 원칙은, TBD 도입에 대한 가장 흔한 반론에 대한 표준 답변이다.
- 릴리스 브랜치에서 직접 고치지 말고 trunk 에 먼저 넣고 체리픽하라는 규칙은 핫픽스 절차 문서에 그대로 옮길 수 있다.
