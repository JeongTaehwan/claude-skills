# AB180 엔지니어링 블로그

https://engineering.ab180.co/

## 한 줄
모바일 어트리뷰션(Airbridge)을 만드는 회사가, 하루 수십억 건 규모의 이벤트를 받아 저장·집계하는 데이터 인프라를 어떻게 굴리는지 한국어로 공개한 기록.

## 페르소나
**"일단 로그부터 쌓자"로 시작한 이벤트 수집이 커져서, 적재는 되는데 집계가 못 따라가는 상황에 놓인 백엔드/데이터 엔지니어.** 주문·결제 이벤트를 RDB에 그대로 밀어 넣다가 조회가 느려지기 시작했고, 컬럼형 스토어나 OLAP 엔진으로 옮겨야 한다는 건 알겠는데 실제로 옮긴 사람의 이야기가 필요하다. 영어권 자료는 규모가 너무 크거나(구글 급) 너무 장난감이라 우리 규모에 맞는 중간 사례가 안 잡힌다.

## 이럴 때 연다
- 이벤트 수집 파이프라인을 새로 설계하는데 수집 → 버퍼 → 적재 → 집계의 각 단계에 뭘 쓸지 고를 때
- 로그성 데이터가 커져서 OLAP 스토어(Druid, ClickHouse, Redshift 계열) 도입을 검토할 때
- 대용량 배치 집계의 재처리(backfill) 전략을 짤 때
- 한국 회사 규모에서 실제로 돌아간 데이터 인프라 사례를 팀에 제시해야 할 때

## 이럴 땐 아니다
- 일반적인 백엔드/웹 개발 사례가 필요하면 `development/techblog-woowahan-com.md` 나 `development/toss-tech.md` 쪽이 폭이 넓다
- 스트리밍 플랫폼 자체의 동작 원리(파티션·오프셋·전달 보장)를 알고 싶다면 사례가 아니라 원문 문서인 `development/apache-kafka.md`
- 분산 데이터 시스템의 이론적 트레이드오프(복제, 일관성, 파티셔닝)를 정리하려면 `architecture/designing-data-intensive-applications.md`

## 무엇이 들어있나
데이터 파이프라인·인프라 운영기가 중심축이다. 어트리뷰션이라는 도메인 특성상 "들어오는 이벤트를 빠짐없이 받아서, 나중에 조건을 바꿔가며 다시 집계한다"는 요구가 강하고, 글들이 그 제약 아래에서 내려진 선택을 설명한다.
사례 기반이라 "이 기술이 좋다"가 아니라 "이 규모에서 이 제약 때문에 이걸 골랐고, 대신 이걸 포기했다"는 형태로 읽힌다.
한국어라 팀 내부 문서에 그대로 인용하거나 스터디 자료로 돌리기 좋다.

## 인용 포인트
- 데이터 스토어 교체를 제안할 때, 벤더 문서 대신 "국내 규모에서 실제로 겪은 문제" 사례로 붙이면 설득력이 다르다.

## 코드 예시

"원본 이벤트는 그대로 두고, 집계는 조건을 바꿔 다시 돌린다"는 제약을 테이블 설계로 옮긴 형태 — 파티션 단위로 지웠다 다시 채울 수 있어야 backfill 이 성립한다.

```sql
-- 원본: append-only, 날짜 파티션
CREATE TABLE events (
    event_at  DateTime,
    device_id String,
    name      String,
    props     String
) ENGINE = MergeTree
PARTITION BY toYYYYMMDD(event_at)
ORDER BY (name, device_id, event_at);

-- 집계: 하루치를 통째로 버리고 다시 채운다 (재실행해도 같은 결과)
ALTER TABLE daily_installs DROP PARTITION '20260819';

INSERT INTO daily_installs
SELECT toDate(event_at) AS d, count() AS cnt
FROM events
WHERE name = 'install'
  AND event_at >= '2026-08-19 00:00:00'
  AND event_at <  '2026-08-20 00:00:00'
GROUP BY d;
```

파티션을 지우고 다시 넣는 동안 그 하루치 집계는 비어 있다 — 조회 쪽이 이 구간을 어떻게 볼지(이전 스냅샷 유지, 또는 조회 차단)를 먼저 정해야 실제로 쓸 수 있다.
