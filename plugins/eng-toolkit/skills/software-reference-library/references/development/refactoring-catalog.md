# Refactoring Catalog (Martin Fowler)

https://refactoring.com/catalog/

## 한 줄
『Refactoring』 2판에 실린 리팩터링 기법들의 정본 목록 — 가치는 기법 설명 자체보다 **각 변형에 붙은 이름이 팀의 공통 어휘가 된다**는 데 있다.

## 페르소나
**리뷰 코멘트가 "이 부분 좀 정리해주세요"에서 멈춰서, 작성자와 리뷰어가 서로 다른 걸 상상한 채 합의했다고 착각하는 테크리드.** 주문 금액 계산 함수가 200줄이 됐는데, 어떻게 쪼개자는 건지 말로 설명하려면 매번 길어지고 결국 취향 싸움이 된다. "Extract Function 하고 Replace Temp with Query 로 정리하자"처럼 한 줄로 지시가 끝나는 어휘가 필요하다.

## 이럴 때 연다
- 코드 리뷰에서 구조 개선을 요청할 때, 모호한 표현 대신 정확한 기법 이름을 쓰고 싶을 때
- 큰 리팩터링을 **되돌릴 수 있는 작은 단계들의 연속**으로 쪼개 계획서를 쓸 때
- 조건문 덩어리, 긴 파라미터 목록, 전역 상태 같은 전형적 문제에 이미 이름 붙은 해법이 있는지 확인할 때
- 리팩터링 PR 을 리뷰할 때, 이 변경이 동작을 바꾸지 않는 변형인지 판단할 때
- 팀 리뷰 가이드에 "이 어휘를 쓴다"고 못 박을 표준 목록이 필요할 때

## 이럴 땐 아니다
- 코드 스멜에서 출발해 "이 냄새엔 어떤 기법인가"를 찾고 싶고 예제 코드가 필요하면 `development/refactoring-guru.md` 가 더 편하다 (한국어 번역도 있다)
- 서식·스타일 정리는 리팩터링이 아니다 — `development/prettier.md`, `development/eslint.md`
- 모듈 경계나 아키텍처 수준의 재배치는 이 카탈로그의 범위 밖이다 — `architecture/martin-fowler-software-architecture-guide.md`, `architecture/hexagonal-architecture.md`
- 리팩터링의 전제인 "동작 보존을 무엇이 보증하는가"가 비어 있다면 기법 목록보다 테스트가 먼저다 — `qa/testpyramid.md`, `qa/software-engineering-at-google-ch-12-unit-testing.md`
- 설계 패턴을 적용하려는 것이라면 `architecture/design-patterns.md`

## 무엇이 들어있나
카탈로그는 기법을 이름 순으로 나열하고, 각 항목에 무엇을 무엇으로 바꾸는지를 짧게 보여준다. 책 본문의 상세 절차(동기, 단계별 변형, 예제)는 책 쪽에 있고, 이 페이지는 **인덱스이자 어휘 사전**이다.
전제가 중요하다. 리팩터링은 "코드를 좋게 고치는 일" 일반이 아니라, **외부 동작을 바꾸지 않으면서 내부 구조를 바꾸는 것**으로 좁게 정의된다. 이 정의를 팀이 공유하면 "리팩터링하면서 버그도 고쳤다"는 PR 이 왜 리뷰하기 어려운지가 자명해진다 — 동작 변경과 구조 변경이 한 커밋에 섞이면 회귀 원인을 분리할 수 없다.
또 하나는 단위의 크기다. 카탈로그의 각 기법은 몇 분 안에 끝나고 언제든 멈출 수 있는 작은 변형이다. 대규모 재작성이 아니라 이런 작은 변형의 연쇄로 구조를 옮긴다는 것이 원저의 방법론이고, 이 관점이 "리팩터링 스프린트를 따로 잡자"는 흔한 제안과 정면으로 충돌한다.
2판 기준이라 예제는 JavaScript 다. 특정 언어 기능에 묶인 기법보다 이름과 의도를 가져다 쓰는 것이 실용적이다.

## 인용 포인트
- 리뷰 가이드에 "구조 개선 요청은 카탈로그의 기법 이름으로 쓴다"는 규칙을 넣을 때의 표준 목록으로 인용할 수 있다.
- "리팩터링은 외부 동작을 바꾸지 않는다"는 정의는, 동작 변경과 구조 변경을 커밋 단위로 분리하자는 규약의 근거가 된다.
- 리팩터링을 별도 일정으로 떼어내자는 제안에 대해, 작은 변형의 연쇄라는 원저의 단위 개념이 반론 근거가 된다.
