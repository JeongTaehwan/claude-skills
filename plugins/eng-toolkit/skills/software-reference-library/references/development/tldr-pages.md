# tldr pages

https://github.com/tldr-pages/tldr

## 한 줄
man 페이지를 대체하지 않고 보완하는 커뮤니티 예제 모음 — 각 명령어당 실제로 자주 쓰는 사용례 몇 줄만 남긴다. 옵션 전수 설명 대신 "이 명령으로 이 일을 하려면 이렇게 친다"만 있다.

## 페르소나
**`tar`, `find`, `openssl`, `docker` 같은 명령을 몇 달에 한 번 쓰는데, 그때마다 옵션 조합이 기억나지 않아 매번 검색하는 엔지니어.** `man tar` 를 열면 수백 줄이 나오고 필요한 건 압축 해제 한 줄인데, 그 한 줄을 찾는 데 시간이 더 걸린다. 검색 결과 블로그는 버전이 오래됐거나 위험한 명령을 섞어 놓는다.

## 이럴 때 연다
- 자주 안 쓰는 CLI 명령의 대표 사용례를 3초 안에 확인하고 싶을 때
- 배포·운영 중 급하게 `journalctl`, `ss`, `kubectl` 같은 명령을 조합해야 할 때
- 팀 온보딩 문서에 명령어 예시를 붙일 때, 손으로 쓰기보다 검증된 예제를 참조할 때
- 오프라인/제한된 서버 환경에서 클라이언트를 미리 설치해 두고 쓸 때

## 이럴 땐 아니다
- 옵션의 정확한 의미, 종료 코드, 플랫폼별 차이가 중요하면 `man` 원문을 봐야 한다 — tldr 은 의도적으로 생략한다
- 학습 경로나 개념 정리는 `development/every-programmer-should-know.md`
- 셸 스크립트를 제대로 짜는 규약은 `development/google-style-guides.md` (Shell Style Guide 포함)

## 무엇이 들어있나
저장소는 명령어 하나당 마크다운 파일 하나 구조이고, 형식이 엄격하게 통일돼 있다 — 한 줄 설명, 원문 문서 링크, 그리고 예제 몇 개. 예제마다 설명 문장과 명령 한 줄이 짝을 이루고, 사용자가 바꿔야 할 부분은 `{{placeholder}}` 로 표시한다. 이 형식 제약이 품질을 유지하는 장치다.
플랫폼별 디렉터리(common / linux / osx / windows 등)가 나뉘어 있어, 같은 명령이라도 BSD 계열과 GNU 계열의 옵션 차이를 따로 담을 수 있다.
다국어 번역이 활발해 한국어 페이지도 상당수 있다.
클라이언트가 여러 언어로 구현돼 있어 `tldr tar` 처럼 터미널에서 바로 조회하거나, 웹에서 검색할 수 있다.
기여 문턱이 낮은 것도 특징이다 — 팀에서 자주 틀리는 명령 예제를 발견하면 PR 로 고칠 수 있다.

## 인용 포인트
- "문서는 완전성과 검색 가능성 사이에서 하나를 골라야 한다"는 주장의 실물 사례다 — 문서 체계를 설계할 때 `development/diataxis.md` 의 4분류 중 how-to 만 극단적으로 특화한 형태로 볼 수 있다.

## 코드 예시

형식 제약이 품질 장치라는 말의 실물 — 사내 명령용 페이지를 tldr 규격 그대로 쓰면 이렇게 된다.

```markdown
# deploy-orders

> 주문 서비스를 배포한다.
> 자세한 내용: <https://wiki.acme.io/runbook/orders>.

- 현재 브랜치를 스테이징에 배포한다:

`deploy-orders --env staging --ref {{브랜치명}}`

- 특정 커밋을 운영에 배포한다 (승인 필요):

`deploy-orders --env prod --ref {{커밋_해시}}`

- 무엇이 바뀌는지만 확인하고 배포하지 않는다:

`deploy-orders --env prod --ref {{커밋_해시}} --dry-run`

- 직전 릴리스로 롤백한다:

`deploy-orders --env prod --rollback`
```

여기 없는 것이 이 형식의 핵심이다 — 옵션의 정확한 의미, 종료 코드, 실패 시 동작은 의도적으로 빠져 있고 링크로 넘긴다. 그걸 채워 넣기 시작하면 `man` 페이지가 되고, "3초 안에 찾는다"는 유일한 이점이 사라진다. how-to 하나만 남기고 나머지를 버리는 결정이 이 저장소의 전부다.
