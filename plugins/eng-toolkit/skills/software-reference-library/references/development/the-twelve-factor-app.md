# The Twelve-Factor App

https://12factor.net/

## 한 줄
배포 가능한 서비스가 갖춰야 할 12가지 조건을 항목별로 못 박은 문서 — 설정은 환경변수로, 프로세스는 무상태로, 로그는 파일이 아니라 stdout 이벤트 스트림으로. 컨테이너 이전에 쓰였지만 오늘날 쿠버네티스 배포가 전제하는 규약과 거의 일치한다.

## 페르소나
**신규 서비스를 부트스트랩하거나, 레거시 서비스를 컨테이너로 옮기려는데 "왜 이건 안 되는지" 매번 설명해야 하는 백엔드 엔지니어.** 설정 파일이 브랜치별로 갈라져 있고, 세션이 인스턴스 메모리에 붙어 있어 스케일아웃이 안 되며, 로그는 각 서버 로컬 디스크에 쌓인다. 리뷰에서 "이렇게 하면 안 된다"고 말할 때 개인 취향이 아닌 인용 가능한 기준이 필요하다.

## 이럴 때 연다
- 신규 서비스 구조를 잡으며 설정/로그/프로세스 모델의 기본선을 정할 때
- 온프레미스 서비스를 컨테이너·오토스케일 환경으로 옮기기 전 사전 점검표가 필요할 때
- 스케일아웃이 안 되는 원인(세션 고착, 로컬 파일 의존, 백그라운드 스레드)을 진단할 때
- 운영 DB 마이그레이션, 관리 스크립트 실행을 어디에 둘지 팀 규칙을 정할 때
- 코드리뷰에서 "설정값을 코드에 하드코딩하지 말자"를 근거와 함께 말할 때

## 이럴 땐 아니다
- 배포 파이프라인과 릴리스 속도 지표는 `development/dora.md` / `development/dora-four-keys.md`
- 브랜치 전략·통합 주기 문제는 `development/trunk-based-development.md`
- 운영 신뢰성(SLO, 온콜, 장애 대응) 체계는 `development/google-sre-books.md`
- 클라우드 아키텍처 전반의 설계 원칙(비용·복원력·보안 축)은 `architecture/aws-well-architected-framework.md`
- 컨테이너 이미지 작성법 자체는 `development/docker.md`

## 무엇이 들어있나
핵심 주장은 "앱은 실행 환경을 알면 안 된다"이다. 코드는 하나이고, 환경 차이는 전부 환경변수(Config)로만 들어온다 — 그래서 `config/production.yml` 처럼 환경별 파일을 코드에 두는 흔한 관행을 정면으로 반대한다.
프로세스 항목이 가장 자주 인용된다. 프로세스는 무상태·무공유여야 하고, 지속되어야 할 것은 전부 외부 백킹 서비스(DB, Redis, 큐)에 넣는다. 로컬 파일시스템과 인메모리 세션은 임시 캐시로만 쓸 수 있다.
백킹 서비스를 "부착 가능한 리소스"로 본다는 점도 특징이다. 로컬 MySQL 과 관리형 RDS 는 앱 입장에서 URL 하나 차이여야 하며, 코드 변경 없이 교체 가능해야 한다.
로그 항목은 앱이 로그 파일을 관리하지 말라고 못 박는다. 앱은 stdout 에 이벤트를 흘리고, 수집·회전·보관은 실행 환경의 책임이다.
그 밖에 의존성 명시적 선언·격리, 빌드/릴리스/실행 단계 분리, 포트 바인딩으로 자기완결적 서비스 되기, 빠른 시작과 우아한 종료(Disposability), 개발/운영 환경 격차 최소화, 관리 작업을 일회성 프로세스로 실행하기가 들어 있다.

## 인용 포인트
- "설정은 환경변수에" — 환경별 설정 파일을 저장소에 커밋하는 관행을 걷어낼 때의 표준 근거.
- "로그는 이벤트 스트림" — 앱이 로그 파일 회전을 직접 하지 않아야 하는 이유를 한 줄로 설명할 수 있다.
- "개발/운영 환경 격차 최소화" — 로컬만 SQLite, 운영은 MySQL 같은 구성을 반대할 때 인용.
