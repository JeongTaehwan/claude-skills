# Google Engineering Practices (eng-practices)

https://github.com/google/eng-practices

## 한 줄
구글이 사내에서 실제로 굴리던 코드리뷰 규범을 그대로 공개한 저장소 — 리뷰어용 가이드와 변경 작성자용 가이드가 짝으로 들어 있다.

## 페르소나
**코드리뷰 규칙을 처음 문서화하려는데, 자기 취향을 규칙으로 굳히는 것처럼 보일까 봐 못 쓰고 있는 리드.** 팀에서 리뷰 논쟁이 반복되지만 중재 근거가 "제 생각엔"뿐이라 설득력이 없다. 외부의, 그리고 실제로 대규모로 운영된 적 있는 규범을 베이스로 깔고 거기서 팀 맥락만 덮는 방식이 필요하다.

## 이럴 때 연다
- 팀 코드리뷰 규칙 문서를 처음 만들 때의 뼈대로
- 리뷰가 감정 싸움으로 번져서 중립적인 제3의 기준이 필요할 때
- 리뷰를 잘 받는 법(작은 변경으로 쪼개기, 설명 붙이기)을 신규 입사자에게 전달할 때
- 여러 언어로 번역된 판본이 있어 팀 구성이 다양할 때 공유용으로
- 사내 문서에 규칙을 포크해 넣고 팀 맥락에 맞게 고쳐 쓸 때

## 이럴 땐 아니다
- 읽기만 할 거라면 웹으로 정리된 `development/google-code-review-developer-guide.md` 쪽이 편하다. 이 저장소는 포크해서 고쳐 쓸 때 값어치가 있다.
- 구글의 엔지니어링 운영 전반(테스트 문화, 대규모 변경, 폐기 정책)은 범위가 다르므로 `development/software-engineering-at-google.md`
- 언어별 코딩 규칙은 `development/google-style-guides.md`
- 리뷰가 아니라 배포·릴리스 절차 문제라면 `development/trunk-based-development.md`

## 무엇이 들어있나
크게 두 갈래다. 리뷰어를 위한 가이드(무엇을 볼 것인가, 어떤 순서로 볼 것인가, 얼마나 빨리 답할 것인가, 코멘트를 어떻게 쓸 것인가, 대립을 어떻게 푸는가)와, 변경을 올리는 사람을 위한 가이드(변경을 작게 쪼개기, 설명 잘 쓰기, 리뷰 코멘트에 대응하기).
관통하는 원칙은 승인 기준을 "완벽"이 아니라 "코드베이스가 확실히 나아지는가"로 잡는 것이다. 이상적이지 않아도 개선이면 통과시키고, 남은 것은 후속 작업으로 넘긴다.
리뷰 대상 우선순위가 명시돼 있다 — 설계와 정확성이 먼저고, 스타일은 뒤다. 스타일 지적은 자동화 도구가 할 일로 밀려 있다.
"작성자 가이드가 따로 있다"는 점이 실무에서 유용하다. 리뷰가 안 굴러가는 원인의 절반은 리뷰어가 아니라 리뷰 불가능한 크기와 설명 없는 변경 쪽이기 때문이다.
마크다운 원문이라 사내 위키로 옮기고 팀 규칙을 덧붙이기 쉽다.

## 인용 포인트
- "완벽함이 아니라 개선" — 리뷰가 무한 왕복될 때 승인 기준을 되돌리는 근거.
- 설계·정확성 → 테스트 → 명명·주석 → 스타일 순의 우선순위. 스타일 지적으로 리뷰가 채워지는 팀에 바로 들이댈 수 있다.

## 코드 예시

규범을 포크해 우리 저장소에 심을 때 가장 먼저 생기는 파일 — "설계와 정확성을 볼 사람"을 경로로 고정해 둔 것.

```
# .github/CODEOWNERS
*                      @org/backend

# 정확성이 걸리는 영역은 도메인 오너가 반드시 본다
/src/payment/          @org/payment
/src/coupon/           @org/promotion
/migrations/           @org/dba

# 계약이 깨지면 다른 팀이 죽는 곳
/api/openapi.yaml      @org/backend @org/mobile

# 스타일은 사람이 보지 않는다 — 포매터 설정 파일만 오너를 둔다
/.prettierrc           @org/platform
/.editorconfig         @org/platform
```

이 파일이 정하는 것은 "누가 보는가"뿐이고, "무엇부터 보는가"(설계 → 테스트 → 명명 → 스타일)는 여전히 문서와 습관의 몫이다. 오너를 촘촘히 걸수록 승인 대기가 길어지는 것도 감안해야 한다 — 지연이 PR 을 키우고 큰 PR 이 리뷰를 무디게 만든다는, 이 저장소가 경고한 바로 그 악순환이 여기서 시작된다.
