# CWE Top 25 Most Dangerous Software Weaknesses

https://cwe.mitre.org/top25/

## 한 줄
"실제로 신고된 CVE 데이터"를 빈도와 심각도로 가중해 산출한, **코드 수준 결함 유형**의 위험도 순위 — 의견이 아니라 집계 결과다.

## 페르소나
**정적 분석 도구를 붙였더니 경고가 수천 건 나와서 무엇부터 고칠지 못 정하고 있는 백엔드 엔지니어.** 도구가 매기는 severity 는 벤더마다 다르고, 전부 고치자니 릴리스가 멈춘다. 팀 밖에서 인정되는 우선순위 기준을 가져와서 "이 유형부터 막는다"는 선을 긋고 싶다.

## 이럴 때 연다
- SAST/린트 규칙의 우선순위를 정하거나, 어떤 규칙을 CI 차단 조건으로 승격할지 결정할 때
- 보안 코드 리뷰 체크리스트를 만들면서 항목을 고를 때
- 특정 결함 유형(예: 인가 누락, 역직렬화, 경로 조작)의 정확한 정의와 완화책을 확인할 때
- 보안 교육 커리큘럼에서 다룰 주제를 선정할 때
- 취약점 리포트에 표준 식별자(CWE-ID)를 붙여야 할 때

## 이럴 땐 아니다
- 웹 애플리케이션 관점의 위험 범주(설계 결함, 설정 오류 포함)를 보려면 `development/owasp-top-10.md` — CWE 는 코드 결함 유형, OWASP Top 10 은 애플리케이션 리스크 범주로 축이 다르다
- 구체적 방어 구현법(입력 검증, 세션, 암호 저장)의 레시피는 `development/owasp-cheat-sheet-series.md`
- 무엇을 어디까지 검증해야 하는가의 요구사항 체계는 `development/owasp-asvs.md`
- 설계 단계에서 위협을 도출하는 절차는 `development/owasp-threat-modeling.md`
- 개발 프로세스 전반에 보안을 심는 조직 차원의 프레임워크는 `development/nist-secure-software-development-framework.md`
- 의존성·빌드 공급망 쪽 위험은 `development/slsa.md` 와 `development/openssf-scorecard.md`

## 무엇이 들어있나
매년 갱신되며, 산출 근거가 공개된다 — 특정 기간의 CVE 를 CWE 유형으로 매핑하고, 발생 빈도와 CVSS 심각도를 결합해 점수를 낸다. 그래서 "전문가 감"이 아니라 재현 가능한 집계라는 점이 이 목록의 힘이다.
각 항목이 CWE 데이터베이스의 상세 페이지로 연결되고, 거기에 결함 설명·예시 코드·탐지 방법·완화책이 정리돼 있다.
순위 변동 자체가 정보다. 어떤 유형이 올라가고 내려갔는지가 업계의 실제 실패 양상 변화를 보여준다.
주의: 순위는 "인터넷 전체"의 통계지 우리 시스템의 위험 순서가 아니다. 커머스 백엔드라면 인가 누락이나 비즈니스 로직 결함이 목록 상위 항목보다 실질 위험이 클 수 있다. 우선순위의 출발점으로 쓰되 도메인 보정을 얹어야 한다.

## 인용 포인트
- 보안 작업에 시간을 배정받아야 할 때, "이 유형이 실제 CVE 통계에서 몇 위"라는 형태의 근거는 감상적 호소보다 훨씬 잘 통과된다.
- 린트 규칙을 끄자는 요청에 대해, 그 규칙이 대응하는 CWE 의 순위를 근거로 반박할 수 있다.
