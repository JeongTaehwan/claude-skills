# Airbnb JavaScript Style Guide

https://github.com/airbnb/javascript

## 한 줄
"왜 이렇게 써야 하는가"를 규칙마다 붙여 놓은 JS 스타일 가이드 — 그리고 사실상 대부분의 ESLint 설정이 조상으로 삼는 문서.

## 페르소나
**PR 리뷰가 매번 취향 싸움으로 번져서 중재 기준이 필요한 테크리드.** 화살표 함수를 쓸지, 구조 분해를 강제할지, `for...of` 를 허용할지 같은 논쟁이 사람마다 다르고, 각자 "이게 더 낫다"고만 하니 결론이 안 난다. 팀 밖의 기준선을 하나 세워서 논쟁 자체를 종료시키고 싶다.

## 이럴 때 연다
- ESLint/Prettier 설정을 처음 잡으면서 어떤 규칙 세트를 베이스로 삼을지 정할 때
- 코드 리뷰에서 스타일 지적이 반복되어 규칙으로 승격시키려 할 때
- 특정 린트 규칙을 끄자는 요청이 올라왔는데, 그 규칙이 원래 왜 있는지 근거가 필요할 때
- 신규 입사자에게 "우리 팀 JS는 이렇게 쓴다"를 한 문서로 전달할 때

## 이럴 땐 아니다
- 포매팅(줄바꿈, 따옴표, 세미콜론)만 자동화하고 싶다면 스타일 논쟁을 아예 없애는 `development/prettier.md` 가 먼저다
- 규칙을 실제로 켜고 끄고 커스텀 룰을 만드는 실행 문제는 `development/eslint.md`
- 타입 설계·제네릭·유틸리티 타입 같은 TS 고유 영역은 `development/typescript-handbook.md`
- Node 서버의 구조·에러 처리·보안 관례는 스타일이 아니라 아키텍처 문제라 `development/node-js-best-practices.md`
- 다른 언어(Java, Python, Go, C++)의 스타일 기준은 `development/google-style-guides.md`

## 무엇이 들어있나
각 규칙이 "Good / Bad" 코드 쌍과 **이유**로 구성돼 있다는 점이 핵심이다. 취향 선언이 아니라 근거가 붙어 있어서, 리뷰에서 인용했을 때 반박이 근거 대 근거로 붙는다.
타입·참조·객체·배열·구조 분해·함수·클래스·모듈·비교 연산자·주석·명명 규칙까지 언어 표면 전반을 덮는다.
React 스타일 가이드가 별도 디렉터리로 함께 들어 있다.
여러 언어로 번역돼 있어 팀 구성이 다양해도 공유하기 쉽다.
주의할 점: 이 가이드는 Airbnb의 맥락(대규모 React 코드베이스)에서 나온 것이고, 일부 규칙은 현대 JS/TS 환경에서 과하거나 낡았다는 비판이 있다. 통째로 삼키기보다 베이스로 깔고 팀 결정으로 덮는 쪽이 실제 운용에 맞다.

## 인용 포인트
- "우리 팀 취향"이 아니라 "널리 쓰이는 기준선"으로 규칙을 제시하면 논쟁이 개인 대 개인에서 벗어난다.
- 규칙마다 이유가 붙어 있으므로, 예외를 허용할 때도 "이 이유가 우리 맥락에는 해당 없다"는 형태로 근거 있게 뺄 수 있다.
