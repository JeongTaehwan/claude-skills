# The Pragmatic Engineer

https://newsletter.pragmaticengineer.com/

## 한 줄
빅테크와 스타트업 내부에서 실제로 어떻게 일하는지 — 온콜, 승진 체계, 인시던트 대응, 조직 개편, 채용, 보상 — 를 현직자 취재 기반으로 다루는 뉴스레터. 코드가 아니라 **엔지니어링 조직의 작동 방식**이 주제다.

## 페르소나
**팀 프로세스를 바꾸자고 제안해야 하는데 "다른 데는 어떻게 하나요"라는 질문에 답할 자료가 없는 리드·매니저.** 온콜 로테이션을 도입하거나 리뷰 규칙을 바꾸거나 레벨 기준을 손보려는데, 근거가 개인 경험뿐이라 설득이 안 된다. 업계 표준이라 할 만한 것의 범위를 알고 싶다.

## 이럴 때 연다
- 온콜·인시던트 대응 체계를 도입·개편하며 다른 회사의 운영 방식을 참고할 때
- 엔지니어 레벨·승진·성과 평가 기준을 만들거나 검토할 때
- 조직 구조(플랫폼 팀, 스쿼드, 오너십 경계)를 재설계할 때
- 이직·연봉 협상·커리어 판단에 업계 맥락이 필요할 때
- 특정 회사의 개발 문화나 대형 장애의 내막을 사실 관계 위주로 알고 싶을 때

## 이럴 땐 아니다
- 규모가 커질 때 생기는 문제의 원리적 분석이 필요하면 뉴스레터가 아니라 `development/software-engineering-at-google.md`
- 배포·복구 성과를 데이터로 벤치마크하려면 `development/dora.md`
- 기술 스택 채택 여부의 업계 신호를 보려면 `development/thoughtworks-technology-radar.md`
- 조직 운영 규칙을 통째로 공개한 문서를 원하면 `planning/gitlab-handbook.md`
- 관리자 역할 자체에 대한 자료 모음은 `development/engineering-manager.md`, `development/awesome-cto.md`

## 무엇이 들어있나
성격이 명확하다 — 의견 칼럼이 아니라 **취재물**에 가깝다. 여러 회사 현직자에게 물어 실제 관행을 모으고, "이 회사는 이렇게 하고 저 회사는 저렇게 한다"는 분포를 보여주는 방식이라, 한 사람의 주장보다 신뢰도가 높고 인용하기도 낫다.
다루는 축은 코드 바깥이다. 승진과 레벨, 보상, 채용 절차, 온콜과 인시던트, 조직 개편과 정리해고, 개발자 도구 시장의 변화. 아키텍처를 배우러 오는 곳이 아니다.
유료 구독 비중이 크다. 무료 공개분만으로도 흐름은 잡히지만, 깊이 있는 회사별 심층 기사는 대체로 유료다. 팀 예산으로 구독을 검토할 만한지 판단하려면 무료 아카이브를 먼저 훑는 게 순서다.
영어권 중심이라 국내 조직 문화·보상 구조와는 맥락이 다르다. 관행을 그대로 옮기기보다 "이 규칙이 어떤 문제를 풀려고 생긴 것인가"를 읽는 편이 낫다.

## 인용 포인트
- 프로세스 변경 제안서에서 "업계 관행"을 주장할 때, 여러 회사 사례를 모아 분포로 보여준 글이 단일 회사 사례보다 반박에 강하다.
