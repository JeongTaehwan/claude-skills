# Diátaxis — 문서 작성 프레임워크

https://diataxis.fr/

## 한 줄
"문서가 뭔가 이상한데 왜인지 모르겠다"를 진단하는 도구 — 문서를 Tutorial / How-to / Reference / Explanation 네 종류로 쪼개고, 한 문서가 두 종류를 겸하려 들 때 나빠진다고 주장한다.

## 페르소나
**README 를 계속 고쳐 쓰는데도 "이거 읽어도 모르겠다"는 말이 반복되는 팀의 문서 담당자.** 신규 입사자용 온보딩 문서에 설치 절차, API 파라미터 표, 아키텍처 배경 설명이 한 파일에 섞여 있어서, 처음 온 사람은 길을 잃고 이미 아는 사람은 필요한 표를 못 찾는다. 문장을 다듬어도 나아지지 않는 이유가 문장이 아니라 구조에 있다는 걸 아직 언어화하지 못했다.

## 이럴 때 연다
- 새 서비스의 문서 디렉터리 구조를 처음 설계할 때 — 어떤 파일을 만들지가 아니라 어떤 종류를 만들지 정해야 할 때
- 비대해진 README 나 위키를 쪼개야 하는데 어떤 축으로 쪼갤지 모를 때
- 문서 리뷰에서 "설명이 부족하다" vs "너무 장황하다"가 동시에 나올 때 — 대개 종류가 섞인 신호다
- 결제·쿠폰처럼 도메인 규칙이 복잡한 모듈에서, 규칙 설명(Explanation)과 연동 절차(How-to)가 뒤엉켜 있을 때
- 사내 문서 템플릿·문서 기여 가이드를 만들 때

## 이럴 땐 아니다
- 문장 스타일, 용어 표기, 목소리 톤 같은 **문장 단위** 규칙은 `development/google-developer-documentation-style-guide.md`
- README 하나에 무엇을 넣을지에 대한 구체적 체크리스트는 `development/standard-readme.md`
- 릴리스 노트·변경 이력의 형식 문제는 `development/keep-a-changelog.md`
- 설계 의사결정의 배경을 남기는 문제는 문서 분류가 아니라 기록 형식의 문제라 `architecture/architecture-decision-records.md`

## 무엇이 들어있나
핵심 주장은 문서를 두 축 — 실무 중 필요한가 / 학습 중 필요한가, 그리고 행동 중심인가 / 이해 중심인가 — 으로 나누면 네 사분면이 나온다는 것이다. Tutorial(배우면서 따라 하는 것), How-to(목표를 이미 아는 사람이 해내는 것), Reference(정확한 정보를 찾는 것), Explanation(왜 이런지 이해하는 것).
가장 반직관적인 대목은 **튜토리얼에서 설명하지 말라**는 지침이다. 초보자에게 배경을 설명하면 친절해 보이지만 실제로는 따라 하기를 방해한다. 마찬가지로 How-to 는 개념을 가르치려 들지 말아야 하고, Reference 는 가르치려 들지 말고 서술만 해야 한다.
프레임워크를 "지도이지 계획서가 아니다"라고 규정한다. 문서를 처음부터 네 종류로 완벽히 설계하라는 게 아니라, 지금 있는 문서를 사분면에 놓고 어긋난 부분부터 조금씩 옮기라는 점진적 사용법을 권한다.
Django, Cloudflare, Gatsby 등 실제 채택 사례가 있는 프레임워크다.

## 인용 포인트
- "이 문서는 튜토리얼인가 레퍼런스인가"라는 질문 하나로 문서 리뷰의 방향 없는 논쟁을 끝낼 수 있다.
- 문서가 나쁜 이유를 "작성자가 글을 못 써서"가 아니라 "한 문서가 두 목적을 겸해서"로 재정의하면, 개선 작업이 개인 비판이 아니라 구조 작업이 된다.
