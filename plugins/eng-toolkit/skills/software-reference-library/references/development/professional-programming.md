# Professional Programming (charlax)

https://github.com/charlax/professional-programming

## 한 줄
"코드를 잘 짜는 법"이 아니라 **조직 안에서 개발자로 제대로 일하는 법**을 주제로 모은 읽을거리 큐레이션 — 설계·커뮤니케이션·문서·의사결정·경력이 알고리즘보다 앞에 온다.

## 페르소나
**기술적으로는 문제없는데 협업에서 계속 마찰이 생기는 3~5년차 개발자를 코칭해야 하는 팀 리드.** PR 설명이 한 줄이고, 설계 논의에서 결론이 안 나면 그냥 자기 방식으로 구현해버리고, 장애 상황에서 무엇을 먼저 알려야 하는지를 모른다. 1:1 에서 말로 설명하는 대신 읽고 스스로 정리할 자료 묶음이 필요하다. 또는 온보딩 3개월 읽기 목록을 만들어야 하는 상황.

## 이럴 때 연다
- 신규 입사자 온보딩 읽기 목록을 만들 때 — 언어 튜토리얼이 아니라 "우리가 기대하는 일하는 방식"을 담을 자료가 필요할 때
- 주니어에게 "코드는 되는데 설계를 못 한다"를 어떻게 성장시킬지 자료로 뒷받침하고 싶을 때
- 시니어/리드 승격 기준에서 기술 외 역량(문서, 협상, 우선순위)을 어떻게 표현할지 참고할 때
- 기술 부채·추정·리뷰 같은 반복 주제에 대해 이미 잘 쓰인 글을 찾을 때
- 스스로 다음에 뭘 읽을지 막혔을 때의 진입점

## 이럴 땐 아니다
- 특정 기술을 어떤 순서로 배울지가 목적이면 `development/developer-roadmap.md`
- 리뷰에서 무엇을 지적할지에 대한 실행 규칙은 `development/google-code-review-developer-guide.md`, `development/google-engineering-practices.md`
- 대규모 조직의 엔지니어링 관행을 하나의 일관된 논지로 읽고 싶으면 큐레이션 대신 `development/software-engineering-at-google.md`
- 매니지먼트·CTO 트랙 자료는 `development/awesome-cto.md`, `development/engineering-manager.md`
- 시스템을 직접 만들며 배우는 쪽은 `development/build-your-own-x.md`
- CS 기초 지식 목록은 `development/every-programmer-should-know.md`

## 무엇이 들어있나
저장소의 전제는 제목에 다 있다 — 프로그래밍 능력과 프로다움은 다른 축이고, 후자는 보통 아무도 가르쳐주지 않은 채 기대된다. 그래서 목록의 무게중심이 알고리즘·자료구조가 아니라 설계 판단, 글쓰기, 코드 리뷰, 추정, 인시던트 대응, 경력 관리 쪽에 있다.
형태는 링크 큐레이션이다. 각 항목이 원문 아티클·논문·책으로 연결되고, 주제별로 묶여 있다. 그래서 이 저장소 자체를 읽는 것이 아니라 **목차로 쓰는 것**이 맞는 사용법이다.
큐레이션의 장점이자 한계도 분명하다. 항목마다 저자가 다르므로 서로 모순되는 조언도 섞여 있고, 무엇을 먼저 읽어야 하는지에 대한 우선순위는 독자가 정해야 한다. 온보딩 목록으로 쓸 때 통째로 던지면 아무도 안 읽는다 — 5~10개를 골라 맥락을 붙여 주는 편이 낫다.

## 인용 포인트
- "프로답게 일하는 법은 별도로 학습해야 하는 기술"이라는 전제는, 온보딩에 기술 외 자료를 넣자는 제안의 근거로 쓰인다.
