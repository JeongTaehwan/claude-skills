# Prisma 공식 문서

https://www.prisma.io/docs

## 한 줄
스키마 파일 하나를 진실의 원천으로 두고 **마이그레이션과 타입 안전한 클라이언트를 함께 생성해내는** TypeScript ORM 의 1차 문서 — 지금은 ORM 을 넘어 관리형 DB·호스팅까지 포함한 제품군 문서가 되어 있다.

## 페르소나
**TypeScript 백엔드에서 DB 스키마와 애플리케이션 타입이 계속 어긋나 런타임에서 터지는 것을 겪고 있는 엔지니어.** 컬럼을 추가했는데 타입 정의를 고치는 걸 잊어 배포 후에 발견했고, 수동 SQL 마이그레이션은 누가 어디까지 적용했는지 추적이 안 된다. ORM 을 도입하려는데, 쿼리가 실제로 어떤 SQL 로 나가는지 통제할 수 없는 ORM 은 쓰기 싫다.

## 이럴 때 연다
- 새 TypeScript 서비스에서 스키마 정의·마이그레이션·쿼리 계층을 한 번에 정할 때
- 기존 DB 에 Prisma 를 붙일 때 — introspection 으로 `schema.prisma` 를 역생성하는 절차
- 마이그레이션을 개발/프로덕션에서 어떻게 다르게 적용해야 하는지 (dev 와 deploy 명령의 차이, 드리프트 감지)
- 주문 생성처럼 여러 테이블을 원자적으로 써야 할 때 — 트랜잭션 API(배치 vs 인터랙티브)의 선택 기준
- 목록 조회가 느릴 때, 관계 로딩이 실제로 몇 번의 쿼리로 나가는지와 로깅으로 확인하는 법
- 서버리스/엣지 환경에서 커넥션 수가 폭발할 때의 커넥션 풀링 대응
- 원시 SQL 로 내려가야 할 때의 이스케이프·타입 처리

## 이럴 땐 아니다
- DB 자체의 동작(격리 수준, 락, 실행 계획)이 문제라면 ORM 문서가 아니라 `development/postgresql.md`
- 인덱스가 안 타는 이유를 알아야 한다면 `development/use-the-index-luke.md`
- API 로 들어오는 **런타임 입력** 검증은 ORM 타입이 대신해주지 않는다 — `development/zod.md`
- 스키마 변경을 되돌리기 어려운 결정으로 다루는 설계 판단은 `architecture/designing-data-intensive-applications.md`
- 통합 테스트에서 진짜 DB 를 띄우고 싶다면 `testing/testcontainers.md`

## 무엇이 들어있나
문서는 크게 **Prisma ORM**(데이터 모델링과 쿼리), **Prisma Postgres**(관리형 데이터베이스), **Prisma Compute**(호스팅·배포), 그리고 CLI 레퍼런스·프레임워크별 가이드로 나뉜다. ORM 만 쓸 생각이라면 첫 번째 섹션과 CLI 레퍼런스만 보면 되지만, 문서 상단이 제품군 전체를 안내하므로 처음 들어가면 범위를 착각하기 쉽다.
ORM 의 설계 중심은 `schema.prisma` 다. 여기에 데이터 소스·모델·관계를 선언하면, 그로부터 마이그레이션 SQL 과 타입이 붙은 클라이언트가 **생성**된다. 스키마가 코드보다 앞선다는 이 방향성이 다른 ORM(엔티티 클래스에서 스키마를 유도하는 방식)과 갈리는 지점이고, 그래서 스키마를 손으로 고치고 클라이언트 재생성을 잊으면 곧바로 타입 불일치가 드러난다 — 이건 단점이 아니라 의도된 안전장치다.
마이그레이션은 개발용 명령과 프로덕션 적용 명령이 분리되어 있고, DB 실제 상태가 마이그레이션 히스토리와 어긋나는 드리프트를 감지한다. 팀에서 누군가 콘솔로 직접 DDL 을 날린 흔적이 여기서 걸린다.
트랜잭션은 여러 쓰기를 한 번에 보내는 배치 방식과, 트랜잭션을 열어둔 채 애플리케이션 로직을 끼워 넣는 인터랙티브 방식이 다르다. 재고 확인 후 차감 같은 로직은 후자를 쓰게 되는데, 트랜잭션이 열려 있는 동안 커넥션을 점유한다는 비용이 따라온다. 문서가 이 트레이드오프를 다루므로, 커머스 도메인에서는 이 절을 먼저 읽는 것이 좋다.
쿼리 로깅이 문서에 있다는 점도 중요하다. ORM 이 만들어내는 SQL 을 눈으로 확인하지 않으면 관계 로딩이 몇 번의 쿼리로 풀리는지 알 수 없다.

## 인용 포인트
- "스키마 파일이 단일 진실 원천이고 클라이언트 타입은 그로부터 생성된다"는 구조는, 스키마 변경 절차를 코드 리뷰 대상으로 승격하자는 제안의 근거가 된다.
- 마이그레이션 드리프트 감지 기능은 "프로덕션 DB 에 수동 DDL 금지" 규칙을 강제할 기술적 수단으로 제시할 수 있다.
