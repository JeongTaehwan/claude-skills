# 카카오 기술블로그

https://tech.kakao.com/

## 한 줄
국내 최대 트래픽을 받는 서비스군(메신저·검색·추천·지도)이 그 규모에서 겪은 문제와 해법을 한국어로 공개하는 곳 — 자체 개발한 인프라·플랫폼 이야기의 비중이 크다.

## 페르소나
**트래픽이 늘면서 기존 구조가 한계에 부딪혔는데, 참고할 사례가 전부 영어권 초대형 회사(구글·넷플릭스)뿐이라 격차가 큰 백엔드 엔지니어.** 우리 규모에 맞는 중간 사례가 필요하고, 무엇보다 팀 설득 자료로 돌릴 수 있게 한국어여야 한다. 이벤트 트래픽이 몰릴 때 큐를 어떻게 감당했는지, 추천을 어떻게 실시간으로 계산했는지 같은 구체가 궁금하다.

## 이럴 때 연다
- 순간 트래픽 폭증(오픈런·타임세일 같은 상황)에 대비한 구조를 설계하며 국내 사례를 찾을 때
- 추천·검색 시스템을 도입하거나 개선하면서 실서비스 적용기가 필요할 때
- 대규모 저장소·캐시·메시징 인프라 운영 사례를 볼 때
- 사내 발표나 기술 제안서에 한국어 레퍼런스를 붙여야 할 때
- if(kakao) 발표 세션과 연계된 심화 자료를 찾을 때

## 이럴 땐 아니다
- 주문·정산·배차 같은 커머스 도메인 설계와 DDD 적용 사례는 `development/techblog-woowahan-com.md` 쪽이 훨씬 두껍다
- 결제·정산 도메인의 테스트 전략과 아키텍처 개선기는 `development/tech-kakaopay-com.md`
- 프론트엔드·UX 엔지니어링 위주라면 `development/toss-tech.md`
- 사례가 아니라 원리·이론(복제, 일관성, 파티셔닝)이 필요하면 `architecture/designing-data-intensive-applications.md`
- 아키텍처 패턴 카탈로그를 원한다면 `architecture/microservices-io.md`

## 무엇이 들어있나
글의 성격이 "이 기술을 소개합니다"보다 "이 규모에서 이런 제약이 생겼고, 그래서 이렇게 했다"에 가깝다. 그래서 결론보다 제약 조건 서술이 더 쓸모 있는 경우가 많다.
다루는 폭이 넓다 — 대용량 저장·처리 인프라, 추천/검색/ML 시스템, 모바일·프론트엔드, 개발 문화와 조직까지. 회사가 크고 조직이 여럿이라 글마다 문체와 깊이의 편차가 있는 편이다.
카카오는 상당수 인프라를 자체 개발해 쓰기 때문에, 오픈소스 그대로 쓰는 팀 입장에서는 그대로 이식되지 않는 글도 섞여 있다. 그런 글은 구현보다 "왜 사내 개발로 갔는가"의 판단 근거를 읽는 게 낫다.
연 1회 규모의 기술 컨퍼런스(if(kakao)) 발표와 내용이 이어지는 경우가 많아, 블로그 글에서 출발해 발표 영상까지 따라가면 깊이가 붙는다.

## 인용 포인트
- 대규모 트래픽 대응 설계를 제안할 때, 해외 사례 대신 국내 서비스의 실제 규모와 선택을 붙이면 "우리랑 상황이 다르다"는 반론을 미리 걷어낸다.
