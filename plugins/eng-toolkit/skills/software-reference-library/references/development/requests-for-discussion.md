# Requests for Discussion (Oxide RFD)

https://www.oxide.computer/blog/rfd-1-requests-for-discussion

## 한 줄
기술 의사결정을 문서로 굴리는 프로세스를 설명하면서, **그 설명 자체를 그 프로세스의 1번 문서로 쓴** 글 — RFC 를 도입할 때 가장 먼저 막히는 "언제 쓰고, 어떻게 상태를 관리하고, 언제 닫는가"를 규정한다.

## 페르소나
**중요한 기술 결정이 슬랙 스레드와 회의 구두 합의로만 남아서, 반년 뒤 아무도 "왜 이렇게 했는지"를 재구성하지 못하는 팀의 리드.** 신규 입사자가 같은 질문을 반복하고, 이미 논의해서 기각한 대안이 다시 제안된다. 문서를 쓰자고는 했는데 언제 쓸지·누가 승인할지·언제 끝난 것으로 볼지가 정해지지 않아 두어 개 쓰고 유명무실해졌다.

## 이럴 때 연다
- 사내 기술 제안·의사결정 프로세스(RFC/RFD/설계 문서)를 처음 설계할 때
- 이미 도입했는데 문서가 리뷰 없이 방치되거나 결론 없이 흐지부지될 때 — 상태 전이와 종료 조건이 빠진 것이 원인인 경우가 많다
- "어떤 크기의 결정부터 문서를 써야 하는가"의 기준선을 팀에서 합의해야 할 때
- 비동기·분산 협업에서 회의 대신 문서로 논의를 돌리려 할 때
- 결정 기록을 나중에 검색 가능하게 남기려 할 때

## 이럴 땐 아니다
- 결정 하나를 짧게 기록하는 **경량 포맷**이 필요한 거라면 프로세스 전체보다 `architecture/architecture-decision-records.md`, `architecture/adr-github-io.md` 가 맞다
- 설계 문서의 내용 구성(무엇을 어떤 순서로 쓸지)이 궁금하면 `planning/design-docs-at-google.md`
- 제품 요구사항 문서라면 `planning/atlassian-prd.md`
- 문서 종류 자체를 체계화하려면 `development/diataxis.md`
- 같은 자료가 기획 도메인에도 색인되어 있다 — 제품·조직 운영 관점의 진입은 `planning/rfd-requests-for-discussion.md`
- 원격·비동기 조직 운영 전반의 사례는 `planning/gitlab-handbook.md`

## 무엇이 들어있나
글의 형식 자체가 논지다. RFD 프로세스를 도입하자는 제안을 RFD-1 로 써서, 프로세스가 자기 자신에게도 적용된다는 것을 보여준다.
핵심은 **문서가 상태를 가진다**는 점이다. 초안에서 논의 중, 논의 종료 후 채택 또는 기각으로 이어지는 상태를 명시하고, 상태에 따라 문서가 어디에 있고 누가 볼 수 있는지가 달라진다. RFC 도입이 실패하는 흔한 이유가 여기서 드러난다 — 문서를 쓰는 규칙만 정하고 **닫는 규칙**을 안 정하면, 결론 없는 문서가 쌓여 아무도 신뢰하지 않게 된다.
또 하나는 논의를 문서에 붙들어 두는 것이다. 코드 리뷰처럼 문서에 직접 코멘트를 달아 논의하면, 결정의 근거와 반대 의견이 결정과 같은 자리에 남는다. 슬랙에서 논의하고 결론만 문서에 옮기면 "왜 다른 안을 버렸는지"가 소실되는데, 실제로 나중에 필요한 정보는 그쪽이다.
적용 범위도 통념보다 넓게 잡는다. 아키텍처뿐 아니라 프로세스·정책·조직 운영 방식까지 같은 프로세스로 다룬다.
Oxide 라는 특정 회사의 규모와 문화에 맞춘 프로세스라는 점은 감안해야 한다. 작은 팀이 그대로 복사하면 무거울 수 있고, 상태 관리와 종료 규칙이라는 뼈대만 가져오는 편이 현실적이다.

## 인용 포인트
- "프로세스 문서를 그 프로세스의 첫 번째 문서로 쓴다"는 방식은, RFC 도입 제안 자체를 첫 RFC 로 쓰자는 실행안으로 바로 옮겨 쓸 수 있다.
- 문서에 상태와 종료 조건을 부여한다는 규칙은, 이미 유명무실해진 사내 설계 문서 제도를 손볼 때의 가장 구체적인 처방이다.
- 논의를 문서에 붙여 남긴다는 원칙은 "결정 근거가 슬랙에서 증발한다"는 문제에 대한 직접적 답이다.
