# Google API Design Guide

https://cloud.google.com/apis/design

## 한 줄
Google 이 2014년부터 내부에서 써 온 API 설계 규약 — REST 와 gRPC 를 하나의 리소스 지향 모델로 통일해서, "동사를 어떻게 URL 에 넣지" 논쟁을 리소스 이름 설계 문제로 바꿔 놓는다.

## 페르소나
**API 설계 리뷰가 매번 URL 네이밍 싸움으로 끝나는 팀의 백엔드 엔지니어.** 주문 취소를 `POST /orders/{id}/cancel` 로 할지 `PATCH /orders/{id}` 로 상태만 바꿀지, 쿠폰 발급이 리소스 생성인지 액션인지 매번 처음부터 다시 논쟁한다. 페이지네이션 파라미터 이름도 엔드포인트마다 다르고, 에러 응답 형식도 제각각이라 클라이언트 팀에서 불만이 나온다. 팀 밖의 기준선이 필요하다.

## 이럴 때 연다
- 새 서비스의 API 규약(리소스 명명, 표준 메서드, 페이지네이션, 에러 형식)을 처음 정할 때
- "이건 표준 메서드로 표현이 안 되는데" 싶은 동작을 커스텀 메서드로 뺄지 판단할 때
- 부분 업데이트에 field mask 를 도입할지 결정할 때
- API 버저닝과 하위 호환 파괴 기준을 문서화할 때
- gRPC 와 REST 를 함께 제공해야 해서 하나의 설계로 양쪽을 커버해야 할 때

## 이럴 땐 아니다
- 더 세밀하고 최신인 규칙(각 주제별 번호가 붙은 제안서)이 필요하면 이 가이드가 직접 위임하는 `development/google-api-improvement-proposals.md` 로 가야 한다 — 이 문서는 개괄, AIP 가 상세다
- HTTP 메서드·상태 코드의 의미론 자체는 `development/rfc-9110-http-semantics.md`
- API 스키마를 기계가 읽는 형태로 문서화하는 문제는 `development/openapi-specification.md`
- 쿼리 모양을 클라이언트가 정하는 모델을 검토 중이라면 `development/graphql-specification.md`
- gRPC 의 구현·스트리밍·인터셉터 등 도구 차원은 `development/grpc.md`
- 서비스 경계를 어떻게 나눌지는 API 문법이 아니라 `architecture/microservices-io.md`, `architecture/ddd-starter-modelling-process.md`

## 무엇이 들어있나
중심 주장은 API 를 **액션의 집합이 아니라 리소스의 집합**으로 설계하라는 것이다. 리소스에 계층적 이름을 부여하고, 그 위에 소수의 표준 메서드 — Get, List, Create, Update, Delete — 를 얹는다. 이렇게 하면 엔드포인트마다 새로 배울 것이 줄고, 클라이언트 라이브러리·문서·권한 모델을 기계적으로 생성할 수 있게 된다.
표준 메서드로 안 되는 동작은 커스텀 메서드로 허용하되, 예외로 취급한다. 즉 `cancel` 같은 동사가 금지되는 게 아니라 **먼저 리소스로 표현할 수 없는지 검토한 뒤에** 쓰는 탈출구로 위치한다. (주문 취소를 취소 리소스의 생성으로 볼 것인지 커스텀 메서드로 볼 것인지 같은 판단이 여기에 해당한다.)
리소스 이름을 컬렉션/ID 가 번갈아 나오는 경로 문자열로 정의하는 방식이 이 가이드의 특징이다. 이름 자체가 전역 식별자 역할을 하므로, ID 를 어디에 어떻게 실을지에 대한 논쟁이 사라진다.
그 밖에 필드 명명 규칙, 표준 에러 모델, 페이지네이션·부분 응답 같은 공통 패턴, 문서화, 버저닝과 호환성, 파일 구조까지 다룬다.
중요한 위치 정보: 이 가이드는 현재 상세 규칙을 AIP 로 위임하는 구조다. 개념을 잡을 때는 이 문서를, 구체적 판단이 필요할 때는 해당 AIP 를 보는 식으로 나눠 쓰는 것이 맞다.

## 인용 포인트
- "동사를 URL 에 넣을지 말지"의 논쟁을, "이 동작을 리소스로 표현할 수 있는가"라는 선행 질문으로 대체하는 프레임은 설계 리뷰에서 즉시 쓸 수 있다.
- 표준 메서드 집합을 먼저 고정하면 인증·페이지네이션·에러 처리 같은 공통 관심사를 일괄 적용할 수 있다는 논거는, 엔드포인트별 자유 설계에 대한 반론이 된다.
- REST 와 gRPC 를 같은 설계 원칙 아래 둘 수 있다는 점은, 두 프로토콜을 병행 제공해야 하는 상황의 설계 근거로 유용하다.
