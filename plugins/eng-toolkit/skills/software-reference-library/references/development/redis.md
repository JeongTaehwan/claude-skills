# Redis 공식 문서

https://redis.io/docs/latest/

## 한 줄
"빠른 캐시"로만 알려진 도구의 실제 문서 — **자료구조 서버**로서의 명령어별 의미와, 영속성·복제·클러스터에서 무엇이 보장되고 무엇이 보장되지 않는지가 분리되어 정리돼 있다.

## 페르소나
**Redis 를 캐시로 쓰다가 재고 차감이나 쿠폰 선착순 발급 같은 "정확해야 하는" 로직까지 얹으려는 백엔드 엔지니어.** `INCR` 이 원자적이라는 것까지는 알지만, 마스터가 죽고 페일오버가 나면 방금 차감한 값이 살아남는지 확신이 없다. 분산 락 구현 글은 많은데 서로 반대되는 말을 하고, 어디까지가 검증된 보장인지 1차 문서로 확인해야 한다.

## 이럴 때 연다
- 캐시 키 설계와 만료 전략을 정할 때 — TTL, 키 축출(eviction) 정책, 메모리가 찼을 때의 동작
- 카운터·랭킹·큐·중복 제거를 어떤 자료구조로 구현할지 고를 때 (String / Hash / Sorted Set / Set / Stream)
- 여러 명령을 원자적으로 묶어야 할 때 — 트랜잭션(MULTI/EXEC), Lua 스크립트, 함수 중 무엇을 쓸지와 각각의 실패 동작
- 분산 락을 직접 구현하려 할 때, 그리고 그 락이 어떤 조건에서 깨지는지 확인해야 할 때
- 재시작이나 페일오버 후 데이터가 얼마나 남는지 판단할 때 — RDB 스냅샷과 AOF 의 내구성 차이
- 데이터가 커져 클러스터로 갈 때 — 키 분산, 해시 태그, 여러 키를 다루는 명령의 제약

## 이럴 땐 아니다
- **최종적 정확성이 돈에 직결되는 데이터의 원천 저장소로 쓸지 판단하는 자리라면** 캐시 문서가 아니라 `development/postgresql.md` 의 트랜잭션·격리 보장과 비교해야 한다
- 메시지 전달 보장이 필요한 이벤트 파이프라인이면 `development/apache-kafka.md`
- 복제·합의·일관성 모델의 일반 이론은 `architecture/designing-data-intensive-applications.md`
- 클레임된 보장이 실제로 지켜지는지에 대한 외부 검증은 `architecture/jepsen.md`
- 캐시를 성능 개선 수단으로 쓸 때의 우선순위 판단은 `development/web-vitals.md` 쪽 프론트 경로와 구분해서 볼 것

## 무엇이 들어있나
문서는 크게 **Develop**(자료구조, 명령어, 클라이언트 라이브러리, 검색·JSON 등 확장 기능)과 **Operate**(서버 운영, 영속성, 복제, 클러스터, 관리형 서비스)로 갈린다. 애플리케이션 개발자는 전자만 보게 되는데, 정확성 판단에 필요한 내용은 대부분 후자에 있다는 점이 함정이다.
자료구조 섹션이 이 문서의 본체다. Redis 를 "키-값 캐시"로만 이해하면 절반을 못 쓰는데, Sorted Set 으로 랭킹과 지연 큐를, Stream 으로 소비자 그룹이 있는 로그를, HyperLogLog 같은 확률적 자료형으로 근사 카디널리티를 다루는 식의 용법이 각 명령어 문서에 시간 복잡도와 함께 붙어 있다. 명령어마다 O(N) 표기가 있다는 점이 중요하다 — 싱글 스레드로 명령을 처리하므로, O(N) 명령 하나가 전체를 멈춰 세울 수 있다. `KEYS` 대신 `SCAN` 을 쓰라는 권고가 이 구조에서 나온다.
영속성 문서는 RDB(주기적 스냅샷)와 AOF(쓰기 로그)를 비교하며, 어느 쪽이든 **동기 디스크 쓰기가 기본이 아니므로 마지막 몇 초의 쓰기는 유실될 수 있다**는 점을 분명히 한다. 복제도 비동기라서, 마스터가 응답한 쓰기가 페일오버 후에 사라질 수 있다. 즉 Redis 의 원자성(단일 명령·Lua 스크립트가 중간 상태 없이 실행됨)과 내구성(그 결과가 장애 후에도 남음)은 서로 다른 얘기이며, 이 구분을 놓친 설계가 재고·쿠폰 사고의 전형적 원인이다.
분산 락 문서도 있고, 알고리즘과 함께 전제 조건·한계를 같이 적어 둔다. 락 자체보다 그 전제를 우리 환경이 만족하는지를 읽는 것이 요점이다.

## 인용 포인트
- "원자성 ≠ 내구성"은 이 문서를 근거로 팀에 설명하기 좋은 구분이다. 복제·영속성 문서의 비동기 서술을 인용하면, 재고·쿠폰 잔량의 원천을 RDB 에 둘지 Redis 에 둘지의 논의가 취향에서 보장 비교로 바뀐다.
- 명령어별 시간 복잡도 표기는 "운영 중 `KEYS` 금지" 같은 규약을 문서화할 때의 직접 근거가 된다.
- 분산 락 문서가 스스로 밝히는 전제 조건은, 락 구현을 승인할지 판단하는 리뷰 체크리스트로 옮겨 쓸 수 있다.

## 코드 예시

"원자성 ≠ 내구성" — 앞 절반은 코드로 얻지만, 뒤 절반은 설정을 확인해야 알 수 있다.

```bash
# 재고 확인과 차감을 한 원자 단위로. 중간 상태는 다른 클라이언트에 보이지 않는다
redis-cli EVAL "
  local left = tonumber(redis.call('GET', KEYS[1]) or '0')
  if left < tonumber(ARGV[1]) then return -1 end
  return redis.call('DECRBY', KEYS[1], ARGV[1])
" 1 stock:sku-42 1

# 여기까지가 원자성이다. 그 결과가 장애 후에 남는지는 아래가 결정한다
redis-cli CONFIG GET appendonly    # no 면 AOF 없음 — 마지막 스냅샷 이후가 통째로 날아간다
redis-cli CONFIG GET appendfsync   # everysec 이 기본 — 최대 1초치 쓰기 유실 가능
redis-cli INFO replication         # 복제는 비동기: 마스터가 OK 한 차감이 페일오버 후 사라질 수 있다

# 싱글 스레드라 O(N) 명령 하나가 전체를 멈춘다 — 운영 중엔 KEYS 대신 SCAN
redis-cli --scan --pattern 'stock:*'
```

Lua 스크립트가 주는 건 "중간 상태가 보이지 않는다"까지다. 위 세 줄이 각각 유실 창을 하나씩 열어 두므로, 이 값을 재고·쿠폰 잔량의 **원천**으로 삼는다는 건 그 창을 감수하겠다는 결정이다. 돈에 직결된다면 원천은 관계형 DB 에 두고 Redis 는 앞단 게이트로만 쓰는 구조를 먼저 검토해야 한다.
