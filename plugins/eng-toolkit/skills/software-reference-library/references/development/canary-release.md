# Canary Release

https://martinfowler.com/bliki/CanaryRelease.html

## 한 줄
카나리 릴리스가 성립하기 위한 전제 — 라우팅 제어, 지표 관측, 즉시 롤백 — 를 명시해서, "일부만 먼저 배포"와 카나리를 구분해 주는 짧은 정의 글.

## 페르소나
**"위험하니까 일부 서버에만 먼저 배포하자"고 정했는데, 정작 무엇을 보고 확대/중단을 판단할지 정하지 않아 배포 때마다 감으로 결정하고 있는 배포 담당자.** 새 결제 로직을 10% 트래픽에만 태웠지만 그 10%에서 실패율이 올라갔는지 확인할 지표가 없고, 문제가 보여도 되돌리는 데 몇 분이 걸린다. 지금 하고 있는 게 카나리인지 그냥 순차 배포인지부터 정리해야 한다.

## 이럴 때 연다
- 블루/그린과 카나리 중 무엇을 쓸지 결정하고 그 근거를 문서화할 때
- 카나리 도입을 제안하면서 "그러려면 이 전제가 먼저 필요하다"를 설득할 때
- 세션 고정(sticky session)이나 DB 스키마 호환처럼 부분 배포가 깨뜨리는 지점을 점검할 때
- 배포 파이프라인의 자동 롤백 조건을 정의할 때

## 이럴 땐 아니다
- 배포 단위가 아니라 코드 안에서 기능을 켜고 끄는 문제라면 `development/feature-toggles.md` — 카나리와 자주 혼동되지만 축이 다르다
- 브랜치 전략과 통합 빈도의 문제라면 `development/trunk-based-development.md`
- 배포 빈도·변경 실패율 같은 지표로 팀 성과를 측정하려면 `development/dora.md` 와 `development/dora-four-keys.md`
- 배포 후 장애가 실제로 터졌을 때의 대응·회고는 `development/postmortem-culture-learning-from-failure.md`
- 릴리스 자동화와 버전 표기 규약은 `development/semantic-versioning.md`

## 무엇이 들어있나
Fowler 의 bliki 항목이라 분량이 짧고 정의에 집중한다. 핵심은 카나리가 "배포 방식"이 아니라 **관측과 롤백이 붙어야 성립하는 검증 절차**라는 점이다.
사용자를 어떤 기준으로 나눌지(내부 직원 → 특정 지역 → 전체 등)의 선택지와, 사용자가 배포 간에 서로 다른 버전을 오가면 안 되는 세션 일관성 문제를 짚는다.
블루/그린과의 관계를 정리한다 — 둘은 배타적이지 않고, 카나리는 트래픽 비율을 점진적으로 옮기는 형태로 볼 수 있다.
데이터베이스 스키마가 두 버전 모두와 호환돼야 한다는 제약이 언급된다. 실무에서 카나리를 무너뜨리는 가장 흔한 원인이 대개 여기다.

## 인용 포인트
- "카나리 하자"는 제안에 대해 "그러려면 트래픽 비율 제어, 버전별 지표 분리, 자동 롤백이 먼저 있어야 한다"를 정의에서 직접 끌어낼 수 있다. 인프라 선행 작업의 근거로 쓰인다.
- 스키마 변경을 배포와 분리해야 하는 이유(하위 호환 마이그레이션)를 이 글로 뒷받침할 수 있다.
