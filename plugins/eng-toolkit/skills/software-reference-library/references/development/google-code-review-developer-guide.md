# Google Code Review Developer Guide (웹 버전)

https://google.github.io/eng-practices/review/

## 한 줄
코드리뷰를 "코드를 어떻게 볼 것인가"가 아니라 "리뷰라는 프로세스를 어떻게 굴릴 것인가"로 다루는 문서 — 무엇을 볼지, 얼마나 빨리 볼지, 어떤 말투로 쓸지가 각각 독립된 장으로 있다.

## 페르소나
**리뷰가 며칠씩 방치되거나, 반대로 사소한 지적으로 스무 번씩 왕복해서 배포가 밀리는 팀의 테크리드.** 리뷰 품질을 올리자고 하면 느려지고, 속도를 내자고 하면 대충 본다는 불평이 나온다. "리뷰는 잘 하자" 수준의 합의로는 아무것도 안 바뀌어서, 응답 시간과 승인 기준을 문장으로 못 박을 근거가 필요하다.

## 이럴 때 연다
- 리뷰 응답 SLA(몇 시간 안에 답을 준다)를 팀 규칙으로 정할 때
- 승인 기준을 "완벽해질 때까지"에서 "지금보다 확실히 나아졌으면 통과"로 옮기고 싶을 때
- 리뷰 코멘트가 공격적이라는 피드백이 나와서 코멘트 작성 규칙을 만들 때
- 리뷰어와 작성자가 의견 대립으로 교착됐을 때, 에스컬레이션 절차의 본보기가 필요할 때
- 큰 PR 이 리뷰 불가능한 크기로 올라오는 걸 막을 근거가 필요할 때

## 이럴 땐 아니다
- 같은 내용의 원본 저장소와 함께 딸린 자료들(작성자 가이드 등)을 통째로 보려면 `development/google-engineering-practices.md`
- 언어별 코딩 컨벤션·포매팅 논쟁은 리뷰 프로세스가 아니라 스타일 기준의 문제라 `development/google-style-guides.md`
- 리뷰 문화가 아니라 엔지니어링 조직 전체의 운영(테스트, 폐기, 대규모 변경)이 궁금하면 `development/software-engineering-at-google.md`
- 커밋 메시지·브랜치 규약은 `development/conventional-commits.md`, `development/trunk-based-development.md`

## 무엇이 들어있나
가장 반직관적인 주장은 **속도가 품질의 반대편이 아니라는 것**이다. 리뷰가 느리면 개발자가 큰 덩어리로 몰아서 올리고, 큰 덩어리는 더 대충 리뷰되고, 그래서 품질이 떨어진다 — 그러니 빠른 응답 자체가 품질 장치라는 논리다.
승인 기준은 "완벽"이 아니라 "개선"이다. 이 코드가 이상적이지 않아도 코드베이스 전체의 건강을 확실히 개선한다면 승인한다는 원칙이 명시돼 있다. 대신 "나중에 하자"는 후속 조치로 남긴다.
코멘트 작성 장은 말투를 실제 문장 수준에서 다룬다 — 사람이 아니라 코드를 두고 말하기, 이유를 붙이기, 명령이 아니라 근거를 제시하기.
교착 해소 절차가 별도로 있다. 감정적 대립을 개인 문제로 두지 말고 대면 논의 → 상위 결정으로 올리는 경로를 문서가 미리 정해 둔다.
리뷰어 관점과 작성자(변경을 올리는 쪽) 관점이 분리돼 있어서, "리뷰 잘 받는 법"도 규칙으로 존재한다.

## 인용 포인트
- "완벽함이 아니라 개선" — 리뷰가 무한 왕복으로 늘어질 때 승인 기준을 되돌리는 한 문장.
- 리뷰 지연이 PR 크기를 키우고, 큰 PR 이 리뷰 품질을 떨어뜨린다는 인과 — 리뷰 SLA 를 도입하자고 설득할 때 그대로 쓸 수 있다.

## 코드 예시

문서의 세 규칙(응답 속도, 완벽이 아니라 개선, 교착 해소 경로)을 팀이 실제로 마주치는 자리 — PR 템플릿 — 에 문장으로 박아 둔 것.

```markdown
<!-- .github/pull_request_template.md -->
## 무엇을, 왜 바꿨나

## 승인 기준 (완벽이 아니라 개선)
- [ ] 이 변경은 코드베이스 상태를 확실히 개선한다
- [ ] 이상적이지 않지만 남겨 둔 부분은 후속 이슈로 분리했다: #___
- [ ] 더 쪼갤 수 있는 변경이면 쪼갰다

## 리뷰 규약
- 첫 응답은 영업시간 기준 24시간 안에 (승인이 아니어도 된다)
- 취향 수준의 제안에는 `Nit:` 접두사를 붙인다 — 승인을 막지 않는다
- 두 번 왕복해도 안 좁혀지면 대면 논의, 그래도 안 되면 테크리드에게 올린다
```

체크박스는 규약을 적어 둘 뿐 지키게 하지 않는다 — 실제로 바뀌었는지는 첫 응답까지 걸린 시간과 PR 크기 분포로만 확인된다. `Nit:` 규약이 없는 상태로 이 템플릿만 붙이면, 사소한 지적이 여전히 승인 차단으로 읽힌다.
