# gRPC 공식 문서

https://grpc.io/docs/

## 한 줄
서비스 정의(.proto)에서 클라이언트·서버 코드를 생성하는 RPC 프레임워크의 공식 문서 — 개념 설명과 언어별 퀵스타트·가이드가 같은 사이트에 붙어 있다.

## 페르소나
**내부 서비스 간 호출이 JSON over HTTP 로 늘어나면서 스펙 불일치와 직렬화 비용이 문제가 되기 시작한 백엔드 엔지니어.** 주문 서비스가 재고 서비스를 부를 때마다 필드 이름 오타나 타입 불일치가 런타임에야 터지고, 타임아웃·재시도 정책이 호출부마다 제각각이다. 계약을 코드 생성으로 강제하고 호출 정책을 프레임워크 층으로 내리고 싶다.

## 이럴 때 연다
- 사내 서비스 간 통신을 REST 에서 스키마 기반 RPC 로 옮길지 판단할 때
- 요청마다 데드라인(타임아웃)을 전파해 느린 호출이 상류로 번지는 걸 막고 싶을 때
- 스트리밍이 필요한 경우 — 대량 데이터 조회를 한 번에 안 받고 흘려보내거나, 양방향 통신이 필요할 때
- 에러를 언어별 예외가 아니라 공통 상태 코드로 표준화하려 할 때
- 인터셉터로 인증·로깅·트레이싱을 호출 경로 전체에 일괄 적용할 때
- .proto 스키마를 바꿀 때 무엇이 하위 호환을 깨는지 확인할 때

## 이럴 땐 아니다
- 브라우저에서 직접 호출하는 공개 API 라면 gRPC 는 전제가 다르다. REST 설계 규약인 `development/google-api-improvement-proposals.md`, 문서화는 `development/openapi-specification.md`
- 클라이언트가 필요한 필드만 골라 받는 문제를 풀고 싶다면 `development/graphql-specification.md`
- 동기 호출 자체를 줄이고 비동기 이벤트로 분리하려는 거라면 `development/apache-kafka.md`
- HTTP 자체의 의미론(상태 코드, 캐시)은 `development/rfc-9110-http-semantics.md`
- 분산 호출의 지연 추적은 `development/opentelemetry-docs.md`
- "원격 호출을 로컬 호출처럼 다루면 왜 위험한가"라는 근본 논의는 `architecture/a-note-on-distributed-computing.md`

## 무엇이 들어있나
핵심 모델은 서비스와 메시지를 Protocol Buffers 로 먼저 정의하고, 거기서 양쪽 코드를 생성한다는 것이다. 계약이 문서가 아니라 컴파일 산출물이 되므로 스펙 불일치가 빌드 시점으로 앞당겨진다.
서비스 메서드는 네 종류로 정리돼 있다 — 단항(unary), 서버 스트리밍, 클라이언트 스트리밍, 양방향 스트리밍. "요청 하나에 응답 하나"만 있는 REST 와 다른 지점이 여기다.
데드라인/타임아웃과 취소가 프로토콜 차원의 개념으로 들어 있다. 클라이언트가 준 데드라인이 호출 체인을 따라 전파되므로, 상류가 이미 포기한 작업을 하류가 계속 수행하는 낭비를 줄일 수 있다.
채널과 스텁, 메타데이터(요청 헤더에 해당), 상태 코드 체계, 인터셉터가 개념 문서에 정리돼 있고, 그 아래로 언어별(Go/Java/Python/Node/C++ 등) 퀵스타트와 튜토리얼이 붙는다.
로드 밸런싱, 인증(TLS·토큰), 헬스 체킹, 리플렉션 같은 운영 주제가 별도 가이드로 있다.

## 인용 포인트
- 데드라인이 호출 체인을 따라 전파된다는 점 — 서비스 간 타임아웃을 각자 상수로 박아 두는 관행을 바꾸자고 설득할 때.
- 스키마에서 코드를 생성하므로 계약 위반이 런타임이 아니라 빌드에서 잡힌다는 것.
