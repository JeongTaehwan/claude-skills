# 쏘카 기술블로그

https://tech.socarcorp.kr/

## 한 줄
"차라는 물리 자원을 시간 단위로 예약·배차한다"는 제약이 있는 회사의 기록 — 재고가 유한하고 겹치면 안 되는 도메인, 그리고 데이터 엔지니어링·테스트 도입기가 축이다.

## 페르소나
**한정 수량 자원의 동시 예약을 다루는 개발자 — 타임세일 재고, 좌석, 대여 슬롯처럼 "두 사람에게 같은 걸 팔면 끝장"인 코드를 짜는 중.** 락을 걸자니 처리량이 걱정이고, 안 걸자니 중복 배정이 무섭다. 이론적으로는 알겠는데 실제 서비스에서 어떤 절충을 했는지 본 적이 없다. 여기에 데이터 파이프라인까지 겸임하고 있다면 더 맞는다.

## 이럴 때 연다
- 예약·배차·좌석처럼 겹치면 안 되는 자원의 동시성 제어 방식을 정할 때
- 시간 구간(from~to)이 있는 재고·가용성 모델링을 설계할 때
- 데이터 웨어하우스·파이프라인을 새로 세우거나 정비할 때
- 테스트 코드가 거의 없는 레거시에 테스트를 도입하는 순서를 짤 때
- 실시간 위치·상태 데이터를 다루는 시스템의 국내 사례가 필요할 때

## 이럴 땐 아니다
- 결제·정산의 금액 정합성이 주제라면 `development/tech-kakaopay-com.md`
- 주문·배송 도메인의 DDD·이벤트 아키텍처 사례는 `development/techblog-woowahan-com.md`
- 이벤트 수집·집계 인프라를 규모 있게 다룬 사례는 `development/ab180.md`
- 동시성·격리 수준의 원리 자체는 사례가 아니라 `architecture/designing-data-intensive-applications.md`
- 인덱스와 쿼리 성능 문제라면 `development/use-the-index-luke.md`

## 무엇이 들어있나
모빌리티 도메인 글은 "물리 세계와 동기화되는 상태"라는 특성이 강하다. DB 상태와 실제 차량 상태가 어긋날 수 있다는 전제가 깔려 있어서, 정합성 복구·보정 로직 이야기가 자연스럽게 나온다. 이 감각은 재고·쿠폰 같은 커머스 자원에도 그대로 옮겨온다.
데이터 엔지니어링 비중이 눈에 띄게 높다. 수집·적재·집계 파이프라인, 데이터 품질, 분석 조직과의 협업 같은 글이 꾸준히 올라온다.
테스트·개발문화 계열은 "없던 것을 도입한 과정"에 대한 글이 많아서, 이미 잘 갖춰진 조직의 자랑보다 도입 초기 팀에 실질적으로 참고가 된다.
한국어이고 규모가 초대형은 아니라, 중견 규모 팀이 그대로 흉내 내볼 수 있는 수준의 사례가 많다는 게 실용적 장점이다.

## 인용 포인트
- 동시 예약 중복을 막는 방식을 팀에 제안할 때, 같은 문제를 실서비스에서 겪은 국내 사례를 근거로 붙일 수 있다.
