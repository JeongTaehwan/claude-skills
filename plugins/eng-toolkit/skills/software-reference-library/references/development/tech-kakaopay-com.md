# 카카오페이 기술블로그

https://tech.kakaopay.com/

## 한 줄
"돈이 틀리면 안 된다"는 제약 아래에서 개발하는 팀이 쓴 글 모음 — 결제·정산 도메인의 아키텍처 개선기와 테스트 전략 이야기가 다른 국내 블로그보다 확연히 두껍다.

## 페르소나
**결제 연동이나 정산 배치를 맡았는데, 실패하면 조용히 금액이 틀어지는 종류의 코드를 짜고 있어 불안한 백엔드 개발자.** PG 응답이 유실됐을 때, 웹훅이 중복으로 들어왔을 때, 배치가 중간에 죽었을 때를 어디까지 방어해야 하는지 감이 없다. 일반적인 "테스트 잘 짜기" 글은 이 불안을 해소해주지 못하고, 같은 도메인을 다룬 사람의 판단 근거가 필요하다.

## 이럴 때 연다
- 결제·정산 도메인의 상태 전이 설계를 하면서 실패·재시도·중복 처리 경계를 어디에 둘지 정할 때
- 금액이 걸린 코드의 테스트 전략(어디까지 단위, 어디부터 통합, 외부 PG는 어떻게)을 세울 때
- 레거시 결제 모듈을 무중단으로 교체·분리하는 계획을 짤 때
- 대사(reconciliation)·정합성 검증 배치를 설계할 때
- 금융 도메인 특유의 규제·감사 요구가 개발 프로세스에 어떻게 반영되는지 볼 때

## 이럴 땐 아니다
- 주문·배송·배차 같은 커머스 도메인 전반의 DDD·이벤트 아키텍처 사례는 `development/techblog-woowahan-com.md`
- 대규모 트래픽·추천 인프라 사례는 `development/tech-kakao-com.md`
- 테스트 전략을 이론적으로 정리하려면 사례가 아니라 `qa/the-practical-test-pyramid.md` 나 `qa/software-engineering-at-google-ch-11-testing-overview.md`
- 외부 결제 API와의 계약이 깨지는 걸 막는 기법 자체는 `testing/pact.md` 또는 `qa/testing-strategies-in-a-microservice-architecture.md`
- 분산 트랜잭션·사가 패턴의 원리는 `architecture/microservices-io.md`

## 무엇이 들어있나
도메인 제약이 글의 성격을 규정한다. 성능이나 개발 편의보다 **정합성과 추적 가능성**이 먼저 오고, 그래서 "빠르게 짜는 법"이 아니라 "틀렸을 때 알아챌 수 있게 짜는 법"에 관한 글이 많다.
테스트 관련 글의 밀도가 특히 높다. 테스트 코드 도입기, 테스트 더블을 어디까지 쓸지, 느린 통합 테스트를 어떻게 관리할지 같은, 결정이 실제로 아팠던 흔적이 남은 글들이다.
아키텍처 쪽은 모놀리스 분리, 레거시 교체, 이벤트 기반 전환 같은 "이미 돌아가는 시스템을 멈추지 않고 바꾸기" 계열이 중심이다. 그린필드 설계 글보다 이런 쪽이 실무에서 더 자주 필요하다.
한국어이고 문단 단위로 인용하기 좋아서, 사내 설계 리뷰 자료에 근거로 붙이기 쉽다.

## 인용 포인트
- 결제 코드의 테스트 비용을 정당화할 때, 같은 도메인 회사가 왜 그만큼 투자했는지를 사례로 붙이면 "과하다"는 반론이 약해진다.
- 레거시 결제 모듈 교체를 단계적으로 하자고 제안할 때, 무중단 전환 사례가 일정 협상의 근거가 된다.
