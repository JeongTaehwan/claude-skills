# Dan Luu

https://danluu.com/

## 한 줄
업계에서 당연하게 통용되는 주장들을 실제 데이터로 재보고 대부분 틀렸다고 결론 내리는 글 모음 — 결론보다 "어떻게 측정했는가"가 본체다.

## 페르소나
**"다들 이렇게 한다"는 이유로 결정이 내려지는 회의에서, 반대하고 싶은데 반대 근거가 자기 직감밖에 없어 매번 지는 시니어 엔지니어.** 마이크로서비스로 쪼개야 한다거나, 이 언어가 더 빠르다거나, 채용 면접이 능력을 잘 판별한다는 주장에 의문이 있지만 상대는 업계 상식을 들고 온다. 상식 쪽을 실측으로 흔든 사례가 필요하다.

## 이럴 때 연다
- 널리 퍼진 기술 통념("~가 더 빠르다", "~는 확장 안 된다")을 검증해야 할 때
- 성능 문제를 추정이 아니라 측정으로 접근하는 방법론이 필요할 때
- 지연 시간·하드웨어 신뢰성·꼬리 지연(tail latency) 같은 주제의 실측 감각을 잡을 때
- 채용, 승진, 보상, 조직 규모 같은 주제에 대해 데이터 기반 반론을 찾을 때
- 논쟁적인 주장을 하려는데 사고의 전개 방식 자체를 배우고 싶을 때

## 이럴 땐 아니다
- 업계 동향·회사 사례·커리어 조언을 정기적으로 받아 보려면 `development/the-pragmatic-engineer.md`
- 분산 시스템의 원리와 트레이드오프를 체계적으로 배우려면 `architecture/designing-data-intensive-applications.md`
- 검증된 학술적 결론이 필요하면 `development/acm-queue.md` 나 `development/papers-we-love.md`
- 클라우드 규모 운영의 정석적 서술은 `architecture/amazon-builders-library.md`

## 무엇이 들어있나
방법론이 일관된다 — 주장을 고르고, 그것을 반증 가능한 형태로 바꾸고, 직접 데이터를 모아 측정하고, 결과가 통념과 어긋나면 어긋난 대로 쓴다. 마음에 드는 결론에 맞춰 데이터를 고르지 않는다는 점이 이 블로그의 신뢰성의 근거다.
주제 범위가 넓다: 하드웨어 신뢰성과 CPU 버그, 웹 페이지 성능과 저사양 기기, 지연 시간, 컴파일러와 언어 성능, 그리고 채용·보상·조직 같은 사회적 주제.
문체가 의도적으로 꾸밈이 없다. 디자인이 없는 사이트 자체가 그 글 하나("웹이 느린 건 기기 탓이 아니다")의 논증이기도 하다.
반박당할 여지를 스스로 열어 두고 한계와 반론을 본문에 적는 편이라, 인용했을 때 역공을 덜 맞는다.

## 인용 포인트
- "업계 표준이니까"라는 논거에 맞설 때, 같은 형태의 주장이 실측에서 무너진 사례를 제시하는 방식이 유효하다.
- 성능 논쟁에서 "추정 말고 측정하자"로 방향을 트는 데 쓸 수 있는 구체적 선례가 많다.
