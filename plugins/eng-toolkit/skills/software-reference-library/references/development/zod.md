# Zod — 스키마 검증

https://zod.dev/

## 한 줄
스키마를 한 번 정의하면 런타임 검증과 TypeScript 정적 타입을 동시에 얻는 라이브러리의 공식 문서 — 타입 선언과 검증 코드가 따로 놀며 어긋나는 문제를 "스키마가 곧 타입"으로 없앤다. 의존성이 없고 Zod 4 가 안정 버전이다.

## 페르소나
**외부 API 응답이나 클라이언트 요청 본문을 인터페이스로 선언해 두고 `as` 로 캐스팅해 쓰다가, 필드가 빠지거나 타입이 달라졌을 때 한참 뒤 엉뚱한 곳에서 터지는 것을 겪은 백엔드/풀스택 엔지니어.** 타입은 컴파일 후 사라진다는 걸 알지만, 검증 코드를 손으로 쓰면 인터페이스와 이중 관리가 되어 곧 어긋난다. 결제 콜백이나 웹훅처럼 남이 보내는 데이터일수록 이 간극이 사고로 이어진다.

## 이럴 때 연다
- API 요청/응답, 웹훅, 큐 메시지 같은 신뢰할 수 없는 입력의 경계 검증을 설계할 때
- 타입 선언과 검증 로직의 이중 관리를 없애고 싶을 때
- 환경변수나 설정 파일을 기동 시점에 검증해 잘못된 배포를 조기에 실패시키고 싶을 때
- 폼 입력 검증(React Hook Form 리졸버 등)이나 tRPC 처럼 스키마를 요구하는 스택을 쓸 때
- 검증 실패 메시지를 사용자에게 보여줄 형태로 가공해야 할 때
- 기존 스키마에서 JSON Schema 나 OpenAPI 문서를 파생시키고 싶을 때

## 이럴 땐 아니다
- 타입 시스템 자체의 규칙(제네릭, 조건부 타입, 구조적 타이핑)은 `development/typescript-handbook.md`
- 언어 중립적인 스키마 표준이 필요하거나 여러 언어에서 같은 스키마를 공유해야 하면 `development/json-schema.md`
- API 계약 자체를 문서/코드 생성의 원천으로 삼으려면 `development/openapi-specification.md`
- Java/Node 진영의 다른 검증 라이브러리 비교가 목적이면 `testing/joi.md` 도 함께 본다
- DB 스키마와 타입을 함께 관리하는 문제는 `development/prisma.md`

## 무엇이 들어있나
설계의 핵심 주장은 "타입 선언과 검증은 같은 것의 두 얼굴이어야 한다"이다. 스키마를 정의하면 `z.infer` 로 정적 타입이 따라 나오므로, 인터페이스를 따로 쓰고 검증 함수를 또 쓰는 이중 관리가 구조적으로 사라진다. TypeScript 타입이 런타임에 소거된다는 사실의 실무적 대응책이 이 라이브러리다.
API 는 불변(immutable) 방식이다. `.optional()`, `.min()` 같은 메서드는 원본을 바꾸지 않고 새 스키마를 반환하므로, 공용 스키마를 파생시켜 써도 서로 오염되지 않는다.
검증 결과를 다루는 경로가 두 가지다 — `.parse()` 는 실패 시 예외를 던지고, `.safeParse()` 는 성공/실패를 값으로 돌려준다. 예외를 흘리면 안 되는 경계(웹훅 핸들러, 배치)에서는 후자가 맞다.
단순 검증을 넘어 변환(transform), 정제(refine), 기본값, 강제 변환(coerce) 을 지원한다. 쿼리스트링의 문자열 `"3"` 을 숫자로 바꾸거나, 두 필드 간 관계 규칙(예: 할인 금액 ≤ 주문 금액)을 스키마에 넣을 수 있다.
판별 유니온(discriminated union)을 지원해 결제 수단이나 주문 상태처럼 종류에 따라 필드가 달라지는 페이로드를 정확히 모델링할 수 있고, 이게 커머스 도메인에서 가장 자주 쓰이는 기능이다.
번들 크기가 작고 외부 의존성이 없으며, JSON Schema 변환이 내장돼 있다. tRPC, React Hook Form 등 생태계 통합이 넓다.

## 인용 포인트
- "TypeScript 타입은 런타임에 존재하지 않으므로 외부 입력은 반드시 런타임 검증이 필요하다"는 논지를, 이 라이브러리의 존재 이유로 그대로 인용할 수 있다.
- 스키마 하나에서 타입과 검증이 함께 나온다는 점은, 검증 코드를 손으로 유지하는 관행을 걷어낼 때의 핵심 근거다.
- `.safeParse()` 와 `.parse()` 의 구분은 "경계에서 예외를 던질 것인가 값으로 다룰 것인가"를 팀 규칙으로 정할 때 논의의 틀이 된다.
