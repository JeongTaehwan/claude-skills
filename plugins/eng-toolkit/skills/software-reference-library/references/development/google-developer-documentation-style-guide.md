# Google Developer Documentation Style Guide

https://developers.google.com/style

## 한 줄
영문 기술 문서의 어투·용어·형식을 항목 단위로 판정해 주는 사전형 스타일 가이드 — "이 표현을 쓸까 말까"를 검색해서 바로 답을 얻는 용도다.

## 페르소나
**영문 API 문서나 릴리스 노트를 여러 명이 나눠 쓰는데, 사람마다 시제·인칭·용어가 달라 한 문서처럼 안 읽히는 상황의 개발자.** 리뷰에서 "여긴 you 를 쓰고 저긴 the user 를 쓴다" 같은 지적이 반복되지만, 어느 쪽이 맞다고 정할 근거가 없어서 매번 취향 논쟁이 된다. 외부 기준 하나를 걸어 두고 논쟁을 끝내고 싶다.

## 이럴 때 연다
- API 레퍼런스·SDK 문서를 영문으로 쓰기 시작하면서 문체 기준을 정할 때
- 릴리스 노트 템플릿을 만들면서 시제와 어투(예: 명령형 vs 서술형)를 통일할 때
- 문서 리뷰에서 표현 지적이 반복돼 규칙으로 승격시키고 싶을 때
- 코드 예제·플레이스홀더·명령줄 표기 같은 형식 규칙이 문서마다 달라졌을 때
- 접근성·포용적 표현(성별 중립, 낙인적 용어 회피) 기준이 필요할 때

## 이럴 땐 아니다
- 문서를 "무엇을 어떤 종류로 나눠 쓸 것인가"(튜토리얼/하우투/레퍼런스/설명)의 구조 문제라면 `development/diataxis.md` 가 먼저다. 이 가이드는 구조가 아니라 문장 층위를 다룬다.
- README 하나의 필수 구성 요소가 궁금하면 `development/standard-readme.md`
- 변경 이력 문서의 형식·버전 표기는 `development/keep-a-changelog.md`, `development/semantic-versioning.md`
- 코드 자체의 표기 규칙(주석·명명)은 `development/google-style-guides.md`

## 무엇이 들어있나
사전처럼 쓰도록 만들어진 자료다. 단어 목록(word list)에서 개별 용어의 권장/비권장 판정을 찾을 수 있고, 나머지는 문장·형식·마크업 규칙으로 나뉜다.
전반적 어조는 "격식은 줄이고 명확성은 올린다" 쪽이다 — 독자를 you 로 부르고, 능동태와 현재 시제를 기본으로 하고, 불필요한 완곡어법을 걷어내라는 지침이 반복된다.
코드 예제·명령줄·플레이스홀더 표기, 그리고 UI 요소를 글에서 어떻게 지칭할지 같은 실무 형식 규칙이 상당한 분량을 차지한다.
포용적 언어 항목이 별도로 있어, 낡은 기술 용어를 대체 표현으로 바꾸는 근거로 쓸 수 있다.
번역·현지화를 염두에 둔 작성 지침도 포함돼 있다 — 관용구와 문화 의존 표현을 피하라는 식.

## 인용 포인트
- 표현 논쟁이 붙었을 때 "사내 취향" 대신 "사실상의 업계 기준"을 근거로 제시할 수 있어, 논의가 개인 대 개인에서 벗어난다.
- 단어 목록이 있어서 규칙을 통째로 읽히지 않고도 링크 하나로 지적할 수 있다.
