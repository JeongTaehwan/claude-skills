# 당근 팀블로그

https://medium.com/daangn

## 한 줄
모놀리스에서 서비스를 떼어내는 과정, 실험 플랫폼 구축, 데이터 조직 구성처럼 **성장 단계마다 무엇이 먼저 깨졌는지**를 한국어로 기록한 팀블로그.

## 페르소나
**서비스가 커지면서 하나의 코드베이스를 여러 팀이 동시에 건드리게 됐고, 분리해야 한다는 건 알지만 어디부터 어떻게 잘라야 할지 모르는 개발 리드.** 마이크로서비스 이론서는 "경계를 잘 잡아라"까지만 말하고, 실제로 트래픽이 도는 서비스를 무중단으로 떼어낸 절차는 안 알려준다. 같은 규모를 먼저 지나간 팀의 순서와 실패가 필요하다.

## 이럴 때 연다
- 모놀리스에서 특정 도메인을 분리하는 마이그레이션 계획을 세울 때
- A/B 테스트·실험 플랫폼을 사내에 구축할지, 외부 도구를 쓸지 판단할 때
- 데이터 조직·플랫폼 팀을 새로 만들 때의 역할 경계 사례가 필요할 때
- 조직이 커지면서 생기는 배포·소유권 문제의 선례를 찾을 때

## 이럴 땐 아니다
- 서비스 분해의 원칙과 패턴 자체(경계 설정, Strangler Fig 등)는 `architecture/microservices-io.md`, `architecture/martin-fowler-software-architecture-guide.md`
- 실험 설계의 통계적 근거가 필요하면 `planning/online-controlled-experiments-at-large-scale.md`, `planning/trustworthy-online-controlled-experiments.md`
- 결제·정산 도메인의 구체 사례라면 `development/tech-kakaopay-com.md`
- 대규모 트래픽 인프라 사례는 `development/line-engineering.md`

## 무엇이 들어있나
글의 강점이 "결과"가 아니라 "순서"에 있다. 무엇을 먼저 떼어냈고 그 동안 기존 시스템과 어떻게 공존시켰는지, 롤백 경로를 어떻게 남겼는지가 서술되는 글이 있다.
실험 플랫폼 관련 글은 개발 조직과 기획 조직의 인터페이스 문제를 다룬다 — 도구를 만드는 이야기지만 실제 논점은 "누가 지표를 정의하는가"에 가깝다.
개발 외에 디자인·데이터·조직문화 글이 섞여 있어 밀도가 고르지 않다. 태그로 걸러 읽는 편이 효율적이다.
스크립트로 접근하면 403이 나지만 브라우저에서는 정상적으로 열린다 — 자동 수집을 시도하다 죽은 링크로 오판하지 않도록 주의한다.

## 인용 포인트
- 서비스 분리 제안서에서 "한 번에 자르지 않고 단계적으로 공존시킨다"는 방침을 정당화할 때, 국내 동일 규모의 선례로 인용할 수 있다.
