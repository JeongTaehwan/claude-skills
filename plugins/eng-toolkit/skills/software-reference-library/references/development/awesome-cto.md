# Awesome CTO

https://github.com/kuchin/awesome-cto

## 한 줄
기술 리더가 코드 밖에서 마주치는 문제 — 채용, 조직 구조, 아웃소싱 판단, 기술 부채 협상, 경영진 보고 — 를 주제별로 묶은 큐레이션 목록.

## 페르소나
**개발은 잘하는데 갑자기 "팀을 맡아라"를 듣고, 처음 겪는 문제마다 검색어조차 모르는 신임 팀리드/테크리드.** 면접에서 뭘 물어야 하는지, 1:1을 어떻게 굴려야 하는지, 리팩터링 시간을 어떻게 정당화해야 하는지 — 개별 블로그 글은 널렸는데 무엇이 정평 있는 글인지 판단할 기준이 없다. 남이 이미 걸러 놓은 목록에서 시작하고 싶다.

## 이럴 때 연다
- 처음 맡는 리더십 상황(첫 채용, 첫 성과 대화, 첫 조직 개편)에 대해 뭘 읽어야 할지 모를 때
- 기술 부채나 플랫폼 작업의 예산을 경영진에게 설득해야 할 때 쓸 논거를 찾을 때
- 팀 규모가 커져서 조직을 나눠야 하는데 분할 기준의 선례가 필요할 때
- 아웃소싱/외주, 채용 대 계약직 같은 판단에 참고할 글이 필요할 때

## 이럴 땐 아니다
- 엔지니어링 매니저 역할 자체의 실무(1:1, 평가, 커리어 래더)에 더 좁게 집중하려면 `development/engineering-manager.md`
- 구글이 실제로 굴린 엔지니어링 조직·프로세스의 서술은 큐레이션이 아니라 원 텍스트인 `development/software-engineering-at-google.md`
- 조직이 아니라 개인 기술 학습 경로를 짜는 거라면 `development/developer-roadmap.md`
- 업계 동향과 다른 회사의 실제 사례가 필요하면 `development/the-pragmatic-engineer.md`

## 무엇이 들어있나
링크 모음이지만 분류가 실제 CTO/리드의 업무 축을 따른다: 채용과 면접, 온보딩, 팀 구조, 문화, 성과 관리, 기술 전략, 아키텍처 결정, 보안·컴플라이언스, 예산과 벤더.
각 링크에 짧은 설명이 붙어 있어 클릭 전에 성격을 판단할 수 있다.
"CTO" 라는 제목보다 실제 범위가 넓어서, 팀 리드나 시니어 개인 기여자가 조직 맥락을 이해할 때도 쓸모가 있다.
큐레이션의 성격상 깊이보다 폭이다 — 여기서 방향을 잡고 원문으로 넘어가는 진입점으로 쓰는 게 맞다.
