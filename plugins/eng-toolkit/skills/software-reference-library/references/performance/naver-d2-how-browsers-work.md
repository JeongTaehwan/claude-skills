# 브라우저는 어떻게 동작하는가?

https://d2.naver.com/helloworld/59361

## 한 줄
렌더링 엔진이 HTML·CSS를 파싱해 렌더 트리를 만들고 레이아웃·페인트를 거쳐 화면을 그리기까지 — "받은 바이트가 픽셀이 되기까지"를 다룬 NAVER D2의 고전. 크리티컬 렌더링 패스 이해의 국내 표준 참고 글이다.

## 페르소나
**"CSS는 왜 head에, 스크립트는 왜 defer로?"라는 후배의 질문에 규칙은 아는데 이유를 설명하지 못한 개발자, 또는 팀 온보딩에서 렌더링 기초를 공유할 한국어 자료를 찾는 리드.** 네트워크에서 바이트를 받은 다음 단계 — 파싱이 왜 멈추는지, 레이아웃과 페인트가 무엇인지 — 를 모르면 로딩 최적화 기법들이 전부 주문(呪文)이 된다.

## 이럴 때 연다
- 팀원에게 렌더링 파이프라인 기초를 공유할 때 — 한국어로 된 검증된 입문 자료가 필요할 때
- 스크립트가 파싱을 막는(parser blocking) 이유, CSS가 렌더링을 막는 이유를 원리로 설명해야 할 때
- 크리티컬 렌더링 패스 최적화 기법을 적용하기 전에 그 패스 자체를 먼저 이해해야 할 때

## 이럴 땐 아니다
- 바이트가 도착하기 전 — 네트워크 구간의 지연 원리는 `performance/high-performance-browser-networking.md`; 이 글은 도착한 다음을 다룬다
- 이해가 아니라 측정·개선 실행이 목적이면 `performance/web-performance-in-action.md`와 `development/lighthouse.md`
- NAVER D2의 다른 글을 훑으려면 `development/naver-d2.md`

## 무엇이 들어있나
브라우저의 주요 구성 요소에서 시작해 렌더링 엔진(WebKit·Gecko)의 동작 흐름 — HTML 파싱과 DOM 트리, CSS 파싱, 렌더 트리 구성, 레이아웃(배치), 페인트 — 을 단계별로 설명한다. 널리 알려진 "How Browsers Work" 계열 연구(탈리 가르시엘의 브라우저 내부 분석)를 바탕으로 한국어로 정리한 글로, 오래된 글이지만 다루는 것이 엔진의 기본 구조라 지금도 기초 자료로 통용된다.

저속 네트워크 맥락에서의 쓸모는 분명하다: 전송을 아무리 줄여도 렌더링이 무엇에 막히는지 모르면 절반만 최적화한 것이다. 이 글이 그 나머지 절반의 지도다.

## 인용 포인트
- 스크립트·스타일이 파싱과 렌더링을 어디서 막는지의 단계별 설명 — "왜 CSS는 위에, JS는 defer"라는 컨벤션을 규칙이 아니라 원리로 만들어 준다.
- 렌더 트리 → 레이아웃 → 페인트라는 단계 구분 자체 — 성능 논의에서 "어느 단계 비용인가"를 가르는 공용 어휘의 한국어 출처.

## 코드 예시

"CSS는 head에, JS는 defer" 컨벤션을 규칙이 아니라 파이프라인 단계로 읽는 형태 — 무엇이 파싱을 멈추고 무엇이 렌더 트리를 막는지가 마크업에 그대로 드러난다.

```html
<head>
  <!-- 렌더 블로킹: 렌더 트리를 만들려면 CSSOM 이 필요하므로 여기서 기다린다 -->
  <link rel="stylesheet" href="/critical.css" />

  <!-- 렌더링에 당장 필요 없는 CSS 는 렌더 블로킹에서 빼 둔다 -->
  <link rel="stylesheet" href="/print.css" media="print" />

  <!-- 파서 블로킹: 이 자리에서 DOM 구성이 멈춘다. 꼭 필요한 게 아니면 쓰지 않는다 -->
  <!-- <script src="/legacy.js"></script> -->

  <!-- 파싱과 병렬로 받고, DOM 완성 뒤 문서 순서대로 실행 -->
  <script src="/app.js" defer></script>

  <!-- 순서·DOM 과 무관한 독립 스크립트만 async -->
  <script src="/analytics.js" async></script>
</head>
<body>
  <h1>주문 내역</h1>
</body>
```

`defer`·`async` 는 실행 시점만 옮길 뿐 다운로드 바이트를 줄이지 않는다 — 저속 회선에서는 파이프라인을 안 막아도 스크립트가 도착할 때까지 화면이 죽어 있는 건 그대로다.
