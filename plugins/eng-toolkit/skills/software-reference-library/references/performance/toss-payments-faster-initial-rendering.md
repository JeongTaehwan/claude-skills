# 조금만 신경써서 초기 렌더링 빠르게 하기

https://toss.tech/article/faster-initial-rendering

## 한 줄
토스페이먼츠가 SSR을 도입하지 않고 — 정적 리소스의 CDN 배포와 코드 스플리팅·트리 셰이킹만으로 — 초기 렌더링을 개선한 실사례 글. "SSR 전환" 같은 큰 공사 없이 지금 구조에서 당길 수 있는 것부터 당기는 접근이다.

## 페르소나
**CSR 앱의 첫 화면이 느리다는 걸 알지만, SSR 전환은 일정·구조상 당장 불가능한 팀의 프론트엔드 개발자.** 검색하면 "SSR 하세요"만 나오는데, 필요한 건 아키텍처 전환 없이 지금 당장 초기 페인트를 당기는 현실적 수순이다.

## 이럴 때 연다
- SSR 도입 없이 초기 페인트를 당겨야 할 때 — 기존 CSR 구조를 유지하는 제약 하에서
- 정적 리소스를 CDN에 태우고 번들을 쪼개는 것만으로 어디까지 개선되는지 사례가 필요할 때
- "SSR 안 하면 성능 개선 불가"라는 이분법을 깨는 반례를 논의에 가져갈 때

## 이럴 땐 아니다
- SSR·스트리밍 전환 자체를 검토하는 단계면 `performance/learning-patterns.md`에서 렌더링 패턴 비교부터, Next.js 구현은 `performance/nextjs-streaming-ssr.md`
- 재방문 전송량이 문제면 `performance/toss-smart-web-service-cache.md` — 같은 토스 계열의 캐시 정책 편이다
- 번들에서 무엇을 빼야 하는지의 철학·기준은 `performance/responsible-javascript.md`

## 무엇이 들어있나
CSR 구조를 유지한 채 초기 렌더링을 개선한 과정 — 정적 리소스를 CDN으로 배포해 전송 구간을 줄이고, 코드 스플리팅과 트리 셰이킹으로 첫 화면에 필요한 JS만 내려보내는 작업을 실서비스 기준으로 다룬다. 제목의 "조금만 신경써서"가 글의 성격을 요약한다: 대공사가 아니라 배포·번들 설정 수준의 개입으로 얻는 개선이다.

## 인용 포인트
- "SSR 없이도 초기 렌더링은 당길 수 있다" — 아키텍처 전환 논의와 당장의 성능 개선을 분리하자는 주장의 실사례 근거.
- 개선 수순의 순서 감각 — 전송 구간(CDN)과 전송량(스플리팅·셰이킹)을 먼저 치고, 렌더링 아키텍처는 그다음 문제로 미루는 우선순위의 참조 사례.
