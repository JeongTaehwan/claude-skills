# size-limit — 실행 시간까지 재는 사이즈 예산 CI

https://github.com/ai/size-limit

## 한 줄
번들 크기뿐 아니라 다운로드+실행 시간까지 계산해, 정한 한도를 넘으면 CI를 실패시키는 성능 예산 도구(Autoprefixer 제작자 작). 이 계열에서 유지보수 상태가 가장 좋은 선택지.

## 페르소나
**한 번 번들을 줄여 놨더니 세 달 뒤 슬그머니 다시 커져 있는 걸 발견한 엔지니어.** 최적화는 이벤트가 아니라 유지의 문제라는 걸 깨달았고, "이 크기를 넘으면 머지 불가"를 사람의 주의력이 아니라 CI로 강제하고 싶다.

## 이럴 때 연다
- npm 패키지나 앱의 사이즈 예산을 CI로 강제할 때(소스 판단) — 한도 초과 시 빌드가 빨간불이 된다
- KB 수치만이 아니라 "느린 기기에서의 다운로드+실행 시간"으로 예산을 표현하고 싶을 때 — 이 도구의 차별점
- 공유 라이브러리·디자인 시스템 패키지가 몸집을 불리는 걸 감시할 때

## 이럴 땐 아니다
- 예산 초과의 원인을 찾는 단계라면 `performance/webpack-bundle-analyzer.md` — 이 도구는 울타리지 지도가 아니다
- 번들 크기가 아니라 페이지 전체 지표(LCP·INP)의 회귀를 막으려면 `performance/lighthouse-ci.md`
- 같은 계열의 원조인 `performance/bundlesize.md`는 정체 상태다 — 새로 고른다면 이쪽이 답이다

## 무엇이 들어있나
설정 파일에 진입점과 한도를 선언하면, CI에서 번들을 빌드해 크기와 함께 다운로드+실행 시간 추정치를 계산하고 한도 초과 시 실패시키는 도구. "150KB면 괜찮은가?"라는 논쟁을 "느린 환경에서 N초"라는 사용자 언어로 바꿔 주는 것이 크기만 재는 도구와의 차이다. 플러그인 구조로 웹팩·esbuild 등과 조합한다.

## 인용 포인트
- "성능 예산은 문서가 아니라 CI 게이트여야 한다"는 프로세스 제안의 대표 구현.
- 예산을 KB가 아니라 다운로드+실행 시간으로 선언할 수 있다는 점 — 느린 기기 기준의 예산 수립 근거.
