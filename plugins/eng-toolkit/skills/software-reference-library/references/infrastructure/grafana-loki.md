# Grafana Loki 공식 문서

https://grafana.com/docs/loki/latest/

## 한 줄
로그 **본문은 인덱싱하지 않고 레이블만 인덱싱**한다는 한 가지 선택으로 비용 구조를 바꾼 로그 저장소 — Prometheus 의 레이블 모델을 로그에 그대로 가져와, 메트릭에서 로그로 같은 레이블을 타고 넘어갈 수 있게 만든다.

## 페르소나
**로그 검색 비용이 감당이 안 돼 보관 기간을 계속 줄이고 있는 백엔드/플랫폼 엔지니어.** 전문 검색 엔진 기반 로그 시스템이 인덱스 때문에 원본보다 큰 저장 공간을 먹고 있고, 정작 실무에서 하는 일은 "이 서비스의 최근 30분 에러 로그"를 보는 것뿐이다. Prometheus 대시보드에서 에러율이 튄 것을 보고도, 그 순간의 로그를 찾으려면 다른 도구를 열어 조건을 처음부터 다시 입력해야 한다.

## 이럴 때 연다
- 로그 저장 비용이 인덱스 때문에 커진 구조를 바꿀 대안을 검토할 때
- 메트릭 알람에서 해당 시점의 로그로 바로 넘어가는 흐름을 만들 때
- 로그에 어떤 레이블을 붙일지(그리고 무엇을 절대 레이블로 만들면 안 되는지) 정할 때
- LogQL 로 로그를 필터링하고, 로그에서 메트릭을 만들어 알람을 걸 때
- 파드 로그를 수집할 에이전트(Promtail/Grafana Alloy)의 파이프라인을 설정할 때
- 로그 보관 기간·삭제 정책을 오브젝트 스토리지 기준으로 설계할 때

## 이럴 땐 아니다
- 메트릭 수집·저장·쿼리 자체는 `infrastructure/prometheus-docs.md`, `infrastructure/promql-querying-basics.md`
- 알람 라우팅·억제·그룹화는 `infrastructure/prometheus-alertmanager.md`
- 대시보드 구성·패널 설계는 `infrastructure/grafana-docs.md`
- 요청 하나가 서비스를 어떻게 지나갔는지(트레이스)는 `infrastructure/jaeger.md`, `infrastructure/opentelemetry-docs.md`
- 무엇을 지표로 삼고 어디에 알람을 걸지의 판단은 `infrastructure/sre-workbook.md`
- 메트릭·레이블 이름 규칙은 `infrastructure/prometheus-metric-and-label-naming.md`

## 무엇이 들어있나
설계의 출발점은 **인덱스를 최소화한다**는 결정이다. 로그 라인은 레이블 집합(스트림)별로 묶여 압축 저장되고, 인덱스는 그 레이블에만 붙는다. 검색은 "레이블로 스트림을 좁힌 뒤 그 안을 훑는" 두 단계가 된다. 그래서 저장 비용은 낮지만, 레이블로 좁히지 않은 광범위 검색은 느리다 — 이 트레이드오프를 이해하는 것이 도구 선택의 전부에 가깝다.

**카디널리티 경고**가 문서 전반에 반복된다. `trace_id`, `user_id`, `pod_ip` 처럼 값이 많은 것을 레이블로 만들면 스트림이 폭발해 성능과 비용이 함께 무너진다. 그런 값은 레이블이 아니라 로그 본문에 두고 검색 단계에서 필터링하라는 것이 규칙이다. Prometheus 의 카디널리티 원칙이 여기서도 똑같이 적용된다.

**LogQL** 은 두 층으로 되어 있다. 스트림 셀렉터(`{app="orders"}`)로 대상을 고르고, 파이프라인 단계(`|=` 문자열 포함, `| json` 파싱, `| label_format`)로 걸러 낸다. 여기에 `rate()`, `sum by ()` 같은 집계를 씌우면 **로그가 메트릭이 된다** — "에러 로그가 분당 몇 건인가"를 별도 계측 없이 알람으로 만들 수 있다는 뜻이고, 계측이 안 된 레거시 서비스에 특히 유용하다.

저장은 오브젝트 스토리지(S3, GCS)를 1차 저장소로 삼고, 보관 기간과 압축을 그 위에서 설정한다. 배포 형태는 단일 바이너리부터 마이크로서비스 모드까지 규모별로 나뉘어 문서화돼 있다.

수집은 Promtail 또는 후속인 Grafana Alloy 가 담당하며, 파일·쿠버네티스 API 에서 로그를 읽고 레이블을 붙여 보낸다.

## 인용 포인트
- "본문이 아니라 레이블만 인덱싱한다" — 로그 비용 구조를 바꾸자는 제안의 핵심 근거이자, 동시에 광범위 검색이 느린 이유의 설명.
- 고카디널리티 값을 레이블로 만들지 말라는 규칙은, 로그 레이블 설계 리뷰의 기준으로 그대로 쓸 수 있다.
- 로그에서 메트릭을 만들 수 있다는 점은, 계측이 없는 레거시 서비스에도 SLO 기반 알람을 붙일 길이 있다는 논거가 된다.
- 메트릭과 로그가 같은 레이블 체계를 공유한다는 사실은, 대시보드에서 로그로 넘어가는 동선을 설계할 근거다.

## 코드 예시

문서가 말하는 "로그를 메트릭으로" — 계측 코드를 넣지 않고 로그만으로 에러율을 만들어 SLO 알람에 쓰는 형태.

```logql
# 1) 스트림을 레이블로 좁히고, 본문은 그 안에서 훑는다
{namespace="orders", app="orders-api"} |= "level=error"

# 2) 구조화 로그라면 파싱해서 필드로 거른다
{namespace="orders", app="orders-api"}
  | json
  | status >= 500
  | line_format "{{.trace_id}} {{.msg}}"   # trace_id 는 레이블이 아니라 본문에 둔다

# 3) 집계하면 메트릭이 된다 — 5xx 비율을 로그만으로 계산
sum(rate({namespace="orders", app="orders-api"} | json | status >= 500 [5m]))
  /
sum(rate({namespace="orders", app="orders-api"} | json [5m]))
```

이 코드가 감추는 것: 이 비율은 로그가 남은 요청만 센다. 프로세스가 죽어 로그를 못 남긴 실패, 로드밸런서에서 끊긴 요청은 분자에도 분모에도 없어서, 진짜 나쁜 순간일수록 값이 좋아 보일 수 있다.
