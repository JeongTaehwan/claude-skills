# USE Method (Brendan Gregg)

https://www.brendangregg.com/usemethod.html

## 한 줄
시스템이 느릴 때 **자원마다 사용률(Utilization)·포화(Saturation)·에러(Errors) 세 가지만 순서대로 확인**해 병목을 좁히는 체크리스트 — 대시보드를 훑으며 감으로 찍는 대신, 빠진 곳 없이 훑었다는 것을 보장하는 절차다.

## 페르소나
**"서버가 느려요"라는 제보를 받고 대시보드 스무 개를 열어 놓고 어디부터 볼지 정하지 못한 백엔드/SRE 엔지니어.** CPU 사용률은 40% 라 괜찮아 보이고, 메모리도 여유가 있다. 그런데 응답이 느리다. 디스크인지 네트워크인지 커널 수준의 대기인지 판단할 방법이 없어서, 결국 아는 지표만 반복해서 들여다보다가 재시작으로 넘어간다. 이 상황에서 필요한 것은 새 도구가 아니라 훑는 순서다.

## 이럴 때 연다
- 원인을 모르는 성능 저하를 앞에 두고 조사 순서를 정해야 할 때
- 인프라 대시보드에 무슨 패널을 둘지 정할 때 — 자원별로 U/S/E 가 다 있는지 점검
- 온콜 인계 문서에 "느릴 때 무엇부터 보는가"를 절차로 적어야 할 때
- CPU 사용률은 낮은데 느린 상황(포화·큐 대기)을 설명해야 할 때
- 용량 증설 요청의 근거를 "체감"이 아니라 포화 지표로 바꿔야 할 때
- 성능 조사 결과를 남에게 재현 가능한 형태로 보고해야 할 때

## 이럴 땐 아니다
- 자원이 아니라 **서비스 단위**로 무엇을 재야 하는가는 `infrastructure/red-method.md`
- 무엇을 목표로 삼고 어디에 알람을 걸지는 `infrastructure/sre-workbook.md`, `infrastructure/sre-book.md`
- 지표를 실제로 수집·쿼리하는 방법은 `infrastructure/prometheus-docs.md`, `infrastructure/promql-querying-basics.md`
- 컨테이너 CPU·메모리 제한과 스로틀링의 동작은 `infrastructure/kubernetes-resource-management.md`
- 요청이 어느 서비스에서 느려졌는지 추적하는 것은 `infrastructure/opentelemetry-docs.md`, `infrastructure/jaeger.md`
- 브라우저·프런트엔드 체감 성능은 `performance/web-vitals.md`, `performance/rail-model.md`

## 무엇이 들어있나
방법은 한 문장으로 요약된다 — **모든 자원에 대해 사용률, 포화, 에러를 확인하라.** 자원은 CPU, 메모리, 네트워크 인터페이스, 스토리지 디바이스, 컨트롤러, 버스처럼 물리적으로 열거 가능한 것들이고, 글에는 자원 목록을 먼저 만들어 표를 채우라는 실행 지침과 OS 별(리눅스, 솔라리스) 명령 대응표가 붙어 있다.

세 지표의 역할이 다르다는 점이 핵심이다. **사용률**은 자원이 일하고 있는 시간 비율이고, **포화**는 처리하지 못해 대기 중인 작업의 양이다. 이 둘을 구분하는 이유는 사용률이 100% 가 아니어도 시스템이 느려질 수 있기 때문이다 — 짧은 구간의 폭주로 큐가 쌓이면 평균 사용률은 낮게 나온다. 그래서 글은 "사용률만 보는 모니터링은 문제를 놓친다"는 입장을 명확히 한다. 대기 큐 길이, run queue, 스왑, 재전송 같은 것이 포화 지표다.

**에러**를 먼저 보라고 권하는 순서도 의도적이다. 에러는 대개 해석이 필요 없고 즉시 실행 가능한 신호라서, 성능 문제로 보이는 것이 사실은 재시도 폭주였던 경우를 초반에 걷어 낸다.

방법의 성격 자체도 명시된다 — 이것은 완전한 진단법이 아니라 **빠르게 문제 영역을 좁히는 초기 스크리닝**이다. 흔한 병목을 놓치지 않는 것이 목표이고, 발견된 영역은 더 깊은 도구(프로파일러, 트레이서)로 파고들라고 말한다.

같은 저자의 다른 글들과 함께 읽으면 "자원 목록 → U/S/E 표 → 이상 항목 → 심층 도구" 라는 조사 파이프라인이 완성된다.

## 인용 포인트
- "사용률이 낮아도 포화될 수 있다" — CPU 사용률이 40% 인데 느린 상황을 설명하는 가장 짧은 근거이자, 대시보드에 큐 길이 패널을 추가하자는 제안의 출처.
- 자원 목록을 먼저 만들고 표를 채우라는 절차는, 성능 조사가 사람마다 달라지는 문제를 팀 체크리스트로 고정하게 해 준다.
- 에러를 먼저 본다는 순서는 온콜 런북의 1단계로 그대로 옮겨 쓸 수 있다.
- "이것은 스크리닝이지 진단이 아니다"라는 자기 한정은, USE 표만 보고 원인을 단정하는 보고를 되돌릴 근거다.

## 코드 예시

USE 표를 리눅스 명령으로 채우는 최소 세트 — 자원마다 사용률·포화·에러를 각각 다른 곳에서 읽는다는 점이 그대로 드러난다.

```bash
# CPU — 사용률(%usr+%sys)과 포화(run queue 길이)를 다른 열에서 읽는다
vmstat 1 5                    # r 열이 실행 대기 큐 = 포화
mpstat -P ALL 1 3             # 코어별 사용률 편중 확인

# 메모리 — 사용률보다 포화(스왑 in/out, OOM)가 먼저다
vmstat 1 5                    # si/so 가 0 이 아니면 이미 늦었다
dmesg -T | grep -i "out of memory"

# 스토리지 — %util 은 사용률, aqu-sz/await 가 포화
iostat -xz 1 5

# 네트워크 인터페이스 — 사용률(대역폭)과 에러/드롭을 분리해 본다
sar -n DEV 1 3
ip -s link show               # RX/TX errors, dropped 카운터

# 컨테이너라면 자원 경계가 노드가 아니라 cgroup 이다
cat /sys/fs/cgroup/cpu.stat   # nr_throttled, throttled_usec = CPU 포화
```

이 코드가 감추는 것: 이 명령들은 전부 노드 관점이라, 컨테이너 안에서 실행하면 호스트 전체 수치를 보여 주기도 한다는 것 — 쿠버네티스에서는 cgroup 지표나 cAdvisor 로 자원 경계를 다시 잡지 않으면 "여유 있음"이라는 잘못된 결론에 이른다.
