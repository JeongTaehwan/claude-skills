# Principles of Chaos Engineering

https://principlesofchaos.org/

## 한 줄
"프로덕션에 장애를 주입한다"는 위험해 보이는 실천을 **가설 검증 실험**으로 재정의한 한 페이지짜리 선언문 — 원칙 다섯 개가 그대로 실험 설계 체크리스트가 된다.

## 페르소나
**"프로덕션에 일부러 장애를 낸다고? 미쳤어?"라는 반응을 넘어야 하는 백엔드/SRE 엔지니어.** 결제 게이트웨이가 응답 없이 늘어졌을 때 주문 API 전체가 같이 죽는 것을 장애로 겪었고, 타임아웃과 서킷브레이커를 넣긴 했는데 그게 실제로 작동하는지 확인할 방법이 없다. 스테이징에서는 재현이 안 되고, 프로덕션 실험은 승인이 안 난다.

## 이럴 때 연다
- 장애 주입 실험을 팀·경영진에 처음 제안하며, "무모함"이 아니라 "통제된 실험"임을 규정으로 보여줘야 할 때
- 실험 계획서를 쓸 때 — 무엇을 정상 상태로 볼지, 폭발 반경을 어떻게 제한할지의 항목 구성
- 외부 결제·배송·쿠폰 연동의 지연/실패 대응이 코드에는 있는데 검증된 적이 없을 때
- 재해 복구 훈련(게임데이)의 규칙을 정할 때
- "스테이징에서 다 테스트했다"는 주장이 왜 부족한지 설명해야 할 때

## 이럴 땐 아니다
- 실험이 아니라 장애가 **이미 난 뒤의 회고**라면 `development/postmortem-culture-learning-from-failure.md`
- 실제 주입 도구가 필요하면 `testing/chaos-monkey.md`, `qa/awesome-chaos-engineering.md`
- 카오스 엔지니어링의 배경·사례를 더 길게 읽으려면 `architecture/chaos-engineering.md`
- 실패에 견디는 설계 패턴(타임아웃·재시도·서킷브레이커·백오프) 자체는 `architecture/amazon-builders-library.md`, `architecture/azure-architecture-cloud-design-patterns.md`
- 분산 시스템이 실제로 일관성 보장을 깨는지 외부 검증한 사례는 `architecture/jepsen.md`

## 무엇이 들어있나
정의부터 통념과 어긋난다. 카오스 엔지니어링은 "시스템을 부수는 것"이 아니라 **프로덕션 환경에서 시스템이 난기류를 견디는 능력에 대한 확신을 쌓기 위해 실험하는 규율**로 정의된다. 목적어가 파괴가 아니라 확신(confidence)이라는 점이 전체 논지를 지탱한다.
전제도 분명하다. 복잡한 분산 시스템의 실패 모드는 설계 문서에서 연역할 수 없고, 실제로 흔들어 봐야만 드러난다. 그래서 "테스트"가 아니라 "실험"이다 — 테스트는 이미 아는 답을 확인하고, 실험은 모르는 답을 찾는다.
고급 원칙 다섯 가지가 그대로 실험 설계 규칙이 된다.
1. **정상 상태(steady state)에 대한 가설을 세운다** — 내부 지표가 아니라 처리량·에러율처럼 시스템의 정상 동작을 대변하는 출력값으로 정의한다. "주문 생성 성공률"이 "CPU 사용률"보다 나은 정상 상태 지표다.
2. **실제 세계에서 일어나는 이벤트를 다양하게 재현한다** — 서버 종료뿐 아니라 네트워크 지연, 의존 서비스 응답 불가 같은 현실적 사건.
3. **프로덕션에서 실험한다** — 트래픽 패턴과 상태가 다른 환경에서는 같은 결론이 나오지 않기 때문.
4. **실험을 자동화해 지속 실행한다** — 일회성 훈련은 시스템이 변하는 순간 무효가 된다.
5. **폭발 반경을 최소화한다** — 프로덕션 실험을 정당화하는 것이 바로 이 조건이다. 무제한 실험은 그냥 장애다.

## 인용 포인트
- "실험 vs 테스트" 구분은 "스테이징에서 다 확인했다"는 반박을 정면으로 다루는 데 그대로 쓰인다.
- 폭발 반경 최소화 원칙은 프로덕션 실험 승인 요청서의 안전장치 항목을 그대로 제공한다 — 이 원칙을 인용하면 논의가 "해도 되나"에서 "어디까지 제한하나"로 옮겨간다.
- 정상 상태를 비즈니스 출력 지표로 정의하라는 부분은, 모니터링 대시보드가 자원 지표 위주인 팀에 관측 지표 재정비를 제안할 근거가 된다.

## 코드 예시

원칙 1(정상 상태 가설)·2(현실적 이벤트)·5(폭발 반경 최소화)를 하나의 실험 정의로 붙인 것 — 결제 연동에 2초 지연을 주입하되, 대상은 파드 하나로 제한하고 시간으로 상한을 건다.

```yaml
# 가설: 결제 응답이 2초 늘어도 주문 생성 성공률은 99% 아래로 떨어지지 않는다
# 중단 조건: sum(rate(orders_created_total{result="ok"}[1m]))
#            / sum(rate(orders_created_total[1m])) < 0.99 가 2분 지속되면 즉시 delete
apiVersion: chaos-mesh.org/v1alpha1
kind: NetworkChaos
metadata:
  name: payment-latency-2s
  namespace: prod
spec:
  action: delay
  mode: one              # 폭발 반경: 선택된 파드 중 하나만
  selector:
    namespaces:
      - prod
    labelSelectors:
      app: payment-proxy
  delay:
    latency: "2s"
    jitter: "0ms"
    correlation: "0"
  duration: "5m"         # 사람이 잊어도 5분 뒤 스스로 걷힌다
```

이 코드가 감추는 것: 중단 조건이 주석으로만 있다는 것 — 이 매니페스트는 지표를 보지 않으므로, 가설이 깨졌을 때 실험을 멈추는 것은 여전히 사람이거나 별도의 감시 장치다. 그 장치 없이 `duration` 만 믿는 실험은 폭발 반경이 시간으로만 제한된 상태다.
