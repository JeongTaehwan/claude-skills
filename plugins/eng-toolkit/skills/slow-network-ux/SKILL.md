# Slow Network UX — 느린 네트워크에서도 쓸 만한 화면

느린 인터넷에서 화면이 불편한 문제는 한 가지 원인이 아니다. **왕복이 많거나(RTT), 서버 응답이 늦거나(TTFB), 렌더링을 막는 리소스가 크거나(CSS·JS·폰트), 콘텐츠가 무겁거나(이미지·미디어), 기다리는 동안 아무것도 안 보여주거나(체감 성능)** — 어디가 병목인지에 따라 처방이 완전히 다르다. 측정 없이 기법부터 고르면 병목이 아닌 곳을 고치게 된다.

이 문서는 **플레이북**(진단 → 기법 선택 → 검증 절차)이다. 기법마다의 근거 — 공식 문서·논문·라이브러리·서적 — 는 `software-reference-library` 스킬의 **성능 도메인**에 항목별 파일로 있다. 찾을 때는 색인 파일을 열지 말고 `python3 ~/.claude/skills/software-reference-library/scripts/find.py "<상황>" --domain performance` 를 쓴다 — 색인 하나가 2만7천 토큰이라 한 번 읽으면 세션 내내 다시 읽힌다. 아래 절차에서 "근거"가 필요해지는 지점마다 무엇으로 찾을지 적어 두었다.

## 원칙: 실제 성능과 체감 성능은 다른 문제다

- **실제 성능**: 바이트가 도착해 픽셀이 그려지기까지의 시간. 전송량 축소·우선순위 조정·캐싱으로 줄인다.
- **체감 성능**: 사용자가 "기다렸다"고 느끼는 시간. 같은 3초도 백지 화면이면 길고, 부분 콘텐츠가 차례로 채워지면 짧다. 실증 연구가 쌓여 있는 영역이지만 **결과가 통념과 다른 경우가 많으니**(진행 바 형태, 스켈레톤 효과) 근거는 성능 도메인에서 검색해 확인하고 인용한다.

느린 네트워크 대응은 둘 다 해야 한다. 실제 성능만 줄이면 여전히 첫 화면까지 백지고, 체감만 다듬으면 데이터 요금과 배터리를 낭비한다.

## 작업 절차

### 1. 재현하고 측정한다 (기법 선택 전에)

- Chrome DevTools → Network → Throttling **Slow 4G/3G**로 문제를 재현한다. 실측 없이 "느리다"는 보고만으로 작업하지 않는다.
- 기준 지표는 Core Web Vitals: **LCP**(최대 콘텐츠 표시, 목표 2.5s), **INP**(반응성, 200ms), **CLS**(레이아웃 이동, 0.1) + **TTFB**(서버 응답, 800ms). 정의·목표치는 `find.py "core web vitals 측정" --domain performance` 와 `development/web-vitals.md`.
- 랩(Lighthouse) 수치와 필드(RUM) 수치는 다르다. 실사용자가 느린 건 필드 데이터로 확인한다.

### 2. 병목을 분류한다

측정 결과를 다섯 갈래로 분류한다. 각 갈래의 기법과 근거 문서는 **기법 이름으로 먼저 찾고**(일반), 그 다음 같은 질의에 `next` 를 붙여 App Router 적용법을 찾는다.

| 병목 | 증상 | 대표 처방 |
| --- | --- | --- |
| **왕복 횟수 (RTT)** | 전송량은 작은데 폭포수가 계단식으로 길다 | 리다이렉트 체인 제거, dns-prefetch/preconnect, 커넥션 재사용, HTTP/2·3 |
| **서버 응답 (TTFB)** | throttle 무관하게 첫 바이트가 늦음 | 정적 렌더링/ISR, CDN, 캐싱, 스트리밍 SSR로 응답 분할 |
| **렌더 블로킹** | HTML은 왔는데 화면이 백지 | Critical CSS, JS defer, 리소스 힌트(preload/preconnect), 폰트 전략, 103 Early Hints |
| **무거운 콘텐츠** | 화면 뼈대는 뜨는데 이미지·미디어가 안 옴 | 반응형 이미지(srcset/sizes), AVIF/WebP, lazy loading, LQIP/blur 플레이스홀더, `fetchpriority` |
| **JS 과다** | 다운로드 후에도 한참 인터랙션 불가 | 코드 스플리팅, 서드파티 지연/워커 격리, 번들 예산, 트리 셰이킹 |

첫 행을 표 맨 위에 둔 건 실수하기 쉬운 순서라서다. "느린 인터넷"을 대역폭 문제로 단정하고 이미지부터 줄이는 게 흔한 오진인데, 실측 연구(Ghana, IMC '14 — 성능 도메인에 있다)에서 실제 병목은 DNS 질의·리다이렉트 체인·TLS 핸드셰이크 같은 **왕복 횟수**였다. 저속 회선일수록 RTT가 크기 때문에 왕복 하나를 없애는 게 바이트 수십 KB를 줄이는 것보다 효과가 크다. 폭포수(waterfall)를 먼저 보고 계단이 몇 개인지 세는 것으로 시작한다.

### 3. 체감 성능을 설계한다

전송량을 줄여도 느린 망에서는 기다림이 남는다. 기다림을 설계한다:

- **무엇이든 > 백지**. 1초 넘게 걸리면 피드백을 준다(Nielsen 0.1/1/10초 한계). 다만 **스켈레톤이 스피너보다 낫다는 통념은 학술 근거가 약하다** — 유일한 비교 실험(Mejtoft 2018)은 통계적 유의차를 찾지 못했다. 스켈레톤의 방어 가능한 이점은 체감 선호가 아니라 **레이아웃을 미리 확정해 CLS를 막는 구조적 효과**다. 그래서 스켈레톤을 쓸 거면 실제 레이아웃과 치수가 일치해야 하고, 일치하지 않을 바에는 스피너가 낫다.
- **스트리밍/점진 렌더링**: 다 준비될 때까지 전체를 막지 말고, 준비된 부분부터 흘려보낸다(React Suspense 스트리밍, `loading.js`).
- **낙관적 UI**: 장바구니 담기·좋아요처럼 성공 확률이 높은 조작은 응답을 기다리지 않고 UI를 먼저 바꾼다. 실패 시 롤백 경로를 반드시 만든다.
- 근거 연구(어떤 대기 표시가 체감 대기를 줄이는지)는 `find.py "스켈레톤 진행률 체감 대기" --domain performance`.

### 4. 적응형 로딩을 검토한다 (선택적)

네트워크 상태에 따라 다른 경험을 내려보내는 기법. **Network Information API는 Chromium 계열 전용**이라 진행적 향상(progressive enhancement)으로만 쓴다 — 감지 실패 시 기본 경험이 동작해야 한다.

- `navigator.connection.effectiveType`으로 2G/3G 감지 → 저화질 이미지·애니메이션 생략·프리페치 중단
- `Save-Data` 헤더 / `prefers-reduced-data` 감지 → 데이터 절약 모드
- 상세는 `find.py "적응형 로딩 네트워크 상태" --domain performance`.

### 5. 재측정으로 마감한다

같은 throttle 조건에서 1번 지표를 다시 잰다. 수치 개선 없이 "적용했다"로 끝내지 않는다. 회귀 방지가 필요하면 Lighthouse CI·번들 예산 도구(성능 도메인에서 검색)를 건다.

## 레퍼런스 라우팅

근거 자료는 전부 `software-reference-library`의 성능 도메인(108개)에 있다. **색인 파일을 열지 말고 검색한다** — `performance/_index.md` 는 2만7천 토큰이고, 한 번 컨텍스트에 올라가면 세션이 끝날 때까지 매 턴 다시 읽힌다.

```bash
python3 ~/.claude/skills/software-reference-library/scripts/find.py "<상황을 그대로>" --domain performance
python3 ~/.claude/skills/software-reference-library/scripts/find.py --show <slug> --only 인용,아니다
```

이 플레이북의 지점과 검색어의 대응:

| 필요한 것 | 이렇게 찾는다 |
| --- | --- |
| 기법별 공식 문서 — 적응형 로딩, Critical CSS, 리소스 힌트, 이미지, 캐싱/오프라인, HTTP/2·3, 스트리밍 | 기법 이름을 그대로 (`"critical css 렌더 블로킹"`) |
| Next.js App Router에서의 구체 적용 — next/image, Suspense 스트리밍, next/font, ISR | `"next.js 이미지 최적화"` 처럼 `next` 를 넣는다 |
| 라이브러리·도구 고르기 — 프리페치, 플레이스홀더, 서비스 워커, 번들 분석 | 도구 성격을 쓴다 (`"번들 크기 분석 도구"`) |
| "근거 있어?" — 스켈레톤·진행률 실증 연구, 지연-매출 상관 | 증상 + 근거 (`"스켈레톤이 실제로 빠르게 느껴지나"`) |
| 깊이 공부 — 서적, 국내 자료 | `"성능 서적"`, `"국내 성능 사례"` |

항목 파일에는 페르소나·"이럴 때 연다 / 이럴 땐 아니다"·인용 포인트가 있다. 인용할 때는 요약을 그대로 옮기지 말고 URL을 fetch해서 원문을 확인한다. 링크 건강은 저장소의 주간 점검(`scripts/audit.py`)이 본다.

## 이 스킬을 쓰지 않는 경우

- 병목이 프론트가 아니라 API 자체 속도일 때(백엔드 쿼리·N+1) — 이 스킬은 화면 전달·표시 계층만 다룬다.
- 네이티브 앱(Flutter 등)의 네트워크 최적화 — 원리는 겹치지만 기법 문서가 웹 전용이다.
- 특정 자료·근거만 필요할 때 — 플레이북 없이 `software-reference-library` 를 바로 검색하는 게 빠르다.
