# 금액·결제 코드를 리뷰할 때 알아야 할 것

드릴을 풀기 전에 읽어도 되고, 몇 개 틀린 뒤에 읽어도 된다. 후자가 더 남는다.

---

## 1. 이 코드베이스가 실제로 반복해서 틀린 것

일반론이 아니라 git 로그에서 나온 것이다. 남의 실수가 아니라 **여기서 실제로 난 것**이라 값이 있다.

### 포인트 한도 base — 같은 질문에 다섯 번 다른 답

```
11775ec  한도 base 에 다구매(정책) 할인 반영
1470bde  base 를 '최종 결제 금액(포인트 미반영)' 으로 정렬
3600425  policyDiscount 가 0 으로 떨어지던 회귀
be392d6  base 를 '소계(sub_total)' 로 재정렬
2ab225d  base 를 '화면 소계 = subtotal' 로 다시 정렬
```

"포인트를 최대 얼마까지 쓸 수 있나"의 기준이 소계인지, 할인 후 금액인지, 최종 결제 금액인지가 정해지지 않았다. 그래서 고칠 때마다 다른 답이 나왔고, 그 사이 회귀가 한 번 더 났다.

**이건 코드 버그가 아니다.** 정의가 없는 것이다. 코드를 다섯 번 고쳐도 안 끝나는 이유가 그것이다.

**리뷰에서 던질 질문**: 이 계산의 base 가 무엇인지 **한 문장으로 적힌 곳이 있는가.** 없으면 지금 정하는 게 수정보다 먼저다.

### '정합' 커밋 103건 — 화면과 결제가 다르다

`WebApp-front` 64건, `WebApp-core` 39건이 "화면 금액 = 결제 금액"을 맞추는 작업이다.

이 숫자가 말하는 건 개별 버그가 아니라 구조다 — **금액을 두 군데서 각자 계산하고 있다.** 화면이 계산한 값과 서버가 계산한 값이 원리적으로 어긋날 수밖에 없고, 그래서 맞추는 작업이 끝나지 않는다.

**리뷰에서 던질 질문**: 이 금액의 **진실은 누구인가.** 화면이 계산한 값을 결제에 그대로 보내고 있으면 그건 클라이언트를 신뢰하는 것이고, 서버가 다시 계산하면 화면과 어긋날 수 있다. 둘 중 하나를 골라야지 둘 다 계산하면 영원히 맞춘다.

### 세금 — 고쳤다가 두 번 되돌림

```
e3405738  fix(order): 주문 요청에 tax(관세/소비세) 전송 — 화면=결제 금액 일치
14014eb4  Revert "fix(order): 주문 요청에 tax..."

0acbacb8  fix(checkout): 결제 토큰 total_amount 를 세금 포함 클라값으로 (STO 정합)
8c621f43  Revert "fix(checkout): 결제 토큰 total_amount..."
```

둘 다 "화면에서 계산한 세금 포함 금액을 서버로 보내자"는 방향이었고, 둘 다 되돌아왔다.

**그럴듯한 수정이 새 문제를 만드는 전형**이다. 화면과 결제를 맞추려고 클라이언트 값을 신뢰하기 시작하면, 정합은 해결되지만 신뢰 경계가 무너진다.

**리뷰에서 던질 질문**: 이 수정이 **클라이언트가 보낸 금액을 서버가 그대로 쓰게 만드는가.** 그렇다면 정합이 아니라 검증이 답이다.

## 2. 금액 코드에서 고정된 것들

도메인이 바뀌어도 안 바뀌는 것들이다.

### 정수 최소 단위 — 그런데 이건 시작일 뿐이다

`0.1 + 0.2 !== 0.3` 이라 부동소수점은 금액에 못 쓴다. 여기까진 다들 안다.

**정수로 바꿔도 안 없어지는 버그가 있다.** 3,000원 할인을 3개 라인에 비율 배분하면 999/1000/1000 이 나온다. 정수 연산은 이 버그를 **없애는 게 아니라 결정론적으로 만든다.** 매번 같은 1원이 어긋난다.

### 배분에는 잔차의 주인이 있어야 한다

정할 것이 셋이다.

| 정할 것 | 기본값으로 안전한 쪽 |
|---|---|
| 반올림 방향 | 내림 (고객에게 유리, 합계 초과 없음) |
| 잔차를 누구에게 | 가장 비싼 라인 / 첫 라인 / 마지막 라인 중 **하나로 고정** |
| 검산 | `sum(line_discounts) === total_discount` 를 코드가 보장 |

**주석에 적으면 다음 리팩터링에서 사라진다.** 코드가 보장해야 한다.

그리고 이건 **비즈니스가 소유한 결정**이다. 개발자가 조용히 정하면 6개월 뒤 검증된 요구사항처럼 굳는다.

### 통화가 하나가 아니게 될 가능성

최소 단위 자릿수가 통화마다 다르다 — KRW 0, USD 2, JPY 0, KWD 3. 암묵적 스케일을 가진 정수 필드 하나는 두 번째 통화가 들어오는 순간 잠재 버그다.

이 프로젝트는 이미 테넌트가 jp/kr/us/tw 넷이다.

### 과거 시점 값은 스냅샷으로 박는다

주문 라인의 가격·상품명·적용된 쿠폰 조건은 **주문 시점 값**이어야 한다. 라이브 상품 행을 조인하면 가격 변경이 과거 주문을 소급해 바꾸고 정산이 무너진다.

### 파생값을 만들기 전에 원본을 쓰는 곳을 셀 수 있어야 한다

할인가를 컬럼에 저장하거나 캐시하려면, 원본을 바꾸는 곳을 **전부** 셀 수 있어야 한다. 못 세면 그 방식을 고를 자격이 없다.

어드민 편집기, 캠페인 스케줄러, 자정 만료 배치가 각각 원본을 바꾸고 아무도 무효화하지 않으면, 목록은 존재하지 않는 할인을 보여주고 결제는 다른 금액을 청구한다.

### 수량·잔액은 읽고-검사하고-쓰지 않는다

```sql
-- 두 요청이 모두 99를 읽고 모두 통과한다
SELECT issued_count ... ; if (count < max) ; UPDATE SET issued_count = ?

-- 조건을 DB가 판정하고 영향 행 수로 읽는다
UPDATE coupons SET issued_count = issued_count + 1
WHERE id = ? AND issued_count < max_issue;
```

**영향 행 수를 판정에 쓰는 것**이 핵심이다. UPDATE 날리고 성공했다고 가정하면 조건부로 만든 의미가 없다.

### 재시도는 반드시 온다

결제 웹훅, PG 콜백, 큐 소비는 두 번 온다. 멱등키를 쓰되 네 가지를 같이 정해야 절반짜리가 안 된다 — 키의 범위, **첫 응답을 저장할 것**, 보관 기간(상대 재시도 정책보다 길게), 두 번째 호출에 뭘 돌려줄지.

## 3. AI가 만든 금액 코드를 볼 때

AI 코드는 **해피패스가 거의 항상 맞다.** 그래서 "돌아가네" 로 넘어가기 쉽다. 틀리는 자리는 정해져 있다.

| 볼 것 | 왜 |
|---|---|
| 반올림이 어디서 몇 번 일어나나 | 중간 단계마다 반올림하면 오차가 누적된다 |
| 배분 후 합계를 누가 보장하나 | AI 는 배분 로직은 잘 쓰는데 검산을 안 붙인다 |
| 이 값의 base 가 무엇인가 | 소계·할인후·최종 중 무엇인지 코드가 말하는가 |
| 화면 값을 서버로 보내나 | 정합 문제를 신뢰 경계로 옮기는 수정인가 |
| 동시 실행에서 어떻게 되나 | AI 는 단일 요청 기준으로 짠다 |
| 재시도되면 두 번 일어나나 | 부작용이 멱등한가 |
| 빈 값·0·음수 | 장바구니 0개, 할인 0원, 환불 후 잔액 |

**AI 의 확신을 신호로 받지 마라.** 틀릴 때도 똑같이 자신 있게 말하고, 근거를 대는 것처럼 보인다.

## 4. 드릴 푸는 법

**답을 먼저 보지 마라.** 이게 전부다. 답을 보면 "아 그렇네" 하고 끝나고 아무것도 안 남는다.

각 문제에서 세 가지를 **적어놓고** 답을 편다.

1. 무엇이 잘못됐나
2. 어떤 입력·상황에서 드러나나 — **구체적 수치로**
3. 어떻게 고치겠나

2번이 제일 중요하다. "동시성 문제인 것 같다" 는 감이고, "장바구니 A 2개(10,000) + B 1개(5,000)에 5,000원 쿠폰이면 라인 합이 4,999가 된다" 는 판단이다. 감으로는 리뷰에서 지적 못 한다.

### 틀렸을 때 볼 것

정답의 **"왜 놓치기 쉬운가"** 절을 읽어라. 무엇이 정답인지보다 **왜 그 코드가 자연스러워 보였는지**가 다음번에 쓸모 있다.

### 기록

푼 뒤에 한 줄만 남긴다 — `문제번호 / 맞음·틀림 / 어느 축인지`.

10문제쯤 쌓이면 패턴이 보인다. "반올림은 잡는데 파생값 stale 은 못 잡는다" 같은 게 나오면 그게 다음에 팔 곳이다.
