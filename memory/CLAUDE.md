# 구현할 때

코드를 쓰기 전에, **내가 새로 추가하는 코드**가 이 셋 중 하나에 해당하는지 본다. 주변에 뭐가 있는지가 아니라 이 변경이 무엇을 만드는지로 판정한다.

1. 크기를 내가 정하지 않는 순회·조회를 새로 만든다
2. 여러 요청·재시도·웹훅이 동시에 건드릴 수 있는 상태에 쓴다 — 금액, 재고, 발급 수량, 잔액, 주문·결제 상태
3. 되돌리기 비싼 것을 만든다 — 스키마, 저장 포맷, 공개 인터페이스, 외부 계약

하나라도 걸리면 `implementation-design` 스킬을 읽고 그 절차를 따른다.

하나도 안 걸리면 그냥 구현한다. 이름 변경, null 가드, 기존 루프 안의 조건 수정, 렌더링 필드 추가, 설정값, 로그 — 여기에 분석을 붙이는 건 도움이 아니라 소음이다. 건너뛴 사실도 말하지 않는다.

애매하면 실패의 모양으로 가른다. 실패가 눈에 보이고 되돌리기 싸면 건너뛰고, 실패가 조용하면(돈·정산·배치·크론·웹훅) 발동한다.

분석은 출력이 아니라 입력이다. 기본 출력은 코드뿐이고, 코드 앞에 검토 과정을 늘어놓지 않는다.

# 프로젝트·기획일 때

새 프로젝트·큰 기능을 시작하거나, 기존 저장소 전체 분석·로드맵·프로토타입을 요청받으면 `project-flow` 스킬을 읽는다 (구조 → 기획서 → 프로토타입 → 구현). 기획서가 없으면 질문부터 하지 않는다. 승인된 기획서로 기능을 구현하는 사이클은 `role-isolation-pipeline`. 일반 구현 요청은 위 게이트만 탄다.

# 팀메이트 모드

여러 단계짜리 일은 메인 세션이 직접 쓰지 않고 역할 에이전트(planner·architect·developer = opus, researcher·ux-designer·prototyper·analyst·doc-reviewer = sonnet, scribe = haiku)에게 맡긴다. 에이전트를 부를 때 모델을 비워 두지 않는다.
