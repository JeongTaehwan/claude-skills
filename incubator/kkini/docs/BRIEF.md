## 사람이 말한 것 (원문 요지)

1차 (2026-09-12): "매일 끼니 해결 관련 추천해주는 앱. 저녁 식사 고민될 때 해주는 것."

2차 (2026-09-12, 프로토타입 v0를 본 뒤): "이게 아니라 내가 해먹거나 시켜먹는 거(시켜먹는 건 집주소 입력 필요).
돈·가격에 맞춰서 메뉴 추천. 몇 인분인지도 입력받아서 만들어 먹을 만한 걸 알려주는 것. 레시피랑 요리 방법."

2차 진술이 뒤집는 v0 가정 (승인 전이지만 사람의 말이 이긴다):
- 갈래: 해 먹기 + **시켜 먹기(배달)**. 나가서 먹기는 언급 없음 → v0의 "A+B, C 제외"는 폐기 대상 (KK-OQ-02)
- 입력: **예산·인분·(배달이면) 집주소**를 받는다 → v0의 "입력 0회"(DC-R04, DC-OQ-02 추천)는 폐기 대상
- 레시피·조리법은 **핵심 산출물** → v0의 "RC 제외"는 폐기 대상
- 가격 맞춤이 추천의 축 → 메뉴별 가격(해 먹기는 재료비, 배달은 메뉴 가격) 데이터가 필요해짐

## 작업 가정 — 사람 승인 전. 문서에서는 `[제안]`으로 표기한다

- 가칭 **끼니 (Kkini)**. 레포 이름도 `kkini`.
- 시장은 한국, 언어는 한국어.
- 첫 범위는 **저녁 한 끼**. 아침·점심·간식은 범위 밖 후보.
- 해결 방식은 세 갈래를 모두 다룬다 — 집에서 해 먹기 / 배달·포장 / 나가서 먹기.
  어느 갈래를 MVP에 넣을지는 미정이며 등급을 매긴다.
- 핵심 가치 가설: 선택지를 많이 보여주는 것이 아니라 **결정을 대신 해주는 것**.
  고민 시간이 줄어드는 것이 성공이다.
- 개발은 사람 1명 + Claude Code 에이전트 팀. 운영비 최소, 관리형 서비스 선호.
- 플랫폼(웹/PWA/네이티브), 스택, 수익화는 전부 미정.

## 문서 규칙 (role-isolation-pipeline 컨벤션)

- 한국어. 요구사항은 한 줄에 하나, 참/거짓을 판정할 수 있는 문장.
- 사람이 정하지 않은 것을 확정처럼 쓰지 않는다.
  - 에이전트의 제안은 `[제안]` + 한 줄 이유.
  - 사람이 정해야 하는 것은 `[미정]` + BLOCKER/LATER 등급 + 구체적으로 막히는 증상.
- 근거를 못 대는 사실 진술에는 `[추정]`.
- 화면·기능마다 두 글자 약칭. 미정 질문 ID는 `XX-OQ-NN`, 절차 문제는 `PROC-OQ-NN`.
